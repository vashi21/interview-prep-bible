Most services don't need an instant reply from each other — they need a message to arrive and get handled reliably, even if the receiver is slow, offline, or scaled down to zero right now. Messaging systems are the piece that makes this decoupling possible, and Kafka is the single most-asked messaging system in HLD interviews, so this chapter spends most of its time there.

01Queues vs Pub-Sub: Two Shapes Messaging Comes In

Every messaging system is built around one core idea: a producer (the sender) writes a message without waiting for the consumer (the receiver) to be ready to read it right away. But there are two very different shapes this can take, and interviewers expect you to know which one fits a given problem.

Point-to-Point Queue: One Message, One Consumer

In a point-to-point queue, every message is delivered to exactly one consumer, even if many consumers are listening on the same queue. Think of it as a shared to-do list: several workers can watch the same list, but each item on it gets picked up and crossed off by only one of them. This is also called the competing consumers pattern, because the workers compete for the next item.

This is the right shape for a job queue. Say users upload videos, and each upload needs to be transcoded into a few resolutions. You don't want ten worker machines all transcoding the same video — you want each video handled once, by whichever worker happens to be free. A queue like Amazon SQS, or RabbitMQ used as a plain queue, does exactly this: the upload service drops one message per video onto the queue, and a pool of transcoding workers pulls from it, with each message going to only one worker.

Publish-Subscribe: One Message, Every Subscriber

In publish-subscribe (pub-sub), a message published to a topic (a named channel) is delivered to every subscriber listening on that topic, not just one. Each subscriber gets its own full copy of the message and processes it independently of the others.

This is the right shape for a fan-out notification. Say an e-commerce order service publishes an OrderPlaced event. Three completely different downstream services care about that one event for three completely different reasons: an email service needs to send a confirmation, an inventory service needs to decrement stock, and an analytics service needs to log it for reporting. Point-to-point wouldn't work here — if only one consumer got the message, the other two services would never find out an order happened at all. Pub-sub gives each of them their own copy, and none of them has to know the others even exist.

The two shapes aren't interchangeable, and picking the wrong one is a real design bug, not just a style choice. Point-to-point on a fan-out problem silently drops work — only one of your three downstream services would ever see the event. Pub-sub on a job-queue problem means every worker processes the same job, which is wasted compute at best and duplicate side effects (like charging a card twice) at worst.

"I'd use a point-to-point queue here because I only want one worker touching each job — duplicate processing would mean double-charging the customer. For the notification fan-out, I'd switch to pub-sub, because every downstream team needs its own copy of the same event."

02Kafka Deep Dive: Topics, Partitions, and Where the Parallelism Comes From

Kafka is a specific, very popular messaging system built as a distributed, ordered log. Interviewers ask about it constantly because a huge share of real production event pipelines run on it. To reason about it well, you need four ideas, in this order: topics, partitions, consumer groups, and offsets.

A topic is a named stream of messages, like orders or page-views. On its own, a topic is just a category name. The actual storage, and the actual parallelism, come from partitions.

Kafka splits every topic into one or more partitions. Each partition is its own ordered, append-only log — new messages are always added to the end, and once written, a message's position never changes. Kafka decides which partition a message goes to using the message's key: it hashes the key and uses that hash to pick a partition, so the same key always lands on the same partition. If a producer doesn't set a key, Kafka's default partitioner spreads messages across the partitions instead — since Kafka 2.4 this is "sticky" rather than strict per-message round-robin, batching a run of messages onto one partition before rotating to the next, which improves batching efficiency without changing the basic idea that keyless messages get distributed rather than pinned to one partition.

This is the detail that gives Kafka its parallelism. Each partition can be written to and read from independently of the others, often on different brokers (the servers that make up a Kafka cluster), and by different consumers at the same time. A topic with one partition can only ever be processed by one consumer at a time, no matter how much hardware you throw at it. A topic with thirty partitions can be processed by up to thirty consumers in parallel. Partition count is the single biggest lever for Kafka throughput, and it's usually decided up front, because you can add partitions to a topic later, but you can't safely remove them, and adding partitions changes which keys land where.

Concretely: if your topic has 3 partitions and messages are keyed by user_id, every event for user_id=42 always lands on the same partition, in the order it was produced. An event for user_id=99 might land on a completely different partition, processed by a different consumer, with no guaranteed timing relationship to user_id=42's events.

That leads straight to the ordering rule interviewers love to probe: Kafka only guarantees order within a single partition, never across a whole topic. If you need every event for a given entity to be processed in the order it happened — say, a user's account balance changing — you must key your messages by that entity's ID, so they all funnel through the same partition. If you don't need cross-key ordering, which is true for most analytics and logging use cases, you can let messages spread freely across partitions and get much higher throughput in return.

03Kafka Deep Dive: Consumer Groups and Offsets

A consumer group is a named set of consumers that cooperate to read a topic. Kafka's rule for dividing the work inside a group is simple and important: each partition is assigned to exactly one consumer within that group at any given time. If a topic has 3 partitions and the group has 3 consumers, each consumer reads one partition and they never step on each other. If the group only has 2 consumers, one of them reads two partitions. If the group has 4 consumers, one consumer sits idle — Kafka never splits a single partition across two consumers in the same group, because that would break the per-partition ordering guarantee from the last section.

This is also how Kafka gets you both point-to-point and pub-sub behavior out of the same topic, depending only on how you set up consumer groups. Put all your consumers in one group, and each message is processed once across the whole group — that's the point-to-point job-queue pattern from section 01. Give two different services their own separate consumer groups reading the same topic, and both services see every message independently — that's the pub-sub fan-out pattern. The topic itself never changes; only the grouping does.

Offsets: A Consumer Group's Bookmark

An offset is just a number: the position of the next message a consumer will read in a given partition. Think of it as a bookmark in a book — the partition is the book, and the offset says which page you stopped on. Kafka stores committed offsets per (consumer group, partition) pair, usually inside an internal Kafka topic itself, so a consumer that restarts can pick up exactly where its group left off instead of starting over from the beginning or losing messages.

If you reset a consumer group back to an old offset — on purpose, to reprocess data after fixing a bug, or by accident — the group re-reads every message from that point forward, including ones it already processed once before. Kafka does not remove or hide those old messages; it just moves the bookmark back. This means anything consuming from Kafka has to tolerate seeing the same message more than once, which is exactly the idempotency problem from Ch.13: your message handler needs to produce the same result whether it runs once or five times on the same message.

"I'd make the consumer idempotent by keying on the message's own ID or the entity ID inside it, and track which IDs I've already applied — that way, replaying from an old offset after a deploy rollback doesn't double-apply anything."

04Kafka Deep Dive: Replication and the In-Sync Replica Set (ISR)

Kafka doesn't store each partition on just one machine — that would mean losing data the moment that one machine dies. Every partition is replicated across several brokers (the servers in a Kafka cluster), based on a replication factor you configure, commonly 3. One replica is elected the leader for that partition; by default, it is the only replica that accepts writes and serves reads. The rest are followers, and their whole job is to continuously copy the leader's log. (Since Kafka 2.4, KIP-392 lets you configure consumers to fetch from a nearby in-sync follower instead, usually to save cross-zone network cost — writes still go through the leader either way, and this is a deliberate opt-in, not the default behavior.)

The in-sync replica set (ISR) is the leader plus every follower that has fully caught up with the leader's latest writes at this moment. A follower that falls behind — because its broker is slow, overloaded, or briefly cut off on the network — drops out of the ISR until it catches back up. This matters because only replicas in the ISR are safe to promote to a new leader if the current leader fails; promoting a replica that is behind would silently lose the messages it never got around to copying.

Why acks=all and min.insync.replicas Matter

A Kafka producer's acks setting controls how many replicas must confirm a write before the producer treats it as successful. acks=0 doesn't wait for any confirmation at all — fastest, but a broker crash can silently lose the message. acks=1 waits only for the leader to write it locally — if the leader dies before followers copy it, the message is still lost. acks=all waits for every replica currently in the ISR to confirm the write, which is what you want for anything you can't afford to lose.

But acks=all alone has a gap: if the ISR has shrunk down to just the leader itself (every follower fell behind), acks=all is satisfied by that one replica confirming, which isn't the durability you thought you were getting. min.insync.replicas closes that gap — it sets the smallest ISR size Kafka will accept a write with at all. Set it to 2 on a replication factor of 3, and Kafka rejects the write outright (the producer gets an error back and can retry) rather than accepting it durably on only one copy. Together, acks=all and min.insync.replicas=2 are the standard pairing when a topic carries data you genuinely cannot lose, like payment events.

This durability isn't free. Waiting for more replicas to confirm adds latency to every write, and setting min.insync.replicas too high means a single slow or down broker can start rejecting writes entirely, hurting availability instead. The interview answer: pick the strictest durability setting the data's cost of loss actually justifies, not the strictest setting available.

05Kafka Deep Dive: Exactly-Once Semantics

"Exactly-once" is the phrase that gets thrown around most loosely in messaging, and it's worth being precise about what Kafka actually guarantees, because the honest answer is narrower than the name suggests.

The Idempotent Producer

By default, if a Kafka producer sends a message and doesn't get an acknowledgment back in time — maybe the message actually got written, but the acknowledgment was lost on its way back — the producer retries and sends it again. Without protection, that retry can create a real duplicate in the log. The idempotent producer setting fixes exactly this one case: Kafka assigns the producer a producer ID and stamps each message with a sequence number, and the broker uses that pair to recognize "I've already written this exact message" and silently drop the duplicate. This is the same idempotency idea from Ch.13 — an operation is written so that repeating it has no extra effect — applied specifically to the producer-retry case.

That's it, though. The idempotent producer only protects against a producer's own retries writing the same message twice to the same partition. It says nothing about the rest of your pipeline.

The Transactional API

Real pipelines usually look like this: read a message from one topic, do some work, write a result to another topic, and mark the input message as processed. If one of those steps succeeds and another fails — you write the output but crash before committing the input offset, say — a restart reprocesses the input and produces a duplicate output. Kafka's transactional API closes this specific gap. It lets a producer wrap the output-topic write and the input-offset commit into one atomic unit, so either both happen or neither does. Combined with the idempotent producer, this is what Kafka actually means by exactly-once — more precisely, exactly-once for Kafka-to-Kafka processing, the common case being a Kafka Streams application or any consume-process-produce loop that stays entirely inside Kafka.

An EM-level answer flags the limit explicitly: this guarantee stops at Kafka's edge. If a consumer's "work" step calls an external payment API or writes to a separate database as a side effect, Kafka's transaction can't make that side effect atomic with the offset commit — you're back to needing that external call to be idempotent on its own (an idempotency key, a unique constraint, something), the same problem the outbox pattern and two-phase commit deal with in Ch.13. That's why exactly-once in a real interview answer is safer stated as "effectively-once for anything that leaves Kafka" — saying that instead of the marketing phrase is a real signal of seniority.

06SQS vs RabbitMQ vs Kafka

These three come up constantly as a compare-and-contrast question, and each one really is the right default for a different situation. Kafka's guarantees were covered above; here's how the other two differ, and a table that pulls the whole comparison together.

Amazon SQS is a fully managed queue — you never run any brokers yourself. A standard SQS queue is at-least-once with best-effort ordering, and a FIFO SQS queue trades away some throughput for strict order and deduplication within a short window. Fan-out on SQS is usually done by pairing it with SNS, a pub-sub topic that pushes a copy of each message into several SQS queues, rather than SQS doing pub-sub natively on its own.

RabbitMQ is a message broker built around flexible routing. Producers publish to an exchange, and routing rules (direct, topic-pattern, or fanout) decide which of possibly several queues each message lands in. This makes it a natural fit when you need complex delivery rules — "route by priority," "route by tenant" — that a plain queue can't express on its own.

07Event Sourcing and CQRS

Event sourcing is a way of storing data: instead of saving only the current state of a thing — an order's current status, an account's current balance — you save every event that ever changed it, in order: OrderPlaced, OrderPaid, OrderShipped. That sequence of events is treated as the source of truth. Current state is never stored directly; it is derived by replaying the events from the start, or from the last saved snapshot for efficiency, and applying each one in order.

This gives you a few things a normal "just update the row" model doesn't. You get a full audit trail for free — you can see exactly how a balance got to its current number, not just the number itself. You also get the ability to rebuild state as of any point in the past, simply by replaying events only up to that point.

CQRS (Command Query Responsibility Segregation) is a separate idea that shows up next to event sourcing so often that people sometimes think they are the same pattern. CQRS just says: use a different model for writes (commands, like "place this order") than for reads (queries, like "show me this user's order history"), instead of forcing one schema to serve both. Writes and reads often have very different shapes and very different scaling needs, and splitting them lets you optimize each side on its own.

The two combine naturally. The event log from event sourcing becomes the single write-side source of truth, and you build one or more read models — plain tables, search indexes, or caches shaped exactly for a specific query — by consuming that same event log and projecting it forward. Need a full-text search view and a simple summary table for the same underlying data? Build both from the same log, and let them evolve independently, or even get rebuilt from scratch by replaying history again.

This isn't free complexity. Read models are built asynchronously from the event log, so there is a lag between a write landing and every read view reflecting it — you've traded strong consistency for flexibility and scale, the same eventual-consistency trade-off covered in Ch.9. You also now own event schema evolution forever: an event written five years ago still has to make sense to whatever code replays it today.

08The Outbox Pattern

Say a business action needs to do two things: save a row in your own database, and publish an event telling the rest of the system it happened — "order created," so email and inventory services can react. Those are two separate systems: your database, and your message broker. A normal database transaction only covers your database. It has no way to also guarantee the broker publish happened, or to roll that publish back if it didn't. This is the dual-write problem: you cannot make "write to my DB" and "publish to the broker" one atomic operation with an ordinary transaction, because they are two independent systems with no shared commit protocol between them (Ch.13 covers why coordinating commits across independent systems, as in two-phase commit, is hard in general).

Both failure orders hurt. Publish first, then have the DB write fail or the process crash before saving: downstream services now think an order exists that your own database never recorded. Save to the DB first, then have the publish fail or the process crash before it goes out: the order is real, but nobody downstream ever finds out about it.

The outbox pattern avoids this by never trying to coordinate two systems in the first place. You add an outbox table to your own database, and when you save the business row, you also insert a row describing the event into that outbox table — in the exact same database transaction as the business write. Since it's one transaction inside one database, this part is atomic by the database's normal guarantees: both rows exist, or neither does. A separate, small relay process then reads new rows out of the outbox table — either by polling it on a timer, or by tailing the database's change log with a tool like Debezium, a form of change data capture (CDC) — and publishes each one to the broker, marking it done once the publish succeeds.

"I'd write the event into an outbox table in the same transaction as the order write, so the two can never disagree, then use a CDC-based relay like Debezium to publish it — that keeps the relay off the request's critical path and out of the transaction entirely."

The outbox pattern doesn't give you exactly-once publishing — it gives you at-least-once. If the relay publishes successfully but crashes before marking the outbox row done, it publishes that same row again on restart. That's a fine trade: you've turned "might silently lose the event" into "might publish it twice," and a duplicate is much easier to handle downstream (make the consumer idempotent, same as everywhere else in this chapter) than a message that never existed at all.

09Backpressure

Backpressure is what happens when a consumer can't keep up with the rate messages are arriving, and it needs a way to say so, instead of quietly falling further and further behind until something breaks — usually memory running out, or latency growing without any bound.

The cleanest signal of backpressure is a pull-based consumption model, which is exactly how Kafka consumers work: a consumer asks the broker for the next batch of messages when it is ready for more, instead of the broker pushing messages at it continuously. If the consumer is slow, it simply asks less often — the broker doesn't need to know or care why, and messages sit safely in the log until someone asks for them.

Systems built on push, or with a queue in front that can still be overwhelmed, need an explicit mechanism instead. A few concrete ones:

  • Bounded queues — give the queue between producer and consumer a hard maximum size. Once it's full, the producer has to block, wait, or handle a rejection, instead of the queue growing memory usage without limit until the process crashes.
  • Rate-limiting the producer — cap how fast the producer is allowed to send, using something like a token bucket (Ch.5 covers the algorithm), so the consumer's real processing rate sets the ceiling instead of the producer's maximum speed.
  • Load shedding — when a queue is full or latency crosses a threshold, deliberately drop the lowest-priority messages instead of trying to process everything late anyway. This trades completeness for keeping the system responsive for the traffic that does get through.

The EM-level framing: backpressure is a capacity-planning decision, not just a coding pattern. A bounded queue and load shedding both decide who is unhappy when the system is overloaded — the producer that gets blocked, or the messages that get dropped — and that choice should be made deliberately, with the product owner, based on which failure mode actually costs the business less.
