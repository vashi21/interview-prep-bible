Before two systems can talk, a name has to become an address, and a request has to travel over a protocol both sides agree on. This chapter covers the plumbing under almost every system you will design in this book: DNS, HTTP/HTTPS, the six ways services talk to each other, and the boxes that sit in front of your servers to route, protect, and speed up traffic.

01How A Name Becomes An Address (DNS)

Every computer on the internet is reached by an IP address — a number like 203.0.113.1 that tells routers where to send packets. Humans are bad at remembering numbers, so we use names instead, like example.com. DNS (Domain Name System) is the system that translates a name into an IP address. Nothing else about the internet works until this translation step happens first.

DNS is organized as a tree, not one giant lookup table. At the top sits a small set of root servers. They do not know the IP address for example.com, but they know which server to ask about anything ending in .com. That next server is a TLD (top-level domain) server, one per suffix like .com, .org, or .in. It does not know example.com's IP address either, but it knows which server owns that domain: the authoritative name server. That server holds the actual DNS records for example.com and gives out the real answer.

You do not talk to all three of those servers yourself every time you load a page. A recursive resolver — usually run by your ISP, or a public one like Google's 8.8.8.8 or Cloudflare's 1.1.1.1 — does that chain of lookups on your behalf and hands you back one answer. It also caches the answer for a while, so the next request for the same name does not repeat the whole chain.

Each DNS record has a TTL (time to live) — a number of seconds the resolver is allowed to cache it before asking again. Typical values run from 60 seconds to a full day (86,400 seconds).

TTL is a trade-off, not a free setting. A long TTL (say, a day) means fewer lookups hit your name servers, which is cheap and fast for everyone downstream. A short TTL (say, 60 seconds) means a DNS change — like pointing a domain at a new server during a failover — reaches the whole internet fast. You cannot have both: pick a short TTL on records you expect to change during an incident, and a long TTL on ones that almost never change.

DNS records come in a few common types. You do not need to memorize the full list, but you should recognize these on sight.

DNS Common DNS record types
  • A — maps a name to an IPv4 address.
  • AAAA — maps a name to an IPv6 address.
  • CNAME — an alias: points one name at another name, not directly at an IP. A name with a CNAME cannot have any other record type at the same time.
  • NS — delegates a subdomain to a set of name servers (this is how the tree hands off from TLD to authoritative server).
  • MX — points a domain at the mail servers that should receive its email.
  • TXT — arbitrary text; commonly used to prove domain ownership or configure email anti-spam rules (SPF, DKIM).

DNS queries mostly travel over UDP on port 53, because a query-and-answer is small and does not need a reliable connection. DNS falls back to TCP when the answer is too large for one UDP packet, or for administrative operations like transferring an entire zone between name servers.

02HTTP And HTTPS, From First Principles

Once you have an IP address, you need a shared language to ask for something and get an answer back. HTTP (HyperText Transfer Protocol) is that language for the web. It is a request/response protocol: a client sends a request, a server sends back exactly one response, and the underlying connection can then be reused for the next request. HTTP is also stateless by default — the server does not remember your previous request unless something extra, like a cookie or a token, carries that state along.

Methods, status codes, headers

A request has a method that states its intent: GET to read something, POST to create something, PUT/PATCH to replace or partially update something, DELETE to remove it. A response carries a status code that states the outcome: 2xx means success, 3xx means "go look somewhere else" (a redirect), 4xx means the client did something wrong (like asking for a resource that does not exist, 404), and 5xx means the server failed while handling a request that was itself fine. Both requests and responses carry headers — key/value metadata like Content-Type (what format the body is in) or Authorization (who is asking).

Status HTTP status code families
  • 1xx — Informational — request received, still processing (rarely seen directly).
  • 2xx — Success — 200 OK, 201 Created, 204 No Content.
  • 3xx — Redirection — 301 Moved Permanently, 304 Not Modified (tells a client its cached copy is still good).
  • 4xx — Client error — 400 Bad Request, 401 Unauthorized (who are you?), 403 Forbidden (I know who you are, you are not allowed), 404 Not Found, 429 Too Many Requests.
  • 5xx — Server error — 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.

HTTPS and TLS

HTTPS is HTTP sent over TLS (Transport Layer Security) instead of a plain, unencrypted connection. Plain HTTP has three problems: anyone on the network path can read the traffic, anyone can alter it in transit, and you have no proof you are actually talking to the server you think you are. TLS fixes all three at once: it gives you confidentiality (traffic is encrypted), integrity (any tampering is detectable), and authentication (the server proves its identity with a certificate).

A certificate is a signed statement, issued by a trusted Certificate Authority (CA), that says "this public key belongs to example.com." Your browser ships with a list of CAs it trusts. When it connects, it checks that the server's certificate is signed by one of them, forming a chain of trust back to a root it already trusts.

Setting up an encrypted connection needs a handshake before any real data can flow. In TLS 1.3, the version most services use today, that handshake takes one round trip: the client and server exchange just enough information to agree on a shared secret key, then switch to fast, ordinary encryption for the rest of the conversation. They use slow public-key cryptography only for that first exchange — encrypting the actual traffic with it end to end would be far too slow at any real scale. TLS 1.2 needed two round trips for the same handshake, which is one reason 1.3 feels faster on a slow network.

"HTTPS is not just for login pages or payment forms. Any endpoint that carries a session cookie, a token, or personal data needs it, because plain HTTP leaks everything in that request to anyone on the same network — a coffee shop Wi-Fi, a compromised router, an ISP."

You will also hear about HTTP/1.1, HTTP/2, and HTTP/3 — these are transport-level upgrades, not new languages. HTTP/1.1 opens several parallel TCP connections per browser tab, to work around the fact that one connection can only handle one request at a time. HTTP/2 fixes that at the root: it multiplexes many requests over a single TCP connection, so they no longer queue behind each other on the same pipe. HTTP/3 goes further and replaces TCP itself with QUIC, a transport built on UDP, which removes a remaining source of stalling — one lost packet on a TCP connection blocks every request sharing it, even ones that have nothing to do with the lost packet.

03Talking Between Services: REST, GraphQL, gRPC, WebSockets, SSE, Long Polling

Once you have more than one service, or a client that needs live updates, plain request/response HTTP is only one option among several. Each of these six styles solves a different shape of communication problem.

REST

REST (Representational State Transfer) models your system as resources — nouns like /users/42 or /orders/9 — and uses HTTP methods on those URLs to act on them. It is simple, it reuses HTTP's own caching and status-code semantics, and almost every engineer already understands it. Its weak point shows up with nested or varied data: a mobile screen that needs a user, their last three orders, and each order's shipping status either gets one bloated response with fields it does not need (over-fetching) or has to make several round trips (under-fetching).

GraphQL

GraphQL is a query language for APIs. Instead of many fixed endpoints, there is usually one endpoint, and the client sends a query describing exactly the fields it wants, across whatever related resources it needs, in a single request. This directly solves REST's over/under-fetching problem. The cost shows up on the server: a naive resolver can trigger an N+1 query problem (one query to fetch a list, then one more query per item to fetch its related data), and because most GraphQL calls are POST requests to one URL, you lose the free caching that HTTP gives REST's GET requests by default.

gRPC

gRPC is a remote-procedure-call framework built on HTTP/2, using Protocol Buffers (protobuf) — a compact binary format defined by a schema file — instead of JSON. Both sides generate strongly typed client and server code from that same schema, so contract mismatches get caught at compile time, not in production. It also supports streaming in both directions, not just one request and one response. This makes it a strong default for calls between services you control, inside your own infrastructure, where low latency and a strict contract matter more than human readability. It is a poor fit for a public, browser-facing API: browsers cannot speak raw gRPC without an extra proxy layer, and a binary payload is harder for an external developer to inspect and debug than JSON.

WebSockets

A WebSocket starts as a normal HTTP request that asks to upgrade the connection, then keeps one TCP connection open and lets either side send a message at any time, in either direction, with no need to open a new request each time. This is the only one of the six that is genuinely full-duplex — both client and server push whenever they have something to say.

SSE (Server-Sent Events)

SSE also keeps a connection open, but only in one direction: the server streams events to the client over plain HTTP. The browser's built-in EventSource API even reconnects automatically if the stream drops. It is simpler to run than a WebSocket — no protocol upgrade, works over ordinary HTTP/HTTPS infrastructure — but the client cannot push data back over that same stream; if it needs to send something, that is a separate, ordinary HTTP request.

Long polling

Long polling gets push-like behavior out of plain request/response HTTP: the client sends a request, the server holds it open without responding until it has new data (or a timeout passes), the client processes the response and immediately fires off another request. It predates both WebSockets and SSE, and it survives today mainly as a fallback where a persistent connection is not possible — some corporate proxies and older infrastructure block the WebSocket upgrade handshake, but they cannot block plain HTTP requests.

"For this chat feature I would use WebSockets, not SSE, because participants both send and receive messages on the same channel — SSE only pushes from server to client, so I would still need a second path for the client to send anything, and at that point I am running two systems to do the job of one."

WebSockets are stateful: a client stays pinned to whichever server instance accepted its connection. That breaks the usual stateless-server-behind-a-load-balancer model. You either route with sticky sessions (same client always hits the same instance) or, better at scale, have every instance publish messages to a shared pub/sub layer (like Redis Pub/Sub or Kafka) so any instance can deliver a message to any connected client, no matter which instance holds that client's socket.

GraphQL is also a build-vs-buy and team-maturity call, not just a technical one. It buys you flexible queries, but it costs you a schema to design and evolve, resolvers to write carefully to avoid N+1 queries, and a caching story you have to build yourself since HTTP-level caching mostly stops working. For a small team building a straightforward CRUD product, plain REST is often the cheaper choice for the first year or two, even if GraphQL would be technically nicer.

04Load Balancers: What L4 And L7 Can (And Cannot) See

A load balancer sits in front of a group of servers and spreads incoming traffic across them, so no single server gets overwhelmed and a server that goes down can be quietly skipped. What differs between load balancer types is which layer of the network stack they operate at, and therefore how much of the request they can actually look at before making a routing decision.

L4: transport layer

An L4 (Layer 4) load balancer works at the transport layer — TCP or UDP. It sees the "5-tuple": source IP, source port, destination IP, destination port, and protocol. It does not open the packet's payload, so it has never seen an HTTP method, a URL path, a header, or a cookie. It just decides which backend gets this connection, using something like round robin or least-connections, and then keeps forwarding packets on that connection to the same backend. Because it does no parsing of anything above the transport layer, it is fast and cheap in CPU terms, and it works for any protocol built on TCP/UDP, not just HTTP.

L7: application layer

An L7 (Layer 7) load balancer works at the application layer. To do that with encrypted traffic, it has to terminate TLS — decrypt the connection itself — before it can read anything inside. Once it has done that, it can see the full HTTP request: method, path, headers, cookies, even the body. That lets it make much smarter decisions: route /api/orders/* to the orders service and /api/users/* to the users service, send a slice of traffic to a canary release based on a header, or keep a user pinned to one backend using a cookie instead of their IP. The cost is more CPU work per request — parsing HTTP and handling encryption — than an L4 load balancer ever does.

Picking L4 over L7 is not just a performance micro-optimization. If you need to route by URL path, by hostname, or by cookie, you need L7 — an L4 load balancer physically cannot make that decision, it never looks that deep into the packet. If all you need is "spread raw TCP connections across healthy backends" for a non-HTTP protocol, L4 is simpler, cheaper, and has nothing extra to configure wrong.

05Reverse Proxy vs API Gateway

A reverse proxy sits between clients and your servers, accepts requests on the servers' behalf, forwards each one to a backend, and returns the backend's response as if the proxy itself had produced it. It hides which servers actually exist behind it, and it commonly also handles TLS termination, load balancing, response caching, and compression — a single well-known entry point instead of clients talking to every backend server directly.

An API gateway is a reverse proxy that has grown API-specific responsibilities, usually because there are now several microservices behind it instead of one application. On top of forwarding traffic, it typically owns authentication (checking a JWT or API key before a request is even allowed through), per-client rate limiting, protocol translation (accept REST from the outside world, call gRPC internally), and sometimes request composition — combining calls to two or three downstream services into the one response a client asked for.

For a system with more than a handful of microservices, building your own auth-and-rate-limiting layer on top of a plain reverse proxy is usually the wrong call. A managed or open-source API gateway (AWS API Gateway, Kong, Envoy) already solves authentication, quotas, and routing in a way every team can plug into, so the build-vs-buy answer is almost always "buy," unless your gateway needs are genuinely unusual.

Every hop adds latency and a new thing that can fail. An API gateway is one more network hop between the client and the service that does the real work, and if it goes down, everything behind it becomes unreachable even if every service is healthy. Most designs accept this because the alternative — every client managing auth and rate limiting against every service directly — is worse, but it is a real trade-off, not a free win.

06CDN In One Page

A CDN (Content Delivery Network) is a network of servers spread across many physical locations, called edge servers or points of presence (PoPs), that cache content closer to the people requesting it. The problem it solves is simple physics: a request from Mumbai to a single origin server in Virginia has to cross a large physical distance, and that costs real time that no amount of clever code removes. A CDN moves a copy of the content to a PoP near Mumbai instead.

Roughly, it works like this: DNS or anycast routing sends a user's request to their nearest PoP. If that PoP already has the content cached (a cache hit), it answers immediately. If not (a cache miss), it fetches the content from the origin server once, serves it, and caches it for next time — this is called the pull model. Some setups instead push content out to edge servers ahead of time. Standard HTTP caching headers, like Cache-Control and ETag, control how long the edge is allowed to keep serving its cached copy before checking the origin again.

CDNs started with static assets — images, CSS, JavaScript, video — but modern CDNs also accelerate dynamic content and absorb large traffic spikes and some denial-of-service traffic before it ever reaches your origin. Real-world examples: Cloudflare, Akamai, Fastly, and AWS CloudFront; Netflix even runs its own purpose-built CDN, Open Connect, to serve video.

This chapter covers only what a CDN is and the problem it solves. Cache placement, cache invalidation strategy, and where a CDN fits into a full scale-up story get deeper treatment in Chapter 2, Scale From Zero to Millions of Users.

Put every piece from this chapter on one path, and a single request's journey looks like this: a name gets resolved by DNS, a CDN edge answers if it can, an L4 load balancer distributes the raw connection, an L7 load balancer or reverse proxy terminates TLS and reads the HTTP request, and an API gateway checks who is asking before routing it to the one microservice that actually handles it.
