Cassandra throws out the idea of a single leader entirely — every machine in the cluster is an equal peer, which is what lets it keep accepting writes even when whole data centers go dark. Neo4j takes the opposite kind of shortcut: it keeps a normal replication story but changes the data model itself, so a question like "who are my friends' friends" is one query instead of a chain of joins. This chapter covers both in enough depth to defend them in an EM-level interview.

01What Wide-Column And Graph Databases Actually Change

Ch.7 covered MySQL, a single-leader relational database. Ch.8 covers document and key-value stores that still route each shard's writes through one primary. The two databases in this chapter each break that pattern, but in different directions.

Cassandra is a wide-column store — it still organizes data into tables with rows and columns, but each row can have a different set of columns, unlike a fixed relational schema (that flexibility is truest of the classic Bigtable-style model; a modern CQL-defined Cassandra table declares a fixed set of columns, and a row just skips storage for any column it never sets). There is no leader node at all — any machine in the cluster can accept any write. That single design choice is where almost everything interesting about Cassandra comes from.

Neo4j is a graph database. It keeps a fairly conventional single-leader replication model under the hood, but it stores data as a network of connected entities instead of tables — so questions about how things relate to each other, not just what their fields contain, become the natural query.

Both come up constantly in HLD interviews for the same reason: an interviewer wants to see you recognize when a relational or document store is fighting the access pattern, and reach for the tool built for it instead.

02The Cassandra Ring: No Leader, Every Node Is A Peer

Cassandra was built at Facebook and later open-sourced; its design deliberately combines two well-known ideas — the decentralized, peer-to-peer architecture from Amazon's Dynamo, and the wide-column data model from Google's Bigtable. The peer-to-peer part is the one that makes Cassandra behave so differently from MySQL or MongoDB.

Every node in a Cassandra cluster is arranged on a logical ring — an ordered loop of positions, not a physical circle of wires. Each node owns one or more token ranges: a token is just a number produced by hashing a row's partition key (the column value that decides which node stores the row) through a partitioner. The default partitioner, Murmur3Partitioner, produces tokens across the full 64-bit range, roughly -2^63 to 2^63-1. A row's partition key hashes to one token, and the node that owns the range containing that token is the row's primary owner.

There is no primary/replica distinction at the node level and no leader coordinating traffic. Any node can receive a client request and act as the coordinator for it — the coordinator computes the token for the request's key, works out which nodes actually own that data, and forwards the request there, merging the responses before answering the client. A different request a moment later might land on a completely different node acting as coordinator.

The replication factor (N) sets how many copies of each row exist. With the simplest replication strategy, the coordinator writes to the node that owns the token, plus the next N-1 nodes walking clockwise around the ring. (Real multi-datacenter deployments use a strategy that places N copies per data center instead, so a whole region can go down without losing every replica.) In production, each physical node typically owns many small, scattered token ranges — called virtual nodes (vnodes) — rather than one big contiguous range. That spreads load more evenly across the cluster and means adding or removing a node only has to reshuffle a fraction of the data, not renegotiate one huge contiguous boundary.

Because there is no leader, there is nothing to fail over. If one of the three replica-holding nodes for a key goes down, the coordinator simply writes to the other two — the request still succeeds as long as enough replicas answer (the exact rule is section 05's quorum math). No election, no promotion, no brief window where writes are rejected while a new leader is chosen.

"Cassandra does not have a primary node the way MySQL does — every node is a peer, any node can coordinate any request, and the replication factor plus consistency level decide how many copies have to agree, not which node is in charge."

03Gossip: How A Leaderless Cluster Tracks Who Is Alive

A ring with no leader still needs every node to agree on who is currently in the cluster, which nodes own which tokens, and which nodes are down. With no central node to hold that list, Cassandra uses a gossip protocol: about once a second, each node picks a few random peers and exchanges what it currently knows — cluster membership, node status, token ownership, schema version, and load. It works the way a rumor spreads through a group of people: nobody talks to everybody, there is no central bulletin board, but because each exchange is with a random peer, the information reaches the whole cluster in a small number of rounds — the number of rounds needed grows only logarithmically with cluster size, not linearly.

Failure detection rides on the same mechanism. Rather than declaring a node dead after one fixed timeout (which false-triggers constantly on a network with normal jitter), Cassandra uses a Phi Accrual Failure Detector. It tracks the recent history of how often gossip messages actually arrive from each node and computes a confidence value, called phi, that the node is genuinely down rather than just briefly slow. A higher phi means more confidence; the threshold is configurable, trading faster detection against more false positives.

Gossip is also why Cassandra has no separate "membership service" to operate or scale — the membership list is just data that lives inside the same peer-to-peer protocol as everything else, which is consistent with there being no leader anywhere in the design.

04The LSM-Tree Write Path And Why Compaction Has To Exist

Cassandra's storage engine is a Log-Structured Merge-tree (LSM-tree). It is built around one rule: never update data in place. That is the opposite of a B-tree engine like MySQL's InnoDB (Ch.7), which finds the exact page a row lives on and rewrites it — usually a random disk seek.

The write path has two steps, both fast, sequential appends:

  • Append the write to the commit log — a write-ahead log on disk, purely for crash recovery. If the node dies, it replays the commit log on restart.
  • Write the same data into the memtable — an in-memory, sorted structure holding recent writes for the active data range.

Both steps are sequential appends: no seek, no read-before-write, no lock contention with other rows. That is the entire reason Cassandra is described as write-optimized — the cost of a write does not depend on how much data already exists.

Once a memtable fills up, it gets flushed to disk as an SSTable (Sorted String Table) — a file that, once written, is never modified again. Over time a node accumulates many SSTables. A read for a given key may have to check the memtable and several SSTables, since older and newer versions of the same row can be spread across different files, with the newest timestamp winning. Deletes do not remove anything in place either — a delete writes a tombstone, a marker meaning "this was deleted at time T," because the SSTable holding the old value cannot be edited.

To avoid opening every SSTable on every read, each one carries a Bloom filter — a small probabilistic structure that can say a key is definitely not in that file, or maybe is (occasionally wrong in that direction, never wrong the other way). Most reads skip most files without touching disk.

Compaction is the background process that keeps this whole system from growing forever: it merges several SSTables into fewer, larger ones, keeping only the newest version of each column and dropping tombstones once they are older than a configured grace period. Two common strategies show the trade-off: SizeTieredCompactionStrategy merges similarly-sized SSTables together and is the general-purpose default; LeveledCompactionStrategy organizes SSTables into size-bounded levels for more predictable read latency, at the cost of more background I/O.

Write-optimized does not mean free. Compaction is where the bill for cheap writes actually gets paid — it uses real CPU and disk I/O, running in the background, competing with live traffic. Fall behind on compaction (too many pending SSTables) and reads get slower because every read has to check more files; that is the operational cost hiding behind "write-optimized."

05Tunable Consistency: The R + W > N Quorum Math

Because there is no leader deciding write order, Cassandra lets each individual read or write choose how many replicas must participate, called its consistency level. For a write, W is how many replicas must acknowledge before the coordinator tells the client the write succeeded. For a read, R is how many replicas must respond (the coordinator returns whichever has the newest timestamp) before the coordinator answers the client. Common levels: ONE (a single replica), QUORUM (a strict majority, floor(N/2) + 1), ALL (every replica), and LOCAL_QUORUM (a quorum within the local data center only, for multi-region deployments).

The rule that decides whether you get strong consistency is: if R + W > N, every possible read set and every possible write set are guaranteed to share at least one replica, so a read is guaranteed to see the most recent acknowledged write. If R + W ≤ N, a read set and a write set can miss each other completely — that is eventual consistency, the read will catch up once replication finishes, but there is a window where it can return stale data.

Worked example: N = 3

With three replicas, QUORUM = floor(3/2) + 1 = 2. Call the three replicas {X, Y, Z}.

  • QUORUM write, QUORUM read (W=2, R=2): R + W = 4 > 3. A write acknowledged by, say, {X, Y}, followed by a read from any 2 of the 3 nodes — even the "worst" pick, {X, Z} or {Y, Z} — is guaranteed to include at least one node from the write set. Two 2-element subsets of a 3-element set cannot both avoid overlapping (2 + 2 = 4, which cannot fit into 3 without sharing at least one element). That guaranteed overlap is what makes this combination strongly consistent.
  • QUORUM write, ONE read (W=2, R=1): R + W = 3, which equals N, not greater than it — this is the trap. A write acknowledged by {X, Y} followed by a read from Z alone can miss the write entirely, because Z was not in the write set. Equal to N is not enough; it still has to be strictly greater.
  • ONE write, ONE read (W=1, R=1): R + W = 2 < 3. Lowest latency, highest availability — the write succeeds even with two of the three nodes down — but no overlap guarantee at all. This is plain eventual consistency.

This is the CAP theorem (Ch.12) showing up as a per-query dial instead of a whole-database setting. Pushing R and W up toward N buys consistency but costs latency and availability — a write at ALL fails outright if even one replica is down. Pushing them down buys speed and uptime but accepts staleness. Cassandra's real pitch is that you get to choose this trade-off per operation, not once for the whole system.

06Cassandra In Production: Netflix

Netflix has run one of the best-known large Cassandra deployments in the industry for years — many clusters spanning multiple AWS regions, storing things like viewing history and other data that has to keep accepting writes even if an entire AWS region has a bad day. That requirement lines up exactly with what a leaderless, multi-datacenter ring is built for: there is no single-region leader to lose, and NetworkTopologyStrategy (section 02) keeps full replica sets in each region so a region failure does not mean data loss or a manual failover.

An EM-level answer adds the build-vs-buy angle: running a large multi-region Cassandra ring yourself is a real operational commitment — compaction tuning, repair jobs, capacity planning per data center. Managed offerings (DataStax Astra, AWS Keyspaces) trade some of that flexibility for someone else owning the 3am pages, which is often the right call until a team's scale genuinely needs to tune the ring itself.

07HBase In Brief: A Master-Based Wide-Column Store On HDFS

HBase is another wide-column store, modeled on Google's Bigtable paper, but it takes the opposite architectural approach from Cassandra. Instead of a leaderless ring, HBase uses a master/RegionServer model, and instead of managing its own files on local disk, it stores everything on HDFS (the Hadoop Distributed File System) — HBase is part of the Hadoop ecosystem, not a standalone store.

An HMaster handles schema changes and assigns regions — contiguous ranges of row keys for a table — to RegionServers, which actually serve reads and writes for the regions they own. Each RegionServer uses the same core LSM-tree idea as Cassandra internally (a write-ahead log plus an in-memory MemStore, flushed to immutable HFiles and compacted in the background) — it is the ownership model wrapped around that engine that differs. ZooKeeper coordinates cluster membership and HMaster failover. Because exactly one RegionServer owns a given region at any moment, HBase gives strong, consistent reads and writes per row by default — there is no quorum dial to tune, unlike Cassandra. Facebook's original Messages product famously ran on HBase, a well-known early production use case.

08Neo4j And The Property Graph Model

A graph database stores data as a network of connected entities rather than tables. Neo4j, the most widely used graph database, is built on the property graph model: data is made of nodes (entities, like a person or an account) and relationships (directed edges between two nodes, like "follows" or "transferred money to"), and both nodes and relationships can carry labels (a type tag — a node might be labeled :Person, a relationship typed :FRIENDS_WITH) and their own properties (key-value attributes — a :TRANSFERRED_TO relationship might carry an amount and a timestamp, just like a node can). This is different from an RDF triple store, another kind of graph database, which represents everything as plain subject-predicate-object statements without first-class properties on the edges themselves — the property graph model is the one that shows up most in interviews, because it maps naturally onto entities and attributes people already think in.

Neo4j is queried with Cypher, a pattern-matching language: instead of describing a set of rows to filter, you draw the shape you are looking for using an ASCII-art-like syntax — (a)-[:REL]->(b) reads as "a node a, connected by a REL relationship, to a node b" — and Neo4j finds every match of that shape in the graph.

The structural reason this is fast is called index-free adjacency: every node physically stores direct pointers to its adjacent relationships and neighboring nodes. Walking from a node to its neighbor is a pointer dereference, not an index lookup — its cost does not depend on how big the overall dataset is, only on how many nodes and relationships you actually visit. A relational join, by contrast, typically needs an index lookup per hop, and that lookup's cost is tied to the size of the tables being joined.

09Why A Graph Model Beats Relational Joins

The diagram above sets up the two cases interviewers actually ask about: a multi-hop traversal (friends-of-friends), and pattern detection across a network (a fraud ring). Both are the kind of question where a relational engine's per-hop join cost adds up fast, and a graph engine's per-hop pointer walk does not.

Social graph traversal: friends-of-friends

In a relational schema, friendships live in a table like friendships(user_id, friend_id). Finding second-degree friends means joining that table with itself once per extra hop:

SELECT DISTINCT f2.friend_id AS fof
FROM friendships f1
JOIN friendships f2 ON f2.user_id = f1.friend_id
WHERE f1.user_id = 123
  AND f2.friend_id <> 123
  AND f2.friend_id NOT IN (
    SELECT friend_id FROM friendships WHERE user_id = 123
  );

Going one hop further (third-degree friends) means adding a third self-join on f3.user_id = f2.friend_id, and the intermediate row count can multiply out at every hop before the final filter trims it back down — each person's row can fan out to however many friends they have. That is why plain joins get painful past two or three hops on a table with many rows per user. Some relational engines offer recursive CTEs to express arbitrary-depth traversal in a single query, but under the hood the engine still executes it as repeated joins with no shortcut, and it is typically much slower than a native graph traversal at the same depth.

The same query in Cypher is one pattern, and adding a hop is one extra segment, not a new join:

MATCH (me:Person {id: 123})-[:FRIENDS_WITH]->(:Person)-[:FRIENDS_WITH]->(fof:Person)
WHERE fof.id <> 123 AND NOT (me)-[:FRIENDS_WITH]->(fof)
RETURN DISTINCT fof

Fraud-ring detection: cycles and shared attributes

Fraud rings tend to show up as one of two graph shapes. The first is a cycle: money moves from account A to B to C and back toward A, and you usually do not know the cycle's length ahead of time. The second is a shared attribute: accounts that look unrelated — different names, different emails — but point to the same device fingerprint, IP address, or payment card.

Cypher expresses "a cycle of unknown length" with a variable-length relationship pattern:

MATCH path = (a:Account)-[:TRANSFERRED_TO*2..5]->(a)
RETURN path

*2..5 means "walk this relationship type between 2 and 5 times." Not knowing the cycle length ahead of time is exactly the case that breaks the SQL self-join approach — you cannot pre-write "the right number" of joins, so you would need a recursive CTE with an explicit cycle guard, and it still has no direct-pointer shortcut between rows the way a graph traversal does.

The shared-attribute case is a pattern with two accounts pointing at the same node:

MATCH (a1:Account)-[:USES_DEVICE]->(d:Device)<-[:USES_DEVICE]-(a2:Account)
WHERE a1.id <> a2.id
RETURN a1, a2, d

On its own that is a plain join on a device_id column in SQL too — not the hard part. The hard part is chaining it: "accounts that share a device with an account that also shares a payment card with a third account" is another self-join per extra hop in SQL, while in Cypher it is one more relationship segment on the same pattern.

Graph databases are excellent at "how are these things connected" questions, and bad at the aggregate, scan-heavy questions a data warehouse is built for — "sum revenue by region for the last quarter across 500 million rows" is not a graph traversal, and Neo4j is not a replacement for the OLAP systems in Ch.10 for that kind of workload.

Adopting a graph database for one feature, like fraud detection, is rarely a full migration. Most teams keep accounts and transactions in their existing primary store and mirror just the relevant edges — account, device, transfer — into Neo4j using change data capture or an event stream. The build-vs-buy question is really "which slice of our data needs graph traversal," not "should we replace our relational database."

"I would reach for a graph database specifically for the traversal, not as a system of record. I would keep account and transaction data in the primary store and mirror only the account-device-transfer edges into Neo4j, so a fraud query that is three or more hops deep runs in milliseconds instead of timing out a recursive SQL query."

  • Coordinator — whichever node received a given request; any node can play this role.

  • Phi Accrual Failure Detector — computes a confidence value that a node is down, based on recent heartbeat timing, instead of one fixed timeout.
LSM The write path and compaction
  • Commit log — write-ahead log on disk, used only for crash recovery.
  • Memtable — in-memory sorted structure holding recent writes.
  • SSTable — immutable file a full memtable is flushed to.
  • Bloom filter — per-SSTable check that quickly rules out "key not here," letting most reads skip most files.
  • Tombstone — a deletion marker, since existing SSTables cannot be edited in place.
  • Compaction — background merge of SSTables that drops overwritten data and expired tombstones.
Levels Consistency levels and the quorum formula
  • ONE — a single replica. Fastest, weakest guarantee.
  • QUORUM — floor(N/2) + 1 replicas, a strict majority.
  • ALL — every replica. Strongest guarantee, weakest availability.
  • LOCAL_QUORUM — a quorum within one data center, for multi-region clusters.
  • Strong consistency rule — guaranteed only when R + W > N, strictly greater.

  • Node — an entity, can carry one or more labels and any number of properties.
  • Relationship — a directed, typed edge between two nodes; can carry its own properties.
