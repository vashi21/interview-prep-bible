This chapter is a bank of sixteen marketplace and location-based systems — ride-hailing, food and grocery delivery, booking platforms, dating and classifieds apps, fleet tracking, and geo-search products — that look different on the surface but are built from the same small set of moving parts.

00How to use this chapter

Almost every problem below is really one of two shapes wearing a different costume. The first shape is "find nearby things fast": a geo-index that answers "what is close to me right now," whether the things are drivers, restaurants, parking spots, or dates. The second shape is "lock a scarce thing so two people cannot get it at once": a seat, a hotel room, a rental car, a parking space, a bike. Once you can recognize which shape (or which mix of both) a new prompt is, you already know the skeleton of your answer before you have drawn a single box. The quick-reference entries below collect the specific techniques that keep reappearing across this chapter's problems, so you are not re-deriving them from scratch under interview pressure.

Geo-Index Two ways to answer "what is nearby"
  • Write-heavy, filter-free (ride-hailing, bike-share): an in-memory, geohash-bucketed structure (Redis geo commands or a hand-rolled geohash map) held by a regional shard. Optimized for constant position updates, at the cost of only doing distance queries well.
  • Read-heavy, filter-rich (Yelp, real estate, classifieds): a search engine's native geo query (Elasticsearch geo_point) that combines distance with category, price, and text filters in one query. Optimized for rich queries over data that rarely moves.
  • Picking the wrong one is the most common mismatch in this chapter: a hand-rolled geo-index for Yelp-style search would not support filters well; a search-engine index for ride-hailing could not absorb millions of location writes per second.
Hold-TTL The hold-then-confirm pattern for scarce inventory
  • Reserve the scarce item (seat, room, car, spot, bike) with a short time-to-live (TTL) hold the instant a user starts checkout, so a second user cannot claim it mid-flow.
  • The hold converts to a real, durable booking on successful payment, or expires automatically and releases back to the pool if the user abandons checkout.
  • Appears at very different scales: seconds-to-minutes and thousands of contenders for one concert seat, versus minutes and one or two contenders for one Airbnb listing or one bike. Match the infrastructure to the actual contention, not the scariest version of the pattern.
Split Two-tier consistency: search vs. booking/money
  • The "browse/search" half of a marketplace can almost always be eventually consistent — a result that is a few seconds stale just means an occasional failed booking attempt, not a broken product.
  • The "confirm/pay" half almost never can be. It needs strong consistency, because a double-booked room or a missed match is a real, visible failure, not a stale read.
  • Naming this split out loud in an interview (which half of your design needs which kind of rigor) is one of the highest-value things you can say — it signals you are not over- or under-engineering either side.
Constraint Database constraints beat application checks
  • A "check if free, then insert" done as two separate steps in application code is a race condition — two requests can both pass the check before either commits.
  • The fix is to make the conflict fail atomically inside the database: a unique constraint for a point-in-time resource (a seat, a parking spot), or a range-overlap exclusion constraint (Postgres GiST) for a date-range resource (a hotel room, a rental car).
  • An application-level check is still worth doing first, for a fast, friendly error message — it is just never the actual safety net.
Ledger Append-only ledgers for money that moves in steps
  • Whenever money sits in escrow or splits across multiple parties (freelance milestones, delivery payouts to restaurant and courier), never store a single mutable "current balance" field.
  • Write every fund, hold, release, refund, and fee-split as its own immutable, timestamped entry. Any balance shown to a user is a computed sum over entries, replayed on demand.
  • This is what makes a dispute answerable months later ("why does this show $400 released") and is the same discipline behind Ch.21's authorize/capture and general ledger patterns.

Design Uber/Lyft (Ride-Hailing)

Problem framing

Strip away the app and this is a real-time matching problem: thousands of moving dots (drivers) and thousands of moving or waiting dots (riders) need to be paired up in seconds, using location data that goes stale within moments of being written. Everything else — pricing, trip tracking, payment — hangs off that one core matching loop.

Clarifying questions

  • Do we match on pure nearest-driver, or batch requests and optimize matches across a short time window? — nearest-driver is simple but can be globally worse (it can send a driver 2 minutes away when a driver 90 seconds away is about to finish a different match); batching a few seconds of requests and solving them together usually lowers average wait time at the cost of a small delay per rider.
  • Is this single-city or global from day one? — decides whether "one shard per metro area" is a valid starting design or we need a harder global partitioning scheme immediately.
  • Do we support scheduled (book-ahead) rides, or only on-demand? — scheduled rides need a separate reservation system that reasons about future driver supply, not live matching.
  • How many vehicle tiers (economy, XL, pool) do we support, and can a pool ride carry two unrelated riders? — pooling turns matching from 1-to-1 into a routing/bin-packing problem.
  • What's the acceptable latency from "rider taps request" to "a driver is assigned"? — this is the single number that decides whether the geo-index has to live in memory or can tolerate a database round-trip.

Requirements

Functional: rider requests a ride with a pickup and drop-off point; system finds and assigns a nearby available driver; both parties see the other's live location during pickup and the trip; the system computes a fare (including surge pricing under high demand); the trip moves through a defined lifecycle (requested → matched → driver arriving → in progress → completed); payment is captured at trip end.

Non-functional: driver-to-rider matching in low single-digit seconds; the system must accept a very high, continuous rate of location-update writes (every active driver, every few seconds); driver location can be a few seconds stale — this is not a system where strong consistency matters; the matching and location layers must be geographically partitioned, because a ride in Mumbai never needs to know about a driver in Chicago; payment and trip-completion records need strong durability once a trip is confirmed.

Capacity estimate

Assume a large global operator: 130 million monthly active riders, 6 million active drivers at any given time worldwide, and 20 million completed trips per day.

Ride requests:
  20,000,000 trips/day
  Average request QPS   = 20M / 86,400s ~= 231/sec
  Peak request QPS (5x, rush hour concentration) ~= 1,160/sec

Driver location updates (the real load, not ride requests):
  6,000,000 active drivers, each pinging location every 4 seconds while online
  Average location-update QPS = 6,000,000 / 4 ~= 1,500,000/sec
  Peak (rush hour, more drivers online + shorter ping interval) ~= 2,500,000/sec

Trip breadcrumb storage (location history kept for the life of the trip + audit window):
  Average trip length ~15 min = 900s -> ~225 pings/trip at 4s intervals
  20M trips/day x 225 pings x ~80 bytes/ping ~= 360 GB/day of breadcrumb data
  (most of this ages out after a short retention window; only trip start/end and a
  sampled path are kept long-term for support/fraud review)

Matching SLA budget:
  Must find, score, and confirm a driver within ~3 seconds end to end, which is why
  driver position has to live in an in-memory geo-index, not be queried from a
  disk-backed database on every request.

The number that actually sizes the system is the 1.5–2.5 million location writes per second, not the ride requests. Ride requests are the business metric; location pings are the engineering bottleneck.

High-level design

A ride request goes to a regional matching service, which asks an in-memory geo-index for nearby available drivers, scores and picks one, and reserves that driver before the rider's app even shows a result. Driver location pings flow through a separate, much higher-volume ingestion path straight into that same geo-index.

Deep dive

The geo-index has to be in memory and regionally partitioned. With 1.5–2.5 million writes per second, a disk-backed database updated on every ping is not viable, and a single global index would put every write from every continent through one bottleneck for no benefit — a rider in Lagos never matches with a driver in Seattle. The standard answer is to shard by geography: encode each driver's position as a geohash (see Ch.16's geohashing primitive) and keep the current position of every driver in a region in an in-memory structure (a geohash-bucketed map, or Redis's built-in geospatial commands) held by the matching cell that owns that region. This trades a small amount of staleness (a few seconds between pings) for the write throughput the problem actually needs.

Nearest-driver matching is a local optimization; batching is a better one. Matching each request the instant it arrives to the closest free driver is simple and fast, but it is greedy — it can assign the closest driver to rider A a moment before a slightly farther but sooner-to-be-free driver would have made both A and rider B happier. Uber's and Lyft's real systems batch requests over a short window (on the order of a few seconds) and solve a small matching problem across all pending riders and available drivers at once, closer to a bipartite matching / assignment problem than a single nearest-neighbor lookup. The trade-off is explicit: a few seconds of extra wait per rider in exchange for a lower average wait and less driver deadheading (empty driving) across the whole pool.

Surge pricing is a supply/demand signal computed per geo-cell, not per request. The pricing service does not recompute a global multiplier — it tracks the ratio of open ride requests to available drivers within each geo-cell (the same geohash buckets used for matching), recomputes that ratio roughly every minute, and caches the resulting multiplier so every fare estimate in that cell reads a cheap cache hit instead of triggering a fresh computation. This is the same idea as Ch.4's cache-aside pattern, applied to a number that changes on a clock, not on every read.

Trade-offs

At 10x scale, the in-memory regional geo-index is what breaks first, not the trip database — a single metro area during a major event (a concert letting out, a stadium emptying) can spike local driver density and request volume far past its provisioned shard capacity. The trade-off is between fixed geographic shards (simple, but a hot city can outgrow its shard) and dynamic re-sharding by load (handles hotspots, but means a driver's "home shard" can change mid-shift, which complicates the connection routing that keeps their location updates going to the right place).

Say this

"I'd keep driver location in an in-memory, geohash-partitioned index rather than a database, because at 1.5 to 2.5 million writes a second, a few seconds of staleness is a completely acceptable trade for not needing every ping to hit disk. The trip and payment records are the part that needs real durability — the live position feed does not."

Final design

One picture: a rider request and a stream of driver pings both flow into a regionally sharded, in-memory geo-index; a matching service batches pending requests every few seconds and solves them against that index and a surge-pricing signal; once matched, the trip hands off to a durable, strongly consistent trip and payment system that no longer cares about millisecond-level location freshness.

EM-level follow-up

Rollout: launch new metros one shard at a time — driver supply has to be seeded before demand, so this is an operations problem as much as an engineering one, and the matching cell for a new city can be spun up independently of every other city. Build vs. buy: the routing and ETA engine (see the Google-Maps-style problem in this chapter) is almost always bought from a mapping provider rather than built in-house in a company's early years — building a global road graph and traffic model is a multi-year investment that only pays off once you are Uber-scale. Cross-team impact: the geo-index and matching cell design is usually owned jointly with a dedicated "marketplace" or "dispatch" team, because pricing, matching, and driver incentives all read and write the same supply/demand signal.

Design a Food Delivery Platform (DoorDash/Swiggy-style)

Problem framing

This is a three-sided marketplace, not a two-sided one: a customer, a restaurant, and a courier all have to be coordinated for one order to succeed. The hard part is not moving data — it is that the bottleneck is physical and human (how fast a kitchen can cook) as often as it is technical, and the system has to sense and react to that.

Clarifying questions

  • Can one courier carry multiple orders at once (batching)? — batching lowers delivery cost per order but adds a routing problem (which order gets picked up and dropped off in which order) and a food-quality risk (cold food from a longer combined route).
  • Does the platform throttle how many orders a restaurant can accept at once? — without this, a popular restaurant can be flooded with more orders than its kitchen can physically cook, leading to long delays and cancellations regardless of how fast the software is.
  • Is payment split immediately, or held until delivery is confirmed? — this decides whether we need an escrow-like hold, similar in shape to the Freelance-marketplace escrow problem later in this chapter, just on a much shorter timescale (minutes, not weeks).
  • Do we need live courier tracking on a map for the customer? — if yes, this reuses the same live-location-ping pattern as the ride-hailing problem above, at a much lower volume.
  • What happens when an item is out of stock after the order is placed? — decides whether substitution/refund logic is in scope, which matters more for grocery delivery but can still happen here (a menu item sells out mid-shift).

Requirements

Functional: browse nearby restaurants and menus; place an order; the restaurant accepts and reports prep progress; the system assigns a courier; the customer and courier both see live status and location; payment is captured and split between platform, restaurant, and courier once delivery is confirmed.

Non-functional: traffic is extremely spiky around meal times (lunch and dinner windows), not smooth through the day; order-state transitions need strong consistency (an order cannot silently be both "accepted" and "cancelled"); browse/search can tolerate a little staleness; the system must be able to signal back-pressure to restaurants that are overloaded rather than accepting orders they cannot fulfill.

Capacity estimate

Assume a large regional operator: 40 million monthly active users, 3 million orders per day, with 40% of daily volume landing inside two peak two-hour windows (lunch and dinner).

Orders/day                = 3,000,000
Average order QPS          = 3,000,000 / 86,400s ~= 35/sec
Peak-window orders         = 3,000,000 x 40% = 1,200,000 across two 2-hour windows
Peak QPS (within a peak window) = 1,200,000 / (2 x 3,600s) ~= 167/sec
Peak QPS with intra-window bursts (2x) ~= 330/sec

Courier location updates (lower volume than ride-hailing, shorter trips):
  600,000 active couriers at peak, pinging every 5 seconds while on a delivery
  Peak location-update QPS ~= 600,000 / 5 ~= 120,000/sec

Order-state writes (an order moves through ~6 states: placed, accepted, preparing,
ready, picked up, delivered):
  3,000,000 orders x 6 transitions = 18,000,000 writes/day
  Average write QPS = 18M / 86,400s ~= 210/sec

Catalog/menu storage (read-heavy, rarely written):
  500,000 restaurants x ~100 menu items x ~1 KB/item ~= 50 GB total, easily cached
  in full on a regional edge cache since it changes far less often than it is read

Unlike the driver-location problem in ride-hailing, this system's hardest number is not raw QPS — it is the 40% of daily volume compressed into two hours, which means the system has to be provisioned for a peak roughly 5-8x its daily average, not the smoother 2-3x multiplier that works for less time-concentrated traffic.

API design

GET  /restaurants/nearby?lat=&lng=&cuisine=          browse (see the Yelp-style problem for the search pattern)
GET  /restaurants/{id}/menu
POST /orders                { restaurantId, items, deliveryAddress, paymentMethodId }
PATCH /orders/{id}/status   { status }              restaurant/courier-driven transitions
POST /orders/{id}/assign-courier   internal, called by the dispatch service
POST /couriers/{id}/location       { lat, lng, timestamp }
GET  /orders/{id}                  poll or subscribe for live status + courier position

High-level design

An order is admitted (or throttled) based on the restaurant's current load, persisted, and then handed to a dispatch service that assigns a courier using the same kind of geo-index pattern as ride-hailing, just matching couriers to a pickup-then-dropoff pair instead of a single pickup point.

Deep dive

Admission control against restaurant capacity, not just infrastructure capacity. The hardest scaling problem here is not servers — it is that a single popular restaurant's kitchen has a real, physical ceiling on orders per hour. If the order service accepts every incoming order and just queues it for the restaurant, the restaurant falls further and further behind, prep-time estimates become wrong, and customers cancel or complain. The real fix is a feedback loop: each restaurant reports (or the system infers from historical accept/prep timing) a rolling estimate of its current order queue depth and average prep time, and the order service throttles new order admission once that queue crosses a threshold — showing the customer a longer wait estimate or temporarily hiding the restaurant, rather than accepting an order it can likely not fulfill on time. This is a fundamentally different bottleneck from ride-hailing, where the constrained resource (drivers) is itself part of the platform's own supply and can be measured directly.

Batching deliveries is a routing trade-off, not a free win. Assigning one courier to two nearby orders cuts delivery cost roughly in half, but it means the first order's food sits in the courier's bag longer while the second is picked up — a real quality cost. The dispatch service has to score candidate batches by combined detour distance and estimated food-temperature risk (a simple proxy: total added time from batching), not just by proximity, and reject a batch that saves money but meaningfully degrades either order.

Payment capture and split needs a short-lived saga, not a single transaction. One order touches at least three parties: the customer is charged, the restaurant is paid for the food, and the courier is paid for the delivery — and these payouts often happen on different schedules (restaurant paid out daily, courier paid per-delivery). This is the same class of problem as Ch.13's Saga pattern: a sequence of local transactions (charge customer → confirm delivery → credit restaurant ledger → credit courier ledger) with compensating actions (refund) if a later step fails, rather than one distributed transaction across three parties' ledgers.

Trade-offs

At 10x scale during a single peak window (say, a city-wide event pushing everyone to order dinner at once), restaurant kitchen throughput is what breaks first, not the order or dispatch services — no amount of horizontal scaling fixes a kitchen that can only make 40 pizzas an hour. The trade-off is between showing customers accurate, longer wait times (protects trust, loses some orders to competitors) and accepting orders optimistically to not lose the sale (higher short-term order count, but more cancellations and worse reviews when the kitchen falls behind).

Say this

"I'd add admission control keyed off each restaurant's live queue depth, not just rate-limit at the infrastructure layer — the real constraint here is kitchen throughput, which is a physical bottleneck no amount of extra servers can fix. Slowing down or hiding an overloaded restaurant protects the customer experience better than accepting an order we can already tell will be late."

Final design

One picture: browse and catalog are a cached, read-optimized path; placing an order runs through admission control gated on restaurant load before it is ever persisted; a dispatch service matches couriers using the same kind of geo-index pattern as ride-hailing; and the money side runs as a short saga across customer, restaurant, and courier ledgers, completed only once delivery is confirmed.

EM-level follow-up

Rollout: launching a new city means seeding both restaurant supply and courier supply before turning on customer demand — sequencing this wrong (demand live before there are enough couriers) produces bad early reviews that are hard to undo. Build vs. buy: routing and ETA for the courier's route is usually bought from a mapping provider (see the Google-Maps-style problem in this chapter) rather than built, and payments/payouts to restaurants and couriers are almost always built on top of a payments platform (Stripe Connect or similar) rather than a homegrown ledger. Cross-team impact: the restaurant-side admission-control signal is jointly owned with whatever team manages restaurant onboarding and support, since restaurants need visibility into why their orders are being throttled.

Design Google-Maps-style ETA and Routing

Problem framing

Given a start point, an end point, and the current state of traffic, return the fastest route and an estimated time of arrival — in well under a second, against a road network with hundreds of millions of segments. The hard part is not knowing the roads; it is answering "which path is fastest right now" fast enough to feel instant.

Clarifying questions

  • Driving only, or also walking, biking, and transit? — each mode has a different graph (transit needs schedules layered on top of a network) and different weighting, which multiplies the scope of "one routing engine" into several.
  • Do we need live traffic, or is a static, historical speed model acceptable to start? — this decides whether we need a real-time ingestion pipeline for crowd-sourced position data at all.
  • Is this worldwide from day one, or one country/region first? — road graph size and the sharding strategy both depend heavily on this.
  • Do we need to re-route automatically when a driver deviates from the suggested path? — turns this from a single request/response query into a continuously running background computation for every active navigation session.
  • How precise does the ETA need to be — a rough number, or turn-by-turn timing? — decides how much of the graph's fine detail (turn restrictions, traffic-light delay estimates) actually matters.

Requirements

Functional: compute the fastest route and an ETA between two points, given current traffic conditions; support multiple travel modes; re-route when a traveler deviates from the suggested path; expose the result as both a full turn-by-turn path and a single ETA number for callers (like a ride-hailing app) who only need the number.

Non-functional: sub-second response for interactive queries; must operate over a road graph with hundreds of millions of edges; must degrade gracefully when live traffic data is sparse (rural roads, low probe density) rather than failing; horizontally scalable to a very high global query volume, most of which is read-only routing requests, not map edits.

Capacity estimate

Assume a large-scale global mapping service: 500 million daily active users issuing an average of 3 route/ETA requests per day (a mix of turn-by-turn navigation and other apps calling the ETA API, like the ride-hailing problem above).

Route/ETA requests/day     = 500,000,000 x 3 = 1,500,000,000 (1.5B)
Average QPS                = 1.5B / 86,400s ~= 17,400/sec
Peak QPS (rush hour, ~4x)  ~= 70,000/sec

Road graph size (worldwide, order-of-magnitude):
  roughly hundreds of millions of road segments (edges) and a similar order of
  intersections (nodes) worldwide; take ~600,000,000 edges x ~100 bytes/edge
  (geometry + speed limit + turn restrictions) ~= 60 GB for the base topology --
  small enough to replicate per regional shard, once compressed and indexed

Live traffic probe ingestion (crowd-sourced position pings from navigating devices):
  Assume 50,000,000 concurrent active navigation sessions at global peak,
  pinging position every 5 seconds
  Peak probe ingestion ~= 50,000,000 / 5 ~= 10,000,000 pings/sec
  This is an order of magnitude larger than the route-request volume itself --
  traffic ingestion, not routing queries, is the largest data-plane number here.

Precomputed shortcut graph ("contraction hierarchy," see Deep dive):
  built offline, refreshed periodically (hours, not seconds); adds meaningful
  storage overhead per region but is what makes sub-second queries possible at all

The two numbers worth saying out loud in an interview: 70,000 queries/sec at peak for routing itself, and a much larger 10 million/sec for the live traffic signal that routing depends on but does not directly serve.

API design

GET  /route?origin=&destination=&mode=driving&departureTime=      full turn-by-turn path + ETA
GET  /eta?origin=&destination=&mode=                               ETA number only, for machine callers
POST /navigation/{sessionId}/reroute   { currentLocation }         mid-trip re-route on deviation
POST /traffic/probe                    { deviceId, lat, lng, speed, timestamp }   crowd-sourced ingestion

High-level design

A routing query hits a regional shard holding a precomputed, hierarchical version of that region's road graph, combines it with a fast-changing live-speed layer, and returns a path. Traffic probes flow through an entirely separate high-volume ingestion pipeline that only feeds that speed layer — it never touches the graph topology itself.

Deep dive

Naive shortest-path search is too slow; the answer is precomputed shortcuts. Running plain Dijkstra or even A* over a graph with hundreds of millions of edges, per query, cannot hit a sub-second budget at this volume. Real routing engines precompute a contraction hierarchy: offline, they rank every intersection by importance and repeatedly "contract" the least-important ones, replacing the paths through them with direct shortcut edges that preserve shortest-path distances. A query then only has to search a small, mostly-highway-level version of the graph near the endpoints, expanding down into local detail only near the origin and destination. This is the same underlying trade as Ch.11's discussion of precomputed indexes: pay a large, offline, periodic cost (hierarchy construction) to make the online read path dramatically cheaper.

Live traffic has to be a separate, fast-changing layer, not baked into the graph itself. Road topology (which streets connect to which) changes rarely; current speed on each segment changes by the minute. Keeping these as two layers — a slow-changing precomputed graph and a fast-changing per-edge speed store, queried and combined at request time — means traffic updates never require rebuilding the expensive contraction hierarchy. The trade-off is that this is an approximation: the "fastest" path found using the precomputed shortcut structure with current speeds applied is very close to, but not always exactly, the mathematically optimal path under live conditions — an acceptable trade for a system that must answer in milliseconds.

Sparse data on low-traffic roads needs a fallback model, not a blank. Crowd-sourced GPS probes cluster on popular roads and are thin or absent on quiet residential streets and rural roads. The speed layer falls back to a historical, time-of-day-based average speed for any edge with too few recent probes, rather than showing no data or a stale single old reading — accuracy degrades smoothly with data density instead of failing outright.

Trade-offs

At 10x global query volume, the constraint that breaks first is memory footprint per regional shard — keeping a fully contracted hierarchy for a large region resident in memory is what makes queries fast, but it does not shrink as query volume grows, only as the map itself grows. The trade-off is between replicating the full in-memory graph across many query-serving replicas (fast, but expensive and slow to propagate hierarchy rebuilds) versus a smaller in-memory "highway skeleton" with disk/SSD-backed local detail paged in on demand (cheaper per replica, but a slower tail latency on queries that need a lot of local detail near the endpoints).

Say this

"I would not run Dijkstra live against the full road graph on every query — at this scale I would precompute a contraction hierarchy offline and rebuild it periodically, then keep live traffic as a separate, fast-changing edge-speed layer applied at query time. That keeps the expensive precomputation off the request path entirely and makes traffic updates cheap."

Final design

One picture: an offline pipeline builds and periodically refreshes a contracted, hierarchical road graph per region; a live probe-ingestion pipeline feeds a much faster-changing per-edge speed store; and every routing query combines the two — the slow-changing shortcuts and the fast-changing speeds — to answer in well under a second.

EM-level follow-up

Rollout: expand region by region, gated on both map data quality and traffic probe density — a region with too few navigating devices to build a reliable live-speed layer should ship with a historical-only model and be upgraded once usage grows. Build vs. buy: most consumer products that need routing (ride-hailing, food delivery, logistics) buy this capability from a mapping provider (Google Maps Platform, Mapbox, HERE) rather than building a road graph and traffic model in-house — the multi-year investment in map data alone rarely pays off below very large scale. Cross-team impact: this service typically becomes a shared platform dependency for every other team that needs "how long will this take" or "what's the best path," which means its SLA becomes everyone else's SLA too.

Design Yelp-style Nearby Search

Problem framing

Given a location and some filters, return nearby businesses ranked by a mix of distance and quality. Unlike the previous two problems, almost nothing here moves — businesses do not change location every few seconds the way drivers do — so this is a read-heavy search-and-ranking problem, not a real-time matching problem.

Clarifying questions

  • Fixed-radius search, or "top K nearest regardless of distance"? — a fixed radius can return zero results in a sparse area; top-K nearest always returns something, but "nearest" might be 40 km away in a rural area, which needs its own UX handling.
  • What filters need to be supported — cuisine/category, price, rating, open now? — "open now" in particular is a time-dependent filter, not a stored fact, and needs different handling than the rest (see Deep dive).
  • Do we need full-text search over business names and review content, or just structured filters? — full text adds a real search-index subsystem on top of the geo-filtering.
  • How fresh does a business update (new hours, closed permanently) need to be? — decides whether the search index can lag the source-of-truth database by minutes without hurting the product.
  • Do we need fraud/fake-review detection in scope, or just display whatever review score exists? — this affects how much trust the ranking score can place on raw rating averages.

Requirements

Functional: search for businesses near a given location within a radius; filter by category, price, rating, and open-now status; sort by distance or by a relevance/quality score; support text search by business name or category; show and accept reviews.

Non-functional: read-to-write ratio is extremely high — businesses are searched constantly and updated rarely; low latency (well under 200ms) for search; eventual consistency is fine for business detail updates (a new review or hours change lagging by a minute or two is not user-visible harm); horizontally scalable read path, since reads dominate by orders of magnitude.

Capacity estimate

Assume a large-scale local-search product: 80 million monthly active users, 30 million daily active searchers, averaging 3 searches per session.

Searches/day             = 30,000,000 x 3 = 90,000,000
Average search QPS       = 90M / 86,400s ~= 1,040/sec
Peak search QPS (lunch/dinner windows, ~5x) ~= 5,200/sec

Business catalog:
  ~5,000,000 active listed businesses
  ~2 KB/business (name, category, address, geo-coordinates, hours, price tier)
  Total catalog size ~= 10 GB -- small enough to fully cache across a handful of nodes

Reviews (grows continuously, unlike the catalog):
  ~200,000,000 reviews on file, growing by ~50,000/day
  ~500 bytes/review (text + rating + metadata)
  Total review text ~= 100 GB and growing, before search-index overhead

Geo-index size:

  index (category, price, hours), because writes are rare: a location almost never

High-level design

A search request goes to a search service backed by a geo-and-text index, kept up to date by a pipeline reading from the business database — not written to directly — so the read-heavy search path never blocks on the same store that handles rare, low-volume business edits.

Deep dive

A search engine's geo-index, not a hand-rolled one, fits this problem's shape. Because writes to business data are rare and reads dominate by orders of magnitude, a purpose-built search engine with native geo support (Elasticsearch's geo_point field type and geo-distance queries, see Ch.11) is a better fit than a custom in-memory structure. It lets one query combine geo-distance filtering with category, price, and text-relevance filtering in a single pass — something a plain geohash-in-Redis structure (the right tool for the ride-hailing problem's high-write, filter-free case) does not do well.

"Open now" is computed at query time, not stored as a fact. Recomputing and rewriting an is-open boolean for 5 million businesses every minute does not scale and is wasted work for the businesses no one is searching for right now. Instead, each business document stores a compact weekly hours schedule, and the search query applies "is this business open at the current request time" as a filter evaluated against that schedule at query time — a small amount of per-query computation, applied only to the handful of candidates a geo query already narrowed down, instead of a constant background recomputation job over the whole catalog.

Ranking needs a quality signal beyond raw average rating. A brand-new business with one five-star review should not outrank a business with 2,000 reviews averaging 4.6 stars — a naive sort by average rating gets this backwards. A more robust score weights the rating by review count (a form of Bayesian averaging that pulls low-count ratings toward the overall mean until enough reviews accumulate) combined with distance decay, so a very close, decently-reviewed business can still outrank a farther, thinly-reviewed five-star one. This ranking layer is also where fake-review detection, if in scope, would feed a trust discount into the same score.

Trade-offs

At 10x scale, the part that outgrows the compact, cacheable business/geo index is reviews and photos — an unbounded, ever-growing dataset, unlike the roughly fixed-size business catalog. The trade-off is keeping review text and photos in a separate, larger, slower store (a blob store plus a wide-column database) from the small, hot, fully-cacheable business metadata and geo-index, and accepting a join at render time between "which businesses match" (fast) and "show me the reviews for this one" (slower, fetched only for the businesses actually opened).

Say this

"I'd back this with a search engine's native geo query support rather than a hand-rolled geo-index, because unlike ride-hailing's constantly-moving drivers, business locations barely ever change — the read-heavy, filter-rich access pattern here fits a search engine's inverted index better than a write-optimized in-memory structure."

Final design

One picture: a rarely-written business database feeds a search-engine-backed geo-and-text index through an async pipeline; searches hit a cache keyed by geo-cell and filters in front of that index; "open now" and quality ranking are computed at query time from stored schedules and review-count-weighted scores, not precomputed and stored as flat facts.

EM-level follow-up

Rollout: entering a new market is a supply (business listing) cold-start problem before it is an engineering one — search quality with 500 listed businesses looks broken even with a perfect index. Build vs. buy: many products at smaller scale use a third-party places/business API (Google Places, for example) instead of building and maintaining their own geo-indexed business catalog from scratch, and only bring it in-house once the business-data ownership itself becomes the product. Cross-team impact: the ranking score's trust weighting is usually jointly owned with a trust-and-safety team, since fake-review detection feeding into ranking is a moderation problem wearing a ranking-algorithm hat.

Design Hotel/Airbnb Booking

Problem framing

This is a search-and-reserve system over a calendar: find listings available for a date range at a location, and book one with an absolute guarantee that the same room or listing never gets sold twice for overlapping dates. The search side looks like the Yelp-style problem above; the booking side is a much harder concurrency problem than either of the previous read-heavy problems.

Clarifying questions

  • Fixed room-type inventory (a hotel with, say, 40 identical "deluxe king" rooms) or unique individual listings (an Airbnb host's one specific apartment)? — a hotel can track a count of remaining rooms per type per night; a unique listing has to track a single yes/no availability per night, which changes how the calendar is modeled.
  • Instant booking, or does the host/hotel need to approve each request? — approval-required flows hold inventory in a pending state rather than confirming immediately, which changes when a slot is actually locked.
  • When is payment captured — at booking, or only after host/hotel approval? — affects whether a failed payment can silently leave a phantom hold on inventory.
  • What is the cancellation policy, and how quickly does cancelled inventory need to reappear in search? — a strict policy with slow release costs the host revenue; fast release risks a race with a concurrent search result that hasn't refreshed yet.
  • How fresh does search availability need to be versus the booking write path? — search can tolerate real staleness (a few minutes); the actual booking confirmation cannot tolerate any inconsistency at all.

Requirements

Functional: search listings by location, date range, guest count, and filters; show real-time-enough availability; book a specific listing for a specific date range with zero possibility of double-booking; support cancellation, which releases the inventory back to availability; let hosts manage their own calendar and pricing.

Non-functional: the booking write path needs strong consistency — this is the one place in this chapter where "eventual consistency is fine" does not apply, because a double-booked room is a real, visible failure, not a stale read; the search/browse path can be eventually consistent and heavily cached; the system must handle sharp seasonal and event-driven demand spikes without allowing a race condition to slip through under load.

High-level design

Browsing and search run against a cached, eventually-consistent index. Booking a specific listing for specific dates goes through a separate path with a hard consistency guarantee at the database, plus a short-lived reservation hold while the customer completes checkout.

Deep dive

Preventing double-booking is a database-constraint problem, not an application-logic problem. Two guests can hit "book" for the same listing and overlapping dates within milliseconds of each other. Checking availability and then inserting a booking as two separate steps in application code is a classic check-then-act race condition (see Ch.13) — both requests can pass the check before either commits the insert. The correct fix is to make the database itself reject the second conflicting write atomically: a composite unique constraint on (listing_id, night) with one row per booked night, or, in Postgres, a range-type exclusion constraint directly on the date range, so the second insert fails at the database rather than relying on an application-level check-then-insert.

Search availability needs a precomputed, intersectable structure, not a live scan. Checking "is this listing free for these 5 nights" against a raw per-night row table, for every listing that matches a city and price filter, on every search, does not scale to millions of listings per query. The practical answer is a compact per-listing availability bitmap (for example, one bit per day for the next 365 days) kept in a fast store and updated on every booking or cancellation, so a search can intersect a requested date range against that bitmap in constant time per listing instead of running a range query per listing against a much larger table.

A short-lived reservation hold protects a multi-step checkout without over-locking inventory. Once a guest starts checkout (selecting dates, entering payment), the listing needs to be provisionally held for the few minutes that flow takes, or a second guest could book it out from under the first. A TTL'd hold in a fast store (a few minutes) reserves the slot; it converts into a real, durable booking on successful payment, or expires and releases automatically if the guest abandons checkout. This is the same hold-then-confirm shape as the Ticket-booking-with-seat-level-concurrency problem elsewhere in this chapter, just under much lower contention here — usually one or two people looking at the same listing and dates at once, versus thousands contending for the same 100 seats.

Trade-offs

At 10x scale — for example, a major event driving a demand surge into one city — the bottleneck shifts from booking-write throughput (still trivially low, one row per booking) to search-read throughput and cache-invalidation pressure: every single booking must invalidate that listing's availability bitmap, and if invalidation is too coarse-grained (a whole city's cache cleared instead of one listing's), a burst of bookings triggers a burst of unnecessary cache misses across many unrelated listings. The trade-off is between longer cache lifetimes (cheaper, but risks showing an already-booked listing as available) and short lifetimes (more accurate, but the highest origin load lands exactly during the demand spikes caching exists to absorb).

Say this

"I would not rely on a check-then-insert in application code to prevent double-booking — I'd put a uniqueness or exclusion constraint on listing and date range directly in the database, so the second conflicting booking fails atomically at the storage layer instead of racing against the first in application logic."

Final design

One picture: search runs against a cached listing index intersected with a per-listing availability bitmap for speed; booking runs through a separate, strongly consistent path with a short-lived hold during checkout and a database-level uniqueness guarantee that makes double-booking structurally impossible, not just unlikely.

EM-level follow-up

Rollout: a new market's real bottleneck is inventory (getting hosts or hotels onboarded), not engineering capacity — the booking system scales fine with zero listings; the business does not. Build vs. buy: payment processing and fraud/risk scoring for bookings are almost always bought (a payments platform with built-in fraud tooling) rather than built in-house at launch, since stolen-card fraud in short-term rentals is a well-studied, high-stakes problem better handled by a specialist. Cross-team impact: dynamic pricing for high-demand dates is typically owned by a separate pricing team that reads the same availability signal this system produces, and trust-and-safety owns the fraud-review flow that can block a booking after payment succeeds but before check-in.

Design a Ticket Booking System with Seat-Level Concurrency (Ticketmaster/BookMyShow-style)

Problem framing

Strip away the buzzwords and this is an inventory system where the inventory units are seats, the inventory is tiny compared to demand for the hottest events, and the one rule that can never break is "no two people ever get sold the same seat." The hard part is not storing seat data — a venue with 60,000 seats is a small table. The hard part is thousands of people trying to write to the same few rows within the same few seconds, the moment a popular on-sale opens.

Clarifying questions

  • Is this seat-level (specific seats on a map) or general admission (just a headcount)? — general admission collapses to a simple decrement-a-counter problem; seat-level needs a live seat map and per-seat state, which is a much harder concurrency problem.
  • How long does a selected seat stay held before it releases back to the pool if checkout isn't finished? — this sets the TTL (time-to-live) for holds and directly controls how many "phantom" holds can exist at once during a rush.
  • Do we need a virtual waiting room for flash sales? — if yes, the design needs an admission-control layer in front of booking, not just a fast booking API.
  • Can one person or one bot script grab many seats under different accounts? — this is an anti-scalping requirement (per-account limits, CAPTCHAs, identity checks) that changes the API and the rate-limiting rules, not just the seat-lock logic.
  • When a booking is cancelled or refunded, does the seat go back on sale immediately? — decides whether we need a resale/secondary-inventory flow layered on top of primary booking.

Requirements

Functional: a user browses events and sees a live seat map with each seat's status (available, held, booked); the user selects one or more seats and gets a short-lived hold; the user pays within the hold window to confirm the booking; an expired hold automatically returns its seats to the available pool; a confirmed booking can be cancelled, which refunds and releases the seats.

Non-functional: correctness beats everything else here — zero double-booking, ever, even under an extreme write burst on the same small set of rows; the system must survive a flash-sale spike without falling over, either by absorbing it or by fairly queueing it; under normal load, booking actions should feel instant (well under a second); a crash of any single booking-service instance must never corrupt seat state, because the seat inventory database — not an in-memory lock — is the one source of truth.

Capacity estimate

The average day on this platform is boring — the interesting number is a single hot on-sale. Picture a 60,000-seat stadium show for a top act, where historically demand runs 15-20x supply. Assume 1,000,000 people try to grab a seat within the first 10 minutes (600 seconds) of the on-sale. That is 1,000,000 / 600 ≈ 1,667 seat-grab attempts/sec sustained over that window, with the first 30 seconds running roughly 3x hotter at the instant of opening ≈ 5,000 requests/sec — against a working set of only 60,000 rows. The number of requests that can actually succeed is capped by supply: if all 60,000 seats get held within the first 3 minutes (180 seconds), that is 60,000 / 180 ≈ 333 successful hold writes/sec, all contending for the same small set of rows, which is the real bottleneck, not aggregate throughput. Assume 90% of holds convert to a paid booking inside a 5-minute checkout window: 54,000 confirmations spread over roughly 8 minutes (480 seconds) ≈ 112 payment confirms/sec — far smaller than the hold-acquisition spike. Seat-state storage is trivial: 60,000 rows × ~200 bytes/row ≈ 12MB for this one event. The real capacity risk is the waiting room: to protect the seat database you admit users at a controlled rate even though 5,000/sec are knocking, which means holding order for up to 1,000,000 concurrent people in a queue, each a lightweight ~200-byte session ≈ 200MB of queue state — small in bytes, huge in spike shape.

High-level design

Deep dive

Preventing double-booking under concurrency. The mechanism has two layers on purpose. A Redis lock (a SET with NX and a TTL) acts as a cheap fast-reject filter: it can reject 99% of losing concurrent requests without ever touching the database. But that lock is not the actual source of truth, because an in-memory lock is not durable — if the Redis node holding it fails over or a network split lets two nodes briefly disagree about who holds it, you can end up with two "granted" seats and no arbiter to catch it (see Ch.12 for why a single node cannot give you a linearizable guarantee for free). The real decision happens inside a database transaction, using an optimistic lock (a version column that must match on update) or a unique constraint on (event_id, seat_id) while status is HELD or BOOKED — see Ch.7 for optimistic locking and SELECT ... FOR UPDATE. Never trust a check-then-set in application code alone; the database constraint is the actual backstop.

All-or-nothing multi-seat holds. A group buying 4 seats together must get all 4 or none. This needs either a deterministic lock-acquisition order (sort the seat IDs before locking, so two competing multi-seat holds can never deadlock on each other) or a single database transaction that takes row locks on the entire set at once and rolls back completely on any conflict.

Flash-sale admission control. One event's 60,000 seats getting 5,000 write attempts/sec is a hot partition that no amount of horizontal sharding fixes — you cannot shard a single popular concert across nodes and still avoid contention on the individual seat rows, because the contention is on specific rows, not spread across a key space. The fix sits in front of the database: a waiting room admits people only at the rate the seat-lock layer can actually process (a form of rate limiting from Ch.5, applied per-event instead of per-user), turning an unbounded stampede into a smooth, bounded queue. This is a different shape of problem than the general "hot shard" issue in Ch.6 — there is fundamentally one hot resource here (one popular show), not a skewed key distribution across many resources.

Trade-offs

At 10x scale — the same platform now running a global on-sale across time zones for 10 million concurrent shoppers — the waiting room's own token/queue store becomes the new hot spot. A single Redis instance issuing strictly ordered admission tokens cannot keep 10 million sessions ordered and durable. The fix is to shard the waiting room by event and accept slightly less strict first-come-first-served ordering, trading perfect fairness for horizontal scale.

Say this

"I would use a Redis lock with a TTL as a cheap fast-reject filter, but I would not treat that lock as the actual source of truth — the durable decision happens in the seat inventory database, via a unique constraint or an optimistic version check inside a transaction, because losing a seat lock to a Redis failover is a correctness bug, not just a performance hiccup."

Final design

A waiting room throttles the flash-sale stampede down to an admittable rate. The booking service takes a cheap Redis lock as a fast-reject, then commits the real decision in a relational database using a per-seat unique constraint or optimistic lock. Confirmed holds get a short TTL and are handed to payment. Any timeout or failure releases the seat automatically through a reaper process listening for lock expiry, keeping inventory consistent even when a client's browser tab simply disappears mid-checkout.

EM-level follow-up

The waiting-room / fair-queueing layer is a strong build-vs-buy candidate: it is only exercised a handful of times a year, for the very hottest on-sales, so a bespoke fair-queueing system sits idle 360 days a year — most companies buy this rather than build it. Also flag the cross-team dependency early: an anti-scalping/fraud team will need hooks into the hold API (device fingerprinting, per-account purchase limits), which is a shared contract the booking team cannot own alone.

Design a Grocery Delivery Platform with Batching and Substitutions (Instacart-style)

Problem framing

This is not "order food, get it delivered." A grocery order is a multi-item shopping list that a real person has to physically pick from a store, and a meaningful slice of items will be out of stock the moment that person reaches the shelf. On top of that, one shopper often carries several customers' orders in the same store trip to make the economics work. The hard part is coordinating a live, in-aisle human decision loop and a shared physical trip across multiple customers' orders — not the delivery routing itself, which is covered by the Google-Maps-style ETA and routing problem elsewhere in this chapter.

Clarifying questions

  • Is inventory tracked live per store, or is it "probably in stock" until a shopper checks? — live feeds mean integrating with each retailer's stock system; without them, substitution-handling becomes the primary mechanism for dealing with unreliable stock data, not a fallback.
  • Can one shopper batch multiple customers' orders into a single store trip? — this changes the unit of assignment from "one order" to "a batch," and requires an in-store pick list that interleaves items from different orders by aisle, not by order.
  • What's the substitution policy when an item is missing — auto-substitute, ask the customer live, or skip and refund? — this is the single biggest UX and trust decision in the design.
  • Is pricing for weight-based items (produce, deli) fixed at order time or set at pickup? — decides whether the final charge must be captured after picking, not at checkout.
  • What's the delivery SLA — a multi-hour same-day window, or under 60 minutes on demand? — a longer window lets batching optimize for cost; a tight window optimizes for speed with fewer orders per batch.

Requirements

Functional: a customer builds a cart from a store's catalog and checks out to an estimated total; the system assigns a shopper (alone or as part of a batch) to fulfill it; the shopper marks each item as found, substituted, or unavailable in real time, visible live to the customer; the customer can approve or reject a substitution live, or a stored default rule decides automatically after a short timeout; the shopper checks out at the store and starts delivery; the final charge reflects what was actually picked and weighed, not the estimate.

Non-functional: substitution decisions need low latency, because a shopper standing in an aisle cannot wait more than a few seconds, so a sane default must exist on both sides of that race; inventory estimates can be eventually consistent, since they were already approximate; the money path (final charge) must be strongly correct — never overcharge, and reconcile promptly if undercharged; the system must handle high fan-out of live updates, since one shopper's action can update several customers' screens at once when batched; the platform must absorb regional demand spikes, like a holiday weekend.

Capacity estimate

Assume 5,000,000 orders/day, spread over roughly 12 active hours (43,200 seconds), giving an average of 5,000,000 / 43,200 ≈ 116 orders/sec, with dinner/weekend peaks running about 4x average ≈ 460 orders/sec. Each order has on average 30 line items, so 5,000,000 × 30 = 150,000,000 item-pick events/day. Each pick event (found/substituted/unavailable plus optional photo metadata) is a small write, say 500 bytes → 150,000,000 × 500B = 75GB/day, or roughly 27TB/year before archival. Assume an 8% out-of-stock rate at pick time (a reasonable range for grocery): 150,000,000 × 8% = 12,000,000 substitution decisions/day, each needing a live customer round-trip within a short window; if 15% of that falls inside the single busiest hour, that is 12,000,000 × 15% / 3,600s ≈ 500 substitution events/sec needing live delivery to a device at peak. Batching: at an average 2.4 orders per shopper trip, 5,000,000 / 2.4 ≈ 2,080,000 shopper trips/day. Live shopper location pings every 10 seconds over an average 45-minute (2,700-second) trip give 2,080,000 × 270 ≈ 560,000,000 pings/day; spread over the same 12-hour active window, that is 560,000,000 / 43,200 ≈ 13,000 pings/sec on average during active hours.

High-level design

Deep dive

Substitution as a real-time, low-latency decision loop. The shopper is physically standing in the aisle and cannot wait on a slow round trip. The design pushes a substitution prompt to the customer over the live channel with a short timeout, around 25-30 seconds; if there's no response, a pre-configured default rule on the customer's profile applies (for example, "accept a similar-brand substitute" or "skip and refund"). The correct answer for a missing item is genuinely a race between a human reading a phone notification and a shopper standing in an aisle, and the system needs a sane default on both sides of that race — it must never block the shopper's progress waiting indefinitely on a customer.

Batching changes the shape of the read path, not just the write path. When one shopper's trip covers three different customers' orders, an item-pick event still belongs to exactly one order (the write is narrow), but the shopper's screen must show one merged, aisle-optimized pick list spanning all three orders at once (the read is a batch-level aggregate). That mismatch is a classic case for a read-optimized view assembled by the batching service, rather than joining across order records on every screen refresh.

Correcting the price after the fact. Checkout can only show an estimate, because weight-based items and any substitutions are unknown until picking finishes. Checkout should authorize a hold with headroom (say 10-15% above the estimate) rather than capturing payment outright, and capture the real amount once the trip is done — see the payments concept chapter (Ch.21 in this series) for authorize-vs-capture mechanics — with a background reconciliation job to handle the rare case where the actual total exceeds the authorized hold.

Trade-offs

At 10x order volume, the live pub/sub fan-out is what breaks first — pushing every single pick event as its own message is fine at 500 substitution-events/sec but gets very chatty at 5,000/sec. The fix is to debounce updates client-side, say pushing a diff every couple of seconds instead of on every single item, trading a little live-feel responsiveness for a much smaller message volume.

Say this

"I'd default to a short synchronous substitution window, maybe 25-30 seconds, before falling back to the customer's stored default rule, because blocking the shopper indefinitely wastes their paid time in the store, but silently substituting every item with zero customer input erodes trust — the timeout is a deliberate compromise between shopper efficiency and customer control."

Final design

Checkout creates an order and authorizes an estimated charge. A batching service groups nearby orders into one shopper trip and hands over a merged pick list. Each item pick is written against its own order and published over a live channel so the right customer sees real-time progress, with substitutions resolved by a timed prompt that falls back to a stored default. Once the trip is done, the order service reconciles actual weights and substitutions into a final charge and hands off to delivery.

EM-level follow-up

Delivery routing and ETA should reuse the routing service built for the Google-Maps-style ETA problem elsewhere in this chapter rather than being reinvented here — that's a build-vs-reuse call inside the same company, not a new build. Cross-team angle: substitution default rules and out-of-stock rates are as much a product/merchandising decision as an engineering one, so rolling out a change to default substitution behavior needs a staged rollout, since it directly affects customer trust and basket size, not just system correctness.

Design a Parking-Spot Finder and Reservation System

Problem framing

Two different problems glued together: a real-time "where's a free spot near me" search over availability that changes every time a car arrives or leaves, and a reservation system that has to hold a specific physical spot for someone who hasn't arrived yet — similar in spirit to seat booking, but with the twist that "availability" can also come from live sensors or cameras, not only from your own booking transactions.

Clarifying questions

  • Are spots sensor-monitored (ground sensors, cameras) or purely reservation-driven, where "free" only means "nobody booked it"? — decides whether this is a real-time state-ingestion problem or a pure booking-availability problem.
  • Can a driver reserve a spot ahead of time, or is it find-and-park only? — decides whether we need a hold-with-TTL mechanism at all, or just a live availability map.
  • Are these on-street municipal spots or off-street lots/garages? — a garage may only know "42 of 200 free," not which exact spot, which changes the granularity of the whole design.
  • What's the grace period between reserving and forfeiting a spot for a no-show? — sets the hold TTL, the same shape of decision as the ticket-booking hold window earlier in this chapter.
  • Do we need dynamic, demand-based pricing? — decides if pricing is a static rate table or a real-time model fed by live occupancy.

Requirements

Functional: a driver searches for available spots near a location, filterable by price, covered, or EV-charging; a driver can reserve a specific spot for a future arrival window, which the system holds; the driver checks in on arrival (geofence, QR code, or gate) to confirm occupancy; a no-show reservation auto-releases after a grace period; the driver checks out and is charged for actual duration.

Non-functional: search results must reflect availability that is at most a few seconds to a couple of minutes stale — in dense areas a 10-minute-stale answer is nearly useless; reservation correctness matters, though a rare double-booking here is milder than in ticket booking (someone just can't park, not a cancelled event), so the design can lean a little more toward availability than the ticket-booking problem's zero-tolerance bar; search is read-heavy and must scale with dense urban query volume; the system must degrade gracefully to lot-level (not exact-spot) availability wherever there's no sensor coverage.

Capacity estimate

Assume the platform covers 50 major cities at an average of 4,000 monitored or reservable spots per city → 200,000 total spots. High-level design

Deep dive

Freshness vs. correctness split across two stores. This problem needs two different consistency bars in the same system. The "is this spot free" answer for search must be fast and can be a few seconds stale, served from a geospatial cache such as Redis's geo commands or a geohash-bucketed index. The "did I actually just win this exact spot" answer at reservation time must go through the durable spot inventory database with the same optimistic-locking discipline as seat booking earlier in this chapter. Search is read-optimized and slightly stale by design; reservation is write-optimized and must be exactly right.

Reconciling sensor truth with reservation truth. A spot can legitimately be "reserved by no one, but a car is sitting in it" (common for on-street municipal parking with no enforcement) or "reserved, but the sensor still shows occupied because the previous driver hasn't left yet." The system has two independent signals — the reservation state machine and the physical sensor state — and they can disagree. The practical fix is to treat sensor state as the signal that drives what shows as searchable, but treat the reservation record as the authority for who is allowed to occupy a spot once reserved, with a short grace-period buffer around the reservation start so an early "occupied" sensor reading right before a reservation begins doesn't wrongly cancel it.

No-show handling and grace periods. Unlike a missed concert-seat hold, which just returns the seat to a large pool of other buyers, a missed parking reservation means a spot sat empty that nobody else could book because it was held. The system needs an aggressive but fair release policy: charge a partial no-show fee if the driver never checks in by the end of the arrival window, and release the spot back into search results immediately at that boundary — the same hold-with-TTL pattern as a ticket checkout window, just with money attached to the miss instead of only losing a place in line.

Trade-offs

At 10x scale — many more cities with dense sensor coverage — the sensor ingestion pipeline is what breaks first. Going from ~5.5 events/sec average to a much higher rate with tighter freshness needs turns "update a cache on each event" into a proper streaming problem, which means moving from ad hoc HTTP ingestion to a real event stream (Kafka, see Ch.14) with the availability cache as a continuously-updated materialized view instead of a pile of individual writes.

Say this

"I'd deliberately let search results be a few seconds stale, served out of a geospatial cache, because in dense parking search the bigger UX risk is showing nothing or being slow, not showing a spot that gets taken a few seconds before you click it. The reservation step itself is where I enforce strict, transactional correctness, not the search step."

Final design

Search hits a geospatial availability cache that's kept fresh by both reservation events and sensor/camera feeds. Reserving a spot is a transactional write against the durable spot inventory database, using the same optimistic-lock discipline as any scarce-inventory booking problem. Check-in and checkout drive the billing clock and reconcile sensor-observed occupancy against the reservation record. No-shows auto-release on a grace-period timer with a partial fee.

EM-level follow-up

Sensor hardware deployment is a slow, city-by-city physical rollout, not a software deploy, so the rollout plan should prioritize the highest-search-volume cities for sensor investment first, rather than a uniform rollout, and the design must degrade gracefully to lot-level availability everywhere else. Build-vs-buy angle: municipal parking data and gate/payment integrations often mean partnering with existing city parking-meter vendors rather than replacing them, which is as much a partnerships problem as an engineering one.

Design a Car Rental Marketplace

Problem framing

This is a two-sided, calendar-based booking system — closer to hotel booking than to seat booking, because the "unit" being reserved is a date range, not a point-in-time slot. On top of that, the "room" here is a specific physical vehicle that has to actually be at a specific location at handover time, and there's a pricing engine that varies by date range, location, and vehicle class. The wrinkle unique to cars: the vehicle itself has to end up back in the right place for the next renter, which is a small logistics problem hiding inside a booking problem.

Clarifying questions

  • Single-fleet operator, or a peer-to-peer marketplace where individual owners list their own cars? — changes trust/verification and payout needs, and whether "fleet" means one company's assets or thousands of independent owners' assets.
  • Can a renter pick up at one location and drop off at another? — one-way rentals mean the vehicle must be repositioned before its next booking, an extra availability constraint beyond simple date-range blocking.
  • Is pricing static per vehicle class, or dynamic and demand-based? — decides whether we need a pricing engine that reacts to local demand and supply, or just a rate card.
  • What happens on a late return? — decides whether the next booking for that vehicle needs a buffer window, and how a collision with the next renter's pickup gets resolved.
  • Do we need damage/incident documentation, like photos at pickup and return? — affects whether the booking record needs media attachments and a dispute workflow.

Requirements

Functional: a renter searches vehicles by location, date range, and class; a renter books a specific vehicle for a date range, which blocks that vehicle's calendar for that range; the owner/fleet approves automatically or manually; pickup and return are recorded with odometer and photos; a renter can modify or cancel within a cancellation-policy window; a renter can extend a booking, which re-checks the next booking's start date.

Non-functional: booking a specific vehicle for a date range must never allow two overlapping bookings on the same vehicle — the same double-booking bar as seat or spot booking, except the conflict check itself is a range-overlap check, not an equality check; search must return results that are actually available for the requested window, not just "exists somewhere"; browsing must stay highly available even if the booking-write path is briefly degraded, because browse volume dwarfs booking volume; the price shown at search time and the price charged at booking confirmation must match closely, with a final re-confirm step absorbing any small drift.

Capacity estimate

Assume 500,000 active listed vehicles, each booking on average 12 times/month → 500,000 × 12 = 6,000,000 bookings/month ≈ 200,000 bookings/day. Travel-style marketplaces typically see browse-to-book ratios somewhere around 50:1 to 100:1; assume 75:1, giving 200,000 × 75 = 15,000,000 searches/day. Spread over 14 active hours (50,400 seconds), 15,000,000 / 50,400 ≈ 300 searches/sec average, roughly 900/sec at a 3x evening peak. Each search is a date-range availability check against a vehicle's calendar plus a location filter — the expensive part is the range-overlap check across many candidate vehicles, not raw request volume. Booking writes: 200,000/day over a 10-hour active booking window (36,000 seconds) ≈ 5.5/sec average — trivial throughput, since unlike a concert on-sale, demand for one specific car rarely spikes into contention with thousands of others for the exact same vehicle at the exact same time. Storage is dominated by media, not metadata: assume 6 photos/booking at ~2MB each = 12MB of media per booking × 6,000,000 bookings/month ≈ 72TB/month, which pushes media to object storage (for example S3) with only a reference URL in the booking record — never stored inline. Booking metadata itself, at roughly 2KB/booking × 6,000,000/ month ≈ 12GB/month, is trivial by comparison.

High-level design

Deep dive

Range-overlap checking is a different shape of concurrency problem than seat booking. Seat booking is "is this exact seat_id currently free," a point check with an equality condition. Car rental booking is "does [startDate, endDate) overlap any existing confirmed booking for this vehicle," a range check. You cannot enforce that with a plain unique constraint the way you can pin a seat_id; you need either a database-level exclusion constraint (Postgres supports range-overlap exclusion constraints natively via GiST indexes) or an application-level transaction that locks the vehicle's calendar row and re-validates no overlap exists immediately before insert, inside the same transaction, to close the race where two renters both pass an initial "looks free" check for overlapping ranges within the same instant.

Search freshness vs. booking correctness, the same split as the parking problem. Search results can be served from an availability cache that's a little stale — a vehicle showing available that gets booked 5 seconds later just means the second renter's booking attempt fails and they see refreshed results, an acceptable UX cost. The booking write itself must go through the authoritative calendar database with the range-overlap guarantee above. It's the same two-tier consistency split as the parking-spot problem, just with a date range instead of a point-in-time spot state.

One-way rentals and repositioning. When pickup and drop-off locations differ, a vehicle's "availability" at a location isn't just "is this date range free" — it's "will this vehicle physically be at this location by this date," which depends on where its prior booking ends. That turns availability search into a small logistics problem: either the marketplace only shows one-way options where the vehicle's prior drop-off already matches the new pickup, or a fleet operator has to actively reposition vehicles between locations, which is a real operational cost that one-way pricing should reflect, not something to treat as free.

Trade-offs

At 10x scale, what breaks first is exactly the calendar-overlap transaction under contention for a small number of extremely popular vehicles or classes in dense cities — for example, the cheapest economy car at a busy airport for a popular weekend. Many renters race to book the same handful of attractive listings for the same dates, turning what looks like a low-throughput problem in aggregate into a hot-row problem for a small slice of vehicles — the same shape of issue as the ticket-booking flash sale, just at a smaller scale.

Say this

"For the conflict check itself I'd lean on the database's own range-overlap exclusion constraint rather than hand-rolling a check-then-insert in application code, because a constraint enforced by the database is the guarantee that holds even if two application servers race each other — the app-level check is a nice-to-have for a fast, friendly error message, not the actual safety net."

Final design

Search reads from an availability cache seeded by the vehicle calendar, for fast and slightly-stale browsing, with a live price quote from the pricing engine. Booking is a transactional write against the calendar database, protected by a range-overlap exclusion constraint, so overlapping date ranges for the same vehicle can never both commit. Pickup and return capture odometer and photos to object storage and drive payment capture and the next availability update. One-way rentals are only offered where the vehicle's location will actually match, or are backed by an explicit repositioning cost.

EM-level follow-up

For a peer-to-peer, Turo-style variant, trust and payout become a build-vs-buy question fast: identity verification and payout are usually bought from a specialized provider rather than built in-house, and the damage-dispute workflow (photos, claims) typically needs a dedicated ops/trust-and-safety team in the loop — which means the booking system's job is to capture clean, timestamped evidence at handover, not to adjudicate disputes itself.

Design a Freelance Marketplace with Matching and Escrow (Upwork-style)

Problem framing

Two problems bolted together: a search and matching problem (helping a client find the right freelancer, or a freelancer find the right job, out of a huge catalog of people and postings), and a trust problem (a client and a freelancer who've never met need to safely exchange money for work, over what might be weeks, without either side walking away with both the money and the work).

Clarifying questions

  • Fixed-price, hourly, or both? — this changes the escrow model entirely: fixed-price naturally maps to milestone-based holds, while hourly needs a running time-tracking and periodic-billing model instead of one lump held amount.
  • Who initiates matching — does the client post and freelancers apply, does the platform actively recommend, or both? — decides how much of this is a search problem versus a recommendation/ranking problem.
  • When does money move into escrow — at contract acceptance, or per milestone as it's created? — changes what "the client has committed funds" actually means, and when a freelancer can start work with confidence they'll get paid.
  • What triggers a release from escrow — freelancer marks complete, client approves, or a time-based auto-release if the client goes silent? — this is the trickiest dispute-avoidance mechanism in the whole system.
  • Do we need human-in-the-loop dispute arbitration? — decides if escrow release is a fully automated state machine or one with a manual-hold/appeal branch.

Requirements

Functional: a freelancer builds a profile with skills and a portfolio; a client posts a job with a budget and required skills; the system surfaces relevant freelancers to the client (or relevant jobs to the freelancer) using skill, budget, and rating matching; client and freelancer agree on a contract (fixed-price with milestones, or hourly with a cap); the client funds escrow for the agreed amount, in full or per milestone; the freelancer delivers work and marks a milestone complete; the client approves, releasing escrow minus a platform fee, or disputes it; a dispute pauses automatic release and routes to review.

Non-functional: money movement (fund, release, refund) must be strongly consistent and fully auditable — this is a ledger problem, not one where eventual consistency is fine, unlike search and matching which can tolerate staleness; matching needs to be fast (sub-second) but its ranking can be approximate and improved offline; the system must never let both parties end up empty-handed, or let one party unilaterally take both the money and the work product; contracts can run for weeks to months with partial payments over time, not just one-shot transactions.

Capacity estimate

Assume 2,000,000 active freelancer profiles and 300,000 new job postings/day. Assume each posting drives roughly 100 units of matching-related activity (recommendation computation plus freelancer browsing and applications combined) → 300,000 × 100 = 30,000,000 matching queries/day; over 16 active hours (57,600 seconds), that's 30,000,000 / 57,600 ≈ 521 queries/sec average, roughly 1,500/sec at peak — a read-heavy ranking problem, similar in shape to the general search concept chapter (Ch.11) but ranked by skill match and reputation instead of text relevance alone. Assume 5% of postings convert to a signed contract → 15,000 new contracts/day, each with an average 4 milestones or billing cycles → 60,000 escrow fund-or-release events/day, roughly 0.7/sec average — tiny in raw throughput, but this is the highest-integrity data path in the system, sized for correctness and auditability, not QPS. Each escrow event writes a handful of immutable ledger entries (hold, capture, fee split, payout) — say 5 entries/event at ~500 bytes each → 60,000 × 5 × 500B = 150MB/day of ledger data, trivial in size, never allowed to be lossy or out of order. For hourly contracts, assume 500,000 active ones logging time in 10-minute snapshots across an 8-hour workday (48 snapshots/day) → 500,000 × 48 = 24,000,000 time-tracking events/day; over an 8-hour window (28,800 seconds), that's ≈ 830 events/sec during work hours — much higher volume but lower stakes per event than escrow, since it only feeds a weekly billing calculation rather than moving money instantly.

High-level design

Deep dive

Escrow as an append-only ledger, not a mutable balance. The single most important decision in this problem: never store "freelancer's pending balance" as a number you increment or decrement in place. Every fund, hold, release, refund, and fee-split is its own immutable, timestamped ledger entry, and any balance shown to a user is a computed sum over entries, not a stored field. This is the same double-entry-bookkeeping discipline real payment systems use, and it's what makes disputes and audits possible after the fact — you can always answer "why does this contract show $400 released" by replaying its entries, which you cannot do if you only kept a running total. See the payments concept chapter (Ch.21 in this series) for authorize/capture and ledger patterns in more depth; this problem's twist is that the "capture" event can be delayed by weeks and gated on a human approval, not an automatic post-purchase trigger.

The auto-release timer as the main dispute-avoidance mechanism. If a client goes silent after a freelancer submits a milestone, the system cannot hold funds in limbo forever, since that punishes the freelancer for the client's inaction — but it also cannot auto-release instantly, since that removes the client's real review window. The standard answer is a fixed auto-release timer, commonly around 10-14 days in real freelance platforms, that fires automatically unless the client explicitly disputes within the window. This converts an open-ended "wait for a human" problem into a bounded state machine with a clear default outcome — the same shape of decision as the seat-booking hold TTL and the grocery substitution-default timeout earlier in this chapter, just with a much longer window because the stakes and the expected human-response latency are both higher.

Matching quality and escrow correctness need genuinely different engineering rigor. The search and recommendation half can be wrong sometimes — a mediocre freelancer ranked too high just means a slightly worse first impression — and can be improved iteratively with offline ranking models, A/B tests, and approximate nearest-neighbor search over skill embeddings. The escrow half cannot be "mostly correct," because being wrong means real money misallocated to the wrong party. In an interview, showing that you know which half of your own design needs which kind of rigor is a strong signal — don't over-invest transactional guarantees into the search path, and don't let the money path lean on eventual consistency.

Trade-offs

At 10x scale, the search and matching index is what needs the most re-architecting — sharding profiles and postings, moving from a single search cluster to a properly partitioned one (see Ch.6 and Ch.11). The escrow ledger, if designed as append-only from day one, mostly just needs more capacity, not a redesign. The trade-off this exposes early: an insert-heavy, append-only ledger scales far more gracefully than people expect, which is itself an argument for paying that design cost upfront rather than "optimizing" it into a mutable balance table for short-term simplicity.

Say this

"I would model escrow as an append-only ledger from day one, even though a single mutable balance column would be far less code to write initially, because the cost of getting money movement subtly wrong and not being able to reconstruct why is much higher than the extra effort of designing an event-sourced ledger up front."

Final design

A client posts a job, and the matching service ranks freelancers by skill, budget, and reputation out of a search index that can be approximate and improved over time. An accepted contract funds escrow per milestone through an escrow service that talks to a real payment provider and records every state change as an immutable ledger entry. Milestone completion triggers either an explicit client approval or a bounded auto-release timer, with a dispute path that pauses automatic release and hands the case to human review. Nothing about the money path is ever inferred from a cached or approximate value.

EM-level follow-up

Build-vs-buy shows up hardest here: most companies do not build their own payment rails or KYC/anti-money-laundering compliance for holding client funds in escrow. They build the contract, milestone, and ledger logic in-house but delegate actual money custody and movement to a licensed payment or marketplace-payments provider, because holding other people's money is a regulated activity, not just an engineering problem. The EM-level answer explicitly separates "what we own" (matching, contract state machine, ledger of intent) from "what we must buy" (regulated money movement), and flags compliance and legal review as a hard dependency on the project timeline, not an afterthought.

Design a Dating App Matching System (Tinder-style)

Problem framing

Strip away the branding and this is a two-sided discovery feed with a strict gate on the back end: show each user a stream of nearby candidate profiles that fit their stated preferences, let them swipe yes or no, and only open a chat when both people have said yes to each other. The hard engineering problems are not the swipe UI — they are picking a good next candidate cheaply at huge scale, and detecting a mutual "yes" correctly and exactly once, even when both swipes land on different servers within milliseconds of each other.

Clarifying questions

  • Is discovery a pure filtered/proximity feed, or does it need a ranking model that scores how desirable two people are to each other? — a pure filter is a geo-and-preference query; a ranking model needs an offline machine-learning pipeline feeding an online scoring layer, which is a much bigger system to build and operate.
  • What is the discovery radius, and does it change by location density? — a fixed 50 km radius wastes queries in a dense city and starves candidates in a rural area, so most real systems expand the radius dynamically until enough candidates are found.
  • Do we need in-app chat after a match, or does the match just unlock an external channel? — this decides whether messaging infrastructure (see the WhatsApp/Messenger-style problem elsewhere in this series) is in scope here or a separate system.
  • What is our policy on re-showing a profile the user already passed on? — "never show again" versus "may resurface after 90 days" changes how big the per-user exclusion set has to be and how long you keep it.
  • Do we need photo/identity verification and abuse moderation at signup? — this adds a trust-and-safety pipeline that gates whether a profile is even eligible to appear in anyone's deck.

Requirements

Functional: a user sets preferences (age range, distance, gender) and pulls a deck of candidate profiles that match those preferences and have not already been swiped on; a user swipes like/pass/superlike on a profile; when two users have both liked each other, the system creates a match and notifies both sides in near real time; matched users can open a chat thread.

Non-functional: fetching the next batch of candidates should feel instant, well under 200 ms; match detection must be strict and exactly-once — no missed matches, and no double-firing the "it's a match" notification; candidate generation itself can tolerate a few seconds of staleness (eventual consistency is fine there); the system must scale to tens of millions of daily active users worldwide, and location data is sensitive enough that it should never be exposed as an exact coordinate to another user, only as an approximate distance.

Capacity estimate

Assume 75 million daily active users, averaging 100 swipes/day each during a session — that is 7.5 billion swipes/day, or roughly 87,000 swipes/sec on average. Usage concentrates in a few evening hours, so assume a 3x peak factor, giving roughly 260,000 swipe writes/sec at peak. Each swipe record is small — a swiper ID, a target ID, an action, and a timestamp packs into well under 100 bytes — so the write-path bandwidth itself, around 25 MB/sec at peak, is trivial; the real cost is that every single one of those 260,000 writes/sec has to be checked against the opposite-direction swipe to see if a match just happened. Total registered users might be 300 million, each with a profile record around 2 KB (bio, preferences, metadata) — about 600 GB of profile text, easily fit for a normal database. Photos dominate storage: assume 6 photos/user at roughly 500 KB each, so 3 MB/user times 300 million users is about 900 TB of images, which belongs in blob storage behind a CDN, not in the profile database itself.

High-level design

Deep dive

Candidate generation without live per-card queries. Querying the geo index fresh for every single card would be wasteful at 87,000 swipes/sec, since most swipes just advance to the next card in an already-computed pool. The common design pre-computes a batch of candidates per user (a "deck") using the geohash grid from Ch.16, refreshes it periodically rather than on every card, and filters out anyone already swiped using a per-user exclusion set — a Bloom filter is a good fit here because it is compact and a false positive only costs you one candidate that should have appeared but did not, which is a far cheaper mistake than showing someone a profile they already passed on.

Mutual match detection has to be race-free. Two swipes that make a mutual match can arrive on two different servers within milliseconds of each other — user A likes user B on one server while user B happens to like user A on another. If both servers independently check "did the other person already like me" and both see "no" before either writes, you get either a missed match or, worse, two separate match-created events firing. The fix is to make the check-and-create step atomic on a single, deterministic owner: derive a canonical pair key (say, the two user IDs sorted and concatenated) so that both swipes always hash to the same partition, then use a single conditional write there — a lightweight transaction or a Redis-backed compare-and-set — to guarantee the match is created exactly once no matter which swipe arrives first.

Ranking, if the product needs it. A pure proximity-and-preference filter is enough for many products, but Tinder's original desirability-scoring approach (an Elo-like rating derived from who likes whom) is a different kind of system: an offline pipeline that recomputes scores from the swipe history, and a fast online layer that blends that score with proximity and recency when building the deck. This is worth mentioning explicitly as a build-later feature, not a day-one requirement, since it adds a whole ML pipeline on top of the discovery path.

Trade-offs

At 10x scale, the per-user exclusion set is the first thing that breaks, not the swipe-write path. A power user who has swiped on tens of thousands of profiles needs an exclusion check on every single deck refresh, and a naive "store every swiped ID forever, check with a database lookup" design turns that into a slow, ever-growing query. Bloom filters cap the memory cost and keep the check fast, at the price of an occasional false positive that silently drops a candidate who should have been shown — an acceptable trade for discovery, which is exactly why it would be unacceptable for match detection, where a false result of any kind is a real bug.

Say this

"I would deliberately run two different consistency models in the same product. Candidate generation can be a few seconds stale — it is fine if a deck briefly includes someone who just became unavailable. Match detection cannot be stale at all, because a missed match or a duplicate match notification is a broken product experience, so I route both sides of a swipe pair to the same partition and use an atomic conditional write specifically for that one step."

Final design

If you had to draw one picture: a discovery service reads a geohash-indexed candidate pool and hydrates it from a sharded profile store, refreshed periodically rather than per-swipe; a swipe service appends every swipe to a write-optimized store and, on every "like," routes a mutual-check to a single deterministic owner per user pair, which atomically creates the match and fires exactly one notification; photos live entirely in blob storage behind a CDN, off the hot request path in both directions.

EM-level follow-up

Build vs. buy: the geo index, message queue, and blob storage pieces are all standard infrastructure worth buying (managed Redis, managed object storage); the desirability-ranking model, if the product needs one, is exactly the kind of thing worth building in-house, because it is the actual competitive differentiator. On rollout: launching in a new country is not just a deploy — it needs local trust-and-safety review (age verification norms, harassment-reporting requirements differ by jurisdiction), which makes it a cross-team dependency on legal and policy, not a pure infrastructure question.

Design a Used-Goods Marketplace (Craigslist/OLX-style)

Problem framing

This is a local classifieds board: sellers post a listing with photos, a description, a price, and a location; buyers browse and search within a city or region; and the two sides talk to each other in-app to agree on a deal that usually completes off-platform (a cash handoff, unlike the escrow-based marketplaces elsewhere in this series). The engineering weight sits almost entirely on the read side — search and browse at huge scale — and on data quality: most listings die within days of being posted, and stale "still available" listings are the single biggest source of user distrust in this kind of product.

Clarifying questions

  • Is payment or escrow handled on-platform, or is the deal completed off-platform? — off-platform (the Craigslist/OLX norm) means no payments system is in scope at all, which is the biggest single difference from the escrow-based marketplaces elsewhere in this chapter.
  • Do different categories need different structured attributes? — a car listing needs mileage and year, a couch listing needs neither; this decides whether the listing schema needs to be flexible per category rather than one fixed table.
  • Do we need in-app chat between buyer and seller? — this adds a lightweight messaging component, distinct from the full real-time chat system covered elsewhere in this series.
  • How aggressively do we need to moderate for scams and prohibited items? — this decides whether moderation runs before a listing goes live (slower, safer) or after (instant post, async takedown).
  • Is search always scoped to a metro area, or do we need cross-region search (e.g. moving to a new city)? — this decides whether the search index can be partitioned by region from the start.

Requirements

Functional: a seller can post, edit, and delete a listing with photos, category, price, and location; a buyer can browse by category and location and free-text search with filters (price range, condition); a buyer can message a seller in-app; listings auto-expire after a configurable window; users can flag a listing as a scam or prohibited item.

Non-functional: search should return results in well under 300 ms; the system is overwhelmingly read-heavy — most users browse far more than they post — so it must handle a huge read:write ratio efficiently; a new listing should be searchable within seconds of posting, since sellers expect instant visibility; eventual consistency for search results is fine, since this is not financial data; and photo uploads must be resilient to bursty traffic (a garage-sale weekend spike).

Capacity estimate

Assume 50 million monthly active users, 5 million new listings/day, and roughly 5 photos/listing at about 300 KB each. That is 5,000,000 x 5 x 300 KB, or about 7.5 TB/day of new photo uploads before any compression, and with an average listing lifetime of roughly 30 days before expiry, the rolling active photo set sits around 7.5 TB x 30, or about 225 TB — call it a few hundred TB once you account for uneven retention, which is comfortably a CDN-and-blob-storage problem, not a database problem. Search load dominates the read path: assume 5 searches/session and 2 sessions/day per user, giving 50,000,000 x 5 x 2 = 500 million searches/day, or roughly 5,800 searches/sec on average, with a 3x evening peak giving about 17,400 searches/sec. Active listings at any moment, given 5 million new listings/day and a roughly 30-day average lifetime, land around 150 million — each a small (roughly 2 KB) metadata record, so total listing metadata is only about 300 GB, trivial next to the photo storage number.

High-level design

Deep dive

Geo, text, and category search combined, with near-real-time freshness. Elasticsearch's geo-distance query combined with category and price filters handles the query shape fine (see Ch.11 §02 for how Elasticsearch shards and merges results), but the harder design decision is the pipeline that keeps the index fresh. Sellers expect their new listing to show up in search within seconds, so the listing database should not be the search system's only source of truth on a delay — a change-data-capture stream off the primary listing store into the index is the standard fix, avoiding both a slow batch reindex and a risky dual-write from the application code itself.

Listing lifecycle and staleness. Most listings do not get explicitly deleted when the item sells — the seller simply stops paying attention. A stale "for sale" listing that a buyer messages about, only to find out it sold three days ago, is the single biggest trust problem in this category of product. The practical fix combines three signals: a hard auto-expiry after N days, an explicit "mark as sold" action, and a heuristic auto-hide for listings with no seller activity (no responses, no logins) for an extended period — none of these alone is reliable, but together they keep the active index honest.

Moderation cannot block the happy path. Posting a listing needs to feel instant, but scam and prohibited-item detection is not instant — it runs a mix of rule-based checks and an ML classifier, sometimes escalating to a human reviewer. The standard design lets the listing go live immediately as "provisional," while an async pipeline reviews it in the background and can pull it down within minutes if it is bad; blocking every post on synchronous review would make normal, honest sellers wait for a system that mostly exists to catch a small minority of bad actors.

Trade-offs

At 10x scale (500 million MAU), a single global Elasticsearch cluster is the first thing to break, and not because of raw query volume — because this product's queries are almost always scoped to one metro area, so a global index wastes effort routing every query through shards that hold data for cities the user will never search. The fix is to partition search indices by geographic region, so a query only ever touches shards relevant to that region — a sharding decision driven by query pattern rather than data volume, the same underlying idea as Ch.6's sharding chapter, just applied to a search index instead of a relational table.

Say this

"Search freshness here can be eventually consistent — a few seconds of lag between posting and searchability is completely acceptable, because this is not financial data. That is exactly why I would use CDC into Elasticsearch instead of a synchronous dual-write: it decouples the write path's latency from the indexing pipeline's latency, and a slow reindex never blocks a seller from posting."

Final design

If you had to draw one picture: a listing service writes to a regionally-sharded primary store; a change stream off that store feeds both a geo-partitioned Elasticsearch cluster for search and an async moderation pipeline; photos go straight to blob storage behind a CDN; and listing freshness is maintained by a combination of auto-expiry, explicit mark-as-sold, and activity-based auto-hide, rather than any single mechanism.

EM-level follow-up

Build vs. buy: a managed search service (Algolia, or a managed Elasticsearch offering) is usually the right call over running your own search cluster from day one, because search relevance tuning and cluster operations are both deep, ongoing investments that only pay off once search quality is a real competitive lever. On rollout: expanding into a new city is mostly a data problem, not a code problem — moderation policy, prohibited-item lists, and even acceptable categories can vary by region, which makes market expansion a cross-team dependency on trust-and-safety and legal, not just a new search-index partition.

Design a Fleet/Last-Mile Logistics Tracking System

Problem framing

This is the ingestion and state-tracking half of logistics, not the route-planning half — see the Google-Maps-style ETA and routing problem elsewhere in this chapter for how a route and ETA actually get computed. Here, a fleet of delivery vehicles or couriers continuously reports GPS location, and the system has to maintain an always-fresh "current position" per vehicle, detect events like arriving at or leaving a stop, and expose all of that to ops dashboards and customer-facing tracking links, over connections that are frequently slow, bursty, or briefly offline.

Clarifying questions

  • How often do vehicles report their location, and does that vary by whether they are active? — a 5-second ping while delivering versus a 30-second ping while idle changes ingestion volume by an order of magnitude, and most fleets do exactly this kind of adaptive reporting.
  • Do we need geofencing — automatic "arrived at stop" or "left the depot" detection? — this turns part of the problem into spatial event detection, not just storing a location.
  • How long do we retain historical traces, and for what purpose (dispute resolution, analytics)? — this decides hot-storage retention windows versus cold-archive policy.
  • Is this a single company's fleet or a multi-tenant platform serving many shippers? — multi-tenancy adds data isolation and per-tenant rate-limiting requirements on top of the core tracking problem.
  • How should the system behave when a vehicle's device loses connectivity? — deciding whether devices buffer-and-replay pings on reconnect changes how the ingestion side has to handle out-of-order and duplicate data.

Requirements

Functional: devices push periodic location pings; the system maintains a current position per vehicle; it detects geofence enter/exit events (arrival/departure at a stop) and fires webhooks or notifications; it exposes a live map for ops and a shareable live tracking link for customers; it stores historical traces for replay and dispute resolution.

Non-functional: the ingestion pipeline must tolerate unreliable mobile uplinks — packet loss, duplicate pings, and out-of-order delivery are the normal case, not the exception; end-to-end latency from a real-world location change to it showing on a dashboard should be under roughly 5 seconds; the pipeline should favor accepting messy data over dropping it, since a gap in the trace is worse than a duplicate; and the design must scale horizontally to fleets of hundreds of thousands of vehicles.

Capacity estimate

Assume 500,000 active vehicles at peak, each pinging every 5 seconds — that is 100,000 pings/sec sustained. Each ping (vehicle ID, lat, lng, speed, heading, timestamp) packs into roughly 150 bytes, so ingestion bandwidth is about 15 MB/sec, trivial for a modern ingestion tier. Daily volume works out to 500,000 x (86,400 / 5) ≈ 8.64 billion pings/day. Raw storage at 150 bytes/ping is about 1.3 TB/day, which a columnar time-series format can typically compress down to 300-400 GB/day; retaining 30 days hot for dispute resolution lands around 10-12 TB of hot storage, with older data moved to cheap cold storage. Separately, live customer tracking pages need their own fan-out budget: assume 2 million concurrent tracking-page viewers during peak delivery hours, each wanting sub-5-second updates — that is a pub-sub fan-out problem sized independently of the raw ingestion pipeline.

High-level design

Deep dive

Out-of-order and duplicate pings are the normal case, not an edge case. Devices on unreliable mobile networks commonly buffer pings and replay them once connectivity resumes, so a ping can arrive minutes late, and a retried batch can duplicate one the server already processed. A system that trusts server-arrival order will show a vehicle jumping backwards on the map whenever a late batch lands. The fix is to always order by the ping's own client-side timestamp, not receive time, and to dedupe on an idempotency key of (vehicleId, timestamp) so a replayed batch is a harmless no-op instead of a corrupted trace.

Geofence checks need spatial indexing, not brute force. Testing every incoming ping against every defined geofence polygon does not scale once a platform has thousands of stops and depots. Indexing geofences by the geohash cells they cover (Ch.16 §09 covers the geohash and quad-tree mechanics) means a ping only needs to test against the small number of geofences whose cells it actually falls in. On top of that, a simple per-vehicle-per-geofence state machine (currently inside or outside) turns "did we just enter or exit" into a cheap transition check instead of a full re-evaluation on every ping.

Fan-out for live tracking is a pub-sub problem, not a polling problem. Most tracking links have exactly one viewer, but a rare, popular shipment might have thousands watching at once, and having every viewer poll the database directly does not scale to that skew. The same per-topic pub-sub pattern used for group-chat and video-signaling fan-out elsewhere in this series applies here: viewers subscribe to a channel keyed by vehicle or shipment, and the current-position store publishes updates into it rather than being queried by every viewer independently.

Trade-offs

At 10x scale (5 million vehicles), a single Kafka partition scheme and a single Redis cluster for current-position both run into per-node throughput and memory ceilings. Sharding the current-position store by a hash of vehicle ID across multiple Redis clusters restores horizontal headroom, at the cost of a routing layer that now has to know which shard owns which vehicle — the same underlying trade-off Ch.6 covers for sharding a database, just applied to a hot key-value workload instead of a relational table.

Say this

"I would put Kafka in front of the stream processor specifically because at-least-once delivery with replay tolerance matters more here than avoiding the small chance of processing a ping twice. Duplicates are cheap to handle with an idempotency key; a dropped ping during a network outage is not something you can recover after the fact, so the design has to bias toward never losing data at the ingestion boundary."

Final design

If you had to draw one picture: devices batch pings into an ingestion gateway that hands them to Kafka, partitioned by vehicle; a stream processor updates a current-position store, appends to a time-series trace store, and checks geofence transitions against a geohash-indexed rule set; geofence events fan out through a webhook service, and current-position updates fan out through a pub-sub layer to both ops dashboards and customer tracking links, so no viewer ever polls the database directly.

EM-level follow-up

Build vs. buy: the ingestion and tracking pipeline itself is usually worth building in-house once it is core to a logistics company's product, but the underlying map tiles, geocoding, and turn-by-turn routing are almost always bought from a mapping platform (Google Maps Platform, Mapbox) rather than built from scratch. On rollout: expanding into a new country needs new geofence data (depots, legal delivery zones) and often different mobile carrier connectivity assumptions, which makes it a cross-team dependency on whoever owns operations and mapping data, not a pure infrastructure deploy.

Design an Airport Gate and Flight-Seat Allocation System

Problem framing

This bundles two related scarce-resource-allocation problems that share the same shape: assigning a physical airport gate to a flight for a limited time window, and assigning a physical seat on a plane to a passenger. Both are about matching a scarce resource to a demand under real-time-changing constraints — gates shift because flights are delayed, and seats shift because passengers check in, no-show, or get bumped from an oversold flight. Neither problem is about raw throughput; both are about correctness under constant, live perturbation.

Clarifying questions

  • Are we solving gate assignment for a single airport, or across an airline's whole network? — a single-airport problem is a bounded scheduling problem; a network-wide version has to account for how one delay cascades into gate conflicts at the next airport down an aircraft's rotation.
  • Does gate assignment need to re-solve in real time as flights shift, or is a nightly batch plan enough? — irregular operations (weather, mechanical delays) can shift dozens of flights at once, which is a fundamentally different problem from a one-shot overnight optimization.
  • Do multiple airlines share the same gates ("common use"), or does each airline own a fixed set? — shared gates make this a multi-tenant airport-operator problem instead of one airline's internal tool.
  • What is the overbooking policy for seats, and how are bumped passengers compensated? — this decides whether confirmed reservations can exceed physical seat count, and by how much buffer.
  • Can an aircraft swap (a smaller plane substituted at the last minute) force a bulk reassignment of already-assigned seats? — this decides whether the seat system needs to support reflowing an entire seat map, not just adding new assignments.

Requirements

Functional: given each flight's estimated arrival/departure time and aircraft type, the system assigns a compatible, available gate with enough turnaround buffer for cleaning and boarding, and re-assigns automatically as times shift, escalating conflicts it cannot resolve automatically. For seats: a passenger's ticket confirms against seat inventory at booking time, and either the passenger picks a specific seat or one is auto-assigned; the system supports overbooking against historical no-show rates and a policy-driven bump process if more passengers show up than there are seats.

Non-functional: gate reassignments must reach display screens and ops dashboards within seconds of a schedule change; seat assignment must be strictly consistent — the same physical seat can never be double-assigned; gate assignment is a constrained scheduling problem (gate-aircraft size fit, minimum turnaround time, taxi/adjacency limits) that needs to re-solve fast enough — seconds, not minutes — to keep up with a busy hub's roughly 50-200 gates during a weather-driven disruption.

Capacity estimate

A large hub airport might run 150 gates and about 1,200 flight movements/day (600 arrivals plus 600 departures) — on average, that is one gate assignment change roughly every 70 seconds across the whole airport, a negligible steady-state rate. The real load is the re-solve during irregular operations: assume a weather event forces 300 flights to shift within a 10-minute window, which is about 0.5 reassignments/sec — still a low number, but each one touches a shared constraint graph, so the cost that matters is compute per solve, not raw request throughput. Seat allocation, sized for an airline group running 5,000 flights/day at an average of 180 seats each, gives 900,000 seat operations/day, or roughly 10/sec on average; even a single large flight's check-in rush, with maybe 100 concurrent check-ins in a few minutes before departure, only pushes system-wide peak to a few hundred seat-lock operations/sec — trivially small next to the stadium-scale numbers in the seat-level-concurrency ticket-booking problem elsewhere in this chapter. Both halves of this system are low-throughput, high-correctness problems, worth calling out explicitly rather than reaching for scale numbers that do not actually apply here.

High-level design

Deep dive

Gate assignment is incremental constraint solving, not a one-shot batch job. The hard part is not the first assignment of the day, it is the cascade: when a delayed flight frees up its gate later than planned, that ripples into which gate the next flight can use, which ripples into the one after that. Re-solving the entire day's schedule from scratch on every schedule change would be far too slow; practical systems bound the re-solve to only the affected time window and gates, treating this as incremental re-planning rather than full re-optimization, which is what keeps the solve fast enough to run every time a flight's estimate changes.

Seat locking reuses the ticket-booking pattern at a much smaller scale. The hold-then-confirm flow here — a short-TTL exclusive hold on a seat, confirmed only within the hold's lifetime, released back to inventory on expiry — is the same core pattern as the seat-level-concurrency ticket-booking problem elsewhere in this chapter. The key difference is scale: a flight has a few hundred seats, not tens of thousands, so a single-node lock, even a plain database row lock inside one transaction, is enough. There is no need for the sharded-lock infrastructure a stadium-scale sale requires — worth saying explicitly, since reaching for that heavier machinery here would be over-engineering.

Overbooking math sits as a business-rules layer on top of the same seat data. Airlines intentionally oversell based on historical no-show rates — a flight with a 4% historical no-show rate on 180 seats might sell 187 confirmed seats. That means the system has to track "confirmed reservation" and "checked-in and physically present" as two different states, not one, and the close-out decision at boarding time (who gets bumped if too many people actually show up) needs a fair, policy-driven ranking — fare class, loyalty tier, check-in order. This is a rules engine reading the same seat-inventory data, not a new storage problem.

Trade-offs

At 10x scale — modeling gate assignment across every airport an airline flies into, in one system, instead of per-airport — the constraint solver's search space explodes, because gate, aircraft, and crew constraints now interact across airports: a delayed departure at one airport cascades into a gate conflict at the next stop on that aircraft's rotation. The practical choice is either a slower, coarser cross-airport solve, or decomposing back into independent per-airport solvers that only exchange one shared signal (this aircraft's real-time ETA) — trading a globally optimal gate plan for a fast, locally correct one.

Say this

"For seat locking, I would deliberately reuse the simplest correct primitive — a short-TTL hold plus a database transaction — rather than building new sharded-lock infrastructure, because a flight's seat count is small enough that this is not the same scaling problem as a high-demand ticket sale. Matching the complexity of the solution to the actual size of the problem is the point."

Final design

If you had to draw one picture: an ops feed drives a flight schedule service, which triggers a constraint-based gate allocation engine that re-solves only the affected window and escalates unresolved conflicts to an alerting service; in parallel, a seat inventory service holds seats with a short-TTL lock, confirms them transactionally, and feeds a departure control system that enforces overbooking policy and the bump workflow at boarding time.

EM-level follow-up

Build vs. buy: most airlines buy their departure control and seat inventory system from an established vendor (Amadeus, Sabre) rather than building it, because it is deeply regulated by IATA standards and is not a competitive differentiator. Gate allocation optimization is sometimes built in-house at hub airports instead, because local taxiway and gate constraints are specific enough that a generic vendor tool underperforms a custom solver. On rollout: a new solver version at a live hub needs a shadow-mode period — running its decisions alongside the current one without acting on them — before cutover, because a bad gate-assignment bug stops airplanes on the ground, not just a webpage.

Design a Real-Estate Listing Search System (Zillow-style)

Problem framing

Buyers and renters search a huge, mostly slow-changing catalog of property listings through a map-first experience — panning and zooming the map re-issues the search — filtered by price, beds, baths, and property type. Two things make this different from a generic search problem: the data is ingested from many external, sometimes-conflicting feeds (MLS, or Multiple Listing Service, sources), and many products in this space also show an automated home-value estimate on every listing, which is a heavy machine-learning computation that still has to serve reads instantly.

Clarifying questions

  • Are listings sourced from MLS feeds, or entered directly by sellers? — MLS sourcing means multiple regional feeds can describe the same physical property differently, which puts a data reconciliation pipeline in scope as a first-class component.
  • Do we need an automated value estimate, or just search over the listed price? — an automated valuation model adds a whole offline ML pipeline to the system's scope.
  • Is search always driven by the map viewport, or do we also need plain text/radius search? — map-bounds search re-fires on every pan and zoom, which shapes both the query and the need for server-side pin clustering.
  • Do we need saved searches with alerts on new matches? — this adds a persistent-query and notification component on top of the base search system.
  • How fresh must "sold" or "pending" status be? — a stale "for sale" listing that is actually already sold is a major trust problem, which drives the ingestion freshness SLA.

Requirements

Functional: a user searches by map viewport plus filters and gets ranked, clustered results; a user views a listing's full detail with photos, facts, and an estimated value; a user saves a search and is notified of new matching listings; a data pipeline ingests updates from multiple MLS feeds and reconciles conflicting records for the same physical property into one canonical listing.

Non-functional: map-bounds search must feel instant, well under 300 ms, since it fires on every pan and zoom; listing status changes (active, pending, sold) must reach search within minutes, not hours, because stale listings directly damage trust; the system is read-heavy by a huge margin — millions of anonymous browsers per listing update; valuation numbers can lag by a day or more, since a home's estimated value does not meaningfully change minute to minute.

Capacity estimate

Assume 200 million monthly visits, 8 searches/session, and 2 sessions/month per visitor on average — that is roughly 1.6 billion searches/month, or about 53 million/day, or about 615 searches/sec on average, with an evening peak of maybe 4x giving roughly 2,500 searches/sec. Nationwide, assume about 2 million currently-active listings, plus a much larger set of historical/off-market property records kept for valuation comparisons — say 150 million property records total. Each core record is small, around 2 KB, so metadata storage is a few hundred GB; photos matter more — assume active listings alone carry about 20 photos at 400 KB each, so 2,000,000 x 8 MB ≈ 16 TB of active-listing images, served through a CDN. Ingestion volume is modest: assuming 5% of active listings change status or price per day, that is 100,000 updates/day, or about 1.2 updates/sec on average feed ingestion — small in absolute terms, but each one needs to reach the search index within the minutes-level freshness SLA, which is the actual design constraint, not the raw rate.

High-level design

Deep dive

Map-bounds search needs server-side clustering, not just a bounding-box query. A geo-bounding-box query filtered by price and beds/baths is a standard Elasticsearch query shape (see Ch.11 §02 for how Elasticsearch shards and merges results), but returning every matching pin at a zoomed-out, city-wide view could mean millions of points. The actual design problem is grouping nearby pins into a single "42 homes" cluster marker, computed server-side per zoom level, because shipping millions of raw points to a browser is both slow and a bad map experience — the map should never render more pins than a human can usefully look at.

Reconciling multiple MLS sources into one canonical property. The same physical house is often described slightly differently by more than one regional MLS feed — square footage off by a few percent, a different photo set, a listing that is active in one feed but already marked sold in another. Without an address- or parcel-ID-based entity-resolution step in the ingestion pipeline, the same home shows up as duplicate pins, or a stale update overwrites a fresher one purely because of feed ingestion order. This reconciliation step has to run before data ever reaches search, not as a search-time deduplication hack.

Serving an ML valuation cheaply means precomputing it off the read path entirely. A Zestimate-style automated valuation model — built from comparable sales, tax records, and property facts — is expensive to run per property and only needs to change slowly, so it is computed as a scheduled batch job (daily is typical) for every property and written into a fast key-value store keyed by property ID. The listing-detail read path then does a trivial point lookup, keeping all the ML complexity off the hot request path entirely. Contrast this with the ETA computation in the Google-Maps-style problem elsewhere in this chapter, which has to run on read because traffic conditions change by the minute — the right call here is precompute, and the right call there is compute-on-read, and knowing which is which is the actual skill being tested.

Trade-offs

At 10x scale — a much larger property catalog, or a sudden spike in search QPS from a viral moment — the first thing to break is index freshness, not raw query throughput. Elasticsearch absorbs more read QPS cheaply by adding replica shards, but the ingestion-to-search-visible pipeline (MLS update, reconciliation, indexing) is a serial dependency chain that does not parallelize as easily, so a sudden update-volume spike (a market-wide price-drop event) can push "for sale" freshness past its minutes-level SLA unless the reconciliation and indexing stages are over-provisioned well beyond steady-state need.

Say this

"I would compute the home-value estimate as a scheduled offline batch job, not on read, because the underlying facts it depends on — comparable sales, tax records — do not change minute to minute. That keeps the read path a simple point lookup, and it is the opposite call from the ETA problem, where traffic really does change minute to minute, so that one has to compute on read."

Final design

If you had to draw one picture: MLS feed adapters push into a reconciliation service that resolves duplicate property records before writing to the source-of-truth listing store; a change-data-capture stream feeds a geo-indexed Elasticsearch cluster for map-bounds search with server-side clustering, and feeds a saved-search matcher for alerts; a separate offline valuation pipeline precomputes value estimates into a fast key-value store that the listing-detail read path simply looks up.

EM-level follow-up

Build vs. buy: a smaller real-estate product should use a managed search service and buy aggregated MLS data from a data vendor rather than building direct feed adapters for every regional MLS — there are hundreds in the US, each with its own quirks — and only build that integration layer in-house once listing coverage and freshness become the actual competitive edge, the way they are for Zillow. On rollout: a new valuation model version needs a shadow/backtest period against known recent sale prices before it replaces the live numbers users see, because a visibly wrong valuation directly damages trust in the whole product, not just that one feature.

Design a Bike/Scooter-Share Fleet Management System

Problem framing

A rider finds a nearby available vehicle on a map, reserves it, unlocks it, rides solo, and ends the trip by parking it — no driver, no live matching negotiation, which is what separates this from the Uber/Lyft problem elsewhere in this chapter. The system has to keep an accurate, near-real-time picture of where every vehicle in a citywide fleet is, whether it is locked, and how much battery it has, while also enforcing where a vehicle is legally allowed to be parked.

Clarifying questions

  • Docked, with fixed stations, or dockless, park-anywhere-within-a-zone? — this changes the core data model completely: docked is "this station has N free slots," dockless is "this vehicle is a free-floating point that must land inside a valid parking zone."
  • Electric or manual? — electric adds a battery-level and charge-state telemetry dimension on top of just location, and a charging/swap logistics workflow for ops.
  • Does unlocking happen via direct Bluetooth from the phone, or a cellular-connected vehicle unlocked by a backend command? — this decides whether the unlock path has to work with no connectivity from the vehicle to the backend at the exact moment of unlocking.
  • Is fleet-rebalancing tooling for ops (vans redistributing vehicles overnight) in scope? — this decides whether a demand-prediction and task-assignment component is part of this system.
  • Are there city-regulated no-parking or no-ride zones that must be enforced? — this adds a spatial rules-validation requirement to both riding and trip-end.

Requirements

Functional: a rider sees nearby available vehicles with battery level on a map; a rider reserves a specific vehicle for a short hold window, then unlocks it; a ride session tracks location for fare and audit purposes; ending a ride validates the parking location against legal zones and computes the fare; vehicles periodically report battery and lock state; an ops dashboard shows fleet distribution and low-battery vehicles needing pickup.

Non-functional: "available" status shown to a rider must be accurate within a few seconds — a brief race where two riders both see the same vehicle is tolerable if resolved cleanly at unlock time; unlock latency should be a couple of seconds at most; the system must tolerate vehicles going offline (dead battery, out of cellular range) without corrupting fleet state; it must scale to tens of thousands of vehicles with citywide concurrent usage.

Capacity estimate

Assume a large city deployment of 20,000 vehicles, each reporting telemetry every 30 seconds while idle and every 5 seconds while on an active ride. Assuming 5% of the fleet (1,000 vehicles) is actively in use at a given moment: 1,000 x (1/5)/sec + 19,000 x (1/30)/sec ≈ 200 + 633 ≈ 833 pings/sec citywide — a small ingestion volume. Ride volume: assume 150,000 rides/day citywide averaging 15 minutes each, so average concurrent active rides ≈ 150,000 x 15 / 1,440 ≈ 1,560, consistent with the 5%-of-fleet assumption above. Reservation-and-unlock flow: 150,000 unlocks/day is about 1.7/sec on average, with a commute-hour peak of maybe 10x giving roughly 17/sec — still small. The nearby-availability query is the interesting one: assume 500,000 map-refresh requests/day from riders just checking the app, about 6 QPS on average and maybe 50/sec at peak, each a geo-radius read against the live fleet-location index. The design challenge here is staleness and correctness at low latency, not raw throughput — every number in this system is modest in absolute terms.

High-level design

Deep dive

Reservation holds prevent double-booking a physical object, but the hold has to reach the hardware. Two riders opening the app at the same instant can both see the same vehicle as available. The software fix is the same short-TTL exclusive hold used for seats in the ticket-booking problem elsewhere in this chapter — reserve for a few minutes, auto-release if not unlocked in time. The twist here is that the hold must also be honored physically: the vehicle's own lock has to refuse to open for anyone but the current holder, which means the unlock command has to carry the reservation's identity all the way down to the hardware, not just live as a backend-only concept that the vehicle itself does not know about.

Vehicles are unreliable IoT devices, and "current location" has to admit that. A vehicle on cellular or Bluetooth can lose connectivity mid-ride, so the backend's idea of "current location" is sometimes stale by design, not by bug. The system should treat the last-known-ping timestamp as a first-class piece of state, so the app can honestly show "last seen 4 minutes ago" instead of confidently showing a location that might already be wrong. Ride-end validation has to tolerate a final ping arriving late — say, once Bluetooth reconnects after the rider has already walked away — by reconciling once it does arrive rather than blocking the rider's checkout on it.

Ending a ride is a spatial-rules check, not just a location write. Ending a ride means validating the parking spot against city-defined no-parking zones and required-parking corrals, which reuses the same geohash-bucketed polygon lookup as the geofencing logic in the fleet-tracking problem earlier in this chapter, just applied once at trip-end instead of continuously. A failed check should still let the rider end the ride — you cannot force someone to keep paying because they parked in the wrong spot — but it should flag the vehicle for a penalty fee and queue an ops pickup task.

Trade-offs

At 10x scale — a company running in 50 cities instead of 1, rather than one city getting 10x bigger — a single live fleet-location store sized for one city's 20,000 vehicles does not automatically become the right shape for 50 independent cities' worth of vehicles and independent geofence rulesets. The natural fix is partitioning fleet state by city or region from the start, since riders never query across city boundaries anyway — trading a slightly more complex routing layer (which shard serves this city) for avoiding one shared, hot store that mixes the load of unrelated cities.

Say this

"Availability data can be eventually consistent — a few seconds of staleness on 'is this vehicle free' is fine, because it gets fully resolved at unlock time anyway. The reservation itself cannot be eventually consistent, because that is the step that actually prevents two people from claiming the same physical bike. Keeping that split explicit is what keeps the design both fast and correct."

Final design

If you had to draw one picture: vehicle hardware streams telemetry through a queue into a fleet-state processor that maintains a geo-indexed live location store; riders read that store for nearby availability, then go through a short-TTL reservation hold that a ride service turns into an unlock command carrying the reservation's identity down to the vehicle; ending a ride runs a geofence-based zone check before finalizing the fare, and fleet-wide location and battery data feed a separate rebalancing analytics pipeline for ops.

EM-level follow-up

Build vs. buy: the fleet-tracking, reservation, and ride backend is usually built in-house since it is the core product, but the physical lock and IoT module are frequently sourced from a vehicle-hardware vendor rather than built from scratch, and payment processing is almost always outsourced (Stripe) rather than built. On rollout: launching in a new city is not just a software deploy — it needs geofence data (legal parking zones, no-ride zones) negotiated with that city's government, which makes market expansion a cross-team dependency on legal, policy, and ops, not just code readiness.
