This chapter is a working set of systems that show up again and again in EM-level interview loops: money-moving systems where a single bug means a real dollar amount is wrong, ranking systems that narrow millions of candidates down to ten in under a second, and the internal platforms — CI/CD, feature flags, config, billing — that every other engineering team ends up building their own systems on top of.

00How to use this chapter

These 24 problems look unrelated on the surface — a payment gateway has nothing to do with a search engine — but the same handful of techniques keep reappearing under different names once you look past the domain. Idempotency keys guard almost every write that involves money or a client that might retry. Append-only ledgers replace a mutable counter wherever "why did this number change" has to have a real answer later. A cheap-broad-then-expensive-narrow funnel shows up wherever a request has to search a huge space in well under a second. A saga with compensating actions replaces a single database transaction wherever a workflow has to span two systems that cannot share one commit. Spotting these patterns once, instead of re-deriving them inside every problem's deep dive, is the fastest way to get through this chapter and the fastest way to sound like you have done this before in an actual interview. The specsheet below is a quick-lookup for the versions of these patterns this chapter leans on most.

Idempotency The idempotency-key pattern
  • What it solves — a network retry or a crashed worker re-sending the same "do this" request must never do it twice, especially when "it" is charging a card or crediting points.
  • How it works — the client supplies (or the system derives) a stable key for the operation; the first request with that key executes and stores its result; any repeat of that key returns the stored result without re-executing anything.
  • Where it must live — enforced with a unique constraint at the database layer, not a check-then-insert in application code, because two servers can race on the same retried request.
  • Recurs in — Payment Gateway, Digital Wallet, E-commerce Checkout, Subscription Billing, Loyalty Points, Developer API Platform metering.
Ledger Append-only ledgers vs. mutable counters
  • Core idea — every money (or points) movement writes a debit row and a credit row inside one transaction, instead of incrementing/decrementing a single balance column in place.
  • Why — a balance shown to a user is a materialized sum over the ledger, never the source of truth itself; this is what makes a "why did my balance change" question answerable months later.
  • The cache trap — a fast balance cache is fine for reads, but a debit must always be a conditional write against the ledger's real running total, never authorized by a possibly-stale cached number.
  • Recurs in — Payment Gateway, Splitwise, Digital Wallet, Loyalty Points.
Funnel Retrieval-then-rank funnels
  • Core idea — a cheap, broad first stage (BM25 scoring, an approximate nearest-neighbor index, simple deterministic rules) narrows millions or billions of candidates down to a few hundred or a few thousand.
  • Then — an expensive, precise second stage (a learned ranking model, a heavier fraud model) only ever runs on that small survivor set, because it cannot afford to run on the full candidate pool at request-time latency.
  • Recurs in — Web Search Engine, Recommendation System, Real-Time Fraud-Detection Pipeline (rules first, model second, human review last).
Saga Sagas with compensating actions
  • Core idea — when a workflow spans two systems that cannot share one database transaction, break it into an ordered sequence of steps, each with an explicit rollback (a "compensating action") if a later step fails.
  • Why not two-phase commit — 2PC's blocking behavior under a node failure is usually worse in practice than a rare, automatically-compensated retry.
  • Recurs in — E-commerce Checkout (reserve, charge, confirm), CI/CD deployment orchestration, Monolith-to-Microservices cutover, Internal Developer Platform provisioning.
Fan-out Push-based fan-out with local fallback
  • Core idea — instead of every reader polling a central system, the central system publishes once and a relay/mirror tier pushes diffs down long-lived connections it already holds open.
  • The other half — every reader keeps a locally cached last-known-good copy, so the central system going down degrades reads to "slightly stale," never to "broken."
  • Recurs in — Feature-Flag System, Global Configuration Service, and the golden-dashboard query cache in the Real-Time Analytics Dashboard Platform.

Design a Payment Gateway

Problem framing

A payment gateway sits between a merchant's checkout page and the outside money-moving world — card networks (Visa, Mastercard), acquiring banks, and issuing banks. It does not hold customer money itself. Its job is to take a checkout request, authorize it against a card or bank account, capture the money, and prove — with an unbreakable paper trail — exactly what happened to every cent, forever. Think Stripe, Razorpay, or Adyen, serving thousands of merchants who each just want a simple API call that either says "charged" or "declined."

Clarifying questions

  • Cards only, or also bank transfers and wallets? — cards need a network round trip and a 3D-Secure step-up flow for fraud checks; bank transfers settle on a completely different, slower timeline. This changes the state machine per payment method.
  • Who holds PCI-DSS scope — do we ever see the raw card number, or does a tokenization layer sit in front of us? — this decides whether our own servers must be audited to the highest PCI tier or whether we can stay out of scope by only ever handling opaque tokens.
  • Is capture immediate, or authorize-now-capture-later (e.g. ship-then-capture for physical goods)? — a held authorization has an expiry (commonly 7 days) and needs its own reminder/expiry job.
  • How many currencies and countries? — each new country usually means a new acquiring-bank relationship and new local payment methods, not just a currency-conversion rate.
  • What is an acceptable window for a merchant to find out a payment succeeded — instant, or is an async webhook within a few seconds fine? — decides whether the checkout call itself must block on the full card-network round trip or can return early and confirm later.

Requirements

Functional requirements:

  • Create a payment intent for an amount and currency, tied to a merchant and (tokenized) payment method.
  • Authorize the payment against the card network / bank.
  • Capture a previously authorized payment (fully or partially).
  • Refund a captured payment (fully or partially).
  • Notify the merchant asynchronously of state changes (webhooks).
  • Reconcile every transaction against the bank's end-of-day settlement file.

Non-functional requirements:

  • A retried request must never double-charge a customer — idempotency is not optional, it's the whole point.
  • The ledger (the record of who owes what to whom) must be strongly consistent; "probably correct" is not acceptable for money.
  • Once a payment is acknowledged as authorized, that fact must never be lost, even if a server crashes mid-request.
  • Authorize latency should stay well under a second end to end, most of which is the card network's own round trip.
  • Every state transition must be auditable — who/what changed a payment's status, and when.

Capacity estimate

Assume a mid-size gateway processing 50 million transactions/day across all merchants. Average TPS (transactions per second) ≈ 50,000,000 / 86,400 ≈ 579/sec. Real-world payment traffic is uneven across time zones and spikes hard around sales events; assume peak runs roughly 5x average ≈ 2,900/sec.

Each transaction produces one transaction record (merchant, amount, status history, risk score) at roughly 1KB, plus two ledger rows for double-entry bookkeeping (a debit and a credit — explained in the deep dive) at roughly 250 bytes each. That's about 1.5KB per transaction. 50,000,000 × 1.5KB ≈ 75GB/day, roughly 27TB/year — small compared to a media platform, but every byte has to be exactly right and kept for years for audits and disputes.

Card-network round trips typically take 200-400ms. The gateway's own added latency (idempotency check, risk scoring, ledger write) should stay under roughly 100-150ms so the whole authorize call finishes comfortably under a second.

API design

POST /v1/payment_intents          -- Idempotency-Key header
     body: {amount, currency, merchant_id, payment_method_token}
     -> {intent_id, status: "requires_confirmation"}
POST /v1/payment_intents/{id}/confirm   -> {status: "authorized"|"declined"}
POST /v1/payment_intents/{id}/capture   {amount?}   -> {status: "captured"}
POST /v1/refunds  {payment_intent_id, amount?}      -> {refund_id, status}
GET  /v1/payment_intents/{id}
Webhook (to merchant): POST {merchant_webhook_url}
     body: {event: "payment_intent.succeeded", intent_id, ...}

High-level design

A synchronous path authorizes and captures; an asynchronous path notifies the merchant and reconciles against the bank at the end of the day.

Deep dive

1) Idempotency is the whole game. Networks retry. A merchant's server might time out waiting for our response and resend the exact same "charge $40" request. Every mutating call takes a client-supplied idempotency key; the gateway stores the key with the request's result, and any repeat of that key returns the original result without touching the card network again (see Ch.13 for idempotency mechanics in general). Without this, a single network hiccup becomes a double charge — the single most common real-world payments bug.

2) Double-entry ledger, not a single balance column. Every money movement writes at least two rows: a debit to one account and a credit to another (e.g. debit the merchant's receivable, credit the gateway's payable), inside one database transaction (see Ch.7 for ACID transactions). This is not paranoia — it's what makes every dollar traceable to exactly where it came from and went, and it's what a reconciliation job can actually compare against a bank statement line by line. This is the same CP (consistent over available) choice Ch.12 makes for a banking ledger: correctness beats uptime here, unlike a shopping cart.

3) Webhooks must survive a crash between "we know" and "we told the merchant." If the ledger write and the webhook publish are two separate steps, a crash in between leaves the merchant never informed of a successful charge. The fix is the outbox pattern from Ch.14: write the webhook event to an outbox table in the same transaction as the ledger write, and a separate relay process publishes from that outbox with retries — so "committed to the ledger" and "will eventually be told to the merchant" become the same guarantee.

Trade-offs

At 10x scale, the ledger database's single-writer transaction log becomes the bottleneck before the API layer does — every authorize, capture, and refund funnels through it because correctness cannot be sharded away carelessly. The trade-off is sharding the ledger by merchant_id (most transactions are single-merchant, so this scales cleanly) versus keeping one global ledger for simpler cross-merchant reporting and settlement reconciliation.

Say this

"I would treat the idempotency key as a first-class part of the API contract, not an afterthought — every mutating endpoint requires one, and the gateway's own database is the arbiter of whether a request is a retry or a new charge, because trusting the client to only retry safely is how double charges happen in production."

Final design

One picture: a checkout request hits a stateless gateway API that checks idempotency, scores fraud risk, then writes a double-entry ledger transaction before calling out to the card network. State changes drop into an outbox that a relay turns into merchant webhooks. A separate nightly job reconciles every ledger entry against the bank's settlement file and flags anything that doesn't match, dollar for dollar.

EM-level follow-up

Rollout into a new country is rarely just a deploy — it usually needs a new acquiring-bank relationship and card-network certification, so the engineering timeline is gated by a legal/compliance timeline, not the other way around. On build-vs-buy: almost nobody builds direct acquiring-bank integrations from day one; most companies start by routing through an existing processor and only build their own acquiring stack once volume justifies the PCI compliance overhead of owning that layer.

Design a Splitwise-Style Expense-Splitting App

Problem framing

This is a bookkeeping app for groups of friends, roommates, or trip companions. It records who paid for what, splits the cost among the people involved, and continuously answers one question: "who owes whom, and how much?" Unlike a payment gateway, no real money moves through the system by default — it's an IOU tracker, and the interesting problems are about correctness of arithmetic and making settle-up easy, not about card networks.

Clarifying questions

  • Do splits need to support percentage and exact-amount splits, or just equal splits? — equal splits are trivial division; exact and percentage splits both need to handle rounding so the parts always sum exactly to the whole.
  • Should the app simplify debts across a whole group (minimize the number of payments needed to settle everyone up), or just show pairwise balances? — simplification is a small optimization problem, not just a lookup.
  • Is real money settlement integrated (pay a friend from inside the app), or is this tracking only, with settlement happening outside the app? — real settlement pulls in a payment gateway as a dependency (see the Payment Gateway problem above).
  • Multiple currencies within one group (a trip abroad)? — this needs a currency-conversion rate captured at the time of the expense, frozen, so balances don't silently drift as exchange rates move later.
  • Can two people edit the same group's expenses at the same time from different phones (offline-first mobile use)? — this decides whether we need conflict resolution for expenses created while offline.

Requirements

Functional requirements:

  • Create a group and add/remove members.
  • Add an expense: amount, payer, and how it's split (equal, percentage, or exact amounts) among a subset of members.
  • View pairwise balances ("you owe Alex $12") and a simplified group-wide settle-up plan.
  • Record a settle-up (mark a debt as paid, optionally via a linked real payment).

Non-functional requirements:

  • Money arithmetic must be exact — split amounts must always sum to exactly the original expense, with no floating-point drift.
  • Balances can be eventually consistent for a second or two after an edit, but must never show a stale amount indefinitely.
  • The system must survive a member deleting an expense after balances were already computed, without corrupting other members' totals.
  • High read-to-write ratio — balances are viewed far more often than expenses are added.

Capacity estimate

Assume 10 million monthly active users, each logging about 4 shared expenses a month — 40 million expense-adds/month, roughly 1.33 million/day, or about 15/sec on average. Evening and weekend usage spikes; assume peak runs about 4x average, ≈ 62/sec.

Storage per expense: the expense row itself (description, amount, payer, timestamps) is roughly 200 bytes. For a typical group of 4 people, four split rows at about 80 bytes each add 320 bytes, so roughly 520 bytes total per expense. 40,000,000 × 520 bytes ≈ 20.8GB/month, about 250GB/year — small, because this system stores facts about money, not money-moving events.

Reads dominate over writes: assume each user opens the app to check balances about 15 times a month. That's 150 million balance-reads/month ≈ 5 million/day ≈ 58/sec average — roughly 4x the write rate, which is why the balance view needs to be cheap to serve, not recomputed from scratch on every request.

API design

POST   /groups                          {name, memberIds[]} -> {groupId}
POST   /groups/{id}/expenses            {amount, payerId, splitType, splits[]}
GET    /groups/{id}/balances            -> {pairwiseBalances[]}
GET    /groups/{id}/settle-plan         -> {transfers[]}   // minimized payment count
POST   /groups/{id}/settlements         {fromUserId, toUserId, amount}
DELETE /groups/{id}/expenses/{expenseId}

High-level design

Expenses are appended to a durable log; a balance service derives and caches the numbers people actually look at, so a read never has to replay history.

Deep dive

1) Money must be stored as integer minor units, never as a floating-point number. $10.00 split three ways is $3.33 + $3.33 + $3.33 = $9.99, a penny short of the original. The fix: store amounts as integer cents (or the smallest unit of the currency), compute each share, and hand the leftover remainder cents to the first payer(s) in a deterministic order, so the parts always sum to exactly the whole (see Ch.7 on why a numeric/decimal column, or here an integer column, beats a float for money). This is a small detail that breaks trust in the whole app if it's wrong even once.

2) Balances are a derived view over an append-only expense log, not a running total mutated in place. Every expense add and delete appends an event; the balance service recomputes net balances from that log rather than incrementing/decrementing a stored total directly (the event-sourcing idea from Ch.14). This makes "someone deleted an expense from three weeks ago" safe — replay the log and every balance downstream of that point is automatically correct, instead of needing a hand-written compensating adjustment.

3) Debt simplification is a small graph problem computed on demand, not a stored structure. Treat each group as a tiny graph — nodes are members, edges are net pairwise balances — and greedily match the person who owes the most against the person who is owed the most, repeating until every edge is zero. This is small enough (a handful of members) to run in memory on every read; it does not need a dedicated graph database like Neo4j from Ch.9 — that tool earns its keep at a much larger, more connected scale than one group's balance sheet.

Trade-offs

At 10x scale — a group with hundreds of members, like an office party fund or a co-living house — a pairwise balance table grows O(n²) with membership, and recomputing all pairs on every expense gets expensive fast. The fix is switching that group's model from "who owes whom" to "who owes the group pool," trading away the friendly per-person clarity for a single per-member net number against a shared pot.

Say this

"I'd store every amount as an integer in the smallest currency unit and never let a float touch a money field — splitting a division cleanly is easy, but making three float-based shares sum back to exactly the original amount is the kind of bug that erodes trust the first time a user notices it."

Final design

One picture: expenses append to a durable per-group log; a balance service replays that log to maintain a cached net-balance table per pair, and runs a small greedy graph simplification over that table on demand to produce a minimal settle-up plan. Money is integers everywhere, and deletes are just another event in the log, not a special case.

EM-level follow-up

Adding real in-app settlement (letting a user actually pay a friend, not just record it) is a build-vs-buy call that pulls in a payment gateway as a dependency — most teams integrate an existing processor rather than build card/bank rails themselves, because the compliance burden (KYC, PCI scope) is completely separate work from the expense-splitting product itself and belongs to a different roadmap.

Design a Digital Wallet

Problem framing

A digital wallet — think Paytm, Google Pay's wallet balance, or Venmo's in-app balance — is a stored-value account: the operator holds a balance on a user's behalf and moves money between users by writing ledger entries instead of by starting a new card or bank transaction every time. This is a different problem from the Payment Gateway above: a gateway routes a single card charge between a merchant and a bank and then is done; a wallet is the long-lived account of record, and a card or bank rail is just how money gets in and out of it.

Clarifying questions

  • Is the wallet a regulated e-money product (the operator must hold customer float at a licensed bank, subject to a regulator)? — this changes almost everything about how strict the ledger and audit trail must be, and adds KYC (identity verification) tiers with transaction limits.
  • Peer-to-peer transfers between two wallets, or only top-up from a card/bank and pay-out to a merchant? — P2P adds a second wallet as a party inside the same transaction, which is where most of the concurrency difficulty lives.
  • Can a balance ever go negative (an overdraft/credit line), or is zero always the floor? — decides whether a debit is a hard constraint enforced by the database or a soft one.
  • Is there interest paid on the held balance? — this pulls in accounting complexity (accruals) beyond simple debit/credit.
  • What are the transaction and daily limits per KYC tier, and who enforces them — the wallet service itself, or a separate fraud/compliance service? — decides whether limit checks live in the hot path or can happen asynchronously.

Requirements

Functional requirements:

  • Create a wallet account, tied to a verified identity.
  • Top up from a linked card or bank account.
  • Transfer money to another wallet (peer-to-peer).
  • Pay a merchant from wallet balance.
  • Withdraw to a linked bank account.
  • View current balance and transaction history.

Non-functional requirements:

  • A balance must never go negative under concurrent debits — this is a hard invariant, not a best effort.
  • Every transaction must be idempotent under client retries.
  • Balance reads should return in well under 100ms — users check this constantly.
  • The transaction history is an immutable audit trail; nothing gets updated in place, only appended.
  • KYC/AML (anti-money-laundering) limits must be enforced before a transaction completes, not after.

Capacity estimate

Assume 100 million registered wallets, with about 20% active on a given day — 20 million daily active users (DAU). Assume each active user does about 3 wallet transactions a day (a top-up, a merchant pay, a P2P send) — 60 million transactions/day. Average TPS ≈ 60,000,000 / 86,400 ≈ 694/sec; peak (paydays, festival shopping days) roughly 5x average ≈ 3,470/sec.

Every transaction writes at least two ledger rows (double-entry: debit one account, credit another). 60,000,000 × 2 = 120 million ledger rows/day, at roughly 250 bytes/row ≈ 30GB/day, about 11TB/year — this has to be kept for years for regulatory audits, so total retained storage is large even though daily volume is modest.

Balance reads are far more frequent than transactions: assume each DAU checks their balance about 5 times a day, 100 million reads/day ≈ 1,157/sec average, peak ≈ 4,600/sec. These must be served from a fast cache, not by summing the ledger on every request.

API design

POST /wallets                                 {userId} -> {walletId}
POST /wallets/{id}/topup       -- Idempotency-Key
     body: {amount, fundingSource}            -> {txId, newBalance}
POST /wallets/{id}/transfer    -- Idempotency-Key
     body: {toWalletId, amount}                -> {txId, status}
POST /wallets/{id}/withdraw    {amount, bankAccountId} -> {txId, status}
GET  /wallets/{id}/balance                     -> {balance, currency}
GET  /wallets/{id}/transactions?cursor=&limit=20

High-level design

A wallet service enforces limits and idempotency in front of a strongly consistent ledger; a fast cache absorbs the balance-read traffic so the ledger only sees writes and occasional cache misses.

Deep dive

1) The negative-balance race condition, and why it must be fixed inside the database, not in application code. Two concurrent debits reading the same balance, both seeing "enough funds," both proceeding, is the classic race that lets a balance go negative. The fix is a single conditional update — UPDATE wallets SET balance = balance - :amount WHERE id = :id AND balance >= :amount — inside one database transaction, so the check and the decrement are atomic (see Ch.7 for row-level locking and isolation levels). A read-then-write in application code is never safe under concurrency, no matter how careful the code looks.

2) A peer-to-peer transfer touches two accounts, and if they're on different shards, that's a distributed transaction. Debiting wallet A and crediting wallet B must happen together or not at all. If both wallets live in the same database shard, one local ACID transaction handles it cleanly (Ch.7). If they're on different shards — which happens once the ledger is sharded by account for scale — the options are a full two-phase commit (expensive and fragile, per Ch.13) or a saga: debit A with a pending state, then credit B, with a compensating credit back to A if the second step fails. Most production wallets pick the saga, because 2PC's blocking behavior under a node failure is worse than a rare, automatically-compensated retry.

3) The wallet ledger is a CP system by design — this is the same call Ch.12 makes for a banking ledger. During a network partition between ledger shards, the wallet must refuse a transfer rather than risk two shards disagreeing about a balance — unlike a shopping cart or social feed (Ch.12's AP example), a wrong balance is not an acceptable temporary state, ever, even for a few seconds.

Trade-offs

At 10x scale with a global user base, a single-region, strongly consistent ledger means every write from a user on the other side of the world pays full cross-region latency. Sharding the ledger by home region reduces that latency for most transactions but turns every cross-region P2P transfer into the saga-with-compensation path from the deep dive — the trade-off is uniform latency (accept the cross-region tax everywhere) versus regional speed at the cost of extra complexity on the (hopefully rarer) cross-region path.

Say this

"The balance check and the decrement have to be one atomic database operation, not two — I'd use a conditional update guarded by the current balance inside the transaction, because a check-then-write pattern in application code will eventually let a negative balance through under real concurrency, and for a wallet that's not a bug, it's a financial loss."

Final design

One picture: a wallet service enforces KYC limits and idempotency, then commits every transfer as an atomic double-entry write in a ledger database that treats correctness as non-negotiable (CP, per Ch.12). A balance cache absorbs the much higher read volume, invalidated on every write. Cross-shard transfers use a saga with a compensating entry instead of a blocking two-phase commit.

EM-level follow-up

Launching a wallet in a new country is usually gated by a banking license or an e-money regulatory approval, not by engineering readiness — this is a cross-team dependency on legal and compliance that can take longer than building the feature itself. On build-vs-buy: the ledger core is almost always built in-house because correctness here is the entire product, but KYC/AML identity verification is almost always bought from a specialized vendor, because that's a compliance-heavy, jurisdiction-specific problem a payments team shouldn't try to own alone.

Design E-Commerce Checkout and Inventory

Problem framing

This is the flow that turns a shopping cart into a confirmed order — think Amazon or Flipkart's checkout button. Strip away the UI and the hard part is one rule that must never break: never sell a unit of stock (a SKU, short for stock-keeping unit — a specific product/variant code) that doesn't actually exist, while also never charging a customer for an order that ultimately can't be fulfilled.

Clarifying questions

  • Is inventory tracked per warehouse/region, or as one global pool? — per-warehouse tracking is what enables "ships tomorrow" promises, but it means checkout must also pick which warehouse fulfills the order.
  • Is this a single-seller catalog or a marketplace where many sellers list the same SKU? — a marketplace needs to pick which seller's stock to draw from, which adds a ranking/allocation decision to checkout.
  • Is payment captured at order-placement or at ship time? — capturing at ship time avoids charging for something that turns out to be out of stock, at the cost of a longer-lived authorization hold (see the Payment Gateway problem above).
  • What oversell rate is acceptable during a flash sale — zero, or a small, insured rate in exchange for a much simpler system? — many real retailers accept a tiny oversell rate and resolve it with an apology and a refund, rather than paying the cost of perfect coordination at extreme concurrency.
  • Does a cancellation or return automatically restock the item, and how fast? — decides whether returns flow through the same reservation system or a separate slower process.

Requirements

Functional requirements:

  • Add/remove items in a cart, with live price and availability.
  • Checkout: reserve stock for the cart's items, charge payment, confirm the order.
  • Cancel an order or process a return, restocking the item.
  • Show a customer accurate stock status (in stock / low stock / out of stock).

Non-functional requirements:

  • No oversell beyond a tiny, explicitly accepted rate during extreme spikes.
  • A customer is never charged for an item that couldn't actually be reserved.
  • Checkout should complete in well under 2 seconds under normal load.
  • An abandoned checkout must release its reservation automatically within a short, bounded time.
  • The system must degrade gracefully under a flash-sale spike on one popular item, rather than falling over for the whole catalog.

Capacity estimate

Assume a mid-size marketplace with 5 million orders/day. Average order QPS ≈ 5,000,000 / 86,400 ≈ 58/sec. A flash sale on a popular category can push this to roughly 20x average momentarily, ≈ 1,160/sec.

Catalog: 50 million SKUs, averaging 3 warehouse-locations each for stock-keeping purposes, gives 150 million inventory rows at roughly 100 bytes/row ≈ 15GB total — small, and easy to keep entirely in a well-indexed relational table or an in-memory-cached layer in front of one.

Cart writes: assume 20 million active carts/day, each updated about 4 times (add, remove, change quantity) — 80 million cart-writes/day ≈ 926/sec average. These are cheap, ephemeral writes, well suited to a fast key-value store rather than the order database.

Order storage: an order record with line items is roughly 2KB. 5,000,000 × 2KB ≈ 10GB/day, about 3.65TB/year — this one has to be kept close to forever for returns, disputes, and tax records.

API design

POST   /cart/items                     {sku, qty}
POST   /checkout/reserve               {cartId} -> {reservationId, expiresAt}
POST   /checkout/confirm  -- Idempotency-Key
     body: {reservationId, paymentToken}         -> {orderId, status}
POST   /orders/{id}/cancel                       -> refund + restock
GET    /catalog/{sku}/availability               -> {status, qty}

High-level design

Checkout is an orchestrated saga — reserve stock, charge payment, confirm the order — with automatic cleanup for anything abandoned mid-flow.

Deep dive

1) Reserve-then-confirm, never decrement-then-hope. A checkout puts a short-lived hold on stock (minutes, not seconds) using a conditional decrement — the same pattern as the seat-hold in the Ticket Booking problem in Ch.19, but spread across millions of SKUs instead of concentrated on one event's seats, so contention is normally per-item, not global. The reservation only becomes permanent once payment succeeds; an abandoned reservation expires and a reaper process returns the stock automatically.

2) Never charge before the reservation succeeds. Checkout is a saga (Ch.13): reserve stock, then charge, then confirm the order — in that order, with compensating actions if any step fails (release the reservation if payment fails; refund and restock if confirmation fails after a successful charge). Charging first and reserving second would routinely charge customers for items that turn out to be unavailable.

3) A single SKU going viral turns "sharded catalog" back into "one hot row," instantly. Sharding 50 million SKUs across many databases solves normal-day contention, but one product trending platform-wide concentrates all its write traffic on one row regardless of sharding — this is exactly the hot-row problem Ch.19's ticket booking solves with a fast-reject lock plus admission control in front of the database. Reuse that pattern here rather than reinventing it; don't try to shard your way out of a single hot key.

Trade-offs

At 10x scale, a single viral SKU during a flash sale becomes the bottleneck regardless of how well the rest of the catalog is sharded, exactly as in Ch.19's ticket booking. The trade-off is the same: add admission control (a waiting room or queue) in front of that one hot item, which slows down the perceived instant-gratification checkout experience for most shoppers in exchange for keeping the database from falling over.

Say this

"I'd model checkout as a saga with reserve, charge, and confirm as separate steps with their own compensating actions, rather than one big transaction — inventory and payment are two different systems of record, and no database transaction can span both, so the ordering and the rollback logic have to be explicit."

Final design

One picture: a checkout orchestrator runs reserve-stock, charge-payment, confirm-order as a saga with compensations at every step. Inventory lives in a database sharded by SKU with a conditional decrement guarding every reservation; a reaper reclaims anything abandoned. A hot SKU gets the same fast-reject-lock-plus-admission-control treatment as a hot event's seat map.

EM-level follow-up

The reservation TTL (how long a hold lasts before releasing) is a cross-team contract between checkout and the warehouse/fulfillment team — shorten it to reduce phantom holds during a sale and you risk legitimate slow checkouts losing their cart; lengthen it and a flash sale's stock looks unavailable longer than it should. On build-vs-buy, checkout almost always integrates an existing payment gateway rather than building card-network relationships in-house — that's a separate, heavily regulated product on its own.

Design an Ad Exchange / Real-Time Bidding System

Problem framing

Every time a person opens an app or loads a page with an ad slot, an ad exchange runs a live auction among dozens of advertisers in well under 150 milliseconds, picks a winner, and returns an ad — before the page has even finished loading. This is real-time bidding (RTB): not a batch job, not a queue that can lag, a hard-deadline auction that happens billions of times a day, following the OpenRTB industry protocol that lets publishers and advertisers speak the same auction language.

Clarifying questions

  • First-price or second-price auction? — in a second-price auction the winner pays just above the second-highest bid, not their own bid; this changes the pricing engine's logic and needs every bid held until the auction closes.
  • What's the hard timeout per bidder, and what happens if a demand-side platform (DSP, an advertiser's bidding system) doesn't respond in time? — a slow bidder must be treated as "no bid," never allowed to hold up the whole auction.
  • How many bidders can a single auction fan out to? — this directly sets outbound request volume, which is a multiple of inbound ad-request volume.
  • Server-side auction, or client-side ("header") bidding where the browser itself calls multiple ad networks? — this changes where the fan-out and timeout logic actually lives.
  • Does a DSP need real-time budget pacing (spend a daily budget evenly, not all in the first hour)? — pacing needs a fast, approximate shared counter checked before every bid, not a strict global lock.

Requirements

Functional requirements:

  • Receive a bid request from a publisher for an ad impression.
  • Fan out the request to eligible DSPs.
  • Collect bids within a strict deadline, run the auction, and pick a winner.
  • Return the winning ad's markup (the actual creative/HTML to render) to the publisher.
  • Log every auction outcome for billing and reporting.

Non-functional requirements:

  • End-to-end p99 latency under roughly 100-150ms — a slow ad auction is a slow page load, and publishers will drop a slow exchange.
  • A non-responding or slow bidder must be dropped, never waited for past its timeout.
  • No double-billing, and never serve an ad from a bidder who didn't actually win the auction.
  • Must sustain massive fan-out QPS with graceful degradation under load, not a hard failure.
  • Per-campaign budgets must not be wildly overspent even under highly concurrent bidding.

Capacity estimate

Assume the exchange handles roughly 1 million ad requests/sec at global peak — large real-world exchanges run at this order of magnitude. If each auction fans out to about 20 eligible DSPs, that's 20 million outbound bid-requests/sec — an order of magnitude more traffic than the inbound request rate, which is the first thing that makes this system expensive.

With a roughly 100ms total auction budget, the number of auctions in flight at any instant is approximately requests/sec × latency = 1,000,000 × 0.1s ≈ 100,000 concurrent auction contexts held in memory across the fleet at once.

Logging: assume every auction produces one compact outcome record (winner, clearing price, bid count) at roughly 100 bytes. 1,000,000/sec × 100 bytes ≈ 100MB/sec, or 1,000,000 × 86,400 ≈ 86.4 billion auctions/day ≈ roughly 8.6TB/day of outcome logs — enough that this needs Kafka-scale ingestion (Ch.14), not a database write per event. Full bid-level debug logs, if kept at all, are normally sampled down to a small fraction of traffic rather than stored in full.

     body: {imp: [...], device, user, timeoutMs}
     -> {seatbid: [{bid: [{price, adMarkup}]}]}
-- internal fan-out call, per DSP, with a strict per-call timeout:

High-level design

A regional edge terminates the publisher's request; an orchestrator fans out to bidders in parallel with a strict per-bidder timeout well inside the total budget, then a pricing engine picks and prices the winner.

Deep dive

1) Fan-out under a hard deadline is the single hardest part of this problem. The orchestrator calls roughly 20 DSPs in parallel, each with a per-bidder timeout set well inside the total auction budget — for example a 60ms bidder timeout inside a 100ms total budget, leaving headroom for network overhead and the pricing step. Any DSP that hasn't responded by its timeout is simply excluded from that auction, treated exactly as "no bid." This is the timeout and circuit-breaker pattern from Ch.15, applied at a scale and a deadline (tens of milliseconds) far tighter than a typical microservice call.

2) Second-price clearing needs every bid held in memory until the auction closes, not settled incrementally. The winner pays just above the second-highest bid, so the pricing engine cannot decide anything until every bidder has either responded or timed out. Contrast this with the Live Auction/Bidding problem in Ch.18, which resolves over seconds to minutes with a single running highest bid visible to everyone — RTB is the same "who's winning" question compressed into under 100ms with no room for a client round-trip; the entire auction happens server-side, invisibly, before the page finishes rendering.

3) Budget pacing needs an approximate counter, not a synchronous global check. Checking a DSP's exact remaining daily budget against a strongly consistent counter before every single bid would add a blocking round trip to every one of 20 million bid requests/sec. Instead, pacing uses a fast, slightly-stale shared counter — the same write-behind approximate-counter idea used for like counts in Ch.17 — accepting a small, bounded amount of overspend risk in exchange for not serializing every bid against one global number.

Trade-offs

At 10x scale (10 million ad requests/sec), naively calling every eligible DSP on every auction multiplies to roughly 200 million outbound calls/sec, which is unsustainable regardless of how much compute is thrown at it. The fix is bidder pre-filtering — skip DSPs whose historical match rate on this kind of inventory or user is near zero — trading a small amount of bid recall (a DSP that might rarely have won anyway) for a large cut in fan-out volume.

Say this

"A slow bidder has to be dropped, not waited for — I'd set each DSP's timeout well inside the total auction budget and treat a timeout exactly like a non-bid, because letting one slow demand partner hold up the auction means every publisher on the exchange pays for that one partner's latency."

Final design

One picture: an edge PoP terminates the publisher's request and hands it to an orchestrator that fans out to eligible DSPs in parallel, each with a strict, deadline-aware timeout. A pricing engine waits for that fan-out to close, computes the second-price clearing price, and returns the winning markup — all within roughly 100ms. Win/loss events stream into a Kafka-scale pipeline for billing and reporting, decoupled entirely from the auction's own latency budget.

EM-level follow-up

Infrastructure cost per request gets scrutinized harder here than in almost any other system in this bank, because the exchange runs a full auction on nearly every ad-supported page load on the internet — a few extra milliseconds of unnecessary compute per auction adds up at this volume. There's also a real privacy/regulatory rollout angle: user-targeting data used in a bid request cannot legally cross into some regions without consent (for example under GDPR), which constrains where bidder fan-out can even happen. Many companies choose to buy exchange connectivity through an existing bidding platform rather than build direct integrations with every publisher and DSP themselves.

Design a Web Search Engine

Problem framing

Strip away the ranking magic and a search engine is two very different systems glued together: a slow, batch pipeline that reads a huge amount of the web and turns it into a lookup structure called an inverted index (a map from each word to the list of documents that contain it), and a fast, read-heavy serving system that turns a short query into a ranked list of results in well under a second. The two halves have almost opposite requirements — one is throughput-optimized and can lag by hours, the other is latency-optimized and must never lag by more than a few hundred milliseconds.

Clarifying questions

  • Are we building general web search, or search over a fixed, much smaller corpus? — general web search has to handle an open-ended, adversarial, constantly-changing corpus (spam, duplicate content, link manipulation); a closed corpus, like the one this chapter's web crawler problem in Ch.20 might feed, is a much smaller and calmer version of the same problem.
  • How fresh do results need to be? — a page about a historical topic can be re-crawled monthly; breaking news needs a much shorter path from "published" to "searchable," which usually means a separate fast-path index on top of the main one.
  • Do we need personalization (search history, location), or is this the same ranked list for everyone who types the same query? — personalization adds a per-user signal into ranking and makes result caching much less effective, since a cached page of results can no longer be shared across users.
  • What's the acceptable end-to-end query latency? — this single number decides how many index shards a query is allowed to fan out to and how expensive the ranking model is allowed to be.
  • Do we need query autocomplete as part of this, or is that a separate feature? — it's usually built as its own small, low-latency service (see Ch.16's typeahead primitive) rather than bolted onto the main query path.

Requirements

Functional: a user submits a text query and gets back a ranked list of relevant results, each with a title, URL, and a short snippet showing why it matched; the system supports basic query operators (phrase match, exclusion) and spelling correction; the corpus is built by continuously crawling and re-crawling pages (crawling itself is its own problem in Ch.20 — this problem assumes a crawler already exists and focuses on what happens after a page is fetched).

Non-functional: query latency in the low hundreds of milliseconds at the 99th percentile; extremely high read QPS with a read:write ratio that is enormous — writes to the index happen in scheduled batches, reads happen continuously; the index can be a little stale (minutes to hours behind the live web) without anyone noticing, so this system favors availability and read throughput over strict freshness; the serving path must survive the loss of any single index shard without going fully down (partial results are fine, a blank page is not).

Capacity estimate

Assume a mid-size general web search product: 500 million monthly active users, averaging 8 searches per active day for the roughly 60% of them who search daily, and an index covering 50 billion pages.

  -> { results: [{ url, title, snippet, score }], totalEstimate, tookMs }

High-level design

Two pipelines share one index. Offline: crawled pages get parsed, tokenized, and turned into postings lists that are written into index shards as new immutable segments. Online: a query gets broadcast to every shard (scatter-gather), each shard returns its best local candidates, and a ranking stage merges and reorders them before anything goes back to the user.

Deep dive

Document-partitioned shards, not term-partitioned. There are two ways to split an inverted index across machines: give each shard all the postings for a subset of terms ("dog" lives entirely on shard 3), or give each shard a subset of documents and let every shard hold a little of every term's postings list. Term-partitioning sounds appealing because a single-word query only has to hit one shard, but it fails in practice: a handful of terms are wildly more common than the rest, so those shards become permanently overloaded, and any multi-term query needs a cross-shard join to intersect postings lists, which is expensive. Real search engines document-partition: every query fans out to every shard, each shard independently intersects postings for all query terms among its own documents, and results merge at the end. This trades a bit of network fan-out for even load and no cross-shard joins — the same shape of trade-off as Elasticsearch's own document-partitioned sharding (Ch.11).

Two-stage ranking, because a full ML model can't run on billions of documents per query. The query service can't afford to run an expensive learned ranking model against every candidate document for every query — at tens of thousands of queries per second, that's not viable. The standard pattern is a cheap first stage (a term-frequency score like BM25, computed per shard, plus a precomputed link-authority score like PageRank that measures how many other important pages link to this one) that narrows billions of documents down to roughly the top 1,000 candidates, followed by an expensive second stage — a learned ranking model with dozens of features — that only has to score those 1,000. This funnel shape (cheap broad retrieval, then expensive narrow re-ranking) shows up again in this chapter's Recommendation System problem, for the same underlying reason.

Freshness without re-indexing the whole web. Rebuilding a 25-30 TB index from scratch is a batch job measured in hours; it can't be the path for a breaking-news page to become searchable. The fix is a small, separate "fresh" index segment that absorbs new and re-crawled pages continuously and gets merged into the main segments on a slower cycle — structurally similar to how an LSM-tree (Ch.9) accepts fast writes into a small in-memory layer and compacts them into larger, immutable layers later. A query checks both the fresh segment and the main index and merges results.

Trade-offs

At 10x query volume, scatter-gather is what breaks first, not the index storage — every query already touches every shard, so the query's latency is bounded by its single slowest shard, and at higher load, tail latency on individual shards gets worse (garbage collection pauses, a noisy neighbor process, a compaction running). The trade-off is between waiting for every shard (complete but slow, since one bad shard delays everyone) and a deadline-based cutoff that returns whatever shards answered in time (fast and always available, at the cost of occasionally missing a relevant result from a slow shard).

Say this

"I'd document-partition the index and accept that every query fans out to every shard, rather than term-partitioning to save fan-out — term-partitioning looks efficient on paper but concentrates load on whichever terms are popular that day, and it turns every multi-word query into a cross-shard postings intersection. Even load beats fewer network hops here."

Final design

One picture: crawled pages flow through an offline pipeline into a document-partitioned, replicated inverted index; a query fans out to every shard, gets cheaply scored candidates back, and a ranking service narrows those candidates with link authority and a learned model before the top 10 go back to the user — with a small, fast-refreshing index segment layered on top for freshness.

EM-level follow-up

Rollout: launch a new language or region as its own index and ranking configuration, not a global flag — tokenization, spelling correction, and ranking signals are all language-specific, so this is naturally a per-locale rollout rather than an all-or-nothing switch. Build vs. buy: very few companies should build general web search from scratch; most "search" features in an interview are actually asking you to design search over your own product's data, where Elasticsearch or a managed search service (Ch.11) covers the index and query layer and you only need to build ranking and relevance on top. Cross-team impact: ranking quality and infrastructure cost are in permanent tension — the ranking team wants more signals and bigger models, infra owns the per-query latency and compute budget those signals consume, and the two need a shared latency budget, not just a shared API.

Design a Recommendation System

Problem framing

A recommendation system's job is to answer one question, over and over, cheaply: out of everything in the catalog, what should this specific person see right now? Underneath the personalization, it's a narrowing problem — go from millions of items down to a handful, fast enough to sit on a page-load path, using signals (past clicks, purchases, watches) that arrive continuously.

Clarifying questions

  • What's the catalog size and how often does it change? — a streaming service with 10,000 titles and a marketplace with 500 million SKUs need very different candidate-generation strategies.
  • Where do recommendations show up — one homepage row, or many contexts (homepage, "similar items," post-purchase email, search re-ranking)? — each surface can want a different balance of relevance, novelty, and business rules (don't show out-of-stock items, don't repeat what was already shown).
  • How do we handle a brand-new user or a brand-new item with no interaction history? — this "cold start" gap decides whether we need a separate fallback path alongside the main personalized model.
  • How fresh does personalization need to be — should a click 30 seconds ago change what's shown next? — near-real-time personalization needs an online feature pipeline in addition to a batch-trained model; if next-day freshness is fine, a much simpler nightly batch job works.
  • Is there a business objective beyond relevance — margin, inventory clearance, diversity of what's shown? — this decides whether ranking is pure predicted-engagement or a blend with explicit business weighting.

Requirements

Functional: given a user and a surface (homepage, item-detail page, etc.), return a ranked list of items personalized to that user; degrade gracefully to a reasonable non-personalized list for new users or new items; incorporate recent behavior (a user who just watched three thrillers should see that reflected soon, not next week); support "more like this" for a given item.

Non-functional: recommendation calls sit on a page-load path, so end-to-end latency needs to be well under 100ms at p99; the system must handle a very high read (recommendation request) rate against a catalog and set of user profiles that are both large; model training is compute-heavy but can run offline on a schedule; the online serving path must never do a full-catalog scan or a full-catalog model inference per request — it must narrow the catalog first.

Capacity estimate

Assume a large streaming/e-commerce platform: 200 million monthly active users, a catalog of 10 million items, and a homepage that renders 5 personalized rows per visit.

  200M users x ~50 interactions/day (views, clicks, purchases, ratings)
    = 10B events/day
  At ~200 bytes/event (userId, itemId, type, timestamp, context)
    = 2 TB/day of raw interaction data flowing through the event stream

Recommendation request load:
  200M MAU, ~120M daily active, each opening the app ~3 times/day
    = 360M home-page renders/day
  Average QPS = 360M / 86,400s ~= 4,170/sec
  Peak QPS (3x for evening peak) ~= 12,500/sec
  Each render needs ~5 rows x ~20 items = 100 scored item slots,
  so the ranking stage handles ~1.25M item-scoring operations/sec at peak
  -- this is why ranking only runs on a pre-narrowed candidate set, not
  the full 10M-item catalog, per request

Embedding storage (item and user vectors from the trained model):
  10M items x 128-dim float32 embedding (512 bytes) ~= 5.1 GB -> fits in
    memory on a handful of nodes, replicated for the ANN index (Deep dive)
  200M users x 512 bytes ~= 102 GB -> sharded across an in-memory
    user-embedding store, not kept on a single node

The number that sizes the online path isn't total users — it's the 12,500 requests/sec at peak, each needing sub-100ms narrowing from 10 million items to about 100 scored slots. That narrowing step, not the model training, is the hard latency problem.

API design

GET /recommendations?userId={id}&surface=home&limit=20
  -> { items: [{ itemId, score, reason }] }

GET /similar-items?itemId={id}&limit=20
  -> { items: [{ itemId, score }] }

POST /events                     { userId, itemId, eventType, ts, context }
  (fire-and-forget interaction logging, feeds the training pipeline)

High-level design

An offline pipeline turns the interaction stream into item and user embeddings (dense vectors that place similar items/users near each other in vector space) via a model like matrix factorization or a two-tower neural network. The online path takes a user, looks up nearby items in that vector space (candidate retrieval), and re-ranks the small candidate set with a heavier model before returning results.

Deep dive

Candidate retrieval has to be approximate, not exact. Finding the true nearest items to a user's embedding among 10 million item vectors, by computing an exact distance to every single one, is too slow to do per request. The standard fix is an approximate nearest neighbor (ANN) index — a structure like HNSW (hierarchical navigable small world) or an IVF (inverted file) index that organizes vectors so a lookup only has to compare against a small fraction of them, trading a small, tunable amount of recall (occasionally missing the true best match) for a lookup that's fast enough to run inside the per-request latency budget.

The retrieval-then-rank funnel exists for the same reason as the search engine's two-stage ranking. ANN retrieval is cheap but produces a rough candidate set (maybe 500-1,000 items); it isn't precise enough to hand straight to the user. A second, heavier model — one that can afford dozens of features per candidate because it only runs on hundreds of items, not millions — does the actual ranking. This is the exact same shape as the two-stage retrieval-then-rerank pattern in this chapter's Search Engine problem: cheap broad narrowing, then expensive precise ordering on the survivors.

Cold start needs an explicit fallback, not a hope that the model handles it. A brand-new user has no embedding worth trusting yet, and a brand-new item has no interaction history to learn from. The practical answer is a separate path: new users get a popularity-based or onboarding-survey-based list until enough interactions accumulate to trust a personalized embedding; new items get boosted into candidate sets using content features (category, description, metadata) rather than collaborative signal, often via a multi-armed-bandit-style explore/exploit policy that deliberately shows a new item to a small slice of traffic to gather the signal needed to rank it properly later.

Trade-offs

At 10x traffic, the online feature store — the piece that supplies "what has this user done in the last few minutes" to the re-ranking model — is what breaks first, not the ANN index. ANN lookups scale by adding read replicas of a mostly-static index; per-request feature freshness needs low-latency reads against constantly-updating per-user state, which is a much harder scaling problem. The trade-off is real-time features (better relevance, but a stateful system that's expensive to scale and can add tens of milliseconds per request) versus features refreshed every few minutes in batch (cheaper and simpler, at the cost of feeling less "alive" to the user).

Say this

"I'd split this into cheap candidate retrieval over an approximate nearest-neighbor index, followed by an expensive re-ranking model that only scores the few hundred survivors — running the heavy model against the whole catalog per request isn't a latency problem you can tune your way out of, it's the wrong shape of computation for the request path."

Final design

One picture: an offline pipeline turns a continuous interaction stream into item and user embeddings; each request retrieves a rough candidate set from an approximate nearest-neighbor index built on those embeddings, re-ranks that small set with a model that blends predicted engagement with business rules and recent activity, and falls back to popularity or bandit-driven exploration whenever the user or item is too new to trust personalization.

EM-level follow-up

Rollout: a new ranking model never fully replaces the old one on day one — it ships behind an experiment (see this chapter's A/B-testing platform problem) to a small traffic slice, with engagement and revenue metrics compared before a gradual ramp. Build vs. buy: a managed vector database (Pinecone, or a managed OpenSearch/Elasticsearch vector index) is usually the right early call over self-hosting FAISS or building an ANN index from scratch — the crossover to building it yourself only comes once query volume or embedding-update frequency makes the per-query pricing of a managed service more expensive than a dedicated team. Cross-team impact: recommendation quality, legal/trust-and-safety (filter bubbles, sensitive-category suppression), and infra cost all pull on the same knobs — candidate-set size and model complexity — so this usually needs a shared review, not just a ranking-team decision.

Design a News Aggregator

Problem framing

A news aggregator doesn't write anything — it pulls articles from thousands of independent publishers, figures out which ones are covering the same real-world event, and presents one clean, ranked feed instead of thousands of overlapping copies of the same story. The two hard parts are recognizing duplicates fast enough to matter and deciding what's actually important right now.

Clarifying questions

  • How many sources, and are they pull (we poll their RSS feed) or push (they call our webhook)? — this decides the shape of the ingestion fleet and how quickly a new article can even arrive.
  • Do we need to group articles about the same story into one "cluster," or just list every article individually? — clustering (deduplication across sources) is the feature that separates a real aggregator from a plain RSS reader, and it's the hardest part of the system.
  • How personalized is the feed — global trending news for everyone, or per-user topic and source preferences? — personalization changes whether we can serve one cached ranked list to everyone or need per-user re-ranking on every request.
  • What's the acceptable delay from "publisher posts a story" to "it shows up in the feed"? — breaking news usually has a tighter target (a few minutes) than routine coverage, and that target is what the ingestion and clustering pipeline has to be built around.
  • Do we need full-text search over the archive, or only a ranked live feed? — search adds an indexing requirement (see this chapter's Search Engine problem) on top of the feed-serving requirement.

Requirements

Functional: continuously ingest articles from a large number of publisher sources; extract clean title/body/image/canonical-URL from raw HTML or feed XML; detect and cluster near-duplicate articles covering the same event; rank clusters by a mix of recency, source authority, and engagement; serve a personalized, paginated feed; support keyword search across the aggregated corpus.

Non-functional: breaking news should be discoverable within a few minutes of publication; the read path is enormously read-heavy relative to writes (people check the news far more often than publishers publish) and must be fast and highly available; clustering can lag by a minute or two without anyone noticing, but an article must never sit un-clustered indefinitely; historical articles need to stay browsable for some retention window, not forever at full query performance.

High-level design

Fetched articles flow through extraction, then a clustering stage that groups them with existing stories about the same event, then ranking. The read path serves personalized feeds from a pre-ranked, pre-clustered set rather than doing any of that work per request.

Deep dive

Near-duplicate detection can't be pairwise comparison. Comparing every new article against every existing article to see if they cover the same story doesn't scale — the earlier estimate showed 250 billion comparisons a day at this volume. The standard fix is locality-sensitive hashing (LSH): break each article's text into overlapping chunks (shingles), compute a compact fingerprint (a MinHash signature) that has the property that similar documents produce similar fingerprints, and bucket articles by fingerprint. A new article only gets compared against the small number of other articles that landed in the same bucket, turning an all-pairs problem into a handful of cheap comparisons per article. It's the same core idea as the near-duplicate-page filtering a web crawler needs (Ch.20), applied to news text instead of raw web pages.

Source authority needs a curated trust signal, not a link graph. A general search engine derives page authority from the web's link structure (this chapter's Search Engine problem, PageRank-style). A news aggregator doesn't have that luxury on a useful timescale — wire services (AP, Reuters) and major outlets need to be recognized as authoritative immediately, not after enough other pages happen to link to them. So ranking uses an explicitly maintained source-trust score (updated occasionally, based on editorial criteria and historical accuracy/engagement) rather than trying to infer authority live from link structure.

Personalize at read time, not by pre-computing a feed per user. With tens of millions of users, pre-computing and storing a fully personalized ranked feed for every single user (fan-out on write, the same pattern Ch.17's Twitter/X design uses for celebrity fan-out) is wasteful here, because the underlying set of ranked story clusters is shared by everyone — what differs per user is a thin layer of topic and source weighting. The practical design computes one well-ranked global (or per-topic) list, cached and shared across all readers, and applies a cheap per-user re-ranking pass (boost followed topics, demote muted sources) at request time. This keeps the expensive ranking work shared instead of duplicated per user.

Trade-offs

At 10x source count, the clustering stage is what breaks first, not ingestion throughput. During a major breaking-news event, hundreds of sources publish about the same thing within minutes, and the LSH bucketing has to decide, in real time, whether a fast-arriving wave of similar-but-not- identical articles is one story or several. The trade-off: a tighter similarity threshold avoids merging genuinely different stories but fragments one breaking story into several near-duplicate clusters that should be unified; a looser threshold unifies breaking news cleanly but risks merging unrelated articles that happen to share vocabulary.

Say this

"I'd use MinHash signatures and LSH bucketing for clustering instead of comparing every new article against the whole recent corpus — at this volume, pairwise comparison is a non-starter, and LSH gets us to only comparing against a small, likely-similar candidate set per article."

Final design

One picture: articles flow from polled or pushed sources through extraction into an LSH-based clustering stage that groups same-event coverage into story clusters; a ranking service scores clusters by recency, curated source trust, and engagement; the feed service serves a shared, cached, ranked list with a thin per-user re-ranking layer on top, and a search index sits alongside for full-text queries into the archive.

EM-level follow-up

Rollout: launch by language and region, not as one global switch — clustering thresholds, source-trust lists, and even what counts as "breaking" are language- and market-specific, so a new locale is closer to a new deployment than a config flag. Build vs. buy: many companies license a syndication/aggregation feed or a dedup API rather than negotiating direct feeds with tens of thousands of individual publishers — the publisher-relationship and licensing burden is often a bigger blocker than the engineering. Cross-team impact: this system has a legal and editorial dependency that pure infra problems don't — publisher licensing agreements and editorial trust policy shape the source list and ranking rules just as much as the engineering team does.

Design a Multi-Region Active-Active Platform

Problem framing

This is the problem an EM gets handed after a single regional outage takes the whole product down: make it so the platform survives losing an entire region, and give users in every region local latency, without falling back to a slow, manual failover. Stripped down, it's a data-ownership and replication problem — deciding who is allowed to write which piece of data, and how those writes reach every other region without becoming one giant distributed transaction.

Clarifying questions

  • Does every entity need to be writable from every region, or can most data have one "home region" that owns writes? — true multi-master (any region writes any row) needs conflict resolution for concurrent writes; single-writer-per-shard avoids that at the cost of higher latency for users temporarily away from their home region.
  • What's the target Recovery Point Objective (RPO — how much data, if any, can we afford to lose) and Recovery Time Objective (RTO — how fast do we have to be back up) for a full regional outage? — an RPO near zero for payment data and an RTO of minutes for the whole platform imply a much more expensive design than "best effort, restore from backup within an hour."
  • Which data actually needs active-active, versus active-passive with fast failover? — treating every dataset the same is usually the wrong call; profile reads might tolerate active-passive fine while payment writes might need true active-active.
  • How many regions, and are they close (tens of milliseconds apart) or far (hundreds of milliseconds, e.g. US-EU-APAC)? — this decides whether synchronous cross-region replication for any data is even physically viable.
  • What's the budget appetite — is doubling (or more) infrastructure cost for active-active acceptable, versus a cheaper active-passive posture with a slower failover? — this is as much a cost conversation as an engineering one.

Requirements

Functional: route each user's traffic to their nearest healthy region; reads and writes both succeed locally in the common case; if a region fails entirely, traffic reroutes to surviving regions and the ownership of that region's data fails over without manual intervention beyond approving the failover; data written in one region eventually becomes visible in every other region.

Non-functional: RPO close to zero for critical data (financial transactions, orders); RTO on the order of a few minutes for full regional failover, not hours; the design must define a clear behavior for concurrent conflicting writes to the same entity from two regions, rather than leaving it undefined; replication lag has to be observable and bounded, because "eventually visible" without a bound is not an operable SLA.

Capacity estimate

Assume a global SaaS platform with three regions (US, EU, APAC), 50 million daily active users split roughly 40/35/25% by region, and 200 million requests/day total.

Request load:
  200M requests/day -> average QPS = 200M / 86,400s ~= 2,315/sec globally
  Peak QPS (4x) ~= 9,260/sec, split roughly by the 40/35/25 regional mix
    -> US peak ~3,700/sec, EU peak ~3,240/sec, APAC peak ~2,320/sec

Write volume and replication fan-out:
  ~10% of requests are writes -> 20M writes/day
  Average write payload ~2KB (including replication metadata/versioning)
    = 40 GB/day of "new" data written across all regions
  Each region replicates its own writes to the other two -> with 3 regions
  that is 3 replication links total. The link count grows as roughly
  n(n-1)/2: 6 regions -> 15 links, 10 regions -> 45 links, which is the
  scaling problem in Deep dive

Failover budget:
  A target RTO of 5 minutes means health detection, traffic re-routing, and
  ownership handoff for the failed region's shards must complete, combined,
  inside that 5-minute window -- which is why health detection can't rely
  on slow DNS TTL expiry alone (see Deep dive)

API design

This system is mostly internal plumbing rather than a user-facing API, but the contracts that matter are:

-- Application traffic (routed transparently by the global traffic manager):
GET/POST /api/... (any product API)   -- routed to nearest healthy region

-- Control plane, used by SRE/platform tooling:
GET  /regions/{id}/health              -> { status, replicationLagMs }
POST /regions/{id}/failover            -> initiates ownership handoff for
                                           that region's home shards
GET  /replication/lag?fromRegion={id}&toRegion={id}

High-level design

Users get routed to their nearest healthy region by a global traffic manager. Each region owns writes for a subset of shards (its "home shards") and asynchronously replicates those writes to the other regions, which keep local read replicas. A control plane watches region health and can reassign shard ownership if a region goes down.

Deep dive

Single-writer-per-shard beats full multi-master for most data. The simplest correct model is: every piece of data has a home region that owns writes to it; other regions hold asynchronously replicated read copies. A user's writes almost always go to their home region, which is fast and needs no conflict resolution. The alternative — letting any region write any row (true multi-master) — needs a conflict-resolution strategy for the case where two regions write the same row before either replication catches up: last-write-wins (simple, but silently loses one write), CRDTs (conflict-free replicated data types, which merge concurrent updates deterministically for specific data shapes like counters or sets), or vector clocks to at least detect the conflict (Ch.13). Most systems default to single-writer-per-shard and reserve true multi-master for the small set of data types (like a shopping cart or a counter) where CRDTs make it tractable.

Failover has to be detected by quorum, not by the failing region reporting itself down. A region that's failing is often the worst-positioned system to reliably say "I'm down" — it might be partially up, flapping, or partitioned from the very health-check system trying to reach it. Real designs use a small quorum of external health-checkers (Ch.13's quorum idea) spread across regions, and require agreement before declaring a region dead and reassigning its shard ownership — a decision that itself needs a consensus protocol like Raft (Ch.12) to avoid two regions simultaneously believing they now own the same shard, a split-brain that would let both accept writes for the same data.

Read-your-own-writes needs an explicit answer, not a hope. If a user writes in their home region and their very next request gets routed to a different region (they traveled, or their home region had a blip), do they see their own write? Two honest options: sticky routing that keeps a user pinned to their home region for a session-length window (simple, but weakens the "always nearest region" latency promise), or a consistency token the client carries that forces the serving region to wait until its replica has caught up to that token before answering (Ch.12's session consistency) — slower on the rare cross-region case, but never wrong.

Trade-offs

At 10x the region count (say, 10+ regions for tighter global latency coverage), full-mesh replication is what breaks first — the number of replication links grows as roughly n(n-1)/2, so 3 regions need 3 links but 10 regions need 45. The trade-off is mesh (every region replicates directly to every other — lower replication latency, but a management and connection burden that grows quadratically) versus hub-and-spoke (every region replicates through a small number of hub regions — far fewer links, but replication latency goes up by a hop and the hub becomes a scaling and failure-domain concern of its own).

Say this

"I'd give each shard a single home region that owns its writes, with async replication to the other regions for local reads, rather than true multi-master everywhere — multi-master only pays for itself on the small slice of data, like counters and carts, where a CRDT gives us a real conflict-free merge; for everything else, single-writer avoids inventing a conflict-resolution policy we'd have to defend in an incident review."

Final design

One picture: a global traffic manager routes each user to their nearest region; each region owns writes for its home shards and asynchronously replicates them to the others in a mesh; a quorum-based, Raft-backed control plane detects regional failure and reassigns shard ownership, while a small set of specific data types (carts, counters) use CRDTs to support true multi-master where it actually pays off.

EM-level follow-up

Rollout: this is never a single cutover — start active-passive with automated (not manual) failover, prove the health-detection and traffic-reroute machinery under real incidents, then move progressively riskier data types to true active-write-anywhere, saving payments and orders for last. Build vs. buy: a globally-distributed database like Spanner or CockroachDB (Ch.11) absorbs a large slice of this problem — it handles cross-region consensus and replication for you — at a real cost premium and with real latency trade-offs for synchronous writes, which is worth pricing against building the replication and failover layer yourselves before committing either way. Cross-team impact: this is usually SRE/platform-owned infrastructure, but every product team's data model has to declare a home-region policy and handle eventual consistency in their own reads — it is an org-wide migration with a steering group, not a single team's project.

Design a Feature-Flag System

Problem framing

A feature-flag system lets engineers turn a piece of code on or off, or roll it out to a percentage of users, without shipping a new deploy. Underneath the product UI, it's a configuration-distribution problem with an unusual constraint: the thing being distributed — which features are on, for which users — has to be readable by every service, on every request, fast enough that checking a flag never shows up as a bottleneck, and it has to work even when the flag system itself is having a bad day, because it's often the tool used to stop an incident.

Clarifying questions

  • What kinds of flags do we need — simple on/off, percentage rollout, or full multivariate targeting by user attributes? — this decides how much logic the evaluation step actually has to run, which matters because evaluation happens on the hot path.
  • How fast does a flag change need to propagate? — a routine rollout tolerating a minute of propagation delay is a very different distribution problem than a kill-switch that has to reach every service within a few seconds during an active incident.
  • What happens if the flag service itself is unreachable — does the requesting service fail open (feature on), fail closed (feature off), or use the last-known configuration? — this single decision determines the whole architecture, because it rules out any design where evaluation requires a live network call.
  • Who manages flag lifecycle — is there a process for archiving old flags, or will this accumulate forever? — an unbounded, ever-growing flag count turns this from a distribution problem into a governance problem too.
  • Do we need this to double as an experimentation (A/B testing) platform, or is that a separate system that happens to reuse flag targeting? — see this chapter's A/B-testing platform problem for the analysis side; a flag system usually only needs to emit clean evaluation events for that system to consume.

Requirements

Functional: engineers create and update flags with targeting rules (boolean, percentage rollout, user-attribute rules, allow/deny lists) through an admin interface; every service's SDK can evaluate any flag for a given user/context; a flag change, especially a kill-switch flip, must reach running services quickly; evaluations are logged for audit and for downstream experiment analysis.

Non-functional: flag evaluation must be sub-millisecond and must never require a network call in the request path; the flag-distribution system must not be a new single point of failure — every service using it must degrade to a safe, cached configuration if the control plane is unreachable; updates need to propagate to all connected services within seconds, not minutes; the system must handle very high evaluation volume, potentially every request of every service, which the design must satisfy without the control plane ever seeing that volume directly.

Capacity estimate

Assume a company running 5,000 service instances that together handle 500,000 requests/sec, with each request checking roughly 5 flags.

Evaluation volume (the number that would break a naive design):
  500,000 req/sec x 5 flags/request = 2,500,000 evaluations/sec
  If every evaluation were a network call to a central flag service, that
  is 2.5M RPCs/sec against one system -- both too slow (network round trip
  on every flag check) and a brand-new single point of failure for every
  request in the company. This is why evaluation has to happen in-process
  inside each service's SDK, against a locally cached ruleset (Deep dive).

Config size (what actually needs distributing):
  10,000 flags company-wide, each with a modest targeting-rule payload
  (~500 bytes average, including percentage-rollout and attribute rules)
    = ~5 MB total configuration -- small enough to hold in memory in every
    single service instance and re-fetch or re-stream in full within seconds

Change/propagation load:
  A few hundred flag changes/day company-wide (low control-plane write QPS,
  well under 1/sec on average) but each single change must fan out to all
  5,000 connected service instances within a few seconds for the
  kill-switch use case -> the hard problem is fan-out breadth and speed,
  not control-plane write throughput

API design

-- Admin/control plane:
POST  /flags                      { key, type, defaultVariant }
PATCH /flags/{key}                { targetingRules, rolloutPercent }
GET   /flags/{key}

-- SDK-facing distribution (long-lived stream, not request/response):
GET /sdk/stream?envKey={key}      -- server-sent events / WebSocket,
                                      pushes full snapshot then diffs

-- In-process SDK call (no network, runs against local cache):
isEnabled(flagKey, context) -> boolean | variant

High-level design

Flag changes go through a strongly consistent control plane, get turned into a versioned config snapshot, and fan out through a streaming relay tier to every connected SDK, which caches the whole ruleset locally and evaluates flags with zero network calls per request.

Deep dive

Evaluation has to be a local, in-process operation, not an RPC. At 2.5 million evaluations per second, a network call per flag check is both too slow (network round trips dominate a sub-millisecond budget) and turns the flag service into a dependency of literally every request in the company. The fix is a full-mirror model: each SDK pulls the entire ruleset once (a few megabytes, per the capacity estimate), keeps it in memory, and evaluates every flag check against that local copy. This is structurally different from a typical cache-aside setup (Ch.4) — it's a push-based full mirror, closer to how a service-discovery client (Ch.15) keeps a local copy of the service registry instead of asking a central directory on every call.

Fast global propagation without a thundering herd requires push, not poll-on-demand. A kill-switch has to reach thousands of SDK instances within seconds. If every SDK reacted to "something might have changed" by immediately re-polling the control plane, that is a self-inflicted thundering herd (Ch.4) against the one system everyone is depending on during an incident. The real design uses long-lived streaming connections (SSE or WebSocket) from every SDK to a stateless relay tier that subscribes once to a pub/sub topic; a single flag change publishes once and the relay tier fans it out over connections it already holds open, so the origin config service only ever sees one publish event, never a stampede of pulls.

Percentage rollouts need deterministic, sticky bucketing. "Roll out to 10% of users" only works if the same user consistently lands in the same bucket across every evaluation, every service, and every SDK restart — otherwise a user flickers between the old and new experience, which defeats the entire point of a gradual, observable rollout. The standard technique is to hash a stable identifier together with the flag key (so different flags don't correlate with each other) and take the hash modulo 100 as the bucket — the same deterministic-hashing idea behind consistent hashing (Ch.5), applied to bucket assignment instead of server assignment.

Trade-offs

At 10x the flag count (tens of thousands of flags accumulated over years without cleanup), the distribution pipe was never really the bottleneck — a bigger config snapshot is still only a few tens of megabytes, cheap to hold and stream. What actually degrades is per-request evaluation cost: walking a longer list of targeting rules on every one of millions of evaluations per second becomes measurable CPU in every service's hot path. The trade-off is flag lifecycle governance (forcing expiration/archival of stale flags, which is an org-process fix, not a code fix) versus scaling the evaluation engine's data structure (indexing rules by flag key so evaluation cost stays flat regardless of total flag count) — most mature systems end up needing both.

Say this

"I'd push the full ruleset to every SDK and evaluate locally, in-process, rather than centralizing evaluation behind an API — at 2.5 million evaluations a second, a network call per check is both too slow for the latency budget and a single point of failure for every request in the company. The control plane's job is distributing config quickly, not answering evaluation queries."

Final design

One picture: a strongly-consistent control plane manages flag definitions; every change becomes a versioned snapshot that streams through a pub/sub-backed relay tier to thousands of long-lived SDK connections; each SDK holds the full ruleset in memory, evaluates flags with zero network calls per request using deterministic sticky bucketing, and persists a last-known-good snapshot to disk so a fresh process boot still gets sane behavior even if the control plane is down.

EM-level follow-up

Rollout: the flag system itself gets dogfooded cautiously — it becomes a dependency of nearly everything else, so it launches on low-risk internal services first, and its own failure mode must always be "serve last-known-good," never "feature disabled" or "service crashes," because that failure mode is what an on-call engineer is relying on during an incident. Build vs. buy: a managed provider (LaunchDarkly, Split.io) is the right default until either per-seat/per-evaluation pricing stops making sense at company scale, or data-residency/compliance requirements force self-hosting — most companies should not build this from scratch. Cross-team impact: once every team relies on it to kill a broken feature during an incident, the flag system's own reliability becomes as operationally important as the deploy pipeline, and its on-call rotation and SLOs need to reflect that, not be an afterthought owned by whichever team built it first.

Design a CI/CD Deployment Platform

Problem framing

A CI/CD platform turns a code push into a running, verified deployment without anyone SSHing into a server by hand. "CI" (continuous integration) means every commit gets built and tested automatically. "CD" (continuous delivery/deployment) means the built artifact gets promoted through environments — dev, staging, production — with safety checks along the way. Think Jenkins, GitHub Actions, GitLab CI, or Netflix's Spinnaker: the pipeline factory that sits between "git push" and "code serving real traffic." A platform team at a company with thousands of engineers builds this so every product team doesn't reinvent their own deploy scripts.

Clarifying questions

  • Continuous delivery (a human approves the push to production) or continuous deployment (fully automatic, no human in the loop)? — this decides whether the pipeline's state machine needs an explicit approval-gate step and who counts as an approver.
  • How many services and how many builds per day? — decides how big the build-worker fleet needs to be and whether a shared build cache is worth the investment.
  • One blessed language/build system, or many (Java, Node, Go, Python all at once)? — a multi-language platform needs a plugin-style executor abstraction, not one hardcoded build script.
  • Which deployment strategies must we support — rolling restart, blue-green, canary? — canary (shifting a small percentage of traffic to the new version and watching its health before going further) needs traffic-shifting and automated rollback, which is a much bigger scope than a plain rolling restart.
  • Do untrusted contributors (fork pull requests from outside the company) trigger builds, or only internal engineers? — decides whether build workers must be sandboxed against arbitrary code running as a security boundary, not just a resource boundary.

Requirements

Functional requirements:

  • Trigger a build on push, pull request, tag, a schedule, or a manual click.
  • Run a defined pipeline: checkout code, build, run tests, package an artifact, then deploy to each environment in order.
  • Store build artifacts and logs, and let anyone look them up later.
  • Deploy with a chosen strategy (rolling, blue-green, or canary), and roll back to a previous known-good version on demand.
  • Gate promotion between environments with human approvals and/or automated health checks.
  • Show pipeline status, deployment history, and exactly who deployed what, and when.

Non-functional requirements:

  • Every step must be safely retryable — a flaky test runner or a network blip must not corrupt pipeline state.
  • One team's huge, noisy build must not starve another team's small, urgent hotfix build.
  • Feedback needs to be fast — a typical build-and-test run should finish in minutes, or engineers stop trusting the pipeline and start bypassing it.
  • Every production deployment must be traceable to a specific commit, an approver (if any), and a timestamp — this is what an incident review or a compliance audit needs.
  • Rollback has to be fast — seconds to a couple of minutes — because a bad production deploy is actively hurting users the whole time it's rolling out.

Capacity estimate

Assume 2,000 engineers across roughly 1,500 services. If each engineer pushes an average of 8 commits/day across all their branches and pull requests, that's 2,000 × 8 = 16,000 builds/day. Spread across a 10-hour working day (36,000 seconds), that's 16,000 / 36,000 ≈ one new build triggered every 2 seconds on average — with sharp bursts right before common push times like end of day or a "merge train" before a release.

If the average build (checkout, compile, unit tests) takes 8 minutes, total build time needed per day is 16,000 × 8 = 128,000 build-minutes, or about 2,133 build-hours. Spread over a 10-hour working window, that needs roughly 213 concurrent build agents on average; real traffic clusters, so budget peak capacity at 2-3x that — roughly 500-600 concurrent sandboxed build workers at peak.

Not every build deploys to production. Assume the 1,500 services deploy to prod an average of 3 times/week each: 1,500 × 3 / 7 ≈ 643 production deploys/day, or about 27/hour — one somewhere in the company roughly every two minutes.

Storage: each build produces an artifact (a compiled binary or container image) averaging 200MB and about 5MB of logs. Raw daily artifact output is 16,000 × 200MB ≈ 3.2TB/day, which would be wasteful to keep forever — with a retention policy of the last 20 artifacts per service plus everything currently deployed, steady-state artifact storage settles around 1,500 × 20 × 200MB ≈ 6TB. Logs at 16,000 × 5MB ≈ 80GB/day, kept hot for 30 days, is about 2.4TB of searchable log storage, with older logs moved to cold storage.

API design

POST /v1/pipelines/{service}/trigger  {ref, trigger_type}
     -> {run_id, status: "queued"}
GET  /v1/runs/{run_id}
     -> {status, stages: [...], artifact_url, logs_url}
POST /v1/runs/{run_id}/approve  {stage, approver}
     -> {status: "promoted"}
POST /v1/deployments  {run_id, environment, strategy}
     -> {deployment_id, status: "in_progress"}
POST /v1/deployments/{id}/rollback
     -> {status: "rolled_back"}
GET  /v1/deployments?service=&environment=
     -> deployment history, who deployed what and when
Webhook (from SCM): POST /internal/webhooks/github  {push event}

High-level design

A commit triggers a build through a queue-backed worker fleet; a separate deployment orchestrator then promotes the resulting artifact environment by environment, checking health at each step.

Deep dive

1) Fair scheduling across teams, not just a single FIFO queue. If every build lands in one shared queue, one team's slow monorepo build can starve a small, urgent hotfix build behind it. The fix is per-team or per-priority queue lanes with dedicated worker pools, the same bulkhead idea from Ch.15 — isolate resources so one noisy consumer cannot exhaust capacity that other, unrelated work depends on.

2) Canary analysis is the hardest part, not the traffic-shifting mechanics. Shifting 5% of production traffic to a new version is a load balancer config change. Deciding automatically whether that 5% is healthy compared to the rest is the hard problem — it needs pulling error rate and latency for the canary group versus the baseline group from the observability stack (Ch.16), and it needs enough canary traffic that the comparison isn't just noise. Too small a canary percentage gives an unreliable signal; too large one means a bad build hurts more real users before anyone notices.

3) The deployment orchestrator has to be resumable, not just retryable. A "promote to staging" action is really several calls to the underlying infrastructure (scale up new pods, drain old ones, update a router), and any one of them can fail partway through. The orchestrator needs to track exactly which step a deployment is on and resume or roll back cleanly from there, the same state-machine discipline a saga uses for a multi-step business transaction (Ch.13) — just applied to infrastructure changes instead of order and payment steps.

Trade-offs

At 10x the build volume, a shared build-worker fleet either sits mostly idle most of the day to have headroom for the morning and evening spikes, or it autoscales aggressively and eats the cold-start latency of spinning up fresh sandboxed containers on every burst. The trade-off is over-provisioning cost versus a slower first build of every burst — most platforms land on a small always-warm pool plus fast autoscaling for the rest.

Say this

"I'd start with human-gated promotion from staging to production, and only add fully automatic canary rollback once we trust the health-check signal in practice, because auto-rollback triggered by a noisy or wrong metric causes its own flapping outages — that's a worse failure mode than a slightly slower human-approved rollout."

Final design

One picture: a push triggers a webhook, the orchestrator enqueues the build into a per-team lane, a sandboxed worker fleet compiles and tests the code and pushes the result to an artifact registry, and a separate deployment orchestrator then promotes that artifact environment by environment — dev, staging, a canary slice of production, then all of production — checking health at each step and rolling back automatically on regression, with every step written to an audit trail.

EM-level follow-up

Rolling this out across an org that's used to manual deploys is a change-management project, not just a platform launch — you migrate service by service, starting with low-risk ones, because deploy velocity and safety directly change how much on-call load every team carries. On build-vs-buy: most companies buy the CI layer (GitHub Actions, CircleCI — build and test execution is a commodity) and build the CD/deployment-orchestrator layer in-house, the way Netflix built Spinnaker, because deployment logic is tightly coupled to your own infrastructure and access-control model in a way a generic vendor product rarely fits well.

Design a Monolith-to-Microservices Migration Plan

Problem framing

This one is not "design system X" — it's "design the migration itself." A company has one large application (a monolith) backing its whole product, and it's now slowing teams down: deploys are slow because everyone ships through one pipeline, and 300 engineers keep stepping on each other's code in one codebase. The task is to plan how to pull services out of that monolith one at a time, while the whole system keeps serving real traffic correctly throughout — not a rewrite from scratch, and not a single big cutover weekend.

Clarifying questions

  • Why now — deploy velocity, a hiring/coordination bottleneck, a scaling limit, or a specific outage that made leadership act? — the answer changes which module gets extracted first; a scaling bottleneck points at the highest-traffic module, a coordination bottleneck points at whichever team keeps colliding with others.
  • Can we tolerate a temporary window where both the monolith and the new service touch the same underlying data? — this decides whether we need the data-sync patterns (change data capture, the outbox pattern) from Ch.14 during the transition.
  • Is any downtime acceptable during a cutover step? — almost always no, which means every cutover has to happen while live traffic keeps flowing.
  • Do we already have enough test coverage on the monolith to trust that the new service behaves identically? — if not, we need a way to compare real production behavior before trusting the new service with real traffic, not just unit tests.
  • Will team boundaries be redrawn to match the new service boundaries? — Conway's Law says a system's structure ends up mirroring the structure of the teams that build it, so service boundaries that don't match team boundaries tend to recreate the same coordination problem in a new shape.

Requirements

Functional requirements:

  • Identify extraction candidates (bounded, coherent pieces of the monolith) and pick an order.
  • Stand up each new service with its own datastore, separate from the monolith's database.
  • Route a configurable, gradually increasing percentage of traffic for that module from the monolith to the new service, without downtime.
  • Keep data correct in both places during the transition, with a way to detect and fix drift.
  • Only remove the old code path once the new service is verified at 100% of traffic.

Non-functional requirements:

  • Near-zero downtime during any single cutover step.
  • No data loss and no double-processing during the window where both systems are live.
  • A fast, safe way to shift traffic back to the monolith if the new service misbehaves.
  • The plan has to ship in small, independently valuable slices — a multi-quarter "big bang rewrite" with nothing shipping in between is the classic way these projects fail or get cancelled halfway through.

Capacity estimate

Assume the monolith serves 50,000 requests/sec (RPS) total. The first extraction candidate, a Notifications module, currently accounts for about 8% of that traffic: 50,000 × 0.08 = 4,000 RPS. Its data lives in a Notifications table with roughly 500 million rows, taking up about 200GB of the monolith's shared database.

To migrate that data with change data capture (CDC — a stream of every row-level change happening in the source database, covered in Ch.14) at a realistic throughput of 50,000 rows/sec, the initial backfill of 500,000,000 rows takes 500,000,000 / 50,000 = 10,000 seconds ≈ 2.8 hours. In practice, budget roughly a day per extraction once you add time for the CDC pipeline to catch up on rows that changed again during the backfill, plus verification before flipping any real traffic.

Traffic shift itself is cheap in compute terms — it's a routing decision, not new load — but the risk is concentrated: 4,000 RPS through a brand-new, unproven service is enough that a bug reaching 100% instantly would be a real incident, which is exactly why the shift has to be staged (1% → 10% → 50% → 100%) rather than a single flip.

     -> {phase, percent_migrated, error_rate_delta}

     -> shifts that percentage of traffic to the new service

     -> shifts traffic back to 0 percent immediately

-- monolith's internal call site already expects, e.g.:

     -> unchanged signature; only the implementation behind it moves

High-level design

A routing façade sits in front of both the monolith and the newly extracted service, shifting traffic gradually while a change-data-capture pipeline keeps data in sync.

Deep dive

1) The strangler fig pattern and the routing layer. Put a façade in front of the monolith that intercepts calls for the module being extracted and routes a configurable percentage to the new service, controlled the same way a feature flag controls a percentage rollout (see the Global Configuration Service problem elsewhere in this chapter for the underlying mechanism) — shift gradually, 1% then 10% then 50% then 100%, watching error rates at every step.

2) The data migration is the real risk, not the code. During the transition, data has to be correct in two places at once. A one-way CDC stream from the monolith's database to the new service's database (Ch.14) is safer than a true dual-write, because dual-write means two systems can disagree about which one is authoritative during the transition — CDC keeps a single, clear source of truth (the monolith) until the moment the new service is trusted enough to take over.

3) Verify behavior before trusting real traffic to it. Shadow traffic — mirroring real production requests to the new service and comparing its response against the monolith's, without acting on the new service's answer — catches behavior drift before any real user is affected. This one technique is usually the difference between a migration that ships quietly and one that generates a string of small incidents.

4) Choosing extraction order by coupling, not by "interesting tech." Extract the module that is high pain (frequent incidents, slow deploys) and low coupling (few callers, a clean boundary) first. The classic mistake is starting with the most tightly-coupled, highest-value module because it feels like the biggest win — that turns a planned two-week extraction into a six-month fight with callers you didn't know existed.

Trade-offs

A gradual dual-write-and-verify migration takes longer and carries real operational overhead — running a CDC pipeline and a reconciliation job for weeks per module — versus a one-shot cutover that's simpler to build but turns any bug into a production incident instead of a quiet rollback. At 10x the entity count, even the reconciliation job's full-table scans stop being cheap, pushing teams toward sampling-based drift detection instead of comparing every row every time.

Say this

"I would not do a big-bang rewrite. I'd extract one bounded, low-coupling module first with the strangler fig pattern, run the new service in shadow mode against real traffic before it serves a single real response, and shift traffic gradually behind a flag with an instant kill switch back to the monolith if error rates move."

Final design

One picture: a routing façade sits in front of the monolith and exactly one newly extracted service at a time. A feature-flag-controlled percentage of traffic shifts gradually while change data capture keeps both datastores in sync and a reconciliation job flags any drift. Each extraction ships and is independently reversible; the project is measured module by module, not by one big cutover date on a calendar.

EM-level follow-up

This is an org-design project as much as an engineering one — Conway's Law means service boundaries end up matching team boundaries whether you plan for it or not, so a migration that actually sticks usually comes with a matching team re-org, and leadership needs to buy into a multi-quarter roadmap made of incremental, demonstrable wins rather than a single "rewrite quarter" with nothing to show until the end. There's nothing to buy for the migration itself, but the tooling underneath it — the CDC vendor, the feature-flag system — is its own set of build-vs-buy calls inside the bigger plan.

Design a Multi-Tenant SaaS Platform

Problem framing

A multi-tenant SaaS (software-as-a-service) platform runs one codebase and a shared pool of infrastructure to serve thousands of independent customers — "tenants" — where each tenant's data must be fully isolated from every other tenant's, even though they all run on the same servers and often the same databases. Think a B2B product like a helpdesk tool or a project-management app sold to thousands of companies. The interview question here is really about tenant isolation, stopping one tenant's heavy usage from degrading everyone else's, and scaling tenants that vary wildly in size — not the product's own business logic.

Clarifying questions

  • Isolation model: one shared database with a tenant_id column, one database per tenant, or a hybrid? — this is the single biggest architecture decision here, and it changes schema design, blast radius, and operational cost all at once.
  • Do tenants vary hugely in size — some with 10 users, some with 50,000? — a big size skew means one sharding scheme won't fit everyone; the largest tenants may need dedicated resources.
  • Does any customer require physically isolated data (a dedicated database or region), for example a government contract? — this forces a dedicated "silo" deployment option for at least some tenants, not just the pooled default.
  • Is cross-tenant reporting or search ever needed for internal, platform-wide analytics? — decides whether the platform needs any safe, deliberate way to break strict per-tenant isolation for internal use.
  • How is usage metered and billed per tenant? — decides whether every request path needs to emit a usage event from day one, rather than bolting metering on later.

Requirements

Functional requirements:

  • Onboard a new tenant: provision an isolated data space and assign a plan.
  • Scope every read and write automatically to the tenant making the request.
  • Support per-tenant plan tiers and feature entitlements (what this tenant's plan allows).
  • Meter usage per tenant for billing.
  • Support tenant-level admin actions: suspend, export all data, or fully delete a tenant.

Non-functional requirements:

  • Strict data isolation — a bug that lets Tenant A see Tenant B's data is the single worst thing that can happen to this business's trust, worse than an outage.
  • Noisy-neighbor isolation — one tenant's heavy usage (a bulk import, a big report) must not slow down other tenants sharing the same infrastructure.
  • Per-tenant scalability — a large tenant's growth should not force a re-architecture of the whole platform.
  • Predictable cost per tenant, so pricing tiers stay profitable as tenants grow.

Capacity estimate

Assume 20,000 tenant companies with a heavy size skew: the top 100 "enterprise" tenants average 2,000 users each (200,000 users total), and the remaining 19,900 "SMB" tenants share the other roughly 300,000 users — about 15 users per tenant on average. Total users: 500,000.

If each user makes an average of 20 API requests/day, that's 500,000 × 20 = 10,000,000 requests/day ≈ 116 requests/sec (RPS) on average. Peak traffic — business hours plus the occasional large tenant running a batch job — runs roughly 8x average, so plan for around 930 RPS at peak.

Data footprint also skews hard: the top 100 tenants average 20GB each (2TB total), and the remaining 19,900 tenants average around 400MB each (about 8TB total) — 10TB company-wide. If a practical limit for one pooled database shard is around 200GB (see Ch.6 for sharding mechanics), that's a minimum of 10TB / 200GB = 50 shards just for raw storage, likely 50-70 once replication and growth headroom are factored in.

Noisy-neighbor math: if one tenant runs a bulk import of 5,000,000 rows at a sustained 5,000 writes/sec, that's 5,000,000 / 5,000 = 1,000 seconds — just under 17 minutes of heavy, sustained write load landing on whichever shard that tenant sits on, which is exactly the kind of load that must not be allowed to slow down every other tenant sharing that shard.

API design

-- tenant resolved server-side from the auth token or subdomain,
-- never from a client-supplied parameter
POST /v1/tenants  (internal control-plane API)
     {company_name, plan} -> {tenant_id, status: "provisioning"}
GET  /v1/tenants/{id}/entitlements
     -> {plan, feature_flags, limits}
GET  /v1/projects
     -> implicitly scoped to caller's tenant_id
POST /v1/tenants/{id}/suspend
DELETE /v1/tenants/{id}
     -> full data purge, e.g. for a GDPR deletion request
GET  /v1/tenants/{id}/usage?month=2026-07
     -> usage totals for billing

High-level design

Every request resolves its tenant at the gateway; a control-plane database maps each tenant to a pooled shard or a dedicated silo, and per-tenant limits stop noisy neighbors before they reach shared storage.

Deep dive

1) Isolation model: pool, silo, or hybrid. A shared table with a tenant_id column (pooled) is cheap to run and easy to onboard new tenants into, but every single query must filter by tenant_id or it leaks data. The safe pattern is to never trust a client-supplied tenant_id — always derive it server-side from the authenticated session, and enforce it at the lowest layer possible, like a database row-level security policy or a query-builder wrapper that injects the filter automatically, instead of relying on every engineer remembering to add "WHERE tenant_id = ?" by hand. Large or compliance-sensitive tenants move to their own dedicated database (silo) once they cross a size threshold, trading operational overhead (more databases to patch and back up) for a much smaller blast radius. This is Ch.6's sharding, except the shard key here is chosen for isolation first, load distribution second.

2) Containing noisy neighbors. A heavy tenant's bulk import or big report can starve everyone else sharing its shard or connection pool. The fix is per-tenant rate limits and connection-pool quotas (Ch.5 covers the rate-limiting algorithms), plus routing bulk or background work to a separate queue and worker pool from the interactive request path — a bulkhead (Ch.15) — so an import job degrades only itself, not its shard-mates.

3) Tenant lifecycle has to be automated, not a manual runbook. Onboarding (assigning a shard, seeding defaults) and offboarding (a full, verifiable data purge on cancellation, often a compliance requirement like GDPR's right to erasure) both need to be idempotent (Ch.13) and automated. At 20,000+ tenants, doing either by hand doesn't scale, and a half-finished delete is a compliance risk, not just an inconvenience.

Trade-offs

At 10x the tenant count, a busy pooled shard that one tenant outgrows needs a live data migration to move that tenant to a less-loaded shard or a silo — invisible to that one paying customer, unlike a normal resharding that can be smoothed across all traffic. The trade-off is investing early in a tenant-to-shard indirection table (so a tenant can move shards without its ID or any client-visible reference changing) versus a simpler direct hash-by-tenant-id scheme that's easier at first but much harder to rebalance later.

Say this

"I'd start every tenant in a pooled, sharded model with tenant_id enforced at the query layer rather than trusted to application code, and only move a tenant to a dedicated silo once it crosses a size or compliance threshold — building silo-per-tenant from day one for a 20,000-tenant business would mean operating thousands of databases before the product even has market fit."

Final design

One picture: every request resolves its tenant server-side at the gateway, a control-plane database maps each tenant to a pooled shard or a dedicated silo, application servers stay stateless and shared across all tenants, per-tenant rate limits and a separate bulk-work queue stop noisy neighbors, and a usage-metering stream carries billing events off the main request path.

EM-level follow-up

Rolling out a new tier like a dedicated-infra "Enterprise" plan touches sales, support, and finance, not just engineering, and moving an existing live tenant from pooled to silo has to happen with zero downtime for that one specific customer — a much higher bar than an ordinary resharding, since there's no way to average the risk across the whole traffic base. On build-vs-buy: most teams buy the pieces that aren't the isolation core — auth (Auth0, Cognito), billing and metering (Stripe Billing, or see the Subscription-Billing problem elsewhere in this chapter) — and build the tenant-isolation layer themselves, because it's the part that actually defines this SaaS's trust and cost model.

Design an Internal Developer Platform

Problem framing

An internal developer platform (IDP) is the self-service layer a platform team builds so product engineers can get a new service, its infrastructure, and its CI/CD pipeline without filing a ticket to another team and waiting. Think Spotify's Backstage, or the internal platforms at companies like Uber and Airbnb. The goal is that "I need a new microservice" turns into "it's running in production with logging, metrics, and a pipeline already wired in" in an afternoon, through self-service templates — not a week of cross-team ticket ping-pong.

Clarifying questions

  • Is the scope a service catalog/portal (visibility only), or does it also provision real infrastructure? — a catalog is a read-only registry; a true IDP also acts, for example spinning up a new Kubernetes namespace and a database.
  • Golden-path templates only, or fully custom infrastructure requests too? — templates ("scaffold a new Go service with our standard middleware") cover most cases cheaply, but a platform with no escape hatch for unusual needs pushes teams to route around it entirely.
  • Who enforces cost — does the platform stop a team from accidentally provisioning $50,000/month of infrastructure by mistake? — decides whether budget guardrails have to be built into provisioning itself, not checked after the fact.
  • Self-service for which resources — compute, databases, queues, secrets — or is database provisioning still a manual step run by a DBA? — the wider the resource surface, the bigger the abstraction the platform needs.
  • Single cluster and cloud, or must the platform abstract multiple clouds and regions? — decides whether the platform can hardcode against one provider's API or needs its own provider-agnostic resource model.

Requirements

Functional requirements:

  • A service catalog: every service, its owner, its dependencies, its on-call rotation, in one place.
  • Self-service scaffolding: generate a new repo, CI pipeline, and deployment manifest from a chosen template.
  • Self-service infrastructure provisioning: request a database, queue, or cache and get it wired up automatically.
  • Golden-path enforcement: a new service comes with logging, metrics, tracing, and basic security scanning already wired in, because it's baked into the template rather than bolted on later.

Non-functional requirements:

  • Provisioning has to be self-service and fast — minutes, not a ticket sitting in a queue for days.
  • The platform must not become a bottleneck itself; if every request still needs a human from the platform team to approve it, it isn't actually self-service.
  • Safe defaults — following the golden path should be the easiest option, so an insecure or non-compliant shortcut requires visible, deliberate extra effort.
  • The underlying resource operations must be idempotent (Ch.13), so re-running a provisioning request after a partial failure doesn't create duplicate infrastructure.

Capacity estimate

Assume 1,000 engineers and about 1,200 services. New-service creation is low-volume: assume roughly 3 new-service scaffolds/day company-wide. The catalog's read side is where routine load shows up — 1,000 engineers checking the catalog or a CI dashboard around 30 times/day each is 30,000 reads/day ≈ 0.35 requests/sec (RPS) on average, peaking maybe 10x during an incident when everyone is asking "who owns this service" at once — roughly 3-4 RPS.

Provisioning requests are also low-volume but high-stakes: assume the 1,200 services each request a new resource or a resize about twice a month — 1,200 × 2 / 30 ≈ 80 requests/day, or about one every 18 minutes company-wide. Each one triggers several downstream calls (create a namespace, create a database, register DNS, write a secret) that must all succeed together or roll back together.

Catalog metadata itself is tiny: 1,200 services × roughly 5KB of ownership and dependency data ≈ 6MB — the catalog's own storage is a non-problem. The real scale challenge is keeping that 6MB of metadata honest against the actual infrastructure footprint it describes, which can be thousands of running pods and hundreds of live databases — a consistency problem, not a storage-volume one.

API design

POST /v1/catalog/services  {name, owner_team, repo_url, template}
     -> {service_id, status: "scaffolding"}
GET  /v1/catalog/services/{id}
     -> {owner, dependencies, on_call, links: {ci, dashboards, runbook}}
POST /v1/provisioning/requests
     {service_id, resource_type: "postgres" | "queue" | "cache", size_tier}
     -> {request_id, status: "pending"}
GET  /v1/provisioning/requests/{id}
     -> {status, resource_endpoint}
POST /v1/templates/{name}/scaffold  {service_id, params}
     -> generates repo, pipeline, and deployment manifest
GET  /v1/catalog/services?owner_team=payments
     -> for ownership audits

High-level design

A developer portal reads and writes a service catalog; a separate provisioning orchestrator turns infrastructure requests into real, tracked resources, with a reconciliation job keeping the catalog honest.

Deep dive

1) The provisioning orchestrator is the hard part, not the portal UI. The portal is a thin catalog and form; the real difficulty is turning "give me a Postgres database" into an ordered sequence of calls — create the instance, create a database user, write the credentials to a secrets manager, register the endpoint, update the catalog — where any step can fail. This needs the same saga pattern with compensating actions from Ch.13: if step four fails, roll back steps one through three, rather than leaving an orphaned, unmanaged database that nobody's catalog knows exists, which is a cost leak and a security gap waiting to be found in an audit.

2) The golden-path-vs-escape-hatch tension. If the platform is the only way to get infrastructure, teams with unusual needs get stuck; if there's always an easy way around it, the platform's guarantees (security scanning, tagging, cost tracking) get bypassed and the catalog quietly goes stale. The practical answer is an escape hatch that's possible but visibly "unsupported" — it requires an extra manual security review and shows up flagged in the catalog as non-standard — so the golden path stays the fast path by design, not by force.

3) Keeping the catalog honest through drift detection. The catalog is only useful if it matches reality, and services get created or decommissioned outside the platform's view — a manual command run directly against the cluster, a forgotten resource nobody cleaned up. A periodic reconciliation job that scans the actual infrastructure and diffs it against the catalog's inventory, flagging orphans, is the same plan-and-apply idea infrastructure-as-code tools use, applied here to "what the catalog thinks exists" versus "what's actually running."

Trade-offs

At 10x the engineer count, the platform team itself becomes the bottleneck if every new resource type needs a bespoke integration built by hand. The trade-off is investing in a generic, pluggable resource-provider abstraction — adding a new resource type becomes "write a provider plugin," a self-service extension — versus a hardcoded integration per resource type that's simpler to build at first but keeps the platform team in the critical path for every new capability forever.

Say this

"I'd build the provisioning orchestrator as an explicit saga with compensating actions for every resource type, because at this scale, cleaning up a partial failure can't be a runbook a human follows by hand — an orphaned, unmanaged cloud resource nobody's catalog knows about is exactly the kind of thing that gets found during a security audit, not during normal operations."

Final design

One picture: a developer portal backed by a catalog of every service and its ownership graph; scaffolding a new service or provisioning infrastructure both go through an orchestrator that runs each step as a saga with rollback, wiring in logging, metrics, and CI by default through templates; a reconciliation job continuously checks that the catalog's inventory matches what's actually running and flags any drift.

EM-level follow-up

Rolling out an IDP is an adoption problem before it's a technical one — if using it is optional and the old ticket-based way still works, adoption stalls. Successful rollouts pick one or two visibly painful existing workflows, like a service provisioning process that used to take two weeks of tickets, fix that first, make the improvement measurable, and only then make the golden path the default for new services while grandfathering old ones in gradually. On build-vs-buy: most companies buy the catalog and portal layer (Backstage is open-source and widely adopted) and build the provisioning orchestrator themselves, because it has to speak to a company's specific internal infrastructure and access-control model, which is rarely generic enough to buy off the shelf.

Design a Global Configuration Service

Problem framing

A global configuration service is the shared source of truth for values that many services need to read and that change independently of any code deploy — timeouts, rate-limit thresholds, which region is currently primary, which model version to serve, kill switches to turn a broken dependency off instantly. Every service in the company reads from it, often on every single request, so it has to be close to 100% available and fast, even though updates themselves are rare. Think Facebook's Configerator, or a store like etcd, Consul, or ZooKeeper used for this purpose. It's the general distribution layer that something like the Feature-Flag System problem, elsewhere in this chapter, would build its per-user targeting logic on top of — this problem is the plumbing underneath.

Clarifying questions

  • Does every service read config on every request (a hot path), or only at startup or on a slow poll? — hot-path reads mean read latency and read availability dominate the whole design; startup-only reads are far easier.
  • How fresh does a change need to be after an operator pushes it — sub-second, or is a minute of propagation lag fine? — a kill-switch use case, like turning off a broken payment provider right now, needs a push model, not just poll-and-cache.
  • What's the blast radius of a bad push — one service, one region, or global? — decides whether staging a config change's rollout, the same way you'd stage a code deploy, is a hard requirement rather than a nice-to-have.
  • Do config values ever depend on each other, or are they always independent key-value pairs? — dependent values need schema validation before a push is allowed to go live at all.
  • Who can write config — any engineer directly, or does every change go through a review step? — decides whether the write path needs an audit log and instant rollback as a first-class feature rather than an afterthought.

Requirements

Functional requirements:

  • Read a config value by key, scoped to a service and environment.
  • Write or update a config value, with every write versioned.
  • Push updates to every subscribed reader with low propagation delay.
  • Roll back instantly to any previous version.
  • Audit every change: who changed it, when, and what the old and new values were.
  • Support a staged rollout of a config change itself — apply it to a small percentage of readers first.

Non-functional requirements:

  • Read availability approaching 100% — a config-read failure must never take down the calling service, so every client needs a safe local fallback, not a hard dependency on the config service being reachable.
  • Read latency in the low milliseconds, since reads often sit on the hot path.
  • Writes are rare and can tolerate more latency, but must be strongly consistent and versioned, so "what was config at time T" is always a well-defined, answerable question.
  • Propagation of an update to every reader should complete in seconds for kill-switch use cases.

Capacity estimate

Assume 5,000 services company-wide with an average of 20 running instances each — 100,000 total reading instances. If each instance polled for a config refresh every 10 seconds, that alone would be 100,000 / 10 = 10,000 reads/sec, purely from routine refresh, before counting a single real change. Switching to a push/watch model (a long-lived connection the server pushes diffs down) drops steady-state read QPS to near zero, but turns the problem into managing 100,000 concurrent open connections instead — a connection-count scaling problem, not a request-rate one.

The config data itself is small: 5,000 services × roughly 50 keys × 200 bytes/value ≈ 50MB total — easily small enough to fit in memory on a handful of machines. The real difficulty is never storage volume; it's distributing that 50MB correctly to 100,000 scattered readers without any single point becoming a dependency they can't live without.

Writes are human-initiated and rare: assume roughly 500 config pushes/day company-wide across every team, or about one every 3 minutes (86,400 / 500 ≈ 173 seconds). Against 10,000 reads/sec, that's a read-to-write ratio on the order of a million to one — the system should be optimized overwhelmingly for cheap, cached, fault-tolerant reads, not for write throughput.

API design

GET  /v1/config/{namespace}/{key}?version=latest
     -> {value, version, updated_at}
PUT  /v1/config/{namespace}/{key}  {value, expected_version}
     -> {version}
     -- expected_version is optimistic concurrency control: it
     -- prevents a lost update if two operators race on the same key
POST /v1/config/{namespace}/{key}/rollback  {to_version}
     -> {version}
GET  /v1/config/{namespace}/{key}/history
     -> [{version, value, changed_by, at}]
POST /v1/config/{namespace}/{key}/stage  {value, rollout_percent}
     -> stages a rollout to a percentage of readers before full push
-- client SDK, not raw HTTP:
WATCH /v1/config/{namespace}
     -> server-push stream of changed keys

High-level design

A versioned store sits at the center, replicated to a small number of regional mirrors, so reads never have to cross a region and never depend on one central system being reachable.

Deep dive

1) Two different failure modes need two different fixes. "The config service is down" and "a config value is wrong" are not the same problem. The fix for the first is every client SDK caching its last-known-good value locally and keeping serving it if the config service is unreachable, rather than failing the caller's request or blocking startup — the same fallback idea behind a circuit breaker (Ch.15), applied to a dependency you read constantly instead of one you call transactionally. This inverts the usual availability conversation: the config service being briefly down should degrade to "stale," which is invisible to almost everyone, not to "broken."

2) Fan-out to 100,000 readers without a thundering herd. If every instance polls the central store directly, one config change turns into 100,000 simultaneous reads the moment every cache invalidates at once. The fix is layered distribution: a small number of regional mirrors pull from the central store, and actual service instances subscribe to their nearest regional mirror through a push/watch stream that delivers only diffs — the same fan-out shape as Ch.4's cache-invalidation problem and Ch.18's presence/pub-sub systems, just applied to config values instead of cache keys or chat messages.

3) A bad config push needs the same discipline as a bad code push. A broken code deploy gets caught by canary analysis, covered in the CI/CD Deployment Platform problem above; a bad config push needs the exact same discipline, because "change the rate-limit threshold globally in one push" has caused real outages at large companies before. The fix is to treat a config change like a deployment — push to 1% of instances or regions first, watch error rates, then widen — which means percentage-based targeting and health-aware rollout have to be built into the config service itself, not just "write a value, broadcast it to everyone."

Trade-offs

At 10x the reading instances (roughly a million), the fan-out tree needs another layer — global store to regional mirrors to per-cluster sub-mirrors to instances — or the regional mirrors themselves become the next bottleneck. The trade-off is propagation latency, since each added layer adds tens to hundreds of milliseconds before every instance sees a change, versus load on the central store, since fewer layers means every mirror hits the source directly, which is fine at 100,000 mirrors but not at a million.

Say this

"I'd treat 'the config service is unreachable' and 'a config value is wrong' as two completely different failure modes with two different fixes — the first is solved by client-side caching so a reader never blocks on us, and the second is solved by staging config changes the same way we'd stage a code deploy, because a bad global config push is operationally identical to a bad global code push."

Final design

One picture: a versioned, strongly-consistent config store sits at the center, replicated to a handful of regional mirrors; every service instance's SDK holds a locally cached last-known-good value and subscribes to its nearest mirror over a push stream for fast propagation; writes go through an audited, staged rollout — 1% then wider, exactly like a code deploy — with instant rollback to any earlier version.

EM-level follow-up

Because a bad config value can cause a company-wide outage just as easily as bad code, mature organizations eventually route config changes through the same review and staged-rollout rigor as a code deploy — sometimes literally the same CI/CD pipeline, with config stored and reviewed as code. The EM angle here is arguing for that unification instead of quietly treating config as a lower-stakes side channel that skips the review a code change would get. On build-vs-buy: almost everyone builds a thin config-serving layer of their own, for the SDK, watch, and staged-rollout semantics tailored to their fleet, on top of a bought or open-source consistent store like etcd or ZooKeeper, rather than reimplementing distributed consensus (Ch.12's Raft) in-house — that part is very rarely worth building from scratch.

Design a Stock-Trading / Order-Matching Engine

Problem framing

This is the core of any exchange: a system that takes buy and sell orders for a symbol (a stock ticker, a crypto pair) and matches them against each other by price and arrival time, then tells the world what traded. Everything else in a trading platform — account balances, risk checks, the pretty chart — sits around this one component, and this one component has to be provably correct, not just "usually right."

Clarifying questions

  • What asset class, and how many symbols? — equities, crypto, and futures all have slightly different matching rules (lot sizes, tick sizes, circuit breakers). Fewer, more liquid symbols concentrate load onto single order books; that changes where the bottleneck lives.
  • What's the latency budget? — a retail brokerage app tolerates a few milliseconds; a venue selling colocation to high-frequency traders is fighting over microseconds. This decides the whole tech stack, right down to the programming language and whether the network stack bypasses the kernel.
  • Which order types must we support? — market, limit, stop, immediate-or-cancel (IOC, cancel whatever doesn't fill instantly), fill-or-kill (FOK, all or nothing). More order types means more matching-logic branches to keep deterministic.
  • Do we need self-match prevention and a full regulatory audit trail? — most real venues are legally required to reconstruct exactly why every trade happened, in order, for years. That shapes the whole persistence design, not just a "nice to have" logging feature.
  • Is one engine instance enough, or do we need multi-region failover with the same guarantees? — this determines whether we can even consider an active-active setup, or whether we're forced into active-passive (see the deep dive).

Requirements

Functional:

  • Accept new orders (limit, market, IOC, FOK), cancels, and cancel-replace requests.
  • Match incoming orders against the resting order book using strict price-time priority: best price first, and among equal prices, whoever arrived first gets filled first.
  • Publish trade executions and live order-book depth (market data) as soon as a match happens.
  • Keep an immutable, ordered record of every order and trade for audit and replay.

Non-functional:

  • Determinism — given the same sequence of inputs, the engine must always produce the same order book state and the same trades, even after a crash and restart.
  • Low latency — sub-millisecond to a few milliseconds matching latency for the hot path.
  • Durability — an order the engine has acknowledged, or a trade it has confirmed, must never be lost.
  • High throughput on hot symbols — a handful of popular symbols can dominate total order flow, especially at market open.

Capacity estimate

Take a mid-size venue: 5,000 listed symbols, roughly 50 million order messages a day (new orders, cancels, and replaces combined) during a 6.5-hour trading day (23,400 seconds). That's an average of about 2,100 messages/sec, but real order flow is heavily bunched at the open and close — a 20x burst multiplier on top of average is a reasonable planning number, so peak load is roughly 40,000-45,000 messages/sec system-wide, and the busiest 20 symbols can easily carry 40% of that peak on their own.

Assume 60% of orders eventually generate a fill (a trade message), so about 30 million trade messages a day. Each order or trade record is small — symbol, side, price, quantity, timestamp, account id — call it 150 bytes. That's roughly 50M x 150B ≈ 7.5 GB/day of raw order-log data, plus a similar amount for trades. Retaining that log for 7 years for regulatory audit (a realistic requirement for a real venue) works out to on the order of 30 TB total — trivial and cheap on object storage, even though it's a lot of individual records.

Market data fan-out is the surprising cost center. If the engine emits roughly 40,000 match events/sec at peak, and each event is broadcast to an average of 50 subscribers actively watching that symbol (retail apps plus institutional feeds), that's about 2 million outbound messages/sec. At ~150 bytes per message, that's on the order of 300 MB/sec of outbound bandwidth just for market data at peak — which is exactly why real exchanges run a dedicated market-data distribution network (often UDP multicast for institutional consumers) instead of fanning out from ordinary application servers.

High-level design

Deep dive

Determinism through a sequenced log, not a database. The trick that makes a matching engine provably correct is to never let the engine itself be the source of truth for ordering. Instead, every accepted order is first appended to a durable, strictly ordered log (a Kafka partition per symbol works well) and given a sequence number. The matching engine is a single-threaded process per symbol that does nothing but read that log in order and apply it to an in-memory order book. Because it's single-threaded and the input is a strict sequence, replaying the same log from the start always produces the same book state — that's what "deterministic" buys you, and it's what makes the audit trail and the disaster-recovery story trustworthy at the same time.

The order book data structure. Each side (bids, asks) is a sorted collection of price levels, and each price level holds a FIFO (first-in-first-out) queue of orders at that price for time priority. A match happens by looking at the best price level on the opposite side and draining its queue front-to-back. This is fast — O(log n) to insert a new price level, effectively O(1) to match at the top of the book — which is why matching itself is rarely the actual bottleneck; the log and the network path around it usually are.

High availability without breaking single-writer correctness. Because correctness depends on exactly one process applying the log in order, you can't run two active matching engines for the same symbol (that would let them apply orders in different orders and disagree on the book — see Trade-offs). The standard fix is active-passive: a standby engine replays the same sequenced log in real time and stays warm, ready to be promoted the moment the primary fails, having already reconstructed the exact same state.

Trade-offs

At 10x scale, the constraint isn't total system throughput — it's the single hottest symbol. Because one symbol's book must be matched by one single-threaded process to stay deterministic, you can't shard a hot symbol across more machines the way you would a stateless API. The only levers left are making that one process faster (pinned CPU threads, avoiding garbage-collection pauses, kernel-bypass networking). Separately, active-passive replication guarantees correctness but caps write availability to one process per symbol at a time — a failover, even a fast one, is a brief gap where that symbol can't accept new orders; an active-active design would close that gap but reopens the determinism problem, since two engines applying orders concurrently can produce two different, both "valid," order books. Exchanges accept both trade-offs because a wrong or unavailable order book is far worse than a short pause or a slower matching process.

Say this

"I'd run the matching engine active-passive, not active-active, per symbol. The moment two processes can independently decide match order, you lose the single global truth about who traded with whom first — and in this domain that's not a performance trade-off, it's a correctness bug that shows up as a regulatory problem."

Final design

One picture: an order gateway does fast pre-trade risk checks, then appends the order to a durable per-symbol sequenced log. A single-threaded matching engine per symbol replays that log into an in-memory order book, producing trades that get persisted for audit and pushed to a dedicated market-data fan-out layer. A warm standby engine replays the same log so failover doesn't mean rebuilding state from scratch.

EM-level follow-up

Rolling out a change to matching logic can't use a normal canary deploy — you can't have two slightly different matching algorithms both live for the same symbol. The real pattern is extensive replay testing against recorded historical order flow, then a cutover during a low-volume window (often only tested first on a low-volume symbol), with the old engine kept warm to roll back to instantly. On build-vs-buy: this is one of the few systems where most companies genuinely buy rather than build — established exchange-technology vendors sell matching engines, and building one in-house is usually only justified when matching logic is the actual competitive product, as it is for an exchange operator itself. Any change here also needs compliance sign-off (rules like Reg NMS or MiFID II constrain what "fair" order handling means), so this isn't purely an engineering decision.

Design a Subscription-Billing System (Recurring Payments and Dunning)

Problem framing

This is the system behind "your card will be charged $12.99 every month" — it tracks who owes what, triggers the actual charge on schedule, generates invoices, and chases down failed payments (called dunning — the process of retrying and reminding a customer after a failed charge) without silently losing revenue or double-charging anyone.

Clarifying questions

  • Flat-fee plans, or usage-based billing too? — usage-based (metered) billing needs a separate metering pipeline; assume flat-fee/tiered plans here and point to the Developer API Platform problem later in this chapter for metering.
  • Which markets and currencies? — multi-currency and tax jurisdictions (VAT, GST) add real complexity to invoice line items and rounding.
  • What's the dunning policy — how many retries, over what window? — this is a business decision (revenue recovery vs. customer annoyance) that the engineering design has to be flexible enough to support without a redeploy.
  • Do we own the actual card charge, or does that live in a separate payment-gateway system? — assume this system depends on the Payment Gateway problem in this chapter for the actual charge; this system owns scheduling, invoicing, and retry logic.
  • Do plan upgrades/downgrades need mid-cycle proration? — if yes, the invoice model needs to support partial-period credits and debits, not just one flat charge per cycle.

Requirements

Functional:

  • Create, change (with proration), and cancel subscriptions; support trials and coupons.
  • Generate an invoice for each billing cycle and trigger the charge through the payment gateway.
  • Retry failed charges on a configurable dunning schedule, and notify the customer at each step.
  • Emit billing events (invoice created, paid, failed) for other systems (email, analytics, finance) to consume.

Non-functional:

  • Exactly-once charging per billing cycle — never double-charge, never silently skip a cycle, even if the scheduler crashes mid-run and retries.
  • Auditable — every dollar charged or credited must be traceable for finance reconciliation, which usually means treating billing data as a ledger, not a set of mutable rows.
  • Idempotent against gateway timeouts — a charge call that times out must be safely retryable without risking a second real charge.
  • Scale to millions of subscriptions with billing dates that cluster (many businesses bill everyone on the 1st of the month).

Capacity estimate

Assume 20 million active subscriptions, mostly monthly. If dates were spread evenly, that's about 20M / 30 ≈ 667,000 due per day, but real-world billing dates cluster around the 1st — call it a 5x spike day, so roughly 3.3 million invoices due on the busiest day. Spread over a 6-hour processing window (21,600 seconds), that's about 153 charges/sec sustained, with bursts toward 500/sec.

Each invoice record with line items is roughly 1 KB. At 20M subscriptions billing monthly, that's 20M invoices/month x 1 KB ≈ 20 GB/month, or about 240 GB/year — small for a relational store, even partitioned by billing date.

Dunning volume: assume a typical 4% initial decline rate. On the peak billing day, 3.3M x 0.04 ≈ 132,000 invoices need retry, spread across a multi-day retry schedule (say attempts on day 1, 3, 7, and 14), so the dunning queue at any moment is a small fraction of that — well within reach of an ordinary delayed-job queue, not a specialized streaming system.

Webhook/notification fan-out is actually the higher-volume side: every invoice event (created, paid, failed) can trigger a webhook to a merchant's own system plus a customer email, so at 20M invoices/month you're looking at tens of millions of outbound notifications/month, needing reliable delivery with retry and backoff — a smaller version of the same delivery-guarantee problem the dunning worker itself solves.

  -> { "subscriptionId": "...", "status": "trialing" }

  { "newPlanId": "pro_annual", "prorationBehavior": "create_prorations" }

  -> { "status": "paid", "amountDue": "12.99", "lineItems": [...] }

High-level design

Deep dive

Exactly-once billing under scheduler restarts. A "scan everyone due today and charge them" job will, at some point, crash halfway through and get restarted. The fix is a per-subscription-per-billing-period idempotency key (subscription id plus the billing period, like "sub_123-2026-08") enforced with a unique constraint at the database layer on the invoice row itself, so a re-run of the scheduler can't create a second invoice for the same period even if two workers race on it. That same idempotency key, or a derivative of it, gets passed to the payment gateway too, so a retried network call can't cause a second real charge.

Proration as ledger entries, not a mutated total. When a customer upgrades mid-cycle, don't just recompute "the new invoice total" — that destroys the ability to answer "why does this invoice say $47.32" later. Instead, record an explicit credit for unused time on the old plan and an explicit debit for the new plan's remaining days as separate, immutable line items. Finance and support both need to reconstruct the "why," not just the final number.

Dunning as a state machine, not a fixed cron job. "Smart" retry timing matters: a card decline is often a soft, temporary issue (insufficient funds today, temporarily over a limit) that clears if you retry at a different time of day or day of week rather than hammering the same moment repeatedly. Model each invoice's retry state explicitly — attempt count, next-retry-at, and terminal states (recovered vs. canceled-for-nonpayment) — so the retry schedule can be tuned as a business policy without touching the charging code itself.

Trade-offs

At 10x scale, the "scan for subscriptions due today" batch job starts competing with live subscription lookups on the same database. The usual fix is to pre-compute a due-list into a queue ahead of time rather than running a live table scan — but that means a plan change made an hour before billing might not be picked up until the next cycle. Pre-computed due-lists remove the scan bottleneck but introduce a window where a very recent subscription change won't be reflected in that day's charge — you're trading a small amount of staleness for a bounded, queryable billing queue, acceptable for most SaaS billing but not if the business promises instant proration on every edit.

Say this

"The one non-negotiable here is idempotency at two layers: our own invoice table has a unique constraint on subscription-plus-billing-period, and every call to the payment gateway carries an idempotency key. That's what lets me safely retry a crashed scheduler run without ever worrying about a double charge."

Final design

One picture: a scheduler emits due-today subscriptions into a queue, an invoice generator builds line items (including proration as separate credit/debit entries), an idempotent charge orchestrator calls out to the payment gateway, and a dunning state machine owns retries on failure — all billing events flow through one bus so notifications and finance reporting stay in sync with the actual charge outcome.

EM-level follow-up

Changing the dunning policy (say, adding a fourth retry attempt) directly affects revenue and churn numbers, so it should roll out as a controlled experiment with finance sign-off — see the A/B-Testing Experimentation Platform problem later in this chapter for how you'd structure that test safely. On build-vs-buy: most companies buy a subscription-billing platform (Stripe Billing, Chargebee, Recurly) rather than build this, and only justify building in-house when billing logic is a genuine product differentiator or volume makes the vendor fees material. Cross-team: finance needs the ledger to tie out to formal revenue-recognition rules, so any change to invoice line-item structure needs their review, not just a product sign-off.

Design a Real-Time Fraud-Detection Pipeline

Problem framing

This system sits between "a transaction was submitted" and "the transaction was allowed," scoring it for fraud risk fast enough that the decision can happen in the critical path — not after the money has already moved. A slower, offline half of the same system reviews flagged cases and feeds confirmed fraud back into the model.

Clarifying questions

  • Is scoring synchronous, in the checkout critical path, or can it run after the fact? — synchronous means a hard latency budget measured in tens of milliseconds; async means you can afford a heavier model but you're now blocking or reversing after the fact.
  • What's the business's tolerance for false positives? — blocking a legitimate customer has a real cost too; this is a risk-appetite question, not a pure engineering one.
  • Rules only, ML only, or both? — rules react instantly to a known new pattern (a fraud team can ship a rule in minutes); ML generalizes to patterns nobody's written a rule for yet but needs training data and time.
  • Do we need a human case-review workflow for flagged transactions? — if yes, this adds a queue and an analyst-facing UI, and a feedback path from confirmed outcomes back into training.
  • What's the traffic shape — steady global volume, or bursty patterns like card-testing attacks concentrated on one merchant or card range? — this affects whether "hot key" skew in the streaming layer is a real concern.

Requirements

Functional:

  • Score every transaction using a combination of deterministic rules and a machine-learning model, returning allow / challenge (e.g., ask for extra verification) / block.
  • Log every decision along with the features used, for audit and for training future models.
  • Accept a feedback signal (confirmed fraud from a chargeback, confirmed legitimate from a dispute resolution) to improve the model over time.
  • Let a fraud/risk team add or change rules without an engineering deploy.

Non-functional:

  • Strict latency budget — for the synchronous case, p99 well under 100ms end-to-end.
  • High availability with an explicit failure policy — the fraud check going down should have a deliberate answer, not an accident (see deep dive).
  • Feature freshness — a signal like "5 failed card attempts in the last 10 minutes" needs to reflect reality within seconds, not minutes.
  • Scale to tens of thousands of transactions/sec at peak (holiday shopping, flash sales).

Capacity estimate

Assume a platform processing 5,000 transactions/sec on average globally, with an 8x peak multiplier for events like Black Friday — about 40,000 transactions/sec at peak. Each transaction needs roughly 30 features looked up (mix of real-time behavioral aggregates and stored profile data), so at peak that's 40,000 x 30 ≈ 1.2 million feature reads/sec. That single number is why the feature store has to be an in-memory key-value store, not a general-purpose database — nothing else clears that read rate at that latency.

For model inference, assume a lightweight gradient-boosted tree model (chosen specifically for speed, not a large deep model) with a p99 inference time of 5ms on CPU, and assume one server replica, with batching, can sustain about 2,000 inferences/sec. To handle 40,000 transactions/sec at peak you need roughly 20 replicas at minimum, so provision around 30 for headroom and failover.

Audit logging: each scored transaction with its features and decision is roughly 2 KB. At 5,000/sec average over a full day (86,400 seconds), that's about 432 million events/day x 2 KB ≈ 864 GB/day of raw data. Ninety days of hot retention for model training and audits is on the order of 75-80 TB, with older data moved to cold storage rather than kept fully queryable.

    "amount": "249.00", "currency": "USD",

  -> { "decision": "allow" | "challenge" | "block",
       "riskScore": 0.83, "reasons": ["velocity_high", "new_device"] }

High-level design

Deep dive

Hitting a sub-100ms budget with a feature store and a model in the loop. The only way this works is by never computing anything expensive at request time. The streaming aggregator continuously maintains rolling counts (like "failed attempts in the last 10 minutes") in the background, so the synchronous path only ever does fast in-memory reads, never an on-the-fly aggregation over raw events. The model itself is chosen for speed over raw accuracy in this path — a small gradient-boosted tree model, not a large neural network — with heavier models reserved for the asynchronous re-scoring path after the decision has already been made.

Fail-open vs. fail-closed is a business decision, not just an engineering one. When the fraud service itself is down or times out, the payment gateway has two choices: fail closed (block everything until it's back) or fail open (allow the transaction, but flag it for after-the-fact review). Failing closed protects against fraud during the outage but takes down all revenue on that path; failing open protects revenue but accepts some fraud exposure during the degraded window. Most payment-adjacent fraud systems choose fail-open, but the right answer genuinely depends on transaction size and the business's risk tolerance — this is a question worth pushing the interviewer on rather than assuming.

Training-serving skew and delayed labels. The model is trained on features computed by a batch job, but served on features computed by a streaming job — if those two pipelines drift apart in subtle ways, the model quietly degrades without any obvious error (this is called training-serving skew). Confirmed-fraud labels also arrive late — chargebacks can take weeks to land — so the training set is always somewhat stale, which is exactly why deterministic rules exist as a fast-reacting complement to ML rather than a legacy leftover: a fraud analyst can ship a new rule the same day a new attack pattern appears, long before enough labeled data exists to retrain a model on it.

Trade-offs

At 10x scale, the streaming aggregator's rolling-window computation is what breaks first, not the model server. A card-testing botnet hammering one BIN (bank identification number) range, or a single very popular merchant, creates hot-key skew in the stream-processing join. The usual fix is a simpler, dedicated fast-path counter (a plain Redis counter with a time-to-live, not a full streaming join) for the highest-cardinality "hot" signals — trading some precision in the windowing for a system that doesn't fall over under skew. Separately, on fail-open vs. fail-closed from the deep dive: whichever you pick, it needs to be a documented, deliberate policy that risk/compliance signed off on — not a default that nobody chose on purpose.

Say this

"I'd default to fail-open with async flagging, not fail-closed, because for most transaction sizes the cost of blocking 100% of legitimate revenue during an outage is worse than the fraud exposure of one degraded window — but that threshold is a business risk call, and I'd want risk and finance to explicitly own that number, not just inherit whatever the engineering default happens to be."

Final design

One picture: a transaction hits a synchronous path that reads pre-aggregated features from an in-memory store, runs them through fast rules and a small ML model, and returns a decision within roughly 80ms — every decision is logged asynchronously for review, retraining, and a feedback loop from confirmed chargebacks back into the model.

EM-level follow-up

Rolling out a new model version needs shadow mode first — score every real transaction with the new model in parallel, but don't let it make real decisions — followed by a staged rollout with an explicit kill switch, because a bad model version doesn't just degrade a metric, it can block real customers or let real fraud through immediately. On build-vs-buy: most companies start with a third-party fraud vendor (Sift, Riskified, Stripe Radar) and only justify an in-house pipeline once volume and unit economics make the ML and ops investment worth it. Cross-team: risk and compliance own the actual block/allow threshold policy; engineering owns the pipeline that enforces it; and in some jurisdictions, legal is on the hook for false-positive complaints, so this genuinely spans three organizations, not one.

Design a Loyalty / Rewards-Points System

Problem framing

This system tracks how many points a customer has earned across many different events (purchases, referrals, promotions) fed by multiple upstream systems, and lets them spend those points on rewards. It looks like a simple counter, but it has to behave like real money — a wrong balance is a customer-trust incident and, at scale, an accounting liability.

Clarifying questions

  • One business, or a shared program across partner merchants? — a shared program (like a credit-card points program or airline alliance) needs a ledger per partner and a settlement process between them; assume a single-business program here.
  • Do points expire? — this changes the design from "one balance integer" to "tracking distinct earned lots with their own expiry dates," so the system can expire oldest-first.
  • Can a redemption take the balance negative, e.g. via a refund clawback? — this drives how strict the debit-side locking needs to be.
  • Is the reward catalog fixed-value cash-back, or a marketplace with limited-inventory items? — limited inventory means we inherit the same overselling problem as e-commerce checkout.
  • Does the app need to show an instantly up-to-date balance right after a purchase? — if the answer is "yes, always," that constrains how much we can lag the earn pipeline behind the purchase event.

Requirements

Functional:

  • Credit points on qualifying events, using earn-rate rules that can vary by event type, partner, or promotion.
  • Show current balance and let members redeem points from a catalog.
  • Expire old points on a first-in, first-out (FIFO) basis, and reverse points on a refund.

Non-functional:

  • Balance correctness above all else — treat this like a financial ledger, not a counter, because that's effectively what it is.
  • Idempotent processing — upstream systems will retry on timeout; the same earn event must never be credited twice.
  • Full auditability — every earn, redeem, expiry, and reversal needs to be individually explainable.
  • Scale to hundreds of millions of accounts with billions of earn events a year, and read-heavy balance-check traffic.

Capacity estimate

Assume 50 million active members, averaging 3 earning events/member/month — that's 150 million earn events/month, or about 5 million/day, roughly 58 events/sec on average, with a 10x holiday-shopping peak putting it near 580/sec. Each ledger entry is small, maybe 150 bytes, so raw ledger growth is about 150M x 150B ≈ 22.5 GB/month, or roughly 270 GB/year — easy for a partitioned relational store, with a multi-year retention window before archiving for dispute resolution.

Redemptions are far lower volume: assume 10% of members redeem monthly, so 5 million/month, about 167,000/day, roughly 2/sec on average. The real risk here isn't throughput, it's contention — a promotion offering 50 discounted items to 500,000 eager members racing at the same moment is a small, hot inventory-contention problem, not a scale problem.

Balance reads dominate: if 50 million members open the app twice a day on average, that's 100 million balance checks/day, about 1,157 reads/sec average and roughly 5,800/sec at peak. This is a read-heavy system by a wide margin, which is exactly why the design caches the current balance aggressively and reserves the ledger itself for history and audit lookups, not every balance check.

  -> { "ledgerEntryId": "...", "pointsCredited": 42 }

  -> { "balance": 4820, "pointsExpiringNext90Days": 300 }

  { "originalEventId": "upstream-txn-123", "reason": "refund" }

High-level design

Deep dive

Treat points like money: an append-only ledger, not a mutable counter. Every earn, redeem, expiry, and reversal is its own immutable row; the "balance" shown to a member is a materialized sum over that ledger, never the source of truth itself. This is the same double-entry mindset used in a digital wallet's ledger — it's what makes a "why did my balance change" support ticket answerable months later, and it's what makes clawbacks and audits mechanical instead of a forensic investigation.

Idempotency has to be enforced at the database, not just in application code. Every partner or point-of-sale integration will retry a timed-out call. The earn event's idempotency key — usually the upstream system's own transaction id — needs a unique constraint on the ledger table itself, because two application servers can both be processing the same retried event at nearly the same moment; app-level "check then insert" logic alone has a race window.

FIFO expiration without scanning every account every night. Instead of iterating through all 50 million members' histories nightly to find what's expiring, tag every earn entry with its own expiry date at write time, and index the ledger so an expiration worker can directly query "entries expiring today" — for example by bucketing writes by expiry month. This turns a full-table scan into a targeted range query.

Redemption against limited-inventory rewards is the same problem as e-commerce checkout. A naive "check balance, then decrement" is a race condition under load. The fix is a conditional write — a compare-and-swap style decrement, or a short-lived reservation with a timeout — not a read-then-write pair. See the E-commerce Checkout and Inventory problem in this chapter for the same pattern applied to physical stock.

Trade-offs

The balance cache is what saves this system at scale — without it, every app open would hit the ledger directly. But a cache bug that under-counts a redemption (serves a stale, too-high balance) lets a member spend points they don't actually have. The fix is to never let the cache be the thing that authorizes a debit: redemption always does a conditional write against the ledger's authoritative running total, and the cache is purely a fast read path allowed to lag by a few seconds, never the decision-maker for a spend. Separately, bucketing ledger writes by expiry month makes expiration cheap to query, but it means the write path has to know the expiry policy at write time — if the business changes how long points live after they've already been written, you can't cheaply re-bucket years of history, only apply the new policy going forward.

Say this

"I'd never let a cached balance authorize a debit. The cache is great for the read-heavy 'show me my balance' path, but redemption has to go through a conditional check against the ledger's real running total — otherwise a stale cache read becomes a member spending points that don't exist."

Final design

One picture: idempotent earn events append to a ledger, a fast cache serves the high-volume balance-read path, redemption debits go through a conditional check against the ledger — not the cache — and expiration plus reversal are just more entries in the same ledger. The whole system is bookkeeping wearing a rewards-app skin.

EM-level follow-up

Launching a new earn-rate promotion (like "5x points this weekend") should be config-driven, not a code deploy — see the Feature-Flag System and Global Configuration Service problems in this chapter for the distribution pattern — and it needs a hard budget cap, since a mispriced promotion is a direct financial liability, not just a product experiment. On build-vs-buy: many mid-size companies use a white-label loyalty platform rather than build the ledger and catalog themselves, but a bank or airline with real regulatory and scale requirements usually builds. Cross-team: outstanding points are a real liability on the balance sheet under breakage accounting rules, so the ledger's expiry and redemption data feeds finance, not just product analytics.

Design an A/B-Testing Experimentation Platform

Problem framing

This is the system that lets a product team say "show 50% of users the new checkout button, keep the rest on the old one, and tell me if conversion goes up" — without every team hand-rolling random assignment, event logging, and statistics from scratch, and getting any of those subtly wrong.

Clarifying questions

  • Self-serve for any team, or a small central team running a few high-stakes experiments? — self-serve pushes more weight onto guardrails (like an automatic sanity check on results) since you can't rely on every user being a statistics expert.
  • Server-side assignment only, or client-side too (mobile/web)? — latency-sensitive UI experiments (like changing a button before first render) often need assignment available locally, without a network round trip.
  • Simple A/B conversion-rate tests, or do we need sequential testing or multi-armed bandits for faster decisions? — this changes the statistics engine significantly; assume standard fixed-horizon A/B testing here.
  • Do experiments need to avoid interfering with each other when a user is in several at once? — if yes, we need "layers" (mutually exclusive experiment groups) as part of the assignment design.
  • Do experiment owners need a live dashboard, or is next-day good enough? — this drives whether the stats engine runs as a streaming job or a nightly batch job.

Requirements

Functional:

  • Define an experiment (variants, traffic allocation percentages, targeting rules).
  • Assign a consistent variant to a user for the life of the experiment.
  • Log exposure (the user actually saw the variant) and outcome/metric events.
  • Compute per-variant statistics — conversion rate, confidence interval, statistical significance — and flag results reliably.

Non-functional:

  • Deterministic and sticky assignment — the same user gets the same variant every time, even across a service restart.
  • Low-latency assignment — often called from the hot path of a page render, so it needs to be well under 10ms.
  • High write throughput for exposure and outcome event logging.
  • No hidden bias from infra failures — an outage must not quietly drop events for only one variant, which would make results look significant for the wrong reason.

Capacity estimate

Assume 100 million daily active users and 500 concurrent experiments running platform-wide, each one targeting roughly 5% of daily active users at random — about 5 million touched users per experiment. If each touched user generates about 2 exposures/day across repeat visits, that's roughly 500 experiments x 5 million users x 2 ≈ 5 billion exposure events/day, or about 58,000 events/sec on average, with a 3x peak multiplier putting it near 174,000 events/sec.

Each exposure event is small — user id, experiment id, variant, timestamp — call it 100 bytes. That's 5 billion x 100 bytes ≈ 500 GB/day of raw exposure data, feeding a columnar analytics store for statistics computation. Thirty to ninety days of hot retention for active experiments is on the order of 15-45 TB, which is easily within reach of a standard data-warehouse setup.

The assignment path itself is read-mostly and needs to answer "what variant is user X in for experiment Y" at up to 174,000 QPS at peak. The key design decision that makes this cheap is that assignment doesn't need a database lookup at all in the common case — it's a pure computation (see deep dive), so the real capacity question is event-logging throughput, not assignment throughput.

High-level design

Deep dive

Deterministic, stateless assignment. Never store "which variant did user X get" in a table you have to query on every request. Instead, hash the pair (user id, experiment id) plus a fixed salt with a fast, well-distributed hash function (MurmurHash is a common choice) into a number in [0, 100), and let each variant own a contiguous slice of that range sized to its traffic allocation. Assignment becomes a pure function — no database call, sub-millisecond, and naturally sticky as long as the experiment's bucket configuration doesn't change mid-flight. That last clause matters: changing traffic allocation partway through an experiment reshuffles who lands in which bucket, which is why experiment configs should be treated as versioned and effectively append-only, not edited in place.

Sample ratio mismatch and the exposure-vs-eligibility distinction. A subtle, common bug is logging "assigned" as if it means "saw the feature." If the control code path fails faster or more often than the treatment path for an unrelated reason, you can end up over-counting control impressions relative to what the traffic split intended, producing a result that looks statistically significant but is actually measuring a bug. The fix is discipline in the pipeline: separate assignment (eligible, purely computed) from exposure (the client confirms it actually rendered the variant) from outcome (the metric itself), plus an automated sample ratio mismatch (SRM) check — comparing the observed variant split against the configured split — that has to pass before anyone is allowed to trust a result.

Interaction effects between concurrent experiments. The same user can be in several experiments at once; if two of them both touch checkout, their combined effect isn't necessarily the sum of their individual effects. The standard fix is "layers" — mutually exclusive experiment groups that guarantee any one user is in at most one experiment per layer — at the cost of fragmenting the available traffic pool as more concurrent experiments compete for layer space.

Trade-offs

At 10x scale, the real bottleneck isn't event throughput — Kafka plus a columnar warehouse scales that horizontally without much drama. It's traffic scarcity: there's a fixed daily-active-user pool, and every additional concurrent experiment either shrinks the sample each one gets (slower to reach significance) or forces more aggressive layering, a prioritization problem for the org running experiments, not something more servers can fix. Separately, hash-based stateless assignment is fast and simple, but it means you cannot cheaply "regrade" an existing user into a different bucket without changing the salt or experiment id — which is exactly the point (it keeps assignment sticky), but it also means a bug in the original bucket-range math can't be silently patched without effectively starting a new experiment for everyone.

Say this

"The key design choice is that assignment is a pure hash function, not a lookup — that's what keeps it off the database and under a millisecond at any scale. Everything downstream, including the sample-ratio-mismatch check, exists to catch the ways that simplicity can go subtly wrong."

Final design

One picture: deterministic hash-based assignment with no database call in the hot path, async exposure and outcome events flowing through a stream into a columnar warehouse, and a stats engine that computes significance behind an automated sample-ratio-mismatch gate before anyone is allowed to read a result as trustworthy.

EM-level follow-up

Most organizations start experimentation with one central team running tests by hand — sometimes literally in a spreadsheet — and only build (or buy) a self-serve platform once demand from other teams grows past what manual review can support; established vendors like Optimizely, LaunchDarkly, or Statsig are usually the right call before headcount-scale usage justifies an in-house platform. Cross-team impact: a bad statistical habit like peeking at results early and stopping as soon as they look good ("p-hacking," inflating false-positive rates by checking too often) is an org-wide credibility risk once enough teams do it — the platform's job is to make the statistically correct path the easy path, for example with built-in sequential-testing corrections, rather than trusting every product manager to know the pitfalls.

Design a Data Pipeline / ETL Orchestration Platform

Problem framing

A platform team is asked to build a hosted service — think an internal version of Apache Airflow or Dagster — that lets hundreds of other teams define, schedule, and monitor their own data pipelines without running any infrastructure themselves. A pipeline here is a DAG: a directed acyclic graph, meaning a set of tasks connected by dependency arrows, where no arrow ever loops back on itself. For example: "wait for yesterday's raw event logs to land in the data lake, then run a job that aggregates them, then load the result into the data warehouse." The platform's job is to run thousands of these DAGs on a schedule, retry the pieces that fail, and keep working even when one tenant's pipeline misbehaves.

Clarifying questions

  • Do pipelines run arbitrary code, or only a fixed set of operators (SQL, Spark job, S3-to-warehouse copy)? — arbitrary code means we need real sandboxing (containers with CPU/memory limits); a fixed operator set lets some tasks skip full isolation.
  • Is this strictly batch, or does it also need to react to streaming events? — batch-only keeps the scheduler simple (poll on a timer); reacting to events adds a whole event-driven trigger path.
  • How many tenants, DAGs, and tasks per day are we designing for? — decides whether one shared metadata database is enough, or we need to shard by tenant from day one.
  • Do we need to support backfills — rerunning a pipeline over a historical date range? — a 90-day backfill can generate thousands of task-instances in seconds, which needs its own throttling so it doesn't drown live traffic.
  • What isolation do we owe one tenant from another? — decides whether we need per-tenant resource quotas and separate queue lanes, or a single shared worker pool is acceptable.
  • What happens on a missed schedule or task failure — page someone, or is a dashboard enough? — decides whether alerting is core to the design or bolted on later.

Requirements

Functional:

  • Users define a DAG (tasks, dependency edges, and a schedule such as a cron expression or "every hour") as code and push it to the platform.
  • The platform schedules due DAG runs and only starts a task once every upstream task it depends on has succeeded.
  • Failed tasks retry automatically with backoff; a task can also be retried manually.
  • Users can trigger a backfill: rerun a DAG across a range of historical schedule dates.
  • Users get a UI/API for run history, per-task logs, and current state.
  • On failure or a missed SLA (service-level agreement — the promised on-time schedule), the platform fires an alert.

Non-functional:

  • The scheduler must be highly available — a scheduler crash must never mean a schedule silently gets skipped.
  • One tenant's misbehaving DAG must not starve another tenant's on-time job (multi-tenant isolation).
  • At-least-once task execution: a task might run more than once (e.g. after a worker crash), so tasks are expected to be idempotent — running one twice has the same effect as running it once — and each task gets a stable identity to make that possible.
  • Scale to tens of thousands of DAGs and millions of task-runs a day.

Capacity estimate

Assume 500 data teams running 20,000 active DAGs, averaging 15 tasks each and 10 scheduled runs a day (a mix of hourly and daily jobs). That's 20,000 × 10 × 15 = 3,000,000 task-instances a day, or about 35 tasks/sec on average (3,000,000 ÷ 86,400 seconds). Real schedules cluster around common times — midnight UTC, top of the hour — so peak load runs closer to 10× average: roughly 350 tasks/sec.

By Little's Law (average concurrent work = arrival rate × average time each item spends in the system), if the average task runs for 3 minutes (180 seconds), average concurrency is 35 × 180 ≈ 6,300 tasks running at once, spiking to 350 × 180 ≈ 63,000 at peak. If each worker node safely runs about 20 lightweight task containers at a time, that's roughly 300 nodes at steady state, autoscaling to about 3,000 nodes at peak.

Metadata: 3,000,000 task-instances/day × 365 days ≈ 1.1 billion rows a year if kept in full; at roughly 500 bytes/row that's about 550 GB/year of task-state metadata. A single well-indexed relational database can hold a rolling 90-day hot window (≈135 GB) with older runs archived to cheaper storage.

Logs: if the average task emits 50 KB of logs, that's 3,000,000 × 50 KB = 150 GB of log data a day — far too much for a database, so logs go straight to object storage with only a pointer kept in the metadata database.

API design

POST /v1/dags/{dag_id}/versions        # register a new DAG spec (tasks, edges, schedule)
POST /v1/dags/{dag_id}/runs            # trigger a run (manual, or a backfill window)
GET  /v1/dags/{dag_id}/runs/{run_id}   # run status + per-task states
POST /v1/dags/{dag_id}/runs/{run_id}/tasks/{task_id}/retry
GET  /v1/dags/{dag_id}/runs?start=2026-01-01&end=2026-03-31  # list runs, e.g. for a backfill range
POST /v1/dags/{dag_id}/pause
POST /v1/task-instances/{id}/heartbeat  # worker -> control plane: "still alive"
POST /v1/task-instances/{id}/complete   # worker -> control plane: final state

High-level design

Deep dive

Scheduler high availability and the "missed schedule" problem. If the scheduler is a single process and it dies for five minutes at midnight, do the 5,000 DAGs scheduled for midnight just never run? The fix is leader election: several scheduler instances run at once, a leader lease (via a database row lease, or a coordination service like etcd/ZooKeeper) decides which one is active, and on failover the new leader's first job is to scan for any schedule window it missed and catch it up — which only works safely if catch-up runs are idempotent.

Multi-tenant isolation (the noisy-neighbor problem). A shared task queue and worker pool mean one tenant's 50,000-task backfill can delay another tenant's small daily job. The fix borrows from rate limiting: give each tenant a resource quota (a maximum count of concurrently running tasks, similar to Airflow's "pools"), route their tasks through separate queue partitions or priority lanes, and enforce container-level CPU/memory limits so a runaway task can't starve its node's neighbors.

Backfill semantics and idempotency. A backfill is really "replay history at high speed," and it must not overwhelm the live queue meant for real-time jobs. Route backfill task-instances through a lower-priority queue lane, and require tasks to write results keyed by their execution date (not append blindly) so replaying the same date twice doesn't double-count data.

Trade-offs

At 10× scale (200,000 DAGs, ~30 million task-instances/day), the single metadata database becomes the write bottleneck — task-state transitions alone would need thousands of writes/sec, well past what one relational primary comfortably sustains. The fix is to shard hot task-state writes by tenant or move them to a horizontally-scalable store, while keeping DAG *definitions* (low write volume) in the simpler relational database — trading one simple system of record for two systems with different consistency guarantees.

Say this

"I'd guarantee at-least-once task execution with idempotent tasks rather than try for exactly-once — exactly-once distributed execution is effectively impossible to guarantee end-to-end. I push the idempotency requirement to the task author and give them a stable execution key — dag_id + task_id + execution_date — they can use to detect and skip duplicate work."

Final design

A control-plane API stores DAG definitions and state in a metadata database. A leader-elected scheduler polls for due schedules and enqueues task-instances onto a task queue. An autoscaling worker fleet pulls from that queue, runs each task in an isolated container, writes logs and artifacts to object storage, and reports state back. Failures and SLA misses fire through an alerting service to on-call. Per-tenant quotas and priority queue lanes keep one tenant's load from starving another's.

EM-level follow-up

Before building this: could a managed offering (AWS MWAA, Dagster Cloud, GCP Composer) meet the bar instead of running the orchestration layer in-house? Building usually only wins on cost at very large scale, or when tenant isolation/security requirements are unusually strict. On rollout: 500 teams currently run cron jobs somewhere — migration has to be incremental, dual-running the old and new schedulers per-DAG until each team cuts over, rather than a single flag-day switch that risks silently dropping someone's pipeline.

Design a Disaster-Recovery and Backup-and-Restore Platform

Problem framing

A platform team is asked to build the backup-and-restore layer that every other team's database sits on top of: automated, scheduled backups; the ability to restore any registered database to a point in time; and a program of regularly testing that those backups actually work. This is not the "stay up during a regional outage" problem (that's the Multi-region active-active platform problem elsewhere in this chapter) — this is the "our data got corrupted, deleted, or encrypted by ransomware, and we need it back" problem. The audience asking for this is usually a platform/SRE team under compliance pressure (SOC2, customer contracts) to prove, with evidence, that every production data store can be recovered within a promised time.

Clarifying questions

  • What RPO/RTO do different data stores need? — RPO (recovery point objective — how much data you can afford to lose, measured in time) and RTO (recovery time objective — how long you can afford to be down) drive whether we need continuous log shipping or nightly snapshots are enough.
  • Which data-store types are in scope — relational, document, object storage, all of them? — each has a different native backup mechanism (binlog/WAL vs. storage-layer snapshot vs. bucket versioning).
  • Does DR need to cross regions, or is single-region backup enough? — cross-region protects against a whole-region disaster but roughly doubles storage cost.
  • Who can trigger a restore, and does it need an approval gate? — a self-serve restore into production is dangerous; most orgs require a second approver for anything touching prod.
  • Do we need to defend against a compromised admin account deleting backups (ransomware)? — if yes, backups need to be immutable, with delete authority separated from normal production credentials.
  • What compliance retention windows apply? — some regulations require years of retained financial records, which changes the storage math a lot.

Requirements

Functional: automated scheduled backups (full + incremental) per registered source; point-in-time recovery via log shipping where the source supports it; cross-region replication of backups for Tier-1 sources; a self-serve restore workflow with an approval gate for production targets; automated restore-verification drills; retention-policy lifecycle management; alerting on backup failure or SLA breach.

Non-functional: differentiated RPO/RTO by criticality tier (below); backups must not meaningfully degrade source production performance; backup storage itself must be durable and, for Tier-1, immutable — meaning it cannot be deleted or altered before its retention date expires, even by someone with normal admin credentials.

Capacity estimate

Assume 2,000 registered data sources holding 500 TB of production data in total — an average of 250 GB per source — split into 300 Tier-1 sources and 1,700 Tier-2/3 sources.

For a Tier-1 source: a daily incremental capturing ~5% churn is ~12.5 GB; 30 days of dailies is 375 GB. A weekly full compressed to ~40% of source size is 100 GB; 12 monthly fulls kept for a year of compliance history is 1.2 TB. That's roughly 1.6 TB per Tier-1 source. Across 300 sources: 300 × 1.6 TB ≈ 480 TB, doubled for cross-region replication ≈ 960 TB.

For Tier-2/3 (smaller, ~200 GB average, lighter retention — a week of dailies plus 3 monthly fulls, ~310 GB per source): 1,700 × 310 GB ≈ 527 TB, single-region only.

Total steady-state footprint: roughly 1.5 PB — about 3× the 500 TB of live production data, a normal ratio once retention windows and cross-region copies are counted.

Throughput: staggering full backups across the week (~1/7 of sources per night) means ~286 sources doing a full backup on any given night, at 250 GB each = 71.5 TB inside a 4-hour window — about 17.9 TB/hr, or roughly 5 GB/s sustained write throughput into the backup storage tier.

Restore check against the 30-minute Tier-1 RTO: hydrating a 250 GB snapshot at 500 MB/s takes ~500 seconds (~8 minutes), leaving over 20 minutes of headroom for provisioning a fresh instance and replaying the WAL up to the failure point.

High-level design

Deep dive

Hitting RPO without hurting production. A snapshot that locks the primary database for minutes is unacceptable on a live payments table. Tier-1 sources instead stream their write-ahead log or binlog (the append-only record of every change) continuously to the backup platform, which can replay it to reconstruct any point in time; the periodic "snapshot" is really just a base point that WAL replay starts from, taken via a storage-layer mechanism (like a volume snapshot) that doesn't block the primary.

Surviving a compromised admin account (ransomware resistance). If backups can be deleted with the same credentials that manage production, an attacker who owns those credentials can destroy your recovery path along with your data. The fix is WORM storage — write-once-read-many object storage (e.g. S3 Object Lock) that mathematically cannot be overwritten or deleted before its retention date — with deletion authority living in a separate security boundary that requires a break-glass process to touch.

Restore drills — proving a backup is actually restorable. An unverified backup is a hope, not a guarantee: silent corruption, a broken WAL chain, or a schema mismatch can all make a "successful" backup unrestorable. The platform runs scheduled automated drills — restore into a sandbox, then validate row counts and checksums against the source — and treats a failed drill as seriously as a failed live backup.

Trade-offs

At 10× scale (20,000 sources, multi-petabyte footprint), a single nightly backup window can no longer fit — you can't stagger 20,000 sources across one 4-hour window without exceeding storage-tier write throughput. The fix is to spread backups across a rolling 24-hour window instead of "the 2am batch," and shift Tier-1 sources fully to continuous log-shipping rather than periodic snapshot-plus-full — trading a simple nightly-job mental model for a continuously-running pipeline that's harder to reason about but scales.

Say this

"I wouldn't apply one RPO/RTO target to every data source — that's how you either overspend protecting databases nobody depends on, or under-protect the ones that actually matter. I'd tier sources by business criticality and only pay for continuous log-shipping and cross-region replication on Tier-1, where a few minutes of lost data is genuinely expensive."

Final design

Per-source agents stream WAL/binlog and periodic snapshots into a backup job queue. An orchestrator enforces tiered schedules and retention policy against a central catalog. Snapshots land in regionally-replicated, immutable object storage. A restore service reads from that catalog and storage on approval-gated request, and a drill runner continuously proves the whole chain actually works by restoring and validating on a schedule — closing the loop that a passive "backup exists" check would miss.

EM-level follow-up

Build-vs-buy: cloud-native offerings (AWS Backup, GCP Backup and DR) cover a lot of this out of the box — building bespoke usually only makes sense for cross-cloud consistency, unusual compliance needs, or cost at very large scale. On rollout: onboarding 2,000 existing databases without ever touching production write paths is the real project risk, so the migration order should start with lowest-criticality sources, prove the restore-drill pipeline works there first, then move up to Tier-1. Cost-wise, 1.5 PB of backups is a real line item — lifecycle rules that move old backups to cheaper cold storage classes matter as much as the initial architecture.

Design a Developer API Platform with Billing and Metering

Problem framing

A company (think Stripe, Twilio, or an internal platform team letting other product teams expose a paid API) needs a platform that authenticates every external API call, counts usage precisely per customer, enforces plan limits in real time, and turns that usage into an accurate monthly invoice. The hard part isn't serving the API — it's that "usage" now equals "money," so every counting bug is a billing dispute, and every dropped event is either lost revenue or an over-charged customer.

Clarifying questions

  • What's the billing model — pure pay-per-call, tiered plans with overage, or a subscription plus usage add-on? — changes whether we need a pricing-rules engine or a flat per-unit multiply.
  • Does a customer hitting their plan limit need a hard real-time cutoff, or is nightly reconciliation enough? — a hard cutoff needs a fast synchronous counter check on every request; without it, metering can be fully asynchronous.
  • Is this one API or many product teams' APIs under one shared metering/billing layer? — multi-product means a shared client library so every team meters consistently, not five different homegrown counters.
  • Do we need multi-currency and tax handling? — pulls in real invoicing/tax complexity that's usually delegated to a specialist system rather than built fresh.
  • Do developers need a self-serve usage dashboard and usage-threshold webhooks? — decides whether the aggregation pipeline needs to expose a low-latency read path, not just a monthly batch.
  • How do we prevent free-tier / trial abuse (one person spinning up many accounts)? — affects whether account creation needs its own fraud signals, separate from metering correctness.

Requirements

Functional: API key issuance and auth scoped per customer/app; per-request usage metering; rate limiting per plan tier; usage aggregation by customer and billing period; pricing-rules engine (tiers, overage) and invoice generation; payment collection (handed off to an actual payment processor — see the Payment gateway problem elsewhere in this chapter for how the money itself moves); self-serve usage dashboards and usage-threshold webhooks.

Non-functional: metering must be accurate to the smallest billable unit — no double-counting, no silent drops; the metering pipeline must not add latency to the API request path (async, not synchronous, on the hot path); every billed unit must be traceable back to a raw request log for dispute resolution; the pipeline must survive the billing engine being down without losing usage events.

Capacity estimate

Assume 50,000 active developer accounts averaging 200,000 API calls each per month: 50,000 × 200,000 = 10 billion calls/month. Average QPS: 10,000,000,000 ÷ (30 × 86,400 sec) ≈ 3,860 requests/sec; at a 5× peak-to-average ratio typical of business-hours traffic, design for roughly 19,000 QPS.

Every call emits one usage event — {api_key, endpoint, quantity, timestamp, idempotency_key} — at roughly 200 bytes. 10 billion events × 200 bytes = 2 TB/month of raw event volume, small enough that a durable log can retain a full week (≈470 GB) for replay and reconciliation.

Aggregating into (customer, endpoint, day) rollups produces about 50,000 × 20 endpoints × 30 days = 30 million rows a month — trivial for a warehouse.

At month end, computing 50,000 invoices (each applying tiered pricing across ~20 endpoint dimensions) at ~50 ms compute each is 50,000 × 50 ms = 2,500 seconds of work — about 42 minutes single-threaded, and easily parallelized across workers to finish in a couple of minutes.

API design

Authorization: Bearer <api_key>                 # carried on every product API call

POST /v1/usage/events                          # gateway -> metering: {api_key, metric, quantity, idempotency_key}
GET  /v1/customers/{id}/usage?period=2026-07   # usage-to-date for the current billing period
GET  /v1/customers/{id}/invoices/{invoice_id}
POST /v1/plans                                 # define pricing tiers + overage rate
POST /v1/customers/{id}/subscriptions          # attach a customer to a plan

High-level design

Deep dive

No double counting. A gateway retry after a timeout must never bill the same call twice. Every usage event carries an idempotency key (typically a request ID), and the metering service deduplicates on that key before an event is counted — the same mechanism the outbox pattern uses to avoid double-publishing, applied here to double-billing.

Keeping metering off the hot path. The API request path can't synchronously wait on a durable write to the metering pipeline — that adds latency and a new failure dependency to every single call. Events are emitted asynchronously (fire-and-forget into a durable stream), buffered locally at the gateway so a brief downstream hiccup doesn't drop events, with periodic reconciliation of raw gateway request logs against metering aggregates to catch any drift before it reaches an invoice.

Real-time quota checks vs. an eventually-consistent bill. Enforcing "reject calls over the hard cap" needs a counter check in single-digit milliseconds — a Redis-backed counter sharded by API key. The actual invoice, by contrast, is computed from the durable, replayable event log and can lag by minutes to hours. These two paths are allowed to briefly disagree (a customer might squeak a few calls over the cap before the counter catches up); the design accepts that and reconciles later rather than forcing one slow, strongly-consistent system to serve both jobs.

Trade-offs

At 10× scale (100 billion calls/month, ~38,600 average QPS, ~193,000 peak QPS at the same 5x peak-to-average multiplier), a single Redis primary tracking per-key quota counters becomes a hot-key bottleneck for the platform's largest customers. Sharding counters by API-key hash across a Redis cluster fixes throughput but relaxes global-quota accuracy slightly — a customer can briefly exceed their cap by a small margin across shards — the same throughput-for-accuracy trade every sharded rate limiter makes.

Say this

"I'd keep the billing source of truth as an immutable, replayable event log, not mutable counters — every invoice needs to be reconstructable and defensible in a dispute. Counters are a read-optimized cache on top of that log for fast quota checks, not the record of truth."

Final design

The gateway authenticates each call, checks a sharded real-time counter for quota enforcement, and asynchronously emits a deduplicated usage event into a durable stream. A metering service consumes that stream into a usage warehouse, which a monthly billing engine turns into reconciled, auditable invoices — with the same durable event log backing both the fast quota path and the slow, correct billing path.

EM-level follow-up

Build-vs-buy: a platform team without deep billing-domain expertise should seriously evaluate Stripe Billing or Metronome before building metering-plus-invoicing in-house — billing edge cases (proration, refunds, tax, dunning) are a deep specialty. Cross-team impact: every product team onboarding to this platform must instrument their API through a shared client library, not a homegrown counter, because a metering bug is now a revenue bug — it deserves the same review rigor as the actual Payment gateway problem, not just normal feature-code review.

Design a Real-Time Analytics Dashboard Platform

Problem framing

An internal observability team is asked to build the platform behind every dashboard employees look at during an incident or a business review — think an internal Grafana backed by a Prometheus-like time-series store. Thousands of services push metrics continuously; thousands of employees have dashboards open, auto-refreshing every few seconds. The platform has to ingest a huge, constant stream of writes and serve a huge, spiky stream of reads, both with tight latency, on the same underlying data.

Clarifying questions

  • Infra metrics, business metrics, or both? — both are just time series (a metric name, some tags, a timestamp, a value), so the design generalizes, but the volume and cardinality profile differs.
  • Mostly fixed, recurring dashboard queries, or heavy ad-hoc exploration? — recurring queries are cacheable and pre-aggregatable; ad-hoc queries need a flexible query engine that can't rely purely on cache.
  • How fresh does "real-time" need to be — seconds, or is a minute of lag fine? — sub-second freshness rules out any heavy batch step in the write path.
  • How long do we retain raw vs. rolled-up data? — drives most of the storage cost calculation.
  • Do different teams need isolation so one team's expensive query can't slow another's dashboard? — decides whether we need separate query lanes/pools per workload type.
  • Does this also drive alerting (a rule that pages someone when a metric crosses a threshold)? — if yes, the same query engine needs a scheduled-evaluation mode, not just interactive queries.

Requirements

Functional: ingest time-series data points from thousands of sources; store and query them with flexible tag filtering and aggregation (sum, average, percentile, group-by); serve saved dashboards of panel queries with auto-refresh; support ad-hoc exploration; evaluate alerting rules against the same data.

Non-functional: sustain very high write throughput; dashboard query p99 latency under roughly 500 ms–1 s even with thousands of concurrent viewers; tiered retention — high resolution for a recent window, downsampled rollups for the long tail; isolation between teams' query load; a few seconds of ingest lag is acceptable, but a data point must never be silently and permanently dropped without a defined policy for it.

Capacity estimate

Assume 10,000 hosts/services, each emitting about 200 distinct time series (one continuously-updating sequence of timestamped values per metric+tag combination, e.g. cpu_usage{host=web-42}), scraped every 15 seconds. Active series: 10,000 × 200 = 2,000,000. Ingest rate: 2,000,000 ÷ 15 sec ≈ 133,000 points/sec average; design for roughly 250,000 points/sec to leave room for growth and bursts.

Each raw point is about 24 bytes (metric ID + timestamp + value); time-series databases compress this heavily with delta-of-delta timestamp encoding and XOR value encoding — the family of techniques Prometheus and Facebook's Gorilla paper popularized — down to roughly 1-2 bytes/point. At 250,000 points/sec × 1.5 bytes ≈ 375 KB/sec ≈ 32 GB/day ≈ 1 TB/month of compressed raw-resolution storage.

Retention: 15 days of native (15-second) resolution raw data (≈480 GB) plus 13 months of 5-minute rollups (≈2.5 TB) plus a few years of 1-hour rollups for long-term capacity planning (a few hundred GB) — roughly 3-4 TB of total compressed storage, which scales with the number of hosts and services, not with headcount.

Query load: with 20,000 employees keeping dashboards open, each showing 6 auto-refreshing panels every 30 seconds, that's 20,000 × 6 ÷ 30 ≈ 4,000 queries/sec from scheduled dashboards alone; round up with ad-hoc traffic to a 5,000 QPS design target. Because most of that traffic hits the same few hundred "golden" dashboards, a cache serving repeated identical queries can absorb the large majority of it — without a cache, a single panel scanning 50,000 raw points at 5,000 QPS would mean scanning 250 million points/sec from storage, which is why the cache is load-bearing, not optional.

High-level design

Deep dive

Cardinality explosion on the write path. Cardinality is the number of unique tag combinations a metric can produce. A well-behaved metric like cpu_usage{host, region} stays bounded, but one bad tag — say a raw user ID or a request ID used as a label — can turn 2 million series into 200 million overnight and take the whole storage tier down, because each unique combination is its own series with its own index entry. The ingest gateway enforces a hard cardinality cap per metric and rejects or downsamples outliers before they ever reach storage; see the sharding techniques used elsewhere in this book for how series get distributed once cardinality is under control.

Blending raw and rolled-up data on the read path. A query spanning "the last hour" should hit raw-resolution data; a query spanning "the last year" should transparently hit hourly rollups instead of scanning a year of raw points. The query engine picks the right resolution tier per time range automatically. Just as important: the handful of "golden" dashboards everyone looks at get their queries pre-computed on a schedule and materialized, rather than recomputed fresh on every single viewer's auto-refresh — that's what actually makes "thousands of QPS at sub-second latency" achievable, because most traffic becomes cache hits, not live scans.

Multi-tenant query isolation and backpressure. One team running a huge ad-hoc query over a year of high-resolution data shouldn't starve everyone else's 30-second dashboard refresh — separate query pools give "dashboard" traffic (fast, cached, SLA'd) priority over "ad-hoc/exploration" traffic (best-effort, can queue). On the write side, when ingest spikes beyond capacity, the system has to choose between dropping the newest points (staying fast, losing some freshness) or queuing them (staying accurate, falling behind); for metrics used in live incident response, staying close to real time usually wins, so bounded queues with drop-oldest are the typical choice.

Trade-offs

At 10× scale (20 million active series, ~2.5 million points/sec), single-node ingest gateways and the tag index — the structure mapping label combinations to series IDs — become the bottleneck first, not raw point throughput. Cardinality, not point rate, is what kills time-series systems at scale. The trade-off is capping cardinality per metric and pushing teams toward pre-aggregated metrics for their highest-cardinality dimensions, at the cost of losing some arbitrary group-by flexibility on raw data.

Say this

"The thing that breaks time-series systems isn't the points-per-second rate — it's cardinality, the number of unique label combinations. I'd put a hard cap on cardinality per metric at the ingest gateway and reject or downsample outliers, because an unbounded high-cardinality tag like a raw user ID can turn 2 million series into 200 million and take the whole cluster down."

Final design

Agents push metrics through an ingest gateway with cardinality guardrails into a buffered write path that shards data into a time-series storage engine, with a stream processor also writing downsampled rollups for long-term retention. A query engine transparently blends raw and rollup data behind a result cache that absorbs almost all dashboard traffic, with separate priority lanes so ad-hoc exploration can't starve scheduled dashboards.

EM-level follow-up

Build-vs-buy: most companies at this scale should evaluate a managed or open-source time-series stack (Prometheus with Thanos/Cortex/Mimir, or a vendor like Datadog) before building bespoke storage — the case for building is usually cost-at-scale (per-host vendor pricing gets expensive past a few thousand hosts) or a data-residency requirement, not that storing time series is uniquely hard. Cross-team impact: because this is a shared platform, one team's unbounded cardinality or expensive query degrades dashboards for the whole company, so the design needs self-serve guardrails — cardinality caps, per-query cost limits — rather than relying on a human to review every team's metrics before they ship.
