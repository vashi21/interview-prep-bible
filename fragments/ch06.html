One database on one machine always runs out of room or runs out of speed. This chapter covers the two fixes — splitting data across machines (sharding) and copying data across machines (replication) — and shows exactly how MySQL and MongoDB each do both in production.

01Why One Box Stops Being Enough

A single database server has two hard limits. Storage: a disk is only so big, and an index only stays fast up to a certain table size. Throughput: one machine can only answer so many reads and writes per second, no matter how good the hardware is.

There are two independent fixes, and real systems almost always use both together:

  • Partitioning / sharding — split your data into pieces (shards) so each machine only holds a subset of it. This fixes the storage limit and spreads write load across machines. "Partitioning" and "sharding" mean the same idea; people usually say "partitioning" for splitting inside one database instance and "sharding" for splitting across separate servers.
  • Replication — copy the same data onto more than one machine. This fixes availability (one machine dying doesn't lose data) and read throughput (more machines can answer read queries).

The rest of this chapter walks through the three ways to shard, the three ways to replicate, and then shows both concepts as they actually exist inside MySQL (via a routing layer called Vitess) and MongoDB (which has sharding and replication built in).

02Splitting The Data: Range, Hash, And Directory Sharding

Every sharding strategy answers the same question: given a row's shard key (the column value you shard on, usually something like user_id), which machine does this row live on? There are three answers.

Range-based sharding

Sort rows by the shard key and cut the sorted list into contiguous ranges. Shard 1 might hold user_id 1 through 1,000,000; shard 2 holds 1,000,001 through 2,000,000; and so on. A lookup just checks which range a key falls into — no computation needed, and range scans (fetch all users between two IDs) stay on one shard.

The weakness: if activity isn't spread evenly across the key range, one shard gets overloaded. New users, new posts, and anything with a rising ID or a rising timestamp all pile up at the newest end of the range — one shard takes all the write traffic while older shards sit idle.

Hash-based sharding

Run the shard key through a hash function (a function that turns any input into a fixed-size, evenly-scattered number) and use the result to pick a shard, usually with hash(key) % number_of_shards or, better, consistent hashing (see Ch.5) so adding a shard doesn't reshuffle everything. This spreads load evenly and kills the "hot range" problem.

The cost: you gave up order. A range query like "all orders from March" now has to ask every shard and merge the results, because March's orders are scattered across all of them by hash.

Directory-based sharding

Keep an explicit lookup table (a directory) that maps each key, or each range of keys, to a specific shard. A router service checks the directory on every request instead of computing an answer with math.

This is the most flexible option: rebalancing means moving individual rows in the directory, not redesigning a formula. The cost is that the directory itself is now a critical, highly-available service — if it's slow or down, every query is stuck, and it's one more moving part to operate.

03Copying The Data: Leader-Follower, Multi-Leader, And Leaderless Replication

Once you know how data is split, the next question is how it's copied. There are three topologies.

Leader-follower (single-leader) replication

One node, the leader (also called the primary), accepts all writes. It streams every change to one or more followers (replicas), which apply the same changes in the same order. Reads can go to the leader or to a follower; writes only ever go to the leader.

This is the simplest topology because there's no ambiguity about write order — one leader decides it. It's what MySQL, PostgreSQL, and a default MongoDB replica set all do.

Multi-leader (multi-master) replication

More than one node accepts writes — commonly one leader per data center — and leaders replicate changes to each other. This gives every region a local leader for low write latency, which matters for multi-region products.

The price is write conflicts: two leaders can accept a write to the same row at nearly the same time, and the system has to reconcile them (last-write-wins, a merge function, or pushing the decision to the application). This is real complexity that single-leader setups never have to think about.

Leaderless replication

There's no leader at all. A client (or a coordinator node) writes directly to several replicas at once and reads from several replicas at once, then reconciles which value is newest using version information and a quorum rule (see Ch.13 for vector clocks and quorum math, and Ch.9 for how Cassandra does this in detail). DynamoDB and Cassandra both work this way.

Leaderless systems trade strict ordering for very high write availability — as long as enough replicas are reachable, writes succeed even if some nodes are down or partitioned off.

04Synchronous Vs Asynchronous Replication, And Read Replicas

Independent of topology, every replication link has to decide when to tell the writer "done."

  • Synchronous replication — the leader waits for a follower to confirm it received (and often applied) the change before telling the client the write succeeded. Safer: if the leader dies the instant after that, the follower already has the data. Slower, and it lowers availability — if that follower is unreachable, the leader can't safely accept the write.
  • Asynchronous replication — the leader commits and replies to the client immediately, then ships the change to followers in the background. Fast and available, but there's a window where a crash on the leader loses whatever hadn't shipped yet.
  • Semi-synchronous replication — a practical middle ground: the leader waits for at least one follower to acknowledge it received the change (not necessarily applied it) before committing, then ships to the rest asynchronously. You pay one round trip of latency and get a durability guarantee that the last write isn't only on one machine.

Read replicas are followers kept around specifically to serve read traffic, not for failover. If your workload is read-heavy — most web apps are — you point read queries at a pool of replicas and keep the leader free for writes. The catch is replication lag: because that link is almost always asynchronous, a read right after a write can come back stale until the replica catches up. Products that need to read their own writes immediately either route that specific read to the leader or check how far behind the replica is first.

An EM-level answer adds the operational side: every read replica you add is another machine someone has to patch, monitor for lag, and fail over correctly. Managed offerings (Amazon RDS read replicas, MongoDB Atlas, PlanetScale for Vitess) absorb a lot of that toil — for a small team, paying for managed replicas is often cheaper than the on-call cost of running them yourselves in year one.

05MySQL In Practice: Sharding And Replication With Vitess

Plain MySQL doesn't shard itself — a single MySQL server is a single leader-follower unit. To shard MySQL, most large companies put a routing layer in front of a fleet of MySQL instances. The best-known one is Vitess, built at YouTube to scale MySQL for YouTube's own metadata, later open-sourced and now a CNCF project. Vitess's own list of adopters includes YouTube, Slack, GitHub, and Square, among others — Slack has talked publicly about moving its core MySQL fleet onto Vitess once a single-primary database ran out of write capacity for its job.

Vitess has three main pieces:

  • VTGate — a stateless query router. Applications connect to VTGate instead of to MySQL directly. It parses each query, figures out which shard(s) it needs using a Vindex (a pluggable rule that maps a column value to a shard), and forwards the query there.
  • VTTablet — a lightweight agent that runs next to every MySQL instance, handling connection pooling, query rewriting, and coordinating with the primary/replica topology for that shard.
  • Topology service — a small, separate key-value store (typically etcd) holding the cluster's shard map: which shard owns which keyrange, and which MySQL instance is currently the primary for that shard.

Vindexes are where all three sharding strategies from section 02 actually show up inside Vitess: a hash vindex hashes the shard key for even distribution, a plain range layout assigns contiguous keyranges to shards, and a lookup vindex keeps an explicit table mapping a secondary column (say, an email address) to its shard — that's directory-based sharding, built in.

Underneath each shard, replication is plain MySQL binlog replication: the primary writes every committed change to its binlog (binary log, an ordered record of data changes), and each replica streams that binlog and replays it. Row-based binlog format (logging the actual changed rows) is the safe default; statement-based logging can replay non-deterministic statements — anything using NOW() or a random function — differently on a replica than it ran on the primary. Replication is asynchronous by default; MySQL also offers a semi-sync plugin for the durability guarantee described in section 04. Vitess ships a component called VTOrc (Vitess Orchestrator) that watches primary health and automates promoting a replica to primary on failure, then updates the topology service so VTGate starts routing writes to the new primary.

Each shard's replicas double as that shard's read-replica pool: VTGate can route read-only queries to replicas and writes to the primary, exactly the read-replica pattern from section 04, just scoped per shard instead of per whole database.

"I'd default to a hash vindex on the primary key so writes spread evenly across shards. I'd only reach for range-based sharding if the dominant query pattern is a range scan on that same key — like pulling a contiguous block of time-series events — because that's the one case where losing locality actually costs more than the hot-shard risk."

06MongoDB In Practice: Shard Keys, Chunks, The Balancer, Config Servers, And Mongos

Unlike MySQL, sharding is built into MongoDB itself — you don't bolt on a separate routing layer. But that also means one decision, the shard key, is much harder to change after the fact.

Choosing a shard key

The shard key is the field (or combination of fields) MongoDB uses to decide which shard a document lives on. Every write and every targeted read goes through this key, so picking it well is close to the single most important decision in a MongoDB sharded design.

The classic mistake is a monotonically increasing key — a field that only ever goes up, like an auto-generated timestamp, an incrementing counter, or MongoDB's own default ObjectId (which embeds a creation timestamp, so it's roughly increasing too). Every new document has the highest value seen so far, so every new document lands in the same range: the top of the key space, which lives on one shard. That shard becomes a hot spot for 100% of write traffic while every other shard sits idle.

This is exactly why MongoDB also offers hashed sharding — hash the shard key's value before using it to pick a shard, the same idea as Vitess's hash vindex. It spreads writes evenly, at the cost of range queries on that key now scattering across every shard, the same trade-off from section 02.

The balancer (below) can't fix a monotonic-key hot spot by splitting chunks. Splitting only relocates already-written, cooling data into its own chunk — new inserts still keep landing at the tail of the range, on whichever chunk currently owns the maximum value, which usually stays on the same shard. The fix has to happen at shard-key design time: hash the key, or prefix it with something that varies (like a hashed user segment), not after the collection is already sharded and hot.

For a long time, a collection's shard key was fixed for life once chosen. Newer MongoDB versions added ways to refine a shard key (add a more selective suffix field) or fully reshard a collection online, but both are heavy, cluster-wide operations — which is exactly why this decision gets so much attention before launch instead of after.

Chunks and the balancer

MongoDB groups contiguous ranges of shard-key values into chunks. Each chunk is capped at roughly 128 MB by default; once inserts push a chunk over that size, MongoDB automatically splits it into two smaller chunks.

The balancer is a background process that watches how many chunks (and how much data) sit on each shard, and migrates chunks from over-loaded shards to under-loaded ones so the cluster stays roughly even. It's the same underlying job as manually rebalancing a directory-based shard map, just automated.

Config servers and mongos

Three (or more) dedicated nodes called config servers store the cluster's metadata: which shard currently owns which chunk, and the shard-key ranges that define every chunk. Since config servers hold data no one can afford to lose, they run as their own small replica set, usually called the CSRS (config server replica set) — the metadata store has the same failover story as any other replica set, see the next section.

Applications never talk to a shard directly. They connect to mongos, a stateless query router — the direct equivalent of Vitess's VTGate. Mongos reads the chunk map from the config servers, works out which shard(s) hold the data for a query's shard-key value, and forwards the query there. A query that omits the shard key can't be routed to one shard, so mongos has to broadcast it to every shard and merge the results — called a scatter-gather query — which is far slower and doesn't get cheaper as you add shards.

07MongoDB Replication: Replica Sets And Failover

Every shard in a sharded MongoDB cluster — and the config server group itself — is a replica set: one primary handling all writes, plus two or more secondaries. This is plain leader-follower replication (section 03), just MongoDB's specific implementation of it.

Secondaries continuously copy the primary's oplog (operations log) — MongoDB's equivalent of MySQL's binlog, an ordered record of every write — and replay it to stay in sync. Replication is asynchronous by default: the primary acknowledges a write as soon as it's applied locally, before any secondary has it. Setting write concern to majority makes the primary wait until a majority of replica-set members have acknowledged the write before it tells the client the write succeeded — MongoDB's version of the synchronous / semi-synchronous trade-off from section 04, applied per write instead of as a fixed server setting.

If the primary becomes unreachable, the remaining members run an election — a Raft-like consensus protocol (see Ch.12) — and promote one secondary to primary, typically within about 10 seconds by default. Mongos and drivers detect the new primary automatically and redirect writes to it; no manual DNS or config change is needed.
