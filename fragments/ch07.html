MySQL is the relational database most candidates already know a little about, which is exactly why interviewers dig deeper here. This chapter builds the mental models behind the questions that separate "I've used MySQL" from "I understand what MySQL is doing for me": how an index actually works and when it silently stops helping, what the four ACID guarantees really promise, how MVCC lets readers and writers stay out of each other's way, and what happens, step by step, when a MySQL primary dies.

01Indexing: B-Tree Vs Hash, And What "Using An Index" Really Means

An index is a separate data structure the database keeps next to your table, built to answer one kind of question fast: "where are the rows with this value?" Without one, the database has to check every row in the table one by one — a full table scan. That's the same difference as using a book's index to jump straight to page 214 versus reading the whole book to find one paragraph.

B-tree indexes (what MySQL actually uses almost everywhere)

A B-tree — technically a B+-tree in MySQL's InnoDB storage engine — is a sorted, balanced tree of pages. A small root page points to internal pages, which point to more internal pages, until you reach the bottom-level leaf pages, which hold the actual sorted key values (and, for InnoDB's primary key index specifically, the whole row). Leaf pages are chained together in sorted order, so once you land on the right leaf, you can walk sideways for a range scan without climbing back up the tree.

Root page:            [ 50 | 100 ]
                        /     |     \
Internal pages:  [under 50][50-99][100 and up]
                        \     |     /
Leaf pages (sorted, chained left-to-right so range
scans and ORDER BY never have to re-descend the tree):
[10][22][31] → [55][61][78][95] → [100][120][144] ...

Because the tree stays balanced and shallow (roughly log(n) levels for n rows), a lookup costs about the same number of page reads whether the table has ten thousand rows or a hundred million. And because the structure is sorted, a B-tree index supports equality (WHERE id = 5), ranges (WHERE id BETWEEN 5 AND 50), prefix matches, and ORDER BY — which is why it's the default index type in almost every relational database, not just MySQL.

InnoDB actually builds two kinds of B-tree index on every table: the clustered index on the primary key, whose leaf pages hold the complete row (the table's data is the primary key's index), and any number of secondary indexes, whose leaf pages hold the indexed column plus a copy of the primary key value — not a raw disk pointer. That means a secondary-index lookup is really two steps: find the primary key in the secondary index, then use it to look the full row up in the clustered index. This second hop is often called a bookmark lookup, and it's part of why an index that returns a lot of rows can still be slower than expected.

Hash indexes

A hash index runs the key through a hash function (a function that turns any input into a fixed-size number, scattered unpredictably across the output range) and uses that number to pick a bucket. Lookups are roughly O(1) — one hop straight to the bucket — for exact-match equality. The catch is that hashing destroys order on purpose: two keys that sort next to each other, like 100 and 101, can land in completely unrelated buckets. So a hash index can answer WHERE x = 5 quickly but cannot answer a range query, an ORDER BY, or a prefix match at all — it has no idea what comes "near" any given key.

In MySQL, you rarely get to choose this yourself. The MEMORY storage engine (in-memory, non-durable tables) lets you pick USING HASH when you create an index. InnoDB — the default engine for every table since MySQL 5.5, and the one almost every production MySQL table uses — does not support user-created hash indexes at all: write CREATE INDEX ... USING HASH against an InnoDB table and MySQL accepts the syntax but silently builds a B-tree anyway. The one hash structure InnoDB does have is internal and automatic: the Adaptive Hash Index (AHI), an in-memory hash table InnoDB builds on its own over pages it notices are getting hit hard with equality lookups, purely to speed those up further underneath the B-tree. You don't design it, you can only turn it on or off (innodb_adaptive_hash_index).

02Four Ways A Perfectly Good Index Gets Ignored

Having an index on a column doesn't guarantee MySQL will use it. These four patterns are the ones that come up constantly in interviews, and in real slow-query logs.

A leading wildcard in LIKE

WHERE name LIKE '%smith' cannot use a B-tree index on name, because a B-tree can only jump to a starting point using a known prefix — and here the prefix is unknown, it could be anything before "smith." MySQL has no choice but to scan every row. WHERE name LIKE 'smith%', by contrast, can use the index: "smith" is a known prefix, so MySQL jumps straight to it in the sorted tree and reads forward until the prefix stops matching. If you genuinely need to search for text anywhere inside a column, the real fix isn't a clever index trick — it's a different tool: MySQL's own FULLTEXT index for word-level search, or a dedicated search engine like Elasticsearch (Ch.11) for substring and relevance-ranked search at scale.

Wrapping the indexed column in a function

WHERE YEAR(created_at) = 2024 or WHERE UPPER(email) = 'A@X.COM' can't use a plain index on created_at or email, even though those columns are indexed. The index stores the raw column values in sorted order; to compare against YEAR(created_at), MySQL would have to compute that function on every single row before it could compare — which is exactly the full scan the index was supposed to avoid. The fix is almost always to rewrite the predicate so the raw column is compared directly: WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01' uses the index normally. Since MySQL 5.7, there's a second fix: create a generated column that stores the function's result (UPPER(email), say) and put a normal index on that generated column — the optimizer can already match a query using the same expression straight to that index in 5.7, and 8.0 works the same way. MySQL 8.0.13 added a more direct option on top of this: a functional index, which indexes an expression directly (CREATE INDEX idx ON users ((UPPER(email)))) without you having to add a visible generated column at all.

Indexing a low-selectivity column

Selectivity is how many distinct values a column has relative to its row count. A status column with only three possible values across ten million rows has very low selectivity — any single value still matches roughly a third of the table. Even with an index, fetching that many rows means a lot of scattered bookmark lookups back to the clustered index (random I/O), which can end up costing more than simply scanning the table in order (sequential I/O). MySQL's query optimizer estimates this cost from table statistics, and it will happily ignore an index that exists if it decides a full scan is cheaper for that particular value — indexing a boolean or a handful-of-values column rarely helps on its own.

Skipping the leftmost prefix of a composite index

A composite (multi-column) index, like one on (last_name, first_name, city), is one single B-tree sorted first by last_name, then by first_name within each last_name, then by city within each first_name. It's like a phone book sorted by last name first: you can efficiently find everyone named "Rao," or every "Rao, Asha," but you cannot efficiently find every "Asha" across all last names without reading the whole book — the book just isn't sorted that way. This is the leftmost prefix rule: this index can serve queries filtering on last_name, or on last_name + first_name, or all three columns, but a query that filters only on first_name or only on city — skipping last_name — gets no benefit from it at all.

"If I see a slow query with WHERE UPPER(email) = ... on an indexed email column, I'd explain that the function wrap is the problem, not the index — MySQL has to compute UPPER() per row to compare, so it can't use the sorted index at all. I'd push to store or query the normalized form directly instead of wrapping it at read time."

None of this is a reason to index everything defensively. Every index you add speeds up the reads it matches, but it also has to be updated on every INSERT, UPDATE, and DELETE that touches that column — so a table with ten indexes can look fast in read benchmarks and still be a write bottleneck in production.

03ACID, One Letter At A Time

ACID is the set of guarantees a transaction gives you. A transaction is a group of one or more operations that the database treats as a single unit. Here's what each letter actually promises, tied to how InnoDB delivers it.

Atomicity — all or nothing

Every operation inside a transaction happens, or none of them do. If a transaction updates three rows and the connection drops after the second one, the database undoes that second change too, as if the transaction never started. InnoDB does this using its undo log — before changing a row, it records how to reverse the change, so a crash or an explicit ROLLBACK can walk the undo log backward and restore the previous state.

Consistency — every rule you defined still holds

A transaction must move the database from one valid state to another valid state, where "valid" means every constraint you've defined still holds: foreign keys point at rows that exist, unique columns stay unique, CHECK constraints stay satisfied. This is the letter people misunderstand most — the database doesn't magically know what "correct" means for your business. It only enforces the rules you told it about. Consistency is really Atomicity and Isolation put to work in service of whatever constraints you defined.

Isolation — concurrent transactions don't see each other's half-finished work

Transactions running at the same time should produce a result as if they ran one after another, even though they were actually interleaved for speed. How strictly MySQL enforces this is tunable — that's the isolation levels in the next section.

Durability — once committed, it survives a crash

After MySQL tells the client a transaction committed, that data must still be there even if the power goes out one millisecond later. InnoDB guarantees this with its redo log, a write-ahead log: every change is written to the redo log on disk (a small, sequential, fast write) before the commit is acknowledged. On restart after a crash, InnoDB replays the redo log to reconstruct any committed changes that hadn't yet been written back to the actual table's data pages. The setting innodb_flush_log_at_trx_commit controls exactly how aggressively that redo log write is flushed to disk per commit — it's the direct dial between "fully durable" and "faster but riskier on power loss."

"I'd say the C in ACID isn't the database keeping your data correct by magic — it's the database enforcing whatever constraints you defined, even under concurrent transactions. The two letters actually doing engineering work are Atomicity and Isolation; Consistency is just those two, applied to your schema's rules."

04Isolation Levels: What Each One Actually Stops

Isolation is tunable because perfect isolation is expensive. Weakening it trades correctness guarantees for concurrency and speed. Three anomalies define the trade-off:

  • Dirty read — reading a row that another transaction changed but hasn't committed yet. If that other transaction rolls back, you read data that never really existed.
  • Non-repeatable read — reading the same row twice inside one transaction and getting two different values, because another transaction changed and committed it in between your two reads.
  • Phantom read — running the same range query twice inside one transaction and getting a different set of rows, because another transaction inserted or deleted rows that match your filter in between.

Read CommittedPreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible
SerializablePreventedPreventedPrevented

That table is the SQL standard's floor — the minimum each level has to guarantee. MySQL's InnoDB does better at its default level than the standard requires: Repeatable Read is InnoDB's default, and thanks to MVCC snapshots (next section) plus a locking technique called next-key locking (a lock on an index record plus the gap before it, which blocks other transactions from inserting a new row into that gap), InnoDB's Repeatable Read prevents phantom reads in nearly all practical cases too — stronger than what the standard demands at that level. Serializable goes further still: as long as autocommit is off — that is, you're inside an explicit transaction — InnoDB implicitly converts plain SELECT statements into locking reads, which is the closest thing to running every transaction one at a time — correct, but it can turn concurrent readers into a queue. (With autocommit on, a plain SELECT is its own self-contained read-only transaction and isn't converted this way.)

"MySQL's default, Repeatable Read, already blocks phantom reads in almost every real case, thanks to next-key locking and MVCC snapshots — that's stronger than the SQL standard technically requires at that level. That's one reason production MySQL rarely needs to reach for Serializable; the default is already close to it for the cases that matter, at a fraction of the concurrency cost."

05MVCC: How MySQL Reads Without Blocking Writers

The naive way to give transactions isolation is locking: a reader takes a lock so no writer can change the row underneath it, and a writer takes a lock so no reader sees a half-finished change. The problem is throughput — readers and writers now constantly block each other, and most real workloads are read-heavy, so this gets painful fast.

MVCC (multi-version concurrency control) solves this by keeping more than one version of a row around instead of just the current one. Every transaction gets a consistent snapshot (in InnoDB, called a read view) of the database as it looked at a fixed point in time, and it reads from that snapshot for its whole duration — it never has to wait for a writer, because it's reading a version that already existed and will never change again.

Roughly how InnoDB does this: every row secretly carries a hidden transaction ID (which transaction last changed it) and a hidden roll pointer to an entry in the undo log holding the row's previous value. A transaction's read view is essentially a list of which other transactions were still uncommitted when the view was created. To read a row, InnoDB checks whether the current version was written by a transaction visible to that read view; if not, it follows the roll pointer back to the previous version in the undo log, and keeps walking backward until it finds a version that was already committed as far as this read view is concerned.

Writers still take row locks and still create new versions when they write — MVCC doesn't remove locking for writes, it removes the need for reads to take any lock at all. That's the core trade it makes: readers never block writers, and writers never block readers, only writer-vs-writer contention on the same row still needs a lock.

Old versions can't be thrown away the moment a newer one exists — InnoDB has to keep every version that some transaction's read view might still need. A single long-running transaction (an open connection left idle mid-transaction, a slow report) can quietly block InnoDB's cleanup process (called purge) from ever discarding old versions, bloating the undo log until that transaction finally finishes. This is a real, common cause of unexplained disk growth in production MySQL.

06Row-Level Vs Table-Level Locking

A table-level lock locks the entire table for the duration of the operation — simple to implement and track, but it means one write blocks every other read and write on that table, even ones touching completely unrelated rows. MySQL's older default engine, MyISAM, works this way; it's largely legacy today.

A row-level lock locks only the specific rows a transaction actually touches, so two transactions updating different rows in the same table can run fully in parallel. InnoDB — the default engine since MySQL 5.5 — locks at the row level, which is a big part of why it replaced MyISAM as the default. The cost is complexity: InnoDB has to track locks per row instead of one flag per table, and two transactions that lock the same rows in a different order can end up in a deadlock — each waiting on a row the other one holds. InnoDB detects this automatically and forcibly rolls back one of the two transactions (the one with less work to undo) so the other can proceed.

07Normalization Vs Denormalization: One Schema, Both Ways

Normalization means organizing a schema so each fact is stored in exactly one place, avoiding data that has to be kept in sync by hand across many rows. Here's one flat, unnormalized order table:

Unnormalized: orders_flat

1002Asha Raoasha@example.comUSB-C Cable19932026-01-04
1003Ravi Shahravi@example.comWireless Mouse79912026-01-05

The problems are all redundancy problems. Asha's name and email are repeated on every row she ever orders — change her email and you must find and update every one of those rows, or the table starts disagreeing with itself (an update anomaly). "Wireless Mouse" and its price are repeated on every order for it too. And if a product has never been ordered, there's nowhere in this table to even record that it exists (an insertion anomaly).

Normalizing pulls each repeated fact out into its own table, keyed by an ID, referenced by foreign key:

CREATE TABLE customers (
  customer_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(120) NOT NULL,
  email       VARCHAR(160) NOT NULL UNIQUE
);

CREATE TABLE products (
  product_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
  name          VARCHAR(160) NOT NULL,
  current_price DECIMAL(10,2) NOT NULL
);

CREATE TABLE orders (
  order_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
  customer_id BIGINT NOT NULL,
  order_date  DATE NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

CREATE TABLE order_items (
  order_id          BIGINT NOT NULL,
  product_id        BIGINT NOT NULL,
  quantity          INT NOT NULL,
  price_at_purchase DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id),
  FOREIGN KEY (order_id) REFERENCES orders(order_id),
  FOREIGN KEY (product_id) REFERENCES products(product_id)
);

Note the explicit FOREIGN KEY (...) REFERENCES ... table-level clause — MySQL parses inline column-level REFERENCES (like customer_id BIGINT REFERENCES customers(customer_id) with no FOREIGN KEY keyword) but silently ignores it: no constraint gets created, no index, and MySQL doesn't even check that the referenced table or column exists. The table-level form above is what actually gives you a real, enforced foreign key.

Now Asha's name and email exist in exactly one row, no matter how many orders she places. A product's name and current price exist in exactly one row, no matter how many times it's sold. Note that price_at_purchase on order_items deliberately keeps its own copy of the price — that's not a normalization mistake, it's a separate fact (what the customer actually paid, at that moment) that has to live somewhere, since current_price keeps changing after the sale.

Now the deliberate denormalization. Say an order-history screen (or a GET /orders/:id endpoint) gets hit on nearly every visit to the app. Rendering it means joining orders to customers for the name, and to order_items and products for each line item — a three- or four-way join on one of your hottest read paths. At real traffic, that join cost shows up directly in p95 latency and in how much CPU and buffer-pool memory that one screen eats. A common, deliberate fix: add a denormalized customer_name column directly onto orders, filled in at order-creation time, so the order-history read becomes a single-table lookup with no join at all.

The cost of that denormalized customer_name column is that it can go stale — if Asha changes her display name next year, her old orders still show the old name unless you explicitly update them. For an order history, that's usually a feature, not a bug: an invoice should show the name as it was at the time of the order, not whatever the customer is called today. That's the general shape of the normalization-vs-denormalization call: normalize for correctness and low update cost, then denormalize specific, hot, read-heavy fields back once you can name the exact query it's slowing down and you've accepted what staleness it introduces.

08Replication And Failover, MySQL Specifically

Chapter 6 introduced binlog-based replication and semi-sync vs async at a high level. Here's what's actually happening mechanically, and what a MySQL failover really does step by step.

How the binlog actually gets from primary to replica

The binlog (binary log) is an ordered record of every committed change on the primary (called the source in current MySQL terminology). Getting it onto a replica is two decoupled jobs, run by two separate threads: an I/O thread connects to the primary and copies binlog events into a local file on the replica called the relay log, and a separate SQL thread (or, in modern MySQL, a pool of parallel apply workers) reads the relay log and actually applies those changes to the replica's own data. Because these two jobs are decoupled, a replica can be fully caught up on receiving events while still behind on applying them — one of the concrete reasons replication lag exists.

Modern MySQL tracks replication position with GTIDs (Global Transaction Identifiers) — a unique ID stamped on every transaction — instead of the older method of tracking a binlog filename plus a byte offset. GTIDs matter most during failover: a replica can figure out for itself exactly where to resume from against a different new primary, because it just asks "which GTIDs have I already applied," instead of a human working out the matching file-and-position by hand.

Semi-sync vs async, precisely

With plain asynchronous replication, the primary commits and replies to the client immediately, then ships the binlog to replicas whenever it gets to it — fast, but a crash right after commit can lose whatever hadn't shipped yet. MySQL's semi-synchronous replication (a plugin you install explicitly with INSTALL PLUGIN, in every version through at least 8.0/8.4) changes one thing: after committing locally, the primary waits for at least one replica to acknowledge it has received the binlog event (not necessarily applied it yet) before telling the client the write succeeded. This closes the "the only copy was on the machine that just died" gap for one round trip of extra latency. Semi-sync also has a safety valve: if no replica acknowledges within rpl_semi_sync_master_timeout, the primary automatically falls back to async for that period rather than hanging forever, then switches back to semi-sync once a replica catches back up — durability is best-effort, not a hard blocking guarantee.

What actually happens during failover

  1. Detection — something monitoring the primary (an orchestration tool like Orchestrator or MHA, a managed service's own health checks, or Vitess's VTOrc from Ch.6) notices it's unreachable. Good setups check from more than one vantage point first, so a single node's network blip doesn't trigger a false failover.
  2. Choosing the new primary — among the surviving replicas, pick the one with the most up-to-date data (the most advanced GTID position). A semi-sync replica is the safest candidate, because it's guaranteed to hold at least the last transaction the old primary acknowledged as committed.
  3. Fencing the old primary — make sure the old primary can never accept another write again, even if it comes back online, usually by forcing it read-only or isolating it from the network. Skipping this risks split-brain: two nodes both accepting writes and diverging.
  4. Promotion — the chosen replica stops replicating and is reconfigured as writable.
  5. Repointing — every remaining replica is told to replicate from the new primary instead (CHANGE REPLICATION SOURCE TO), and the endpoint applications actually connect to — a virtual IP, a DNS record, or a proxy layer like ProxySQL or VTGate — is updated so writes route to the new primary with no application code change.
  6. Accepting the data-loss window, if any — any transaction that committed on the old primary but never reached any replica is gone for good once that old primary is fenced off. With pure async replication that window can be several seconds of writes; running at least one semi-sync replica is specifically what shrinks that window to effectively zero.

"I'd run one semi-sync replica for durability and any number of plain async replicas for read scaling — you only pay the extra round trip of semi-sync latency on the write path, once, and you get a hard guarantee that a write surviving on only one machine never happens. The async replicas stay cheap and fast for reads, where a little staleness is fine."

An EM-level answer adds the build-vs-buy angle: everything in the failover steps above — detection, election, fencing, repointing — is exactly what managed offerings like Amazon RDS Multi-AZ or Aurora automate for you, typically completing a failover in well under a minute with no one paged. Running Orchestrator or MHA yourself gives more control (useful at very large fleets, or when you need cross-region topologies a managed product doesn't offer) but it's real operational surface a team has to own, test, and be ready to debug at 3 a.m.

Index B-tree vs hash, quick facts
  • B-tree — sorted, balanced tree; supports equality, range, prefix, and ordering. InnoDB's only user-facing index type.
  • Hash — O(1) equality only, no range/order/prefix. Available on MEMORY tables; InnoDB only builds one internally (Adaptive Hash Index), automatically.
  • Clustered index — InnoDB's primary key index; leaf pages hold the full row.
  • Secondary index — leaf pages hold the indexed column plus the primary key, so a lookup is index-then-clustered-index (a bookmark lookup).
Index miss Four ways a query skips an index
  • Leading wildcard — LIKE '%x' has no known prefix to jump to; forces a full scan.
  • Function-wrapped column — WHERE YEAR(col) = ... needs per-row computation; rewrite as a range on the raw column, or index a generated column.
  • Low selectivity — a column with few distinct values matches too large a share of rows for the index to be worth the random I/O.
  • Skipping the leftmost prefix — a composite index on (a, b, c) only helps queries filtering on a, or a+b, or all three, in that order.
ACID One line per letter
  • Atomicity — all of a transaction's changes happen, or none do (InnoDB: undo log).
  • Consistency — every constraint you defined still holds after the transaction.
  • Isolation — concurrent transactions look as if they ran one after another (tunable — see levels below).
  • Durability — once committed, it survives a crash (InnoDB: redo log, a write-ahead log).
Isolation Four levels, one line each
  • Read Uncommitted — prevents nothing; can see another transaction's uncommitted writes.
  • Read Committed — blocks dirty reads only.
  • Repeatable Read — blocks dirty and non-repeatable reads; MySQL's default; InnoDB also blocks most phantoms here via MVCC + next-key locks.
  • Serializable — blocks all three; MySQL does it by making plain reads take locks too.
Locks Row-level vs table-level
  • Table-level — one lock for the whole table; MyISAM (legacy); simple, low concurrency.
  • Row-level — locks only touched rows; InnoDB (default); high concurrency, can deadlock.
  • Next-key lock — InnoDB locking a row plus the gap before it, to stop phantom inserts.
  • Deadlock — InnoDB detects the cycle automatically and rolls back the cheaper-to-undo transaction.
Replication Binlog, GTID, semi-sync, failover
  • Binlog — ordered log of committed changes on the primary; replicas stream and replay it.
  • I/O thread vs SQL thread — receiving events and applying them are decoupled; a source of lag.
  • GTID — a unique ID per transaction, so a replica can resume against a new primary without manual file/offset math.
  • Semi-sync — primary waits for one replica to ACK receipt before committing; falls back to async on timeout.
  • Failover — detect, elect the most up-to-date replica, fence the old primary, promote, repoint the rest.
