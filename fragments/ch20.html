Every problem in this chapter is a piece of shared infrastructure — the kind of system one platform team builds so dozens of other teams never have to solve the same hard problem twice. You have already met most of the underlying ideas as concepts in earlier chapters; here you build the full service around each one, end to end, under interview pressure.

00How to use this chapter

Read this chapter differently from a product-feature problem bank. Nobody asks you to "design Bitly" because Bitly is the point — they ask it because a URL shortener is the simplest possible container for cache-aside reads, range-based ID allocation, and a read-heavy capacity estimate. The same is true for every problem here: a distributed lock service, a rate limiter, a job scheduler, a config-propagation system. Each one is infrastructure that other engineering teams depend on, which means each one repeats a small set of hard sub-problems — a single key getting hammered far harder than the rest of the keyspace, a shared dependency that must not become a bigger outage than the thing it protects, a delivery guarantee that has to be honest about what it cannot promise. Once you can name these recurring shapes, a problem you have never seen before in an interview stops feeling unfamiliar — it is usually two or three of these shapes wearing a different product name.

Sharding The hot-key problem, and the fix that keeps showing up
  • The problem: sharding by key (Ch.6) spreads different keys across different nodes, but it does nothing for one single key that is suddenly taking a huge share of all traffic — a viral video's view counter, one customer's aggressive scraping key, a celebrity account's cache entry. Hashing that one key always lands on the same shard no matter how many shards the cluster has.
  • The fix: split the one logical hot key into many physical sub-keys internally (hash a request or session field into one of, say, 128 sub-shards), then sum or merge across sub-shards at read time. This shows up almost identically in the Distributed Counter Service, the Distributed Rate Limiter, the Distributed Cache, and the Distributed Message Queue problems in this chapter.
  • The cost: reads now have to fan out and merge instead of hitting one place, and the sub-shard count is a bet — too few and the hot key still concentrates load, too many and you carry that overhead on every ordinary, non-hot key too.
Availability Fail-open vs. fail-closed — say it out loud, do not let it be an accident
  • Any service that sits in front of other traffic — a rate limiter, an API gateway, a config-propagation sidecar — has to decide what happens when its own backing store is unreachable.
  • Fail-closed (reject everything until the dependency is back) turns a small outage in the protector into a full outage in everything it protects.
  • Fail-open (allow everything through, with alerting) accepts a short window of unprotected traffic in exchange for keeping the platform up — almost every real production system defaults to this, wrapped in a circuit breaker (Ch.15) so the failure is fast, not a pile of slow timeouts.
  • Naming this trade-off explicitly, instead of letting it fall out of whatever a client library happens to do on timeout, is one of the fastest ways to sound like a senior engineer in this chapter's problems.
Delivery At-least-once plus idempotency, because exactly-once is not honestly on the table
  • No distributed system can guarantee a message, a job trigger, or a webhook fires exactly once across a crash, a retry, or a network drop right after success — the acknowledgment itself can be lost.
  • The honest target is at-least-once delivery plus a contract that the receiving side is idempotent (safe to run twice), usually via an idempotency key or a fencing token the receiver checks itself.
  • This exact pattern repeats in the Distributed Job Scheduler, the Distributed Lock Service, the Distributed Task Queue, and the Webhook Delivery System — different products, same honest limit.
Architecture Speed layer vs. batch layer (the Lambda-architecture split)
  • When "fast" and "exactly correct" pull in different directions, several problems in this chapter resolve the tension by building two paths instead of one: a fast, approximate streaming path for dashboards and live UI, and a slower, exact batch path that is the actual source of truth for anything money or audits touch.
  • The Ad-Click Aggregation system bills off a nightly reconciliation job, not the live dashboard number. The Distributed Counter Service keeps an approximate in-memory read separate from a durable, strongly consistent one. The Leaderboard keeps Redis as the fast live board and Cassandra as the rebuildable source of truth.
  • The lesson to state explicitly in an interview: letting the fast number and the exact number disagree for a bounded window is a deliberate design choice, not a bug you failed to catch.
Strategy Build vs. buy has a default answer for almost everything in this chapter
  • Nearly every problem here is a mature, well-understood category with a managed or open-source answer already: Kafka or SQS for a message queue, etcd or ZooKeeper for a lock service, DynamoDB or Cassandra for a key-value store, S3 for object storage, Kong or an API gateway product for multi-tenant rate limiting.
  • An EM-level answer names the real off-the-shelf option before defending a build, and reserves "we should build this ourselves" for a specific, named gap the bought option cannot cover — a latency requirement, a cost curve at extreme scale, or a control need like a per-tenant memory quota.
  • Rollout for shared infrastructure is its own recurring theme too: phased, cohort-by-cohort migration with a dual-write or shadow period, never a single company-wide cutover, because a bug here fails every dependent team at once.

Design a URL Shortener (Bitly-style)

Problem framing

A growth/marketing tooling company wants a public service that turns a long URL into a short alias, like bit.ly/abc123, so it fits in a tweet, an SMS, or a printed flyer, and so the owner can see how many people clicked it. Strip away the analytics dashboard and the custom-domain features, and this is really one small problem: map a short code to a long URL, and make that lookup extremely fast and extremely reliable, because it sits on the path of every link click across the internet.

Clarifying questions

  • Can paying customers pick a custom alias instead of a random code? — a custom alias needs a uniqueness check against user input; a system-generated code does not, since we control the generation.
  • Do links expire, or live forever? — an expiring link needs a cleanup job and a way to serve a "this link is gone" page; a permanent link needs storage that keeps growing without bound.
  • Do we need per-click analytics (device, location, referrer)? — this turns a simple redirect into a system with an attached event pipeline, not just a lookup table.
  • Should the redirect be a permanent (301) or temporary (302) HTTP redirect? — a 301 gets cached by the visitor's browser, so a repeat click never even reaches our servers; that is great for our load, but it means we never see that second click, which breaks click analytics.
  • What is the expected read-to-write ratio? — this decides how aggressively we can cache, and whether the write path needs to scale at all past a certain point.

Requirements

Functional requirements:

  • Given a long URL, generate a short code and return a short URL.
  • Given a short code, redirect the visitor to the original long URL.
  • Support an optional custom alias for paying users.
  • Support an optional expiration date, after which the short link stops resolving.
  • Track a click count per link (basic analytics, not a full dashboard).

Non-functional requirements:

  • The redirect must be fast — well under 100ms at p99 (99 out of 100 requests are at least this fast) — since a slow redirect is a slow load for every page that links out through us.
  • The redirect path must stay highly available; a short link is often the only copy of that URL a user has, so serving stale-but-correct data beats returning an error.
  • A short code, once handed out, must never resolve to a different URL than the one it was created for.
  • Once a link is created and acknowledged, it must not be lost — losing a link breaks every place it was already shared.
  • Click counts can be eventually consistent; being off by a few clicks for a few seconds is fine.

Capacity estimate

Assume the service creates 100 million new short links a month. Write QPS (queries per second) ≈ 100,000,000 / (30 × 86,400 seconds) ≈ 38.6/sec average. Link creation is bursty around marketing campaign launches, so provision for roughly 5x that at peak, about 193/sec — a tiny number in absolute terms.

Reads (redirects) dominate. A typical link-shortening product sees on the order of 100 redirects for every 1 creation over the life of a link. That puts average read QPS at roughly 3,860/sec, and peak (5x) at about 19,300/sec. This read:write ratio is the single number that decides most of this design: it is a heavily read-skewed system, so almost all of the engineering effort goes into the redirect path, not the creation path.

Storage: one link record (short_code, long_url up to ~2KB, owner_id, created_at, expires_at, click_count) is roughly 300 bytes once you allow for a generously long URL. Over 5 years at 100 million/month that is 6 billion links, so 6,000,000,000 × 300 bytes ≈ 1.8TB — small enough that storage is never the bottleneck here, only lookup speed is.

Short code length: using base62 (a–z, A–Z, 0–9, 62 symbols), a 6-character code space is 62^6 ≈ 56.8 billion possible codes, comfortably more than the 6 billion links projected above, with room to keep growing for years before a 7th character is needed.

API design

POST   /v1/links
       {long_url, custom_alias?, expires_at?} -> {short_code, short_url, created_at}

GET    /{short_code}                -> 302 redirect to long_url (or 404/410 if missing/expired)

GET    /v1/links/{short_code}/stats -> {click_count, created_at, expires_at}

DELETE /v1/links/{short_code}

High-level design

Two paths that barely touch: a small, low-traffic write path that allocates a code and stores the mapping, and a huge, latency-critical read path that resolves a code to a URL and emits a click event asynchronously.

Deep dive

1) How to allocate short codes without a coordination bottleneck. The naive approach — pick a random 6-character string and check the URL store for a collision — works, but every creation now costs a read plus a write, and collisions get more likely as the space fills. A cleaner approach borrows the range-allocation idea from Ch.16's reusable ID generation section: a small allocator service hands each application server a reserved block of, say, 10,000 sequential integers at startup, and that server converts integers in its own block to base62 locally, with zero coordination needed per request and zero collision risk, since no two servers ever share a block. A Snowflake-style ID (also Ch.16) is the other common option when you want the code itself to encode a rough creation timestamp.

2) Why 302, not 301, even though 301 is "more correct" for a permanent link. A 301 response tells the browser "this redirect never changes, cache it yourself" — the browser then skips our server entirely on the next click from that device, which is great for load but means our click counter silently undercounts, and we lose the ability to redirect the same short code somewhere else later (say, after a link is reported and needs to point to a warning page instead). A 302 keeps every click flowing through our redirect service, at the cost of that server doing real work on every single click instead of a fraction of them.

3) The hot-link problem. A link posted by a large account can get millions of clicks in minutes, all hitting one cache entry. Because the redirect path is cache-aside on Redis (see Ch.4 for the mechanics), a single hot key is cheap to serve as long as it stays in cache — the real risk is a cold cache right as the burst starts. Some designs pre-warm the cache for links crossing a click-velocity threshold, the same instinct as the celebrity fan-out problem elsewhere in this chapter's sibling chapters.

Trade-offs

At 10x scale, the redirect service's absolute compute cost stays manageable — it does almost no work per request beyond a cache read — but the Redis tier's single-node throughput ceiling shows up first, and a handful of viral links concentrate load on whichever shard owns them despite consistent hashing spreading the rest of the keyspace evenly. The trade-off is finer sharding of the cache keyspace (more operational overhead, more nodes to keep warm) versus accepting a slower path for the small number of extreme outlier links.

Say this

"I would use a 302 redirect instead of a 301, even though the link is meant to be permanent, because a 301 gets cached by the visitor's browser and we would lose visibility into repeat clicks and the ability to redirect a reported link elsewhere later. That's worth the extra load on our redirect service."

Final design

One picture: a range-based code allocator hands out collision-free short codes so writes need no coordination; the mapping lands in a sharded key-value store; the read path is a thin service backed by a Redis cache doing cache-aside lookups, issuing 302 redirects, and emitting click events onto a queue that an async pipeline aggregates into click counts — keeping the redirect itself on the critical path as light as one cache read.

EM-level follow-up

Build-vs-buy: for the first couple of years, this entire system fits comfortably on a managed key-value store (DynamoDB, or even a single well-indexed MySQL table per Ch.7) plus a managed Redis instance — there is no need to run your own sharded cluster until link volume is genuinely large. On rollout: because expired or deleted links must stop resolving, changing the deletion or expiration policy is a customer-facing contract change (a link a customer already printed on marketing material breaking is a support incident), so it needs a deprecation notice, not a silent flip.

Design Pastebin (Text/Snippet Sharing)

Problem framing

An engineering tools team wants a service where anyone can paste a block of text — a stack trace, a config file, a code snippet — and get back a link that shows that exact text, optionally with an expiration date or a password. Unlike the URL shortener, the thing being stored is arbitrary, possibly large, content, not a fixed-size pointer — so the core problem shifts from "make one tiny lookup fast" to "store large blobs cheaply and serve them back without dragging a database down with them."

Clarifying questions

  • What is the maximum paste size? — a 10KB limit and a 10MB limit lead to very different storage designs; a small cap keeps everything in a normal database row, a large one forces a dedicated blob store.
  • Are pastes editable after creation, or is every paste immutable once created? — immutability unlocks aggressive caching and CDN edge delivery, since content that never changes never needs cache invalidation.
  • Is there a "burn after read" option, where a paste is deleted the moment it is first viewed? — this adds a strict, immediate-delete requirement on top of the normal expiration sweep.
  • Do pastes need access control (private, unlisted, password-protected)? — a password-protected paste needs an auth check on the read path, which changes it from a pure cache-friendly static fetch to a gated one.
  • Is anonymous pasting allowed, or does every paste need an owner account? — anonymous pasting removes an entire auth subsystem from the MVP but makes abuse (spam, malware hosting) harder to trace and rate-limit per user.

Requirements

Functional requirements:

  • Create a paste with text content, an optional language tag (for syntax highlighting), and an optional expiration.
  • Fetch a paste by its ID, both as a rendered page and as raw plain text.
  • Support paste visibility: public, unlisted (link-only), or password-protected.
  • Delete a paste (owner-initiated, or automatic on expiration).

Non-functional requirements:

  • Reads of a given paste should be fast and should scale independently of how many pastes exist, since a small number of pastes get shared widely and read repeatedly.
  • Once a paste is acknowledged as created, its content must not be lost or corrupted — a stack trace pasted for a live incident cannot silently come back empty.
  • Large pastes must not degrade the system for everyone else creating small ones at the same time.
  • Expired and "burn after read" pastes must actually stop being retrievable, on a bounded delay — this is a stated privacy promise, not just a storage-cost cleanup.

Capacity estimate

Assume 1 million new pastes created per day. Write QPS ≈ 1,000,000 / 86,400 ≈ 11.6/sec average, maybe 50/sec at peak — a small write volume in absolute terms.

Assume an average paste size of 10KB (a mix of short snippets and longer logs, with a hard cap around 1MB to bound abuse). Storage for content: 1,000,000 × 10KB ≈ 10GB/day, roughly 3.65TB/year of raw text content.

Metadata is much smaller: a row of (paste_id, owner_id, language, created_at, expires_at, visibility, blob_pointer) is roughly 200 bytes, so 1,000,000 × 200 bytes = 200MB/day — cheap enough to sit in a normal fast metadata store even as content volume grows.

Reads: assume each paste is viewed an average of 20 times across its lifetime (shared once, opened by several people). That is 20 million reads/day, or roughly 230/sec average, peaking around 1,000/sec — modest, and a very good candidate for caching since a large share of those reads hit a small number of recently-shared, still-hot pastes.

API design

POST   /v1/pastes
       {content, language?, expires_in?, password?, visibility, burn_after_read?}
       -> {paste_id, url}

GET    /v1/pastes/{id}          -> {content, language, created_at} (requires password if set)
GET    /raw/{id}                -> plain text body
DELETE /v1/pastes/{id}

High-level design

Small, hot metadata is kept separate from large, cold blob content, and because a paste is immutable once created, most reads never need to reach the origin at all.

Deep dive

1) Separating metadata from blob content. Storing a 1MB paste inline in a normal database row bloats that table's working set, which slows down every other query against it, because the database's buffer pool (see Ch.7) now has to hold huge rows just to satisfy a query that only needed the tiny metadata columns. Splitting the design into a small, fast metadata store (paste_id, owner, expiry, a pointer) plus a large object store for the content itself — the same shape as the distributed object storage problem elsewhere in this chapter — keeps the hot metadata table small and fast regardless of how large individual pastes get.

2) Immutability turns the read path into a pure CDN problem. Because a paste's content never changes once created (in this design, "editing" creates a new paste rather than mutating an old one), the raw content endpoint can be cached at the CDN edge, keyed by paste_id, with a very long time-to-live — most reads never reach our origin servers at all. This is the opposite instinct from the URL shortener problem earlier in this chapter, where we deliberately avoided browser/edge caching on the redirect to preserve click visibility; here there is no analytics reason to avoid caching, so we lean into it fully.

3) "Burn after read" versus batch expiration. A normal TTL can be enforced lazily (check expires_at on read, plus a background sweep for storage reclaim) because being a few minutes late to delete an expired paste is harmless. Burn-after-read is a stronger promise — the paste must become unreadable the instant it is first viewed, which means the read path itself has to perform a delete-on-read (or at least an atomic "mark consumed") rather than leaving cleanup entirely to a background job, and that delete has to also invalidate anything already sitting in the CDN cache for that paste_id.

Trade-offs

At 10x scale, the blob store's ingest bandwidth is what strains first, not the metadata store — a burst of large pastes (someone scripting uploads of multi-hundred-KB logs) can saturate write bandwidth well before the small metadata rows become a bottleneck. The trade-off is enforcing a stricter per-paste size cap and per-user upload rate limit (protects the system, frustrates a legitimate power user) versus accepting the bandwidth cost and scaling the blob tier's ingest path horizontally.

Say this

"Since a paste never changes once created, I would push almost all read traffic to a CDN edge cache keyed by paste_id, and only fall back to our origin on a cache miss. That is a very different call from the URL shortener case, where I deliberately kept caching off the hot path to preserve click analytics — here there is no such trade-off, so I take the free caching."

Final design

One picture: a paste service that writes small metadata to a fast metadata store and large content to an object store; reads are served primarily from a CDN edge cache because content is immutable; a background sweep worker enforces expiration and burn-after-read by deleting from both the metadata store and the blob store, and invalidating the CDN entry.

EM-level follow-up

Build-vs-buy: the blob tier is close to a textbook case for a managed object store plus a managed CDN (S3 and CloudFront, or equivalents) rather than running your own — there is very little product-specific logic in "store a blob, serve it back." On rollout and cross-team impact: "burn after read" is a legal/privacy promise, not just a feature, so its delete guarantees (how fast, how thorough, does it also purge CDN edge caches globally) are worth a sign-off from whoever owns privacy commitments before shipping, not a decision one engineer makes unilaterally.

Design a Distributed Rate Limiter (as a Standalone System)

Problem framing

A platform team at a company with a public API (think a payments or social API used by thousands of third-party developers) and roughly 500 internal microservices needs one shared answer to "is this caller allowed to make this call right now?" Ch.5 covered the algorithms behind that yes/no answer — token bucket, leaky bucket, fixed and sliding windows — and Ch.16 introduced the idea of centralizing that logic into its own service instead of letting every team re-implement it. This problem is that service, built out fully: multi-tenant, on the hot path of nearly every request in the company, and dangerous to get wrong, because a rate limiter that fails badly can take down more than the thing it was protecting.

Clarifying questions

  • Is this limiting external API customers, internal service-to-service calls, or both? — this decides the trust model and whether limits are keyed by API key, by service identity, by IP, or some mix of all three.
  • What's the limit granularity — per user, per API key, per endpoint, or some combination? — finer granularity means a much larger key space to track, which changes the storage and sharding story.
  • On a rejection, do we hard-fail with a 429, or queue and retry the caller later? — a queue-and-retry design needs a queue behind the limiter, not just a stateless check.
  • If the rate limiter's own backing store is unreachable, should we fail open (allow everything) or fail closed (reject everything)? — this single decision decides whether a rate-limiter outage becomes a platform-wide outage or a brief, tolerable over-admission of traffic.
  • Do limits need to be exact, or is a small, bounded over-admission acceptable in exchange for lower latency? — an exact global count needs a round trip to a shared store on every single check; an approximate count can be answered locally most of the time.

Requirements

Functional requirements:

  • Given a key (user, API key, or service) and a cost, answer allow or deny against that key's configured limit.
  • Support multiple limit tiers per key at once (for example, a burst limit and a separate, larger sustained limit).
  • Allow limits to be configured or changed per tenant without redeploying any service.
  • Expose current usage and remaining quota back to the caller, so clients can back off gracefully.

Non-functional requirements:

  • The check itself must add very little latency — under 5–10ms at p99 — since it sits in front of every protected request.
  • The limiter must be more available than the average service it protects, because if it isn't, protecting a service with it makes that service's effective availability worse, not better.
  • It must scale horizontally to at least the combined peak QPS of everything it fronts.
  • A limiter outage must degrade gracefully (see the fail-open discussion below) rather than causing a wider outage than the risk it was built to prevent.

Capacity estimate

Assume this limiter fronts 500 internal services plus a public API with 50,000 active API keys, at a combined platform peak of 2 million rate-limit checks/sec — a scale comparable to a large company's shared API gateway layer. Each check is a small operation (an atomic increment plus a comparison), and a well-tuned single Redis node can sustain on the order of 100,000 operations/sec for small values like counters. To handle 2 million checks/sec with real headroom (not running every shard at its ceiling), you need on the order of 20–30 Redis shards for throughput alone, plus replicas for availability — call it 40–60 nodes total.

Storage is small relative to that throughput: counters typically live only a few minutes (the length of the rate-limiting window) before expiring. With 50,000 API keys and, say, 10 endpoint-level sub-limits each, that is 500,000 active counters at roughly 100 bytes apiece, about 50MB — this system's entire challenge is calls per second, not bytes stored, which is the opposite shape from a system like the distributed cache problem elsewhere in this chapter, where memory footprint is what drives cluster size.

API design

POST /v1/ratelimit/check
     {key, resource, cost=1} -> {allowed: bool, remaining, reset_at}

PUT  /v1/ratelimit/policies/{tenant}
     {limit, window_seconds, burst} -- admin config, propagates to all limiter nodes

GET  /v1/ratelimit/usage/{key}     -> {used, remaining, reset_at}

High-level design

A stateless fleet of limiter nodes sits in front of every protected call, backed by a sharded counter store, with limits loaded from a small, cached policy store.

Deep dive

1) Centralized-exact counting versus local-approximate counting. Ch.16 pointed out the failure mode of naive per-instance counters: ten service instances each tracking their own local count quietly allow ten times the intended rate, since each one only sees its own slice of traffic. A single shared Redis counter fixes that by giving one exact, global count — at the cost of a network round trip on every single check, which adds up at 2 million checks/sec. The design most production limiters converge on is a hybrid: each limiter node keeps a fast local approximate count and syncs deltas to the shared store every second or so, trading a small, bounded amount of over-admission (a caller might briefly get slightly more than its exact limit) for far lower latency and far less load on the shared store.

2) Fail-open versus fail-closed. This is the decision that separates a good rate limiter design from a dangerous one. Fail-closed — reject every request when the counter store can't be reached — turns a rate-limiter outage into a full platform outage, because the safety mechanism itself becomes the single point of failure. Fail-open — allow every request through when the store is unreachable — accepts a short window of unthrottled traffic in exchange for keeping the platform up, wrapped in a tight circuit breaker (Ch.15) so a slow store fails the check fast instead of piling up timeouts. Almost every real-world rate limiter fails open by default, precisely because the alternative failure mode is worse than the thing rate limiting exists to prevent.

3) Multi-tier limits need more than one counter per check. A pure fixed window lets a caller burn its entire quota in the first millisecond of a new window and then again at the boundary of the next one — the classic boundary burst problem covered in Ch.5. Supporting both a burst limit (a small token bucket) and a separate sustained limit (a larger window) means each check has to atomically touch two counters instead of one, usually via a small Lua script run inside Redis so the two updates stay consistent under concurrent hits from the same key.

Trade-offs

At 10x traffic (say, after a major product launch quadruples public API usage), the shared counter store is what breaks first, not the stateless limiter fleet — a handful of hot keys (a customer running an aggressive scraper) concentrate load on a single shard regardless of how well the rest of the keyspace is hashed. The trade-off is sharding the counter keyspace even finer for hot keys specifically (more nodes, more operational surface) versus falling back to node-local approximate limiting just for those outlier keys, accepting looser enforcement on the worst offenders in exchange for protecting the shared store.

Say this

"I would default this to fail open behind a circuit breaker. Failing closed sounds safer, but it means a rate limiter outage becomes a full platform outage, because the exact thing meant to protect the system becomes its single point of failure. A brief burst of unthrottled traffic during a rare outage is a much better failure mode than taking down every service that depends on the limiter."

Final design

One picture: a stateless rate limiter fleet in front of every protected call, doing fast local-approximate counting synced periodically to a sharded, consistent-hashed Redis counter store, checking burst and sustained limits together via one atomic script, loading tenant policy from a small cached config store, and failing open behind a circuit breaker if the counter store becomes unreachable.

EM-level follow-up

Build-vs-buy, echoing Ch.16's framing: most API gateways (Kong, Envoy, AWS API Gateway) ship a competent per-key rate limiter out of the box, and that is enough for a large share of companies — build a bespoke shared service only once you need cross-service, cross-region shared limits that an off-the-shelf gateway plugin genuinely cannot express. On rollout: because a limit change here is effectively a cross-team API contract (500 services rely on the same fail-open default and the same policy propagation delay), a change to the default fail behavior or the sync interval needs a staged rollout with per-tenant overrides, not a single global flip.

Design a Distributed Cache (as a Standalone System)

Problem framing

A platform infrastructure team has outgrown a single Memcached or Redis box shared informally between teams, and now needs to design and run their own horizontally-scalable, multi-tenant caching tier — effectively "build the thing Redis Cluster or a managed Memcached fleet already is" — as an internal offering that dozens of services depend on. Ch.4 already covered how a service uses a cache (cache-aside, eviction, thundering herd); this problem is the other side of that relationship: how do you build the cache cluster itself so it stays fast, fair, and available as the number of tenants and the size of the working set both keep growing.

Clarifying questions

  • What is the target hit ratio and read:write ratio? — a cache expected to run above 90% hit ratio needs enough memory to hold most of the working set, not just the hottest sliver of it.
  • Does cached data need to survive a node restart, or is it pure, rebuildable-from-source cache? — a pure cache can treat a node loss as a bunch of extra misses; a cache expected to persist needs replication and possibly disk-backed persistence, closer to a database.
  • Do we need only simple GET/SET, or also richer structures like lists, sets, or sorted sets? — richer structures mean the cache is closer to a lightweight in-memory database than a flat key-value cache.
  • Is this multi-tenant — many teams sharing one cluster? — if so, one noisy tenant must not be able to evict another tenant's entire working set, which is a fairness problem on top of a caching problem.
  • Do we need strict consistency on invalidation across regions, or is eventual fine? — cross-region strict invalidation adds real coordination cost; most caching use cases are fine with a short window of staleness.

Requirements

Functional requirements:

  • GET, SET (with a TTL — time-to-live, after which an entry auto-expires), and DELETE on a key.
  • Atomic increment on a key, for counters built on top of the cache.
  • At least one richer structure (a list or hash) in addition to plain string values.
  • Multi-tenant namespacing, so keys from different teams never collide.

Non-functional requirements:

  • Sub-millisecond to low-single-digit-millisecond latency at p99 for a single-key operation.
  • Horizontally scalable by adding nodes, without remapping the entire keyspace every time.
  • A single node failure should cause a bounded increase in misses for the keys it owned, not a cluster-wide outage.
  • One tenant's traffic pattern must not be able to evict another tenant's working set.

Capacity estimate

Assume the cluster serves 50 internal services, totaling 2 million GET/SET operations/sec at peak, at roughly a 10:1 read:write ratio — about 1.8 million reads/sec and 180,000 writes/sec. A well-provisioned single cache node handling small values can sustain on the order of 100,000–150,000 ops/sec; targeting 120,000 ops/sec per node with real headroom implies about 17–20 nodes for throughput alone.

Memory is usually the tighter constraint. Assume the combined hot working set across all 50 tenants is 5TB (average value size 2KB, roughly 2.5 billion keys — a plausible combined footprint for a mid-size platform). At around 64GB of usable cache RAM per node, that is roughly 80 nodes just to hold the data, which exceeds the 17–20 nodes the throughput math required — memory footprint, not raw ops/sec, is what decides this cluster's size. With a replication factor of 2 for availability, that is roughly 160 machines total.

API design

GET  /namespace/{tenant}/{key}
SET  /namespace/{tenant}/{key}   {value, ttl_seconds}
DEL  /namespace/{tenant}/{key}
INCR /namespace/{tenant}/{key}   {by=1}

In practice this is exposed as a thin client library API, not raw HTTP — the library embeds the routing logic described below, so callers see plain function calls like cache.get(tenant, key).

High-level design

A ring of cache node shards, each with a replica, coordinated by a small topology service and a gossip-based membership protocol, addressed by client libraries that know the current hash ring.

Deep dive

1) Smart client versus proxy layer. A smart client library embeds the hash ring and talks directly to the node that owns a key — one network hop, fast, but every language's client needs its own correct implementation, and every client needs to stay in sync as the ring changes. A proxy tier centralizes routing in one fleet that every language talks to identically, at the cost of an extra network hop on every request and a new fleet that itself needs to scale and stay available. Both approaches rely on the same consistent-hashing-with-virtual-nodes mechanics from Ch.5; this is a question of where that logic lives, not whether it's needed.

2) Rebalancing on membership change. Consistent hashing already bounds how many keys move when a node joins or leaves (Ch.5) — but bounded is not zero. The design choice is whether a joining node gets pre-warmed from its replica's data before it's added to the ring (slower to bring up capacity, no cold-start miss spike) or added immediately and left to warm up from real traffic misses (faster to add capacity during an actual incident, at the cost of a temporary miss-rate bump for the keys it now owns).

3) Multi-tenant isolation. Without limits, one tenant's misbehaving batch job can fill shared memory and evict every other tenant's working set — this is the exact failure mode that Meta's "Scaling Memcache at Facebook" paper and comparable large-scale cache deployments have had to defend against. The fix is a per-tenant memory quota enforced inside each node (a namespace prefix plus a tracked byte budget per tenant), so eviction pressure caused by one tenant only evicts that tenant's own keys, never a neighbor's — a fairness problem with the same shape as the multi-tenant rate limiter problem earlier in this chapter, applied to memory instead of request rate.

Trade-offs

At 10x scale, the topology/membership layer is what needs the most care, even though it carries little traffic itself — it is the single source of truth every client and node relies on to agree where a key lives. The trade-off is a simple, eventually-consistent gossip-based membership view (always available, occasionally briefly stale) versus a strongly consistent membership store like ZooKeeper or etcd (Ch.12/Ch.13), which never lies about topology but is briefly unavailable during its own leader election.

Say this

"I'd enforce a per-tenant memory quota inside each cache node rather than relying on a single shared eviction pool. Otherwise one team's batch job with a bad cache key pattern can evict every other team's working set on a cluster everyone depends on, and that's an outage caused by isolation we didn't build, not by capacity we didn't have."

Final design

One picture: a cluster of cache node shards on a consistent-hashing ring with virtual nodes, each shard with an async replica, gossip-based membership feeding a small topology service, a smart client library (or proxy tier) doing the routing, and a hard per-tenant memory quota inside each node so no single tenant can evict another's data.

EM-level follow-up

Build-vs-buy: this is one of the clearest cases in the whole chapter for buying rather than building — managed offerings (ElastiCache, managed Memcached/Redis) cover almost everything here, and a bespoke cluster is only justified once the managed offering's cost at scale, or its lack of a per-tenant quota knob, becomes the actual limiting factor. On rollout: migrating 50 existing services onto one shared cluster has to be a phased, per-tenant onboarding with conservative quotas set upfront, not a single cutover — the first team onto a new shared resource always discovers the isolation gaps the hard way if quotas aren't already in place.

Design a Web Crawler

Problem framing

A search engine team needs a system that starts from a list of seed URLs, downloads pages, follows the links on those pages to find more pages, and keeps doing this across a large fraction of the public web, on a recurring schedule, without getting any of the company's IP ranges blocked for hammering someone's server. The two hard parts are not "how do I download a web page" — that part is easy — they are: how do you avoid re-fetching what you've already seen at a scale of billions of URLs, and how do you avoid overwhelming any single website while still crawling the whole web fast.

Clarifying questions

  • Is this a whole-web crawl or a bounded set of seed domains, like a vertical search engine? — this decides the size of the frontier (the queue of URLs not yet fetched) and how aggressively new domains get discovered versus ignored.
  • How fresh does content need to be — recrawled daily, weekly, monthly? — freshness requirements decide the total crawl budget and whether the crawler needs a revisit policy that prioritizes fast-changing pages.
  • Must we respect robots.txt and per-domain crawl-delay, and are there legal constraints on which sites we can crawl at all? — this decides whether politeness is a soft nicety or a hard, unconditional gate in front of every fetch.
  • What content types matter — HTML only, or also PDFs, images, and JavaScript-rendered single-page apps? — JS-rendered pages need a headless browser in the fetch pipeline, which is far more expensive per page than a plain HTTP GET.
  • Do we need to detect near-duplicate content (mirrors, tracking-parameter variants of the same page), not just exact duplicate URLs? — this adds a content-hashing step on top of simple URL-based deduplication.

Requirements

Functional requirements:

  • Given seed URLs, discover linked URLs and add new, unseen ones to the crawl frontier.
  • Fetch page content, extract text and outgoing links, and hand extracted text to a downstream indexer.
  • Respect each domain's robots.txt rules and crawl-delay.
  • Avoid re-fetching unchanged pages more often than the freshness policy requires.
  • Avoid infinite crawl loops and crawler traps (URL spaces designed, intentionally or not, to generate endless distinct URLs).

Non-functional requirements:

  • Must never overload any single target site — politeness is a hard requirement, not a best-effort one.
  • Must scale horizontally to fetch billions of pages within the freshness window.
  • Must be resumable after a crash without redoing already-completed work.
  • Already-visited-URL and near-duplicate-content checks must stay cheap at billions-of-URLs scale, not degrade into a full database lookup per discovered link.

Capacity estimate

Assume a target of 3 billion pages crawled per month — a large, mid-tier-search-engine scale, well short of "the entire web, daily." Average fetch rate ≈ 3,000,000,000 / (30 × 86,400) ≈ 1,160 pages/sec. Politeness constraints spread load unevenly (some domains get crawled in short bursts respecting their crawl-delay, others sit idle), so provision for roughly 3x that at peak, about 3,500 pages/sec.

Bandwidth: assume an average raw page size of 100KB (HTML plus inline metadata, before any stripping). Average bandwidth ≈ 1,160 × 100KB ≈ 116MB/sec, roughly 10TB/day of raw fetched bytes.

Storage: after parsing down to extracted text and metadata, a page is roughly 10KB. That's 3,000,000,000 × 10KB = 30TB/month of extracted content. The URL bookkeeping itself is also non-trivial: 3 billion known URLs at roughly 100 bytes each (the URL string, a hash, and crawl state) is about 300GB just to track what has been seen — this is exactly why a naive full index of every URL string doesn't scale, and why the seen-URL check described below needs a compact probabilistic structure in front of it.

Discovery rate is much higher than fetch rate: each page has roughly 50–100 outgoing links, so new links are discovered at 50–100x the actual fetch rate. At the 3,500 pages/sec peak fetch rate from above, that means the deduplication layer has to handle on the order of 175,000–350,000 candidate-link checks/sec at peak, far more load than the fetch pipeline itself sees.

API design

POST /v1/seeds
     {urls: []}                        -- add seed URLs to the frontier

GET  /v1/crawl/status
     -> {pages_crawled, frontier_size, active_domains}

GET  /v1/pages/{url_hash}
     -> {content, fetched_at, outgoing_links: []}

GET  /v1/frontier/next?worker_id=      -- internal: a fetcher worker pulls its next URL
     -> {url, politeness_delay_ms}

High-level design

A frontier of per-domain queues feeds a large fetcher pool gated by a politeness check; fetched pages are parsed for links, which flow through a dedup filter before either re-entering the frontier or being dropped as already seen.

Deep dive

1) The frontier as a queue-of-queues, not one global queue. A single global FIFO queue lets one enormous domain (a massive blog host with millions of pages) dominate the crawl and starve everyone else, and makes politeness nearly impossible to enforce, since there is no natural place to track "how long since we last hit this specific domain." The standard fix is a small queue per domain, with a scheduler that round-robins across domains and only pulls from a domain's queue once its crawl-delay has elapsed since the last fetch — the same fairness shape as the multi-tenant rate limiter problem earlier in this chapter, just enforced against outbound requests to other people's servers instead of inbound requests to our own.

2) Cheap already-seen checks at billions-of-URLs scale. Checking "have we seen this URL" against a full authoritative index for every discovered link, at 50–100x the fetch rate, is far too much load for a direct database lookup per link. A Bloom filter — a compact, probabilistic in-memory structure that can say "definitely not seen" with certainty and "possibly seen" with a small, tunable false-positive rate — sits in front of the real seen-URL store, absorbing the overwhelming majority of checks entirely in memory, and only a small fraction of "possibly seen" results ever fall through to the authoritative store to confirm.

3) Crawler traps and near-duplicate content. Some sites generate effectively infinite distinct URLs — calendar pages, session IDs embedded in the URL, faceted search parameters — which would let a single domain's frontier queue grow forever. URL normalization (stripping known tracking and session parameters before the dedup check) catches part of this; a hard cap on crawl depth and on pages fetched per domain per cycle catches the rest. Separately, near-duplicate pages — the same article mirrored on several domains, or wrapped in a different template — are not caught by URL comparison at all, since the URLs are genuinely different; they're caught by a content hash (a fingerprint of the extracted text, ignoring boilerplate like navigation menus) so the same content doesn't get indexed many times over under different addresses.

Trade-offs

At 10x scale, the per-domain fairness scheduler inside the frontier tends to strain before raw fetch throughput does — with 10x more discovered domains, the in-memory structure tracking "which domain is due, and when" needs its own sharding across scheduler instances. The trade-off is a coarser, batched view of domain due-times (some domains get crawled slightly off from their exact politeness schedule, but the scheduler scales horizontally) versus a fully precise per-domain schedule that is easier to reason about but does not shard as cleanly.

Say this

"I would put a Bloom filter in front of the authoritative seen-URL store rather than checking every discovered link against that store directly. Discovery happens at 50 to 100 times the fetch rate, so a direct lookup per link would make deduplication the actual bottleneck of the whole crawl, not the fetching itself."

Final design

One picture: seed URLs feed a frontier of per-domain queues that enforce crawl-delay; a politeness gate checks robots.txt before every fetch; a large horizontally-scaled fetcher pool stores raw pages in a blob store; a parser extracts links and text; a Bloom-filter-backed dedup layer, checked against an authoritative seen-URL store only on a possible hit, decides which links re-enter the frontier; and a content-hash step catches near-duplicate pages that URL-based dedup would miss.

EM-level follow-up

Build-vs-buy: unless crawling itself is the core product, an off-the-shelf crawling framework (Apache Nutch at large scale, Scrapy at smaller scale) covers most of this — a fully bespoke distributed crawler is usually only justified when crawl breadth or freshness is the actual product differentiator. On rollout and cross-team impact: crawler behavior is a legal and reputational surface, not just an engineering one — a misconfigured crawler getting a company's IP range blocked, or violating a site's terms of service, is the kind of failure that should be reviewed with legal or infra leadership when setting politeness defaults and per-domain rate caps, not tuned unilaterally by whichever engineer is on call that week.

Design A Distributed Job Scheduler

Problem framing

A distributed job scheduler is the infrastructure behind "run this thing later, or run this thing every hour, forever" — a cron daemon that works across thousands of machines and thousands of independent teams instead of one box. Think of a platform team building a shared "Scheduler-as-a-Service" that other engineering teams register jobs with: nightly report generation, hourly cache warm-ups, "send this reminder in three days," a batch pipeline trigger. Google's SRE book describes exactly this problem under the name "distributed cron," and AWS EventBridge Scheduler and Kubernetes CronJobs are productized versions of the same idea. Strip away the UI and this is really about one thing: reliably deciding, across a fleet of nodes, which of millions of jobs is due right now, and firing each one exactly once under normal conditions.

Clarifying questions

  • Are jobs purely time-triggered, or can they also be event-triggered (like "run when a file lands")? — event triggers add a whole watch/notify subsystem; the interviewer confirms this system is time-triggered only, both recurring cron schedules and one-off delayed jobs.
  • What does a job actually do when it fires — call an HTTP endpoint, publish a message to a queue, or run a container? — this decides whether the worker fleet needs to manage compute (containers) or just make network calls, which is far simpler.
  • What happens if a job's previous run has not finished when its next scheduled time arrives — skip, queue, or allow overlap? — this decides whether the system needs per-job mutual exclusion, tying directly into the distributed lock service problem elsewhere in this chapter.
  • Can one tenant's misbehaving job degrade another tenant's on-time triggering? — decides whether per-tenant quotas and isolation are in scope, or a single shared best-effort pool is acceptable.
  • What is the acceptable delay between a job's scheduled time and it actually firing? — decides how fine-grained the "what is due" check has to be, and how much jitter can be added to smooth out bursts.

Requirements

Functional requirements:

  • Register a job with either a cron expression (recurring) or a specific run_at timestamp (one-off), a target (HTTP callback or queue message), a retry policy, and a concurrency policy (skip, queue, or allow overlap).
  • Pause, resume, and cancel a job.
  • Query a job's execution history and current status.
  • Manually trigger a job on demand, for debugging.

Non-functional requirements:

  • Trigger accuracy: a due job fires within a few seconds of its scheduled time at p99 (99th percentile — 99 out of 100 executions).
  • At-least-once triggering — a job that was due is never silently skipped, even across a scheduler-node crash.
  • No single point of failure in the control plane that decides what is due.
  • Scales to millions of registered jobs across thousands of tenants without one tenant's burst delaying another tenant's jobs.
  • A missed trigger window (the scheduler itself was down) is caught up according to a per-job policy — run immediately on recovery, or skip and wait for the next scheduled time.

Capacity estimate

Assume 200,000 registered jobs across 3,000 tenant teams, with a blended average recurrence interval of 20 minutes (some jobs fire every minute, some once a day; 20 minutes is a reasonable planning average across that mix).

Average trigger rate ≈ 200,000 jobs ÷ 1,200 seconds (20 minutes) ≈ 167 triggers/sec. That number hides the real problem: cron schedules cluster at round times. If 15% of jobs (30,000) are set to fire "at the top of every hour," all 30,000 become due inside the same one-second window once an hour — a burst roughly 180 times the average rate, arriving in a single second. This is exactly why a real scheduler adds jitter, covered in the deep dive.

Storage for job definitions is tiny: each job (cron expression or run_at, target URL or queue name, payload template, retry and concurrency policy, tenant ID) is roughly 1.5KB. 200,000 × 1.5KB ≈ 300MB total — comfortably fits in a normal replicated relational store.

Execution history is the bigger number. At one execution per job per 20 minutes, that is 200,000 × 72 runs/day ≈ 14.4 million executions/day. At roughly 400 bytes per execution record (job_id, scheduled_time, actual_trigger_time, status, retry_count, duration), that is 14.4M × 400 bytes ≈ 5.76GB/day, about 2.1TB/year at full resolution — enough to justify rolling anything older than 30-90 days out to cheaper cold storage.

A naive "select jobs where next_run <= now()" query against 200,000 rows, run once a second, is completely fine at this size on a normal database. That query pattern stops scaling long before the job count reaches tens of millions, which is why the deep dive below replaces it with something else once you push past this scale.

API design

POST   /v1/jobs
       {tenant_id, schedule: {cron | run_at}, target: {type: http|queue, url|queue_name},
        payload, retry_policy, concurrency_policy, timeout_ms} -> {job_id}
PATCH  /v1/jobs/{job_id}          {pause|resume|update_schedule}
DELETE /v1/jobs/{job_id}
GET    /v1/jobs/{job_id}/executions?cursor= -> {executions[], next_cursor}
POST   /v1/jobs/{job_id}/trigger  (manual run-now, for debugging)

High-level design

A Scheduler API handles job CRUD (create/read/update/delete) against a durable job store. The interesting part is a fleet of scheduler nodes, each elected leader over one shard of the job space, continuously checking which of its own jobs are due and handing due work off to a trigger queue that a separate worker fleet drains.

Deep dive

1) Exactly-once triggering does not exist — design for at-least-once plus idempotent handlers. No distributed system can guarantee a job fires precisely once: a scheduler node can crash right after deciding a job is due but before recording that it triggered it, and on restart it has no way to be certain whether the trigger actually went out. The honest target is at-least-once triggering with a fencing mechanism (see the distributed lock service problem in this chapter) that makes double-triggering rare rather than impossible, combined with a contract that every job's HTTP or queue target must be idempotent — safe to receive twice. This mirrors the idempotency discussion in Ch.13 and the "effectively-once" framing Ch.14 uses for Kafka.

2) Finding "what is due" has to stop being a table scan once job count grows. At 200,000 jobs, polling a database with an indexed range query once a second is fine. At tens of millions of jobs, that query — and the row-locking it implies if multiple scheduler nodes poll the same table — becomes the bottleneck. The standard fix is a time-wheel or a min-heap priority queue kept in memory per shard, where each job sits in a bucket keyed by its next-run time; advancing the wheel by one tick is O(1) work to find "what is due in this bucket" instead of scanning every row. The second fix, for the top-of-hour thundering herd from the capacity estimate, is jitter: spreading a batch of simultaneously-due jobs across a few seconds instead of firing all 30,000 in the same instant, which smooths the trigger-queue's write rate without meaningfully hurting any individual job's timing.

3) Exactly one node must be responsible for a given job's shard, with fast failover. If two scheduler nodes both believe they own the same hash range, they both fire the same due job — a correctness bug, not just an inefficiency. This is solved with the same leader-election pattern the distributed lock service problem in this chapter is built around: each shard's ownership is a lease, renewed on a heartbeat, backed by a small consensus cluster (Ch.12). If a shard leader crashes, its lease expires and another node picks up that hash range within one lease interval — a bounded, known delay rather than an indefinite outage for that shard's jobs.

Trade-offs

At 10x the job count, the "what is due" detection mechanism breaks before the trigger queue or the worker fleet does. A time-wheel per shard scales linearly with shard count, so the fix is adding more shards — but more shards means more independent leader elections to manage, and a shard rebalance (moving hash ranges between nodes when you add capacity) briefly risks either double-triggering or missed triggers for the jobs in transit. The trade-off is between a simple, coarse-grained sharding scheme that rebalances rarely but in big, risky steps, versus a finer-grained one that rebalances often in small, safer steps but adds more leader-election overhead.

Say this

"I would not try to guarantee exactly-once triggering — I would guarantee at-least-once with a fencing token from the lock service, and push the idempotency requirement onto every job's target, the same way Kafka pushes it onto consumers. Trying to make the scheduler itself perfectly exactly-once is the wrong place to spend the complexity budget."

Final design

One picture: a durable job store sharded by job_id, a fleet of scheduler nodes each holding a leased leadership over one shard of that space, each leader scanning a per-shard time-wheel to find due jobs and pushing them onto a trigger queue, and a stateless worker fleet draining that queue to actually call each job's target and record the result.

EM-level follow-up

Build-vs-buy: most companies should not build this from scratch — Kubernetes CronJobs, AWS EventBridge Scheduler, or Airflow cover the vast majority of use cases, and a custom scheduler is worth building only when you need tenant-level isolation guarantees or trigger-latency SLAs those tools do not offer out of the box. On rollout, migrating teams off ad hoc cron jobs on individual VMs is a slow, cohort-by-cohort process — you keep the old cron running in parallel with the new service until you have proven, for that team's jobs specifically, that trigger timing and retry behavior actually match, because a silently-dropped nightly billing job is a much worse outage than a slow migration.

Design A Distributed Message Queue

Problem framing

This is not "use a queue in your design" — it is "you are the team that builds the queue." Picture the infrastructure team at a large company that has outgrown a hosted broker's cost or feature limits and decides to operate its own partitioned, replicated messaging system as company-wide infrastructure — the same problem LinkedIn solved when it built Kafka, or the problem AWS solves internally for SQS. Ch.14 covers how a caller uses a queue — acks, in-sync replicas (ISR), consumer groups, offsets. This problem is about building the broker that provides those guarantees: the on-disk log format, the replication protocol, and the metadata layer that decides who is the leader for what.

Clarifying questions

  • Do messages need strict ordering, and if so, at what granularity — globally, or per key? — decides whether a single global log is enough or the system needs to partition by key and only guarantee order within a partition.
  • Is at-least-once delivery acceptable, or does a caller need exactly-once? — decides whether the broker needs an idempotent-producer mechanism and a transactional write path, or a simpler design is enough.
  • How long does data need to be retained, and does a consumer ever need to replay old messages? — decides whether this is a disappear-on-ack queue (like classic SQS) or a retained, replayable log (like Kafka).
  • How many independent consumer groups read the same stream? — decides how much read fan-out the storage layer has to sustain beyond the producer's write rate.
  • What is the acceptable publish latency versus durability trade-off — does the caller pick per message, or is it fixed per topic? — decides whether the broker exposes a per-write acknowledgment-level knob.

Requirements

Functional requirements:

  • Producers publish messages to a named topic, optionally with a partition key that determines which partition a message lands on.
  • Consumers read via named consumer groups; within a group, each partition is delivered to exactly one consumer at a time (the same rule Ch.14 covers from the client side).
  • Order is preserved within a partition.
  • Retention is configurable by time or size, independent of whether any consumer has read the data yet, so multiple consumer groups can read at their own pace and replay history.

Non-functional requirements:

  • Once a producer's write is acknowledged, the message is never silently lost, even if the broker that received it crashes immediately after.
  • Sustains millions of messages/sec cluster-wide with horizontal scaling by adding brokers and partitions.
  • Publish latency: low single-digit milliseconds at p99 for the fastest acknowledgment mode, low tens of milliseconds for the safest mode.
  • No single point of failure, including the metadata layer that tracks which broker leads which partition.

Capacity estimate

Target: 2,000,000 messages/sec average across the cluster, average message size 1KB, so roughly 2GB/sec of payload. With a replication factor of 3 for durability, every byte is written to a leader plus 2 followers, so total write bandwidth across the cluster is about 3 × 2GB/sec ≈ 6GB/sec.

If a single broker's disk can sustain roughly 500MB/sec of sequential append-only writes (a reasonable planning number for a fast local SSD doing pure sequential I/O), the cluster needs at least 6GB/sec ÷ 500MB/sec ≈ 12 broker-equivalents purely for write bandwidth. Add headroom for read traffic, cross-availability-zone replication overhead, and uneven partition placement, and a real deployment lands closer to 30-40 physical brokers.

Retention: assume a 7-day default. 2GB/sec × 86,400 sec/day ≈ 172,800GB/day of raw payload; over 7 days that is roughly 1.21PB, and at replication factor 3 the cluster needs about 3.6PB of disk provisioned in total.

To spread that load and give consumer groups room to parallelize, plan for on the order of 10,000-20,000 partitions across all topics — enough that no single partition's sustained throughput comes close to saturating one broker's disk or network link on its own.

Reads dominate, same as almost every system in this bank: if each message is read by 3 independent downstream consumer groups on average (analytics, fraud detection, notifications), cluster-wide read throughput is roughly 3 × 2,000,000 ≈ 6,000,000 messages/sec.

API design

POST /topics                              {name, partitions, replication_factor, retention_ms}
POST /topics/{topic}/messages             {key, value, partition_key?} -> {partition, offset}
GET  /topics/{topic}/partitions/{p}/fetch?offset=&max_bytes= -> {messages[], next_offset}
POST /consumer-groups/{group}/offsets/commit  {topic, partition, offset}
GET  /consumer-groups/{group}/offsets?topic=  -> {partition: offset}

High-level design

Producers publish through a router that knows, from cluster metadata, which broker currently leads each partition. Each partition is an append-only log replicated to a small set of followers; a controller broker, elected via consensus, owns the job of assigning partitions to brokers and tracking who is currently in each partition's in-sync replica set.

Deep dive

1) The append-only log is the single biggest performance decision in the system. Each partition is stored as a sequence of immutable segment files on disk, and a write is always appended to the end of the current segment — never a random-access update. This turns every write into cheap sequential disk I/O instead of the random seeks a general-purpose database pays for, which is the entire reason a purpose-built queue can sustain gigabytes per second on ordinary disks. A separate sparse index file (offset-to-byte-position) lets a consumer seek to an arbitrary offset without scanning the whole segment. Old segments age out and get deleted once they fall outside the retention window — deletion itself is cheap because it just drops whole files, never a row-by-row scan.

2) Replication safety is a producer-visible knob, not a fixed guarantee. Ch.14 explains how a caller reads acks=0/1/all and min.insync.replicas from the outside; building the broker means implementing what those settings actually do. acks=0 returns to the producer the instant the write is handed to the network — fastest, and a leader crash before the write lands on disk loses it silently. acks=1 waits for the leader's own disk to accept the write, still losing it if the leader dies before any follower copies it. acks=all waits for every replica currently in the in-sync replica set (ISR) to confirm — the safe default for anything the business cannot afford to lose, at the cost of waiting for the slowest in-sync follower on every write. Implementing this correctly means the leader has to track, in real time, exactly which followers are caught up enough to count as "in sync," because promoting a lagging follower to leader after a crash would silently drop every message it never got a copy of.

3) Consumer offsets can be tracked by the broker or by the client, and that choice ripples through everything. A broker-tracked model — the broker itself remembers each consumer's read position, closer to how classic SQS visibility timeouts work — keeps the client dead simple, but the broker now has to store and scale a cursor per consumer, and a redelivery-timeout race can double-deliver a message under load. A client-tracked model — Kafka's approach — pushes the consumer to commit its own offset, which scales beautifully because offsets are cheap and the broker does not have to manage per-consumer state, but every consumer now needs its own replay-safe, idempotent processing logic. The same choice cascades into partition reassignment: when a broker joins or leaves, the controller (elected the same way a Raft or Paxos leader is elected, Ch.12) has to recompute which broker leads which partition, and a badly-coordinated reassignment can briefly make two brokers each believe they lead the same partition — a split-brain the controller's own consensus protocol exists specifically to prevent.

Trade-offs

At 10x the message rate, a single hot partition breaks before the cluster's aggregate capacity does — one poorly chosen partition key sends a disproportionate share of traffic to one leader broker's one disk. More partitions spreads that risk but multiplies replication overhead and the number of open file handles and index structures every broker has to manage; fewer, larger partitions keeps per-broker overhead low but concentrates risk on whichever partition gets unlucky. There is no setting that avoids this trade-off — only a partition-key design choice made before the hot key exists.

Say this

"I would default new topics to acks=all with min.insync.replicas set to 2 on a replication factor of 3, because losing an acknowledged message is usually a worse outage than a slightly slower write — and I would only relax that for topics carrying data that is genuinely disposable, like raw clickstream telemetry, where a dropped message just slightly undercounts a metric."

Final design

One picture: producers write through a router to whichever broker currently leads a given partition; each partition is an append-only log replicated to a small set of followers; a consensus-elected controller assigns partitions to brokers and tracks each partition's in-sync replica set; consumer groups read independently and commit their own offsets, so any number of downstream systems can replay the same retained log at their own pace.

EM-level follow-up

The honest build-vs-buy answer here is that almost nobody should build this: Kafka, SQS, and RabbitMQ (compared directly in Ch.14) already solve this problem well, and operating your own broker is a multi-year commitment of a dedicated team's time. It is worth doing only at a scale, or with a cost or compliance constraint, that a managed or open-source option genuinely cannot meet — and even then, the rollout is a slow one: shadow-write to the new broker alongside the incumbent, compare delivery and latency for months, and only cut production traffic over topic by topic, because a broker-level bug does not fail one feature, it fails every team relying on it at once.

Design A Distributed Key-Value Store

Problem framing

This is the classic "build something like DynamoDB, Cassandra, or Riak from scratch" question — a general-purpose, horizontally-scalable store that other teams put session data, user profiles, feature-flag state, or product catalog entries into, addressed only by key. It sits in the same design tradition as Amazon's 2007 Dynamo paper. The key distinction from the distributed cache problem earlier in this chapter: a cache is allowed to lose data, because a miss just falls back to the real source of truth. A key-value store like this one is often the source of truth itself for whichever team owns the data in it, so an acknowledged write must never silently disappear.

Clarifying questions

  • Is this the primary source of truth, or a derived copy that can be rebuilt? — decides whether write-loss is ever acceptable; the interviewer confirms this is a source of truth for its callers.
  • What does the value size distribution look like — a few hundred bytes, or tens of kilobytes? — decides whether values live inline or as pointers into a separate blob store, similar to the distributed object storage problem elsewhere in this chapter.
  • Do callers need range scans, or strictly single-key get and put? — decides whether a pure hash-partitioned design is enough, or the system needs something closer to a sorted range store.
  • Does every operation need strong consistency, or can most callers accept eventual consistency for lower latency and higher availability? — the interviewer confirms most access patterns (sessions, profiles) can tolerate eventual consistency, with a stronger mode available per request.
  • Should the system stay available if an entire replica goes down, even at the cost of returning slightly stale data? — decides an availability-first (AP) design versus a consistency-first (CP) one, in Ch.12's CAP terms.

Requirements

Functional requirements:

  • put(key, value, ttl?), get(key), delete(key).
  • Conditional put (compare-and-swap) using a version token, so a caller can safely say "only update if nobody else changed this since I last read it."
  • Batch get for multiple keys in one round trip.

Non-functional requirements:

  • Horizontally scalable by adding nodes with no downtime and a small, predictable amount of data movement per node added.
  • Tunable per-request consistency, defaulting to available and partition-tolerant (AP) since most callers value uptime over strict freshness.
  • p99 read and write latency in the single-digit milliseconds.
  • Survives the loss of an entire availability zone without losing acknowledged data or going fully unavailable.
  • Self-healing: after a node failure, the data it held is automatically re-replicated elsewhere without an operator stepping in.

Capacity estimate

Assume 500 million distinct keys, average value size 1KB: 500 million × 1KB ≈ 500GB of raw, unreplicated data. At a replication factor of N=3, total stored data is about 1.5TB.

Traffic: 200,000 reads/sec and 20,000 writes/sec average, a 10:1 read-to-write ratio typical of a profile or session store. At a 3x peak factor, that is 600,000 reads/sec and 60,000 writes/sec, roughly 660,000 total operations/sec at peak.

Per-node planning budget: assume one node sustainably serves about 20,000 operations/sec under a mixed read/write load with replication overhead. 660,000 ÷ 20,000 ≈ 33 nodes needed for throughput alone. Storage alone needs far fewer: 1.5TB ÷ 200GB-per-node budget ≈ 8 nodes. Throughput dominates, so a real cluster lands around 33-40 physical nodes — each one carved into roughly 100-256 virtual nodes on the consistent-hashing ring (Ch.5) so that adding or removing one physical node only moves a small, even slice of the total data.

API design

PUT    /kv/{key}                    {value, ttl_seconds?} -> {version}
PUT    /kv/{key}?if_version={v}     {value} -> 200 OK or 409 Conflict
GET    /kv/{key}                    -> {value, version}
GET    /kv?keys=k1,k2,k3            -> {k1: {...}, k2: {...}, k3: {...}}
DELETE /kv/{key}

High-level design

Any node can act as the coordinator for a request. It hashes the key onto the consistent-hashing ring (Ch.5) to find the N nodes that own that key's replica set, forwards the write or read to them, and waits for a configurable quorum before responding. Membership and failure detection ride on a gossip protocol; a background anti-entropy process keeps replicas in sync even when they briefly disagree.

Deep dive

1) Consistent hashing with virtual nodes decides both placement and rebalancing cost. Ch.5 covers the mechanics; the design decision specific to this problem is how many virtual nodes to give each physical node. Too few, and one physical node's share of the ring can be meaningfully uneven, causing a hot node. Too many (100-256 is a common range), and load balances well, and — critically — adding or removing one physical node only moves a small, even slice of total data, because that node's virtual nodes are scattered across many small ranges rather than one big contiguous chunk.

2) Quorum reads and writes trade consistency for availability, and the same math shows up under a partition. With N replicas, a write acknowledged by W of them and a read checking R of them are guaranteed to overlap on at least one up-to-date replica whenever R + W > N (Ch.9 works this out in full for Cassandra; Ch.8 covers the same idea, less exposed as a dial, inside DynamoDB). During a network partition, a strict quorum can make a write fail outright if too few replicas are reachable. Dynamo-style systems relax this with a sloppy quorum: write to any W reachable nodes, even ones outside the key's "proper" replica set, and buffer a hint for the unreachable proper replica to catch up once it returns — hinted handoff, shown in the diagram. This is the PACELC trade-off from Ch.12 made concrete: during a partition, the system chooses availability over strict consistency.

3) Sloppy quorums create conflicting writes that need a resolution strategy, and repair has to be cheap. If two coordinators accept writes to the same key on different, only-partially-overlapping sets of replicas during a partition, the replicas end up disagreeing about the current value. Last-write-wins (compare timestamps, keep the newer one) is simple but silently drops one write. Vector clocks (Ch.13) detect true concurrency instead of just picking a winner, surfacing both values as "siblings" for the application to merge — the choice Riak makes, following the original Dynamo paper, versus Cassandra's deliberate choice of the cheaper last-write-wins. Either way, replicas eventually need to reconcile in the background; comparing entire key ranges byte-for-byte would be far too expensive at this scale, so anti-entropy repair uses Merkle trees (Ch.9) — hash trees that let two replicas find exactly which sub-ranges differ in a handful of hash comparisons, transferring only the actual mismatched data.

Trade-offs

At 10x the traffic, a single hot key — one viral profile, one flag everyone reads — breaks before the ring's aggregate capacity does, because a hot key still only lives on N specific nodes no matter how many total nodes the cluster has. Adding nodes does not fix a hot partition. The trade-off is a request-level cache in front of the store for hot keys (fast, but reintroduces the staleness the KV store itself was tuned to avoid) versus splitting one logical hot key into several physical keys and aggregating client-side (correct, but pushes real complexity onto every caller of that key).

Say this

"I would default this store to an AP design — available and partition-tolerant, in Ch.12's terms — because the callers I would expect, session and profile data, care far more about never seeing an error page than about seeing the absolute latest write. I would keep a stronger, quorum-majority read path available as an opt-in for the handful of callers that genuinely need it, rather than paying that latency cost by default for everyone."

Final design

One picture: keys are placed on a consistent-hashing ring with virtual nodes; a coordinator forwards each request to the N nodes that own a key, waits for a tunable read or write quorum, falls back to a sloppy quorum with hinted handoff during a partition, and reconciles any resulting conflicts in the background through vector clocks or last-write-wins plus Merkle-tree anti-entropy.

EM-level follow-up

Build-vs-buy is the first question any EM asks here: DynamoDB, Cassandra, and ScyllaDB are mature, well-understood answers, and a company only builds its own when it has a specific cost profile at extreme scale or a latency and data-locality requirement a managed option cannot meet. If the decision is to build, the cross-team cost worth flagging up front is operational: this becomes a stateful, always-on piece of shared infrastructure the moment two teams depend on it, which means a dedicated on-call rotation and an explicit availability SLO from day one, not something bolted on after the first incident.

Design A Distributed Unique ID Generator

Problem framing

Almost every backend service eventually needs to hand out an ID for a new row, order, or event, and a single database's auto-increment column stops working the moment that table gets sharded (Ch.6) — two shards handing out IDs independently either collide or lose any global ordering. The product framing: a platform team offers a shared, embeddable "ID Generation" library or service so every other backend team can mint unique, roughly time-sortable IDs without a central counter becoming a bottleneck or a single point of failure. This is exactly the problem Twitter's original Snowflake solved, and the same design pattern Instagram and Sony's Sonyflake reuse.

Clarifying questions

  • Does the ID need to be sortable by creation time, or is pure uniqueness enough? — decides between a Snowflake-style layout and a plain UUID, the comparison Ch.16 covers in full.
  • What is the maximum number of ID-generating processes running at once, now and a few years out? — decides how many bits to reserve for the worker/machine ID field.
  • What is the peak ID-mint rate on a single busy node? — decides how many bits go to the per-millisecond sequence field.
  • Are these IDs ever shown to end users, for example in a URL? — decides whether leaking rough creation time or origin machine is a real information-leak concern worth mitigating.
  • Is the deploy environment fast-churning containers, or a small number of long-lived hosts? — decides how aggressively worker-ID leases need to be reclaimed after a process dies.

Requirements

Functional requirements:

  • Generate a unique ID through a single local, in-process function call — no network round trip on the hot path.
  • IDs are roughly sortable by creation time.
  • A one-time bootstrap step assigns each process a worker ID before it starts minting.

Non-functional requirements:

  • No shared bottleneck and no single point of failure on the ID-generation hot path itself.
  • Sustains the company's full ID-mint volume with large headroom, now and after several years of growth.
  • IDs are compact — 64 bits — so they behave well as database primary keys and index entries (Ch.7).
  • Safe under normal clock drift (small NTP time corrections) — an ID is never reused, even across a clock adjustment.

Capacity estimate

Use the Snowflake bit layout from Ch.16: 1 sign bit, 41 bits of timestamp (milliseconds since a custom epoch), 10 bits of worker ID, 12 bits of per-millisecond sequence — 64 bits total.

Company-wide target: 80,000 IDs/sec average across every service, 300,000 IDs/sec at peak (many sharded write paths minting simultaneously during a traffic spike).

Per-node ceiling from the 12-bit sequence field: 2^12 = 4,096 IDs per millisecond per worker, which is 4,096,000 IDs/sec if any single node ever needed to mint that fast — vastly more than any real node approaches, so raw throughput per node is never the actual constraint.

Worker-ID pool from the 10-bit field: 2^10 = 1,024 concurrently active worker IDs. At 300,000 IDs/sec peak spread across however many containers happen to be running, 1,024 slots is comfortable headroom right up until the company runs more than roughly 1,000 ID-generating processes at once — at that point the real constraint, covered in the deep dive, is running out of worker IDs, not running out of throughput.

41-bit timestamp range: 2^41 milliseconds ≈ 2.199 × 10^12 ms, which works out to roughly 69-70 years of range from the chosen custom epoch before the timestamp field wraps around — comfortably longer than this system is likely to run unmodified.

API design

generate_id() -> uint64                          // in-process library call, no network hop
GET  /v1/id -> {id}                               // fallback network call for a process
                                                    // that cannot embed the library
POST /v1/worker-ids/lease {process_hostname} -> {worker_id, lease_ttl}   // once, at startup
POST /v1/worker-ids/{worker_id}/renew                                   // periodic heartbeat
DELETE /v1/worker-ids/{worker_id}                                       // on graceful shutdown

High-level design

Every service instance embeds a small ID-generation library. At startup it leases a worker ID from a lightweight coordination service; after that, generating an ID is a purely local operation with no network call at all. The coordination service is only ever on the path once per process lifetime, not once per ID.

Deep dive

1) Clock drift is a correctness bug here, not a performance problem. The whole scheme assumes each node's clock only ever moves forward. If NTP corrects a machine's clock backward, or a virtual machine gets paused and resumed with a stale clock, the node risks generating an ID with a timestamp earlier than one it already issued — a collision or an ordering violation, not just a slow response. The standard mitigation: on every ID generation, compare the current time against the last timestamp this node used; if the current time is behind, refuse to generate new IDs (or briefly wait) until the clock catches back up, and alert loudly, because a machine silently minting backward-dated IDs is far worse than one that briefly stalls.

2) Worker-ID exhaustion, not throughput, is what actually causes outages in practice. With only 10 bits of worker-ID space (1,024 values), a fast-churning container environment can genuinely run out: if worker IDs are leased but never reliably reclaimed, a rolling deploy that cycles through thousands of pod restarts over a few weeks can exhaust the pool even though far fewer than 1,024 processes are ever running at once. The fix is a lease with a short time-to-live (TTL), renewed on a heartbeat exactly like the leases in the distributed lock service problem in this chapter — if a process crashes without releasing its worker ID, the lease expires and the ID is automatically reclaimed rather than permanently lost.

3) Sortable IDs leak information, which matters once they are user-visible. A Snowflake ID's leading bits are a timestamp, so anyone who can see two IDs can infer roughly how far apart in time they were created, and the worker-ID bits leak which machine or shard produced them. That is harmless for an internal primary key, but a real concern if the ID appears in a public URL — a competitor could infer signup order or estimate traffic volume by watching how fast IDs increment. Products that expose IDs externally often keep Snowflake internally for its indexing benefits and issue a separate, opaque, non-sequential ID (a UUID, or a format like ULID/UUIDv7) at the API boundary specifically to avoid that leak — worth naming explicitly rather than assuming one ID format has to serve both jobs.

Trade-offs

At 10x the company's process count, the failure that shows up first is worker-ID pool exhaustion under container churn, not per-node sequence exhaustion — the 12-bit sequence field has orders of magnitude more headroom than any real node needs. The trade-off is allocating more bits to the worker ID (a bigger pool, safer against churn, but fewer sequence bits and a lower per-node throughput ceiling) versus keeping the original split and investing instead in more aggressive lease reclamation — the second option keeps the bit layout untouched but adds real operational complexity to the lease service.

Say this

"I would pick a Snowflake-style ID over a UUID here specifically because this is going to be a primary key — a roughly time-ordered ID keeps new rows landing at the end of the B-tree index instead of scattered across it, the insert-performance problem Ch.7 covers for random primary keys. The one-time worker-ID bootstrap is a small price for keeping every actual ID generation fully local and network-free."

Final design

One picture: every service instance embeds a Snowflake-style generator; a small coordination service only ever hands out and reclaims worker IDs at process startup and shutdown, never on the per-ID path; the 64-bit layout — timestamp, worker ID, sequence — is sized against expected node count and per-node throughput up front, since changing that split later means touching every ID-generating process at once.

EM-level follow-up

Rollout is the hard part of this problem in practice: migrating an existing auto-increment primary key to Snowflake IDs across a live system is a multi-quarter effort, because every service that stores, displays, or compares that ID has to handle the new 64-bit format — it is a cross-team migration, not a one-team change, usually run as a dual-write period followed by a backfill and a staged cutover of reads. On build-vs-buy: there is rarely a reason to invent a new bit layout — reusing an established, well-tested Snowflake derivative saves the team from re-discovering the clock-drift and worker-ID-exhaustion bugs the hard way.

Design A Distributed Lock Service

Problem framing

A distributed lock service is shared infrastructure that lets many independent processes agree on "who gets to do this one thing right now" — either a long-lived leadership role (leader election) or a short-lived exclusive turn (mutual exclusion). Google's Chubby elects the leader for GFS and Bigtable; Kubernetes leans on etcd for exactly this; ZooKeeper elects HBase's HMaster. Inside this very chapter, the distributed job scheduler problem needs exactly this primitive to make sure only one node triggers a given shard's due jobs at a time. Ch.13 covers the mechanics — Redis Redlock, ZooKeeper's ephemeral sequential znodes, fencing tokens — and Ch.16 frames it briefly as a reusable service; this problem is the full interview treatment of that service on its own.

Clarifying questions

  • Is this for leader election (one long-lived winner) or mutual exclusion (many short-lived critical sections), or both? — decides default lease lengths and whether a fair queue for waiters is worth building.
  • Can the resource being protected check a fencing token on its own writes? — decides whether the lock service can actually guarantee end-to-end safety, or only reduce the odds of a conflict, covered in the deep dive.
  • What is the acceptable failover time if the lock service's own leader crashes? — decides cluster size and election-timeout tuning.
  • How many distinct locks are held concurrently at peak, and how short-lived are they? — decides whether one shared consensus group is enough, or the lock namespace needs to be sharded.
  • Do callers need a blocking wait-and-notify API, or is poll-and-retry acceptable? — decides whether a watch or streaming mechanism is required.

Requirements

Functional requirements:

  • acquire(lock_name, holder_id, ttl) returns granted-plus-fencing-token, or denied.
  • renew(lock_name, holder_id, fencing_token) extends an active lease.
  • release(lock_name, holder_id, fencing_token) gives up a lock early.
  • watch(lock_name) streams notifications to waiters when a lock is released or expires.
  • The same primitive serves both leader election and short-lived mutual exclusion — a leader election is just a very long-lived lock on a well-known name.

Non-functional requirements:

  • Safety above everything else: the same lock is never granted to two holders at the same time, even across a network partition or a long garbage-collection pause on a client.
  • The lock service's own availability must exceed whatever it is protecting — it cannot be a bigger single point of failure than the problem it solves.
  • Acquire and renew latency in the tens of milliseconds is acceptable; this is not a hot-path, high-throughput system.
  • Bounded, predictable failover time if the lock service's own internal leader crashes.

Capacity estimate

Assume 5,000 microservice instances company-wide. Of those, about 200 hold long-lived leader-election roles (one leader per job-scheduler shard, one controller for various clustered systems), plus roughly 5,000 short-lived mutual-exclusion locks in active use at any given moment (for example, "only one instance of this nightly batch job runs at once").

Leases renew every 5 seconds — short enough to fail over quickly, long enough not to flood the cluster with heartbeats. Steady-state renewal load ≈ (200 + 5,000) ÷ 5 sec ≈ 1,040 operations/sec, a modest number.

Peak load looks different: a mass-restart event — a company-wide deploy, a data-center failover — can push thousands of instances to acquire or re-acquire locks within the same few seconds. Plan for a burst on the order of 5,000-10,000 operations/sec for a short window, and load-test specifically for that scenario rather than the steady state.

Storage is never the constraint: a lock record (name, current holder, lease expiry, fencing token, waiter queue) is roughly 200 bytes, so even 50,000 concurrently tracked locks is only about 10MB. The number that actually matters is quorum write throughput — every acquire, release, and renew is a replicated consensus write (Ch.12), not a fast in-memory operation, and a single Raft or Paxos leader typically sustains on the order of a few thousand to the low tens of thousands of committed writes/sec, each costing a few milliseconds of round trip to a majority of the cluster. That ceiling comfortably covers the 1,040/sec steady state and is tight enough at a 5,000-10,000/sec burst to be worth explicitly load-testing before launch.

API design

POST /locks/{name}/acquire {holder_id, ttl_ms} -> {granted: bool, fencing_token, expires_at}
POST /locks/{name}/renew   {holder_id, fencing_token} -> {ok, new_expires_at}
POST /locks/{name}/release {holder_id, fencing_token} -> {ok}
GET  /locks/{name}/watch   -> stream of {event: released|expired, name}

High-level design

Clients talk to any node of a small, odd-sized cluster running a consensus protocol. Every write — acquire, renew, release — goes through the elected leader and is committed to a replicated log before it is acknowledged, so the lock table stays consistent across a majority of nodes even if some nodes crash. The resource each lock protects checks the fencing token itself before honoring any write.

Deep dive

1) A fencing token is the mechanism that makes the whole design actually safe. Ch.13 covers the concept in depth; the point worth restating here is that the lock service by itself cannot guarantee mutual exclusion end to end. A holder can hit a long garbage-collection pause or a network stall, silently lose its lease while paused, wake up believing it still holds the lock, and then perform the protected action anyway — a "zombie" write from a client that no longer holds the lock. The fix is that every successful acquire returns a monotonically increasing fencing token, and the resource the lock protects — not the lock service — must reject any write carrying a token older than the newest one it has already accepted. That check has to live in the resource itself; the lock service has no way to intercept the zombie's write after the fact.

2) A single fast in-memory store cannot be a safe lock service by itself. A naive lock built on one Redis node's SET key value NX PX ttl is only as safe as the assumption that no two clients can ever both believe they hold it — but a single node can fail over, or even just have a slow disk flush, in a way that briefly breaks that assumption. This is exactly the Redlock debate Ch.13 covers: Redlock tries to patch this by requiring a majority of several independent Redis instances to agree within a tight time budget, and it is genuinely useful for reducing accidental double-work, but Martin Kleppmann's well-known critique argues it still is not a rigorous safety guarantee under an unlucky process pause. A real lock service needs every acquire and lease-renewal to be a majority-quorum consensus write, not a fast, best-effort one — which is the actual reason systems like Chubby, ZooKeeper, and etcd exist as separate, deliberately boring, consensus-based systems instead of "just use the cache."

3) The lease TTL is a bet, and thundering herds happen on release. A lease-based lock trades one failure mode for another: without a TTL, a crashed holder that never releases leaves the lock stuck forever; with a TTL, a holder that is merely slow — not dead — can lose the lock mid-operation once its lease expires, which is exactly the scenario the fencing token exists to make harmless rather than to prevent. Picking the TTL too short causes false lock loss under normal load spikes; picking it too long delays failover after a genuine crash. Separately, when a popular lock is finally released, every blocked waiter tends to wake up and retry at the same instant — mitigated with jittered backoff, or better, a fair, first-in-first-out waiter queue built into the lock service itself, the same trick ZooKeeper's sequential-znode recipe gets for free.

Trade-offs

At 10x the number of services contending for short-lived locks, the consensus leader's write throughput becomes the ceiling — every acquire, release, and renew is a quorum commit, and a single Raft leader tops out in the thousands-to-low-tens-of-thousands of commits/sec range regardless of how much CPU or memory the machine has. The trade-off is sharding the lock namespace across multiple independent Raft groups (more total capacity, more operational complexity, and cross-shard locks becoming awkward to reason about) versus accepting the ceiling and pushing teams toward fewer, coarser-grained locks with longer lease TTLs instead.

Say this

"A lock service on its own cannot guarantee mutual exclusion end to end. I would have every acquire return a monotonically increasing fencing token and require the protected resource to reject any write carrying a token older than the last one it accepted — that is what actually stops a paused client from corrupting data after it has silently lost the lock, and it is true no matter which lock backend sits behind the service."

Final design

One picture: a small, odd-sized Raft or Paxos cluster commits every acquire, renew, and release to a replicated log before acknowledging it; each grant is a lease with a heartbeat-renewed TTL and a monotonically increasing fencing token; a watch mechanism gives waiters a fair queue instead of a wake-everyone free-for-all; and the resource each lock protects checks the fencing token itself, because the lock service alone cannot make that guarantee end to end.

EM-level follow-up

Build-vs-buy here has a clear default answer: almost nobody should build this from scratch. Use etcd, ZooKeeper, or a lighter-weight equivalent built on a cloud database's conditional writes, and spend engineering effort instead on the fencing-token contract with whatever resource each lock protects — that part is application-specific and cannot be bought off the shelf. On rollout: the moment two unrelated teams depend on this service, it becomes shared, critical-path infrastructure, and an outage in it can take down both teams' systems at the exact same time — worth an explicit availability SLO and a dedicated on-call from day one, not something added after the first joint incident.

Design a Leaderboard

Problem framing

A leaderboard takes a stream of score changes and answers two questions fast: "what are the top scores right now" and "where do I rank." Think of a mobile battle-royale game running a live weekly tournament for tens of millions of players, where every match ending updates a score and the in-game screen has to show your rank within a couple of seconds. Strip away the game skin and it is a ranking service: write a score, read a rank, read a sorted range around a player, at very high write and read rates.

Clarifying questions

  • Is this one global leaderboard, or many scoped windows (daily, weekly, season, all-time)? — why it matters: multiple windows mean multiple sorted structures kept in sync from the same score events, not one shared store.
  • Does every player need their exact rank, or only the top-K? — why it matters: serving "my rank" for millions of concurrent players is a much harder read pattern than serving one shared top-50 list that everyone can cache.
  • Can scores go down, or only up? — why it matters: a monotonically increasing score lets you use simpler counters in places; a score that can drop (lose a match, get penalized) needs a true read-modify-write update.
  • How are ties broken? — why it matters: "same score" needs a deterministic secondary rule (usually whoever reached that score first), or two players will see different ranks on different requests.
  • How stale can the board be? — why it matters: if a few seconds of lag is fine, you can batch and cache aggressively; if it must be instant, you cannot.
  • What is the read:write ratio? — why it matters: leaderboards are almost always read-heavy — far more people check the board than change their score in any given second — which pushes the design toward caching reads hard and keeping writes cheap.

Requirements

Functional: submit or update a player's score for a given board; fetch the top-K entries; fetch a given player's rank and score; fetch a small window of players around a given player's rank ("nearby players"); support several time windows (daily/weekly/season/all-time) that roll over automatically.

Non-functional: read latency under about 100ms at the 99th percentile, since this is rendered on a live game screen; a few seconds of end-to-end staleness on rank updates is acceptable; the write path must handle bursty spikes (everyone finishes a match around the same in-game moment); the score value itself must always be correct — approximate rank is fine, an approximate score is not, because scores often gate real prizes.

Capacity estimate

Assume 10 million daily active players (DAU), each playing about 3 sessions a day, and each session produces roughly 20 score-update events (kills, match end, bonus events).

Writes: 10M × 3 × 20 = 600M score updates/day → 600,000,000 / 86,400 ≈ 6,944 writes/sec average. Tournament finales and prime-time hours push this to roughly 5× average, so plan for about 35,000 writes/sec at peak.

Reads: each player checks the leaderboard screen roughly 15 times a day (end of match, opening the app, checking a friend's rank). 10M × 15 = 150M reads/day → 150,000,000 / 86,400 ≈ 1,700 reads/sec average, and roughly 8,700 reads/sec at peak.

Storage: a weekly board with 10M active entries, at roughly 100 bytes per entry once you include the sorted-structure bookkeeping, is on the order of 1GB. Keeping four windows (daily, weekly, season, all-time) in memory at once is only a few GB total — leaderboard state is tiny compared to almost any other system in this book; the challenge is request rate, not data volume.

API design

POST /v1/leaderboards/{boardId}/scores
  body: { "userId": "...", "scoreDelta": 250, "matchId": "..." }

GET  /v1/leaderboards/{boardId}/top?limit=50

GET  /v1/leaderboards/{boardId}/rank/{userId}
  -> { "rank": 18342, "score": 88450 }

GET  /v1/leaderboards/{boardId}/around/{userId}?radius=5
  -> the 5 players above and below this player

POST /v1/leaderboards/{boardId}/reset
  admin-only, used by the window-roller to close out a window

High-level design

Deep dive

  1. Sorted sets are the right primitive, not a database ORDER BY. Redis's sorted set is really an in-memory skip list (a linked structure that keeps entries ordered and supports fast lookup) with built-in "give me rank of X" and "give me the range around rank Y" operations at O(log N) — roughly the cost of one extra comparison each time the data set doubles. Running the equivalent query as SELECT ... ORDER BY score DESC LIMIT ... OFFSET ... against a relational database re-sorts a huge table on every request and falls over long before 35,000 writes/sec.
  2. One node is fine until it is not. 10M members fits comfortably on a single well-resourced Redis primary with a replica for failover — you do not need to shard the sorted set itself yet. Past a certain member count or write rate, a single node cannot hold the whole board and you shard by a bucket (for example, by region), then merge the top-K from each shard with a k-way merge (each shard hands you its already-sorted top items, and you interleave them into one final sorted list) at read time. That merge step is the real cost of sharding a leaderboard: any single query for the true global top-K now has to fan out to every shard.
  3. The live board is a cache, not the source of truth. Every score update goes to Redis synchronously (the board must be right, right now) and to a Kafka topic asynchronously, which a consumer uses to write the same event into Cassandra. If a Redis node is lost, you rebuild the sorted set from Cassandra instead of losing scores — the classic pattern of an in-memory structure for speed backed by a durable log for recovery.
  4. Ties need a packed sort key — sized to fit inside a double's exact-integer range. Redis stores a sorted-set score as an IEEE-754 double, which only represents integers exactly up to 2^53 (about 9.007 quadrillion). A naive pack like score * 10^12 - timestamp blows past that instantly — even a modest score of 10,000 times 10^12 is 10^16, already outside the safe range, so the timestamp digits the trick depends on get silently rounded away and ties stop resolving correctly. The version that actually works picks a multiplier sized to the real score range (if scores realistically top out in the hundreds of thousands, multiplying by 10^6 keeps the packed value comfortably under 2^53) and packs in a timestamp measured in seconds since the window opened, not raw epoch milliseconds, so the tie-break component only needs as many digits as the window is long. Done that way, "reached the same score earlier" still ranks higher with no separate tie-break query — the arithmetic just has to be checked against the double's precision limit before picking the multiplier, instead of assuming a bigger exponent is always safer.

Trade-offs

At 10× the scale, a single sorted set stops fitting one machine's memory and CPU comfortably, and you are forced to shard. Sharding breaks the guarantee that "top 50" is exactly correct, because you are now merging approximate top-K lists from independent shards — a player sitting at rank 51 on the true global board might not appear in any shard's local top-50 slice, so you either over-fetch from each shard (ask each shard for its top 200, not top 50, before merging) or accept a small amount of inaccuracy at the tail of the merged list.

Say this

"I would keep the live leaderboard entirely in Redis sorted sets — that data structure already gives me O(log N) rank and range queries, which is exactly the operation set a leaderboard needs. I would not try to compute rank with a SQL ORDER BY on every request; that re-sorts the whole table each time and cannot keep up with tens of thousands of writes per second. Redis is the fast, in-memory answer; Kafka plus Cassandra behind it is the durable answer, so a lost Redis node is a rebuild, not data loss."

Final design

Score updates land on a Score Ingest Service, which writes synchronously to a Redis sorted set (the live board players see) and asynchronously to Kafka, which a consumer persists into Cassandra as the durable system of record. Reads go through a Leaderboard Read Service backed by the same Redis sorted set, with the top-K list cached at the CDN edge since it is identical for every viewer between updates. A Window Roller closes out expired windows (daily/weekly/season) on a schedule, snapshots the winners, and opens the next window's key.

EM-level follow-up

An EM-level answer adds two things. First, build-vs-buy: for most companies, a managed Redis (ElastiCache, MemoryDB) is the right call over running your own cluster — leaderboard traffic is spiky and predictable (tournament finales), and paying for managed failover beats paging your own on-call for a Redis primary failure at 2am. Second, cross-team impact: score submissions are an obvious target for cheating, so the ingest path needs a hook for an anti-cheat or fraud team to validate or delay suspicious score jumps before they hit the public board — which changes "submit score" from a single synchronous write into a small pipeline with a validation step, and that is a conversation you have with the trust-and-safety team before launch, not after the first cheating complaint.

Design an Ad-Click Aggregation and Counting System

Problem framing

An ad network shows ads and gets paid, usually per click (cost-per-click, or CPC) or per thousand impressions (cost-per-mille, or CPM). This system counts every impression and click, in near real time for advertiser dashboards, and exactly for the number that ends up on an invoice. The two halves of that sentence — "near real time" and "exactly" — are in tension, and most of the design is about resolving that tension deliberately instead of by accident.

Clarifying questions

  • Does billing accuracy have to be exact, or can dashboards and invoices tolerate different precision? — why it matters: if invoices must be exact, you cannot bill directly off a fast streaming aggregate; you need a slower, exact reconciliation step somewhere.
  • How should duplicate or fraudulent clicks (bots, accidental double-clicks, click farms) be handled? — why it matters: this decides whether fraud filtering sits on the synchronous hot path (adds latency to every click) or runs asynchronously and corrects the numbers afterward.
  • What query patterns does the dashboard need — per-ad per-minute, per-campaign per-day, top ads in the last hour? — why it matters: this decides the aggregation granularity and whether you need a real analytical (OLAP) store or plain counters are enough.
  • Can events arrive late, for example from a mobile client that buffers clicks while offline? — why it matters: late data breaks naive fixed time windows and forces a decision about how long to wait before calling a window "final."
  • How long must raw click events be retained? — why it matters: advertisers and regulators sometimes dispute a bill months later, which drives raw-event retention and therefore storage cost far more than the aggregates do.

Requirements

Functional: ingest impression and click events at high volume; aggregate counts by ad, campaign, and advertiser over configurable time windows; serve near-real-time dashboard queries; produce an exact, fraud-filtered count that billing can rely on; support reprocessing/audits of historical data.

Non-functional: ingestion must absorb large, bursty spikes without dropping events; counting must be idempotent (retrying or duplicating an event must not double-count it) because money depends on it; dashboards should be fresh within roughly a minute; the system must never silently lose a billable click, even if that means being slow to finalize the number.

Capacity estimate

Assume the network serves 2 billion ad impressions/day with a 1% average click-through rate (CTR, the fraction of impressions that get clicked) → 20 million clicks/day.

Impressions: 2,000,000,000 / 86,400 ≈ 23,150/sec average; at roughly 5× peak (peak advertising hours) that is about 115,000/sec.

Clicks: 20,000,000 / 86,400 ≈ 230/sec average, about 1,150/sec at peak. Combined ingestion has to be sized for roughly 116,000 events/sec at peak — this is the number that decides you need a partitioned, durable ingest queue (Kafka) in front of anything else, since no single database write path handles that comfortably.

Storage: each raw event (ad id, campaign id, device id, timestamp, geo, a click id used for de-duplication) is roughly 200 bytes. 2.02 billion events/day × 200 bytes ≈ 400GB/day raw, or roughly 12TB for a 30-day raw retention window before compression; typical columnar compression brings that down to somewhere around 2.5–4TB. Aggregated data is tiny by comparison — on the order of a few GB/day for minute-level rollups across the ad catalog.

API design

  body: { "clickId": "...", "adId": "...", "campaignId": "...",
          "deviceId": "...", "ts": "..." }

  -> billed, reconciled numbers

High-level design

Deep dive

  1. Exactly-once counting for money, on top of an at-least-once pipeline. Networks retry, clients double-fire, and bots replay. Every click carries a clickId (or a hash of ad id + device id + a time bucket) used as an idempotency key — the aggregator checks a dedup store before counting a click, so a retried event increments the count zero times, not twice. This is the same idempotency idea used in the Distributed Counter Service and Webhook Delivery problems elsewhere in this chapter; here the stakes are simply higher because a duplicate directly overcharges an advertiser.
  2. Fast-and-approximate vs. slow-and-exact is a deliberate split, not a bug. The streaming aggregator produces dashboard numbers within about a minute, using a watermark (a rule like "assume all events for this minute have arrived once we have seen events timestamped 2 minutes later") to close windows — but mobile clients can buffer clicks offline for hours, arriving well after any reasonable watermark. Rather than holding every window open indefinitely, the design accepts that streaming numbers are approximate and runs a nightly batch job (this is a Lambda architecture: a fast "speed layer" plus a correct "batch layer") that re-reads the full raw archive and produces the number that actually appears on the invoice.
  3. Fraud filtering runs off the hot path. Scoring every click synchronously for bot behavior would add latency to the ad server's response and couple ad serving to a fraud model's uptime. Instead, a fraud scorer consumes the same event stream asynchronously and tags suspicious clicks; those tags are honored by the nightly reconciliation before the final bill is cut, so dashboards may show slightly inflated numbers for a few hours that get corrected the next day — a trade-off worth stating explicitly to an advertiser and to an interviewer.
  4. Hot partitions from viral ads. Partitioning the Kafka topic by ad_id is the natural choice for keeping one ad's events together, but a single viral ad can dominate one partition. The fix is to salt the key (append a random 0–9 suffix per ad) to spread one ad's traffic across several partitions, then merge those sub-counts at aggregation time — the same hot-key sharding pattern discussed under the Distributed Counter Service problem.

Trade-offs

At 10× traffic, the nightly Spark reconciliation job — which re-reads the entire raw archive — starts taking longer than the night it is supposed to run in. The fix is to move from a full nightly re-scan to incremental reconciliation (only reprocess the last day's partitions plus any late-arriving data), which is more code and more moving parts than "just re-read everything," but it is what keeps the exact-count job finishing before advertisers expect their numbers.

Say this

"I would deliberately separate the dashboard numbers from the billing numbers. The stream gives advertisers a near-real-time count with roughly a minute of lag, but the number on the invoice always comes from a nightly batch job that re-reads the raw click log from cold storage and produces an exact, fraud-filtered count. That is a Lambda-architecture trade-off on purpose: fast but approximate for the dashboard, slow but exact for the money."

Final design

Click and impression events flow from the ad server through an ingest service into a partitioned Kafka topic. A stream aggregator produces near-real-time, minute-level rollups for dashboards and writes durable windowed counts for billing, while every raw event also lands in a cold archive. A nightly batch job re-reads that archive, applies fraud filtering, and produces the exact counts that generate invoices — the dashboard and the invoice are allowed to disagree slightly for a few hours by design.

EM-level follow-up

Build-vs-buy shows up directly in the OLAP layer: a managed streaming analytics store (BigQuery streaming, a hosted ClickHouse/Druid) is usually cheaper than running and tuning your own cluster for the first couple of years, and the EM angle is asking whether this team should own database operations at all versus focusing on the aggregation logic itself. Cross-team impact is unavoidable here: finance/billing needs a written reconciliation SLA and an audit trail they can point to when an advertiser disputes a charge, and the trust-and-safety team owns the fraud model — this system only calls it, it does not build it.

Design a Log Aggregation System

Problem framing

Picture an engineering org running 500 microservices across several Kubernetes clusters. Every service writes log lines about what it is doing, and none of that is useful unless it is collected in one place, searchable by an on-call engineer during an incident, and kept long enough to satisfy an audit. A log aggregation system is the pipeline that gets log lines from a container's stdout to a search box, at a volume that spikes hardest exactly when things are already going wrong.

Clarifying questions

  • Are logs structured (JSON with fields) or free text? — why it matters: structured logs index cleanly and cheaply; free text needs a fragile parsing layer (pattern matching that guesses field boundaries) that breaks whenever a team changes their log format.
  • How fresh does search need to be for on-call use? — why it matters: seconds-level freshness during an incident is a much harder target than "searchable within a couple of minutes," and it changes how much buffering the pipeline can do.
  • What is the hot (searchable) retention window versus the total retention required for compliance? — why it matters: hot storage on fast disks is expensive; most of the retention requirement is usually satisfied by cheap cold storage that is not instantly searchable.
  • Do different teams need access isolation, and is there sensitive data (PII, tokens) that ends up in log lines? — why it matters: this adds a redaction step before indexing and per-team access control on top of just "collect everything."
  • How much does log volume spike during an incident, relative to steady state? — why it matters: the pipeline has to survive exactly the moment demand for it is highest, or it fails the one job that matters most.

Requirements

Functional: collect logs from every pod/host; parse, enrich (attach service name, pod, trace id), and optionally redact sensitive fields; index logs for both free-text and structured-field search; support alerting on log patterns (for example, error-rate thresholds); retain logs in a searchable hot tier for some days and in a cheaper cold archive for longer; support per-team access control.

Non-functional: the pipeline must not become a new source of outages — a slow or overloaded indexer must never block or crash the applications producing logs; it must absorb large volume spikes without losing data; search latency needs to be low enough to be usable while debugging live; cost has to stay proportional to log volume, which for 500 services is enormous.

Capacity estimate

Assume 500 services averaging 20 pods each → 10,000 running containers, each emitting roughly 50 log lines/sec in steady state, at about 500 bytes per line once metadata (pod, trace id, timestamps) is attached.

MetricSteady stateIncident spike (roughly 5x lines/pod)
Log lines/sec10,000 × 50 = 500,000/sec~2,500,000/sec
Ingest throughput500,000 × 500B ≈ 250MB/sec~1.25GB/sec
Raw volume/day≈ 21.6TB/day—

Storage: keeping 7 days hot (searchable) at roughly 21.6TB/day raw, with an index overhead and a replication factor of 2 for availability, lands on the order of 300–400TB of hot, SSD-backed capacity — a real cost driver. Compressing raw logs for cold archive (roughly 5× smaller) and keeping 90 more days for compliance adds on the order of 300–400TB more, but on much cheaper object storage. This tiering — expensive hot, cheap cold — is the main cost lever in the whole design.

  body: NDJSON batch of { service, pod, ts, level, message, trace_id, ... }

GET  /v1/search?query={query}&service={service}&from={from}&to={to}&limit={limit}

GET  /v1/logs/stream?service={service}&podId={podId}
  server-sent events / websocket live tail

  body: { "matchQuery": "...", "threshold": 50, "windowSec": 300,
          "notifyChannel": "pagerduty:oncall-payments" }

High-level design

Deep dive

  1. The pipeline must fail open toward the application, not into it. The single worst failure mode for a log system is: an outage causes a huge log spike, the spike overwhelms the indexer, and the indexer's back-pressure ripples back to the applications, causing a second outage in the exact moment logs are needed most. The fix is Kafka sitting between the agents and the indexer as a durable buffer — if the indexer falls behind, you get search lag, not data loss and not a stalled application. Agents also keep a local disk buffer and, as a last resort, drop the lowest-priority (debug-level) logs first rather than blocking the app.
  2. Schema-on-write beats schema-on-read at this scale. Free-text logs need a central parsing layer to guess field boundaries (grok-style patterns), which silently breaks the moment a team changes a log line's wording. Pushing structured JSON logging as a standard at the source turns "what fields does this log have" into a contract the producing team owns, instead of a guessing game the platform team maintains forever.
  3. Hot/cold tiering is a cost decision, not just a storage decision. Keeping everything in a hot, replicated Elasticsearch/OpenSearch cluster is the simplest design and the most expensive one. After the hot retention window, compressed logs move to an S3-style object store (see the Distributed Object Storage problem in this chapter for how that layer itself works), and a "rehydration" job can pull an old time range back into a temporary hot index on demand — trading a slower first search for a much smaller standing cost.
  4. Redaction has to happen before indexing, not after. Log lines routinely leak things they should not — a customer's phone number, an accidentally logged auth token. A redaction stage in the stream processor applies known-sensitive-field rules before anything is written to the searchable index, because scrubbing data after it is indexed and possibly already returned in a search result is too late.

Trade-offs

At 10× the service count, the hot index's shard count and per-node memory become the bottleneck — more shards means more coordination overhead per query, but too few shards means uneven load across the cluster. The usual fix is shortening the hot retention window further and leaning harder on cold-tier rehydration, which is fine for routine debugging but adds real delay for anyone investigating something from three weeks ago.

Say this

"I would never let application pods write logs directly and synchronously into the search index. I would put a durable queue — Kafka — between the agents and the indexer, so that if the indexing cluster degrades during an incident, we get lag, not data loss, and critically the application itself never blocks on logging."

Final design

Log agents on every pod ship to a collector, which writes into Kafka as a durable buffer. A stream processor parses, enriches, and redacts each log line before writing it into a hot search index for recent data and a cold, compressed archive for long-term retention. An alerting engine reads the same Kafka stream in parallel to fire on error patterns, and a query gateway federates search across the hot index and, on demand, the cold archive.

EM-level follow-up

Build-vs-buy is the dominant question here: self-hosted ELK/OpenSearch versus a managed vendor (Datadog, Splunk, Coralogix-style platforms) trades engineering time for a bill that scales directly with log volume, and at real scale that bill becomes large enough that renegotiating it or building an internal aggregator becomes a legitimate cost project, not just an engineering preference. Rollout is org-wide, not a single deploy: moving 500 services onto structured logging is a phased migration led by a platform team, service by service, with a shared logging library rather than a mandate with no path to comply. Cross-team, security/compliance owns retention and redaction policy, and SRE owns keeping the pipeline itself healthy — which is its own on-call rotation.

Design a Distributed Object Storage System (S3-style)

Problem framing

This is the storage layer itself — the system behind a product like Amazon S3 or Backblaze B2. It stores arbitrary bytes (images, videos, backups, data-lake files) addressed by a simple key inside a bucket, not by a file path in a shared filesystem. No directories, no in-place edits — you put a whole object, you get a whole object, you delete a whole object. The entire point of the system is being a durable, cheap, and close-to-infinitely scalable place to keep a byte, at a cost per gigabyte that a database could never hit.

Clarifying questions

  • What does the object size distribution look like — mostly small thumbnails, mostly large video files, or a mix? — why it matters: it decides whether multipart upload and chunking are a rare edge case or a core code path.
  • What durability target is expected, and is that the same as the availability target? — why it matters: durability ("will this byte still exist in a year") and availability ("can I read it right now") are different guarantees with different costs, and interviewers often use imprecise language for both.
  • Does a PUT need to be immediately, strongly consistent for a following GET, or is eventual consistency acceptable? — why it matters: it decides whether the metadata layer needs a single linearizable commit point or can tolerate a replication lag window.
  • Is multipart upload for very large objects required from day one? — why it matters: uploading a 50GB file as a single stream is fragile; supporting independently retryable parts is a meaningfully different upload API.
  • Is versioning or soft-delete required? — why it matters: it changes the metadata model from "one pointer per key" to "one pointer per key-version," with real storage cost implications.

Requirements

Functional: PUT/GET/DELETE an object by (bucket, key); list objects in a bucket by key prefix; multipart upload for large objects; object versioning; per-object metadata; lifecycle rules (auto-delete or move to cheaper storage after N days).

Non-functional: extremely high durability — designing for something on the order of "eleven nines" annual durability, meaning the odds of losing any given object in a year are vanishingly small; high availability (on the order of 99.99%); strong read-after-write consistency for newly written objects; horizontal scalability to many petabytes and billions of objects; cost efficiency is not a nice-to-have here — it is the product's entire reason to exist.

Capacity estimate

Assume 500 million objects stored, averaging 2MB each → 500,000,000 × 2MB = 1PB of logical data.

MetricAveragePeak

Write throughput2,000 × 2MB = 4GB/sec20GB/sec
GET requests (roughly 10:1 read:write)20,000/sec100,000/sec

Metadata: 500M objects × roughly 200 bytes per record (bucket, key, size, checksum, version, shard pointers) ≈ 100GB — small enough to live in a normal, if heavily sharded, key-value store. The important point: metadata and blob bytes are separate concerns with completely different scaling problems.

Physical storage cost depends entirely on the durability strategy. Naive 3× replication of 1PB logical data needs 3PB of physical disk. Erasure coding (splitting each object into, say, 6 data shards plus 3 parity shards — a "6+3" scheme, where any 6 of the 9 shards reconstruct the whole object) needs only about 1.5× overhead, or 1.5PB physical, for comparable or better durability.

  headers: Content-Type, Content-MD5

High-level design

Deep dive

  1. Erasure coding buys durability without 3× the disk. Triple replication is simple and gives good durability, but it costs 3× the storage for every byte. Erasure coding splits an object into data shards plus parity shards spread across separate failure domains (different disks, racks, or data centers), so losing several shards still lets you reconstruct the object — typically at roughly 1.5× overhead instead of 3×. The cost is CPU to encode and decode, and a slower repair path (rebuilding from parity math costs more than copying a spare replica), which is a fine trade for a system whose whole value is being the cheapest place to store a byte.
  2. Metadata sharding is the real scaling problem, not the bytes. Blob storage is "dumb" and scales by adding disks; the metadata service — the map from bucket/key to physical shard locations — is where the hard sharding trade-off lives. Hashing the key for sharding spreads load evenly but breaks efficient prefix listing (listing everything under a common prefix has to fan out to every shard). Range-partitioning by key keeps prefix listing cheap but risks a hot shard when one customer writes a long run of sequential keys. Real object stores have historically leaned toward range-based schemes specifically because "list by prefix" is such a common operation.
  3. Strong read-after-write consistency comes from one commit point. A PUT is not acknowledged to the client until the metadata pointer is durably committed and enough shards are confirmed written — that metadata commit is the single point every subsequent GET resolves through, so a client can never observe a half-written object. This is a deliberate design choice, and it is different from many caches and CDNs, which are eventually consistent on purpose for speed.
  4. Multipart upload turns one fragile transfer into many retryable ones. Streaming a 50GB object as a single request means any network blip restarts the whole thing. Splitting it into independently uploaded parts (each its own retryable PUT with its own ETag) and only assembling a logical manifest at the end — not physically copying bytes together — means one failed part costs you re-uploading that part, not the whole object.

Trade-offs

At 10× scale, disk failures stop being rare events you react to and become a constant background condition — with enough storage nodes, some disk somewhere is always being repaired. The background scrubber and repair pipeline moves from "nice to have" to a first-class scaling bottleneck: if repair throughput cannot keep up with the failure rate at this scale, durability quietly degrades even though nothing looks obviously broken. Hash-sharded metadata that looked fine at 500M objects can also start showing hot shards once a few customers run high-QPS sequential-key workloads, forcing a harder migration toward range-partitioned metadata.

Say this

"I would not reach for 3x replication as the durability strategy at this scale — it is the simplest option but it burns three times the disk. I would use erasure coding: split each object into data shards plus parity shards spread across failure domains, so I can lose several shards and still reconstruct the object, at roughly 1.5x storage overhead instead of 3x. The cost is CPU for encoding and slower rebuilds, which is a good trade for a system whose whole value proposition is being the cheapest place to keep a byte."

Final design

A stateless API layer handles PUT/GET/DELETE and routes to a metadata service that is the single source of truth for where an object's shards live. Writes go through a placement service that erasure-codes the object across a large storage node fleet spread over failure domains; a background repair loop continuously scrubs for lost shards and re-encodes them. Multipart upload lets very large objects be sent as many small, independently retryable parts.

EM-level follow-up

The build-vs-buy answer here is almost always "buy": most teams should use S3, GCS, or a self-hosted S3-compatible system (like MinIO) rather than building this from scratch, and an EM-level interviewer is often testing whether you know what building it in-house actually costs in reliability-engineering headcount — you would only build this yourself if you were a cloud provider, or had an unusual data-residency or cost constraint that justified it. Rollout for a company migrating off a legacy shared filesystem happens bucket by bucket, with a dual-write shadow period before cutover, not a big-bang switch. Cross-team, security dictates encryption-at-rest and audit-log requirements, and finance cares deeply about hot/cold storage tiering, because storage is a direct line item on the cloud bill.

Design a Distributed Task Queue with Retries and a Dead-Letter Queue

Problem framing

Across almost any engineering org, dozens of services need to say "do this work, but not right now, in this request" — send a welcome email, resize an uploaded image, sync a record to a third-party CRM. A task queue is the system that takes those units of work, hands them to a pool of workers, retries them with backoff (a growing delay between attempts) when they fail, and — after enough failed attempts — parks them in a dead-letter queue (a DLQ, a separate holding area for tasks that could not be completed) instead of retrying forever or silently dropping them. This is different from the Distributed Job Scheduler problem elsewhere in this chapter, which is about running things on a time trigger (like cron); a task queue runs things on an explicit enqueue call, as soon as a worker is free. It also builds on top of the Message Queue problem in this chapter rather than replacing it — a task queue is usually the retry/DLQ semantics layered on an existing broker, not a new broker from scratch.

Clarifying questions

  • Do tasks of the same type or the same entity need to run in order? — why it matters: ordering requirements limit how freely you can shard work across workers and partitions.
  • Are task handlers idempotent — safe to run twice with the same input? — why it matters: any queue offering at-least-once delivery will occasionally deliver a task twice, so the answer decides whether de-duplication has to be built into every handler.
  • Is the retry policy (fixed delay vs. exponential backoff, max attempts) the same for every task type, or configurable per type? — why it matters: a "send email" task and a "call a flaky third-party API" task usually need very different retry budgets.
  • What happens to a task once it lands in the DLQ — automatic paging, or a UI for a human to inspect and replay it? — why it matters: this decides whether the DLQ is just storage or needs its own service with alerting and a replay path.
  • How large can a task payload be, and should large payloads be inlined or passed by reference? — why it matters: a queue is a poor fit for storing large blobs directly; big payloads usually get stored elsewhere and referenced by a pointer in the task.

Requirements

Functional: enqueue a task (type, payload, priority, optional delay, max retries); have a worker pool pull and execute tasks; automatically retry failed tasks with backoff; move a task to the DLQ once retries are exhausted; give visibility into the DLQ and support manual or automated replay; isolate one task type's failures from starving unrelated task types.

Non-functional: at-least-once delivery (a task will sometimes run more than once, and the system is explicit about that instead of pretending otherwise); no task is ever silently lost; the worker pool scales horizontally with load; task latency stays bounded under normal conditions; a broken downstream dependency for one task type must not block unrelated task types from running.

Capacity estimate

Assume an org enqueues 50 million tasks/day across roughly 200 task types. 50,000,000 / 86,400 ≈ 580 tasks/sec average; end-of-day batch jobs push this to roughly 5× at peak, or about 2,900 tasks/sec.

Assume an average task takes 500ms to execute. One worker can finish 1000ms / 500ms = 2 tasks/sec, so sustaining 2,900 tasks/sec at peak needs at least 2,900 / 2 ≈ 1,450 concurrent worker slots; with roughly 2× headroom for safety, plan for about 2,900 worker slots spread across an autoscaled pool.

Assume 2% of tasks fail on their first attempt (a normal rate for calls that depend on flaky downstream systems) → 1,000,000 retries/day, and assume 0.1% of all tasks (about 50,000/day) exhaust every retry and land in the DLQ.

Storage: keeping 7 days of task execution history for debugging is 50,000,000 × 7 ≈ 350 million records at roughly 500 bytes each ≈ 175GB — a normal-sized database workload. DLQ storage at 50,000/day for a 90-day investigation window is about 4.5 million records, only a couple of GB — the DLQ is small; the value it holds (unfinished work) is what matters, not its size.

  body: { "type": "resize-image", "payload": {...},
          "priority": "normal", "delaySeconds": 0,
          "maxRetries": 5, "idempotencyKey": "..." }

High-level design

Deep dive

  1. Retries should never tie up a worker slot. The naive approach — a worker sleeps in-process and retries — burns a worker doing nothing useful for the whole backoff window. The better approach re-enqueues the failed task into a delay-tiered structure (for example, separate retry-30s, retry-5m, and retry-1h queues, or the broker's native delayed-delivery feature) so the worker is immediately free to pick up other work, and the failed task only comes back to the main broker once its delay has passed.
  2. Jitter prevents a self-inflicted second outage. Plain exponential backoff (doubling the delay each attempt) without randomization means every task that failed because a downstream dependency went down will retry at the same moments, in lockstep, and slam that dependency the instant it starts recovering — a thundering herd. Adding jitter (a small random offset to each computed delay) spreads those retries out so recovery is not immediately re-broken by the retry traffic that was waiting for it.
  3. One broken task type should not starve the rest. If a single downstream dependency is fully down, its task type can fill up shared capacity with retries while unrelated, healthy task types wait behind them. Partitioning the broker by task type (each type gets its own concurrency budget) and adding a circuit breaker per downstream dependency (stop pulling that task type for a cooldown period after N consecutive failures) keeps one outage from becoming an org-wide backlog.
  4. At-least-once delivery pushes correctness into the handler, not the queue. A worker can crash after finishing a task but before acknowledging it, which means the same task gets delivered again — this is inherent to any practical at-least-once system, and true exactly-once delivery is not achievable without cooperation from the receiving side. The fix is requiring an idempotency key per task and having each handler check a dedup store before doing real work — the same pattern used for click de-duplication in the Ad-Click Aggregation problem in this chapter.

Trade-offs

At 10× scale, the delay-tiered retry queues need careful partition-count planning: too few partitions caps how many retries can run concurrently, too many adds coordination overhead in the consumer groups reading them. At the same time, the task metadata store — updated on every single attempt, for every task — becomes a write-heavy hot table; a single relational table stops keeping up, forcing a move to a sharded or wide-column store, or accepting that the "check my task's status" API is only eventually consistent.

Say this

"The retry logic should not live inside a worker's sleep loop — that ties up a worker slot doing nothing. I would model retries as re-enqueuing into delay-tiered queues, or use the broker's native delayed-delivery support, so a failed task is completely off the worker until its backoff window elapses. And I would always add jitter to the backoff — otherwise every task that failed because a downstream dependency went down retries in lockstep and hits that dependency at the exact moment it is trying to recover."

Final design

Producers enqueue through a Task Queue API into a broker partitioned by task type. An autoscaled worker pool pulls and executes tasks; failures go to a retry scheduler that re-enqueues with exponential backoff plus jitter through delay-tiered queues. Once a task exhausts its retry budget, it moves to a dead-letter queue with its full failure history, surfaced through a monitor that alerts the owning team and supports replaying the task back through the same enqueue path.

EM-level follow-up

Build-vs-buy: most orgs should not build a broker from scratch for this — see the Message Queue problem in this chapter for that build. A task queue is usually a thin layer of retry, DLQ, and per-type isolation logic on top of an existing broker (Kafka, SQS, Redis), and the EM-relevant framing is "we are building task semantics, not a queue primitive." Rollout: making idempotency keys mandatory across dozens of existing handlers is an org-wide migration, not a one-service code change, and needs a phased enforcement (warn, then require) owned by a platform team. Cross-team: DLQ alerting thresholds need to be agreed with each task-owning team individually, since "50,000 DLQ entries a day" is meaningless without knowing which team's task type they belong to and what their tolerance for backlog actually is.

Design a Metrics/Time-Series Ingestion Pipeline (StatsD/Prometheus-style)

Problem framing

Every service in a company needs to answer "is it healthy right now, and how did it behave five minutes ago." That means every service continuously emits small numbers — request counts, latencies, queue depths, memory usage — and something has to collect, store, and let people query billions of those numbers a day, fast enough to power a live dashboard and an alert that pages someone within a minute of a real problem. This is the system an internal platform team builds so no product team has to solve "where do our numbers go" for itself; think of the pipeline underneath Prometheus, Datadog, or Uber's M3.

Clarifying questions

  • Push (agents send data out) or pull (a central system scrapes each service)? — decides network topology, service-discovery needs, and who is responsible for buffering when the network is slow.
  • What is the cardinality budget — how many unique label combinations can one metric name have? — the single biggest scaling risk in this whole system; a label like user_id can turn one metric into millions of distinct series overnight.
  • What retention and resolution do we need — raw data for a day, rolled-up averages for a year? — decides whether we need a downsampling/compaction stage.
  • Is alerting part of this system, or does something else consume the stored data for that? — decides whether we build a rule-evaluation engine or just a store-and-query API.
  • Do percentiles (p95, p99 latency) need to be exact, or is an approximation acceptable? — exact percentiles across many hosts are expensive; most production systems accept an approximation.

Requirements

Functional requirements:

  • Every service can emit counters (things that only go up), gauges (a point-in-time value), and histograms/timers (a distribution, for latency).
  • The system collects those emissions, whether pushed by an agent or scraped from an endpoint.
  • Users can query a metric by name and label filters over a time range, with functions like sum, rate, and percentile.
  • Alert rules can be defined against a query expression and evaluated on a schedule, firing a notification when a threshold is crossed.

Non-functional requirements:

  • Emitting a metric from application code must be effectively free — fire-and-forget, never blocking the request that triggered it.
  • The system must absorb millions of data points a second without falling over; occasionally dropping a point under extreme load is acceptable, crashing is not.
  • Dashboard queries over the last few hours should return in a couple of seconds.
  • Storage must compress well, since the data is almost entirely small, regularly-spaced numbers.

Capacity estimate

Assume 50,000 hosts and containers, each emitting roughly 500 distinct time series (CPU, memory, and per-endpoint latency and count), collected every 15 seconds — a typical Prometheus scrape interval. That is 50,000 × 500 = 25,000,000 points every 15 seconds, or about 1.67 million points/sec.

Compression matters enormously here. Facebook's Gorilla time-series paper reports getting compressed storage down to roughly 1.37 bytes per data point on average, using delta-of-delta timestamp encoding plus XOR-based value encoding — call it "roughly 2 bytes/point" for a rough estimate with some overhead. At 1.67M points/sec, that is about 288GB/day of compressed raw data, or roughly 865GB/day with a replication factor of 3. Keeping 15 days of raw-resolution data needs on the order of 13TB; long-term rollups (1-minute, 1-hour averages) add only a small fraction more, since a rollup point covers many raw points.

Wire bandwidth into the collectors, before compression, is roughly 1.67M points/sec × ~20 bytes per point (a small protobuf-encoded point with a series reference) ≈ 33MB/sec sustained.

The real risk is not point volume, it is cardinality — the number of unique combinations of metric name and label values. 50,000 hosts × 500 base metric names is already 25 million series; if a team adds a label like per-endpoint or per-status-code on top, that multiplies further and can push active series counts into the hundreds of millions, which is what actually exhausts a time-series database's memory and index, not raw write throughput.

API design

// Ingest (StatsD-style push, over UDP, fire-and-forget)
orders.checkout.latency_ms:42|ms|@0.1
api.requests.count:1|c

// Ingest (Prometheus-style pull — the collector scrapes this from the service)
GET /metrics -> text exposition format, one line per series

// Query
GET /api/v1/query_range?query=rate(http_requests_total[5m])&start={ts}&end={ts}&step=15s

// Alert rules
POST /v1/rules {expr, for_duration, labels, annotations} -> {rule_id}

High-level design

Every host runs a lightweight local agent (a StatsD daemon or a Prometheus client library exposing a scrape endpoint). A central gateway either pulls from those endpoints or receives pushed flushes, and hands data to an ingestion buffer so a burst of writes never hits storage directly. Ingestion workers parse, compress, and route each point to a time-series store sharded by series identity; a downsampler periodically compacts old data into rollups; a query engine answers range queries; and an alert evaluator runs stored rule expressions on a schedule and fires notifications.

Deep dive

1) Cardinality explosion is the failure mode, not throughput. Sharding by series id (see Ch.6 for sharding mechanics) spreads write load evenly, so raw write volume rarely takes this system down. What does take it down is a team adding an unbounded label — a raw user ID, a request ID — to a metric, which silently creates a new, never-repeated time series on every single emission. The store has to keep an index entry for every series that has ever existed within its retention window, and an unbounded-cardinality label can grow that index by millions of entries in an afternoon. The fix is a hard cardinality budget per metric name, enforced at ingestion, that rejects or drops label combinations past a limit rather than letting one team's mistake degrade the shared platform for everyone.

2) Compression is what makes the storage tier affordable. Time-series data has a shape that plain row storage wastes: timestamps arrive at near-fixed intervals, and consecutive values from the same series are usually close to each other. Delta-of-delta timestamp encoding (storing how much the interval between two points differs from the previous interval, which is usually zero) plus XOR-based value encoding (storing only the bits that changed from the previous value) is how systems following the Gorilla design get down to roughly a byte or two per point, instead of the 16 bytes a naive (timestamp, value) pair would need.

3) Percentiles cannot be averaged across hosts. A p99 latency computed independently on 500 hosts cannot be combined into a correct global p99 by averaging those 500 numbers — averaging percentiles is mathematically wrong. The fix is to have each host emit a mergeable histogram (bucketed counts, as Prometheus histograms do, or a structure like HdrHistogram or t-digest) rather than a pre-computed percentile, and compute the percentile once, centrally, from the merged bucket counts across all hosts at query time.

Trade-offs

At 10x scale, the time-series database's in-memory index is usually what breaks first, not the ingestion pipeline — a slow cardinality leak from one team's new label can double active series counts over a few weeks and quietly push every query and every host's index memory footprint up with it. The trade-off is a strict, automatically enforced cardinality limit (which will occasionally reject a metric a team genuinely needed) against a soft, advisory limit that keeps everyone happy until the exact week it does not.

Say this

"I would enforce a cardinality budget at ingestion time, not just document one, because the actual outage mode for these systems is almost always a runaway label, not write throughput — the pipeline itself is built to shard and absorb bursts, but nothing stops one team's request-ID label from taking down the shared index for everyone unless the platform rejects it at the door."

Final design

A local agent on every host emits or exposes metrics; a central gateway pulls or receives them into a buffer; ingestion workers compress and shard writes into a time-series store; a downsampler builds long-term rollups; and a query engine plus an alert evaluator read from the same store to power dashboards and paging.

EM-level follow-up

This is usually a build-vs-buy call: running your own Prometheus/Thanos-style stack gives full control over cardinality policy and cost, while a managed vendor (Datadog, Grafana Cloud) removes the operational burden at a per-metric price that scales uncomfortably once cardinality grows. Rolling this out org-wide means shipping naming and cardinality conventions before onboarding teams, not after — retrofitting a cardinality budget onto metrics that already exist is far harder than enforcing one from the first emitted point. It is also worth contrasting with the log aggregation system elsewhere in this chapter: logs are unstructured text optimized for search, metrics are structured numbers optimized for math, and trying to force one pipeline to do both usually serves neither well.

Design Typeahead/Autocomplete as a Standalone Service

Problem framing

Typeahead is the dropdown of suggestions that appears under a search box as someone types, updating on every keystroke. Framed as a standalone service — the way a search team would build it for the rest of the company to call — the problem is: given a prefix, return the best few completions in well under a hundred milliseconds, at a query volume many times higher than the actual number of searches, because it fires on every keystroke, not just on submit.

Clarifying questions

  • Is the corpus mostly static (a product catalog) or does it need to reflect trending queries within minutes? — decides whether a nightly batch rebuild is enough or a streaming update path is required.
  • Does it need to support multiple languages and typo tolerance? — a fuzzy/edit-distance match is a materially different (and more expensive) lookup than an exact-prefix match.
  • Is ranking purely by global popularity, or personalized per user? — personalization adds a per-user signal that has to be blended in without blowing the latency budget.
  • How large is the corpus — thousands of product names, or hundreds of millions of historical search queries? — decides whether the whole structure fits in memory on one box or needs sharding.

Requirements

Functional requirements:

  • Given a prefix, return the top 5-10 ranked completions.
  • Support near-real-time trending — a suddenly popular query should surface within minutes, not after the next full rebuild.
  • Support multiple languages.
  • Rank by a blend of global popularity and freshness; optionally boost the requesting user's own recent searches.

Non-functional requirements:

  • p99 latency under roughly 50-100ms, so suggestions feel instant while typing rather than lagging behind keystrokes.
  • Extremely high read QPS relative to actual searches performed, since every keystroke is a request.
  • Availability over strict freshness — a slightly stale suggestion list beats an error or a blank dropdown.

Capacity estimate

Assume 500 million daily active users, each performing 5 searches a day, and typing an average of 8 characters before selecting a suggestion or hitting submit. Suggestion requests (fired per keystroke) ≈ 500,000,000 × 5 × 8 = 20 billion/day. Average QPS ≈ 20,000,000,000 / 86,400 ≈ 231,000/sec, peaking around 700,000/sec at 3x.

That is the read side. The write side that keeps the suggestions fresh is driven by submitted queries, not keystrokes: 500,000,000 × 5 = 2.5 billion submitted searches/day feed the frequency-counting pipeline, averaging ≈ 29,000/sec, peaking around 87,000/sec — roughly 8x less traffic than the read path, which is the useful number to know: this system is dominated by reads, not writes.

Corpus size: assume 100 million unique tracked terms, each carrying a frequency count and metadata averaging 50 bytes ≈ 5GB total — small enough to fit entirely in memory, replicated across every serving node.

API design

GET /v1/suggest?q={prefix}&lang=en&limit=8 -> {suggestions:[{text, score}]}

// Internal, fire-and-forget from the search-submit path
POST /v1/ingest {query_text, ts, user_id, country}

High-level design

An online serving path holds a sharded, in-memory trie with precomputed top-K completions cached at each node, so a request is just a lookup, never a live tree walk. An offline pipeline consumes the submitted-query log, aggregates frequency in sliding windows, and periodically rebuilds and atomically swaps in a fresh trie snapshot, so freshness is a background concern that never touches the read path's latency.

Deep dive

1) Precomputed top-K, not live traversal. Ch.16 covers why a trie fits prefix search structurally — every node already represents one prefix, and everything under it starts with that prefix. The engineering problem in a real deployment is not the trie walk itself, it is refreshing the top-K suggestions cached at each node as popularity shifts, without recomputing the whole structure from scratch on every update. The pattern here mirrors the distributed counter service elsewhere in this chapter: submitted queries feed a fast-moving frequency count, which periodically gets folded into a full batch rebuild that swaps in atomically, the same shape as a blue-green deploy applied to a data structure instead of a service.

2) Sharding when the corpus outgrows one box's memory. 5GB fits comfortably today, but a multi-language, catalog-scale corpus can outgrow a single host. The standard split is by language or by a hash of the first character or two, so most requests touch exactly one shard; a request near a shard boundary needs to fan out to the neighboring shard and merge results, which is the one place this design pays a real cost for sharding.

3) Blending freshness into a mostly-static structure. A full trie rebuild might run every few hours, too slow for a genuinely trending term. The fix is a small, fast-refreshing delta layer on top of the base trie — recent-window counts that get checked and merged into the returned ranking before the next full rebuild replaces them — rather than trying to make the whole structure update live on every query.

Trade-offs

At 10x scale, sharding by character prefix starts to hurt more than it helps — popular first letters concentrate load unevenly, and near-boundary queries fan out and merge on a growing share of traffic. The trade-off is a smarter, popularity-aware shard key (harder to build and rebalance) against simple character sharding that quietly develops hot shards as the corpus grows.

Say this

"I would keep the read path a pure in-memory lookup against precomputed top-K suggestions, and push all the freshness logic into an offline pipeline that rebuilds and atomically swaps a new snapshot — scoring suggestions live on every keystroke would blow the latency budget the moment the corpus gets large, and it is unnecessary since popularity does not meaningfully change keystroke to keystroke."

Final design

A sharded, in-memory trie with precomputed top-K per node serves reads with a single lookup; a streaming aggregator tracks recent query frequency for near-term freshness; and a periodic batch rebuild plus atomic snapshot swap keeps the base structure current without ever blocking a read.

EM-level follow-up

Build-vs-buy here often comes down to Elasticsearch's built-in completion suggester (fast to stand up, less control over ranking blend) versus a custom trie service (more control, more to operate). Rollout of a new ranking blend should be shadow-tested — log what the new ranking would have returned alongside the old one, compare click-through, and only then flip traffic — because a bad ranking change is invisible in error rates but very visible in user experience. Cross-team, the submitted-query log this pipeline consumes is usually shared with analytics and ad-targeting teams, so changing its schema is a multi-team negotiation, not a unilateral change.

Design a Webhook Delivery System With Retries

Problem framing

A webhook is how a platform tells a customer's own server "something happened" — a payment succeeded, an order shipped — by making an HTTP POST to a URL the customer registered. The hard part is not sending one request; it is guaranteeing delivery to thousands of customer-owned servers that are, individually, unreliable, slow, or briefly offline, without letting any one of them affect delivery to anyone else. This is the system behind Stripe's and GitHub's webhook platforms.

Clarifying questions

  • Is at-least-once delivery acceptable, with the customer expected to deduplicate? — exactly-once delivery over an unreliable network to code you do not control is not achievable; this decides whether we design around that fact from the start.
  • Does ordering matter per resource (e.g., "created" must arrive before "updated" for the same object)? — affects whether deliveries for one resource must be serialized through the same worker lane.
  • How long do we keep retrying before giving up, and what happens then? — decides the dead-letter policy and whether a human or an automated alert gets involved.
  • Do customers need a delivery log and the ability to manually replay a past event? — if yes, delivery attempts and payloads need durable, queryable storage, not just transient retry state.

Requirements

Functional requirements:

  • Customers register an endpoint URL plus which event types they want.
  • On a subscribed event, POST a signed JSON payload to every matching registered endpoint.
  • Retry failed deliveries with backoff, up to a bounded number of attempts.
  • Sign every payload (HMAC) so the customer can verify it genuinely came from the platform.
  • Let customers view delivery history and manually redeliver a specific event.

Non-functional requirements:

  • At-least-once delivery — an event must never be silently dropped.
  • One customer's slow or dead endpoint must never delay delivery to any other customer, or to unrelated events for the same customer.
  • Low delivery latency (seconds) when the endpoint is healthy.
  • Must absorb bursty fan-out — a single internal event can need delivery to thousands of registered endpoints at once.

Capacity estimate

Assume a payments-style platform processing 50 million billable events/day, and an average of 1.3 registered endpoints per event (most customers have one endpoint, larger ones have several for different event types). That is 65 million first-attempt deliveries/day. Average QPS ≈ 65,000,000 / 86,400 ≈ 750/sec, peaking around 3,750/sec at 5x for a bursty event such as a batch settlement run.

Assume 5% of first attempts fail (customer endpoint timeout or 5xx) and need retries, and those retried deliveries succeed after an average of 1.3 extra attempts. That is roughly 65,000,000 × 0.05 × 1.3 ≈ 4.2 million extra attempts/day, or about 49/sec average — retries add roughly 6% to steady load, a real but not dominant cost.

Total delivery-attempt rows/day ≈ 69 million; at roughly 500 bytes per logged attempt (endpoint, status code, timestamp, a pointer to the payload) that is about 35GB/day of delivery-log data, or roughly 12-13TB/year, most of which is old enough within weeks to move to cold storage. Event payloads themselves, stored once and referenced by pointer rather than duplicated per attempt, average about 2KB × 50 million events/day ≈ 100GB/day.

API design

POST   /v1/webhook_endpoints {url, event_types[], secret} -> {endpoint_id}
GET    /v1/webhook_endpoints/{id}/deliveries?cursor={c} -> {attempts[], next_cursor}
POST   /v1/webhook_endpoints/{id}/deliveries/{delivery_id}/redeliver

// Outbound request the platform sends to the customer's URL
POST {customer_url}
X-Signature: HMAC-SHA256(secret, body)
X-Event-Id: evt_123
X-Delivery-Attempt: 2
Body: {event_type, event_id, created_at, data}

High-level design

Internal events land on an event topic; a dispatcher fans each one out into per-endpoint delivery tasks, isolated into per-endpoint queue lanes so one customer's backlog cannot block another's. Delivery workers make the actual HTTP call and check a per-endpoint circuit-breaker state before trying, so a clearly dead endpoint stops being hammered. Failures go to a retry scheduler with exponential backoff; exhausted retries land in a dead-letter store, and every attempt is written to a customer-visible delivery log.

Deep dive

1) Per-endpoint isolation is the whole point. A naive single global delivery queue means one customer's dead endpoint, with thousands of queued retries, can starve delivery workers away from every healthy customer. Partitioning delivery into per-endpoint (or consistently-hashed, bounded-count) lanes, plus a circuit breaker (Ch.15) per endpoint that stops attempting immediately after enough consecutive failures, keeps a single bad actor from becoming everyone else's outage.

2) Retries need to not occupy a worker while waiting. Naively sleeping a worker thread between retry attempts wastes capacity doing nothing. This is the same retry-and-dead-letter mechanic covered in the distributed task queue with retries and a DLQ problem elsewhere in this chapter — a retry_at timestamp polled by a scheduler, or a queue technology with native delay support, rather than a blocking sleep. What is specific to webhooks is that the "task" always ends in a network call to code the platform does not control, so per-attempt timeouts must be strict and independent, and a slow customer server cannot be allowed to tie up a worker indefinitely.

3) Exactly-once is not on the table. The network can drop a response after the customer's server has already processed the request, making a retry look like the customer got it twice. The platform's job is at-least-once delivery plus a stable event ID and signature so the customer's own handler can deduplicate — not a guarantee the platform itself cannot make honestly.

Trade-offs

At 10x scale, a batch job firing millions of events to thousands of endpoints at once can outgrow a fixed number of delivery lanes — too many customers registering around the same time means either widening the lane count (more coordination overhead) or accepting that new endpoints queue up behind existing backlog for longer than usual.

Say this

"I would design for at-least-once delivery with an idempotency key, not try to promise exactly-once — over an unreliable network to a server we do not control, exactly-once is not honestly achievable, so the right contract is guaranteed eventual delivery plus a stable event ID the customer can dedupe against."

Final design

Events fan out per subscription into isolated, per-endpoint delivery lanes; workers deliver with a circuit breaker guarding each endpoint; failures go through a non-blocking exponential-backoff retry scheduler; exhausted retries dead-letter; and every attempt is logged for customer visibility and manual replay.

EM-level follow-up

This is a real build-vs-buy call — managed webhook-delivery platforms like Svix or Hookdeck exist specifically so companies do not build this themselves. Migrating from a legacy at-most-once notifier needs a dual-write or shadow period, not a hard cutover, since customers may be relying on the old (weaker) behavior without realizing it. Cross-team, a failed delivery usually surfaces first as a customer support ticket, so support tooling needs read access to the delivery log keyed by event ID, or every investigation starts with an engineering escalation that did not need to be one.

Design a Distributed Counter Service (Extreme Write-Throughput Counting)

Problem framing

Some numbers get incremented by an enormous number of independent actions in a very short window — a view counter on a viral video, an impression counter on a heavily-served ad, a like counter on a post that just got picked up by an algorithm. The distinctive difficulty here is not total system throughput, it is that every one of those increments targets the exact same single counter key, which ordinary sharding by key does not help with at all.

Clarifying questions

  • Does the number shown need to be exact, or is a close approximation fine for the UI? — an exact count (billing, royalties) needs a stronger durability path than a display number that can be a few seconds and a few counts stale.
  • How skewed is traffic — is it spread across millions of counters, or can a single counter spike enormously on its own? — decides whether hot-key handling is a rare edge case or the central design constraint.
  • Can an increment be lost on a node crash, or must every increment survive? — decides how aggressively we can trade durability for raw throughput.
  • Do reads need strong consistency ever, or is "eventually correct" always acceptable? — decides whether we need two read paths (fast/approximate and slow/exact) or just one.

Requirements

Functional requirements:

  • Increment a named counter by a delta, accepting batched increments.
  • Read a counter's current value, with a choice between a fast approximate read and a slower, strongly consistent one.
  • Create and reset counters.

Non-functional requirements:

  • Sustain extremely high increment throughput concentrated on a single counter key — this is the central design challenge, not an edge case.
  • The write path must never add latency to the user-facing action (a like tap, a video play) that triggered the increment.
  • Increments must eventually be durable even across a node crash, with a bounded, known window of possible loss.
  • Reads can lag writes by a couple of seconds without being considered wrong.

Capacity estimate

Assume a single trending video peaks at around 500,000 view-increments/sec — comparable to real viral-moment spikes reported by major video and social platforms. Splitting that one logical counter into, say, 128 physical sub-counters (hashed by a per-request or per-session value) spreads it to roughly 500,000 / 128 ≈ 3,900 increments/sec per sub-counter — a load a single in-memory counter (an atomic value in Redis, or an in-process atomic integer) absorbs easily.

At the platform level, assume 2 billion total increment events/day across millions of active counters. Average QPS ≈ 2,000,000,000 / 86,400 ≈ 23,150/sec, peaking around 230,000/sec at a 10x multiplier for concentrated viral spikes — but the number that actually matters for the design is the single-key peak of ~500,000/sec, since that load lands on one logical counter, not spread across the platform.

Durable checkpointing: assume increments collapse into roughly 100 million periodic checkpoint writes/day (many increments to the same active counter merge into one write per flush interval) at roughly 100 bytes/row ≈ 10GB/day — trivial. In-memory footprint: even 10 million concurrently hot counters, each split into 128 shards of 8 bytes, is 10,000,000 × 128 × 8 bytes ≈ 10GB total — comfortably fits in a caching tier.

API design

POST /v1/counters/{key}/increment {delta:1} -> 202 Accepted
GET  /v1/counters/{key}?consistency=approx -> {value, as_of}
GET  /v1/counters/{key}?consistency=strong -> {value, as_of}
POST /v1/counters/{key}/reset

High-level design

A client action hits a lightweight edge write API that batches increments over a short window before forwarding a single combined delta. That delta lands on one of many physical sub-shards behind the logical counter key, held in an in-memory store. A flusher periodically sums the shards and checkpoints the total to a durable store. Reads either sum the in-memory shards for a fast approximate value, or fall back to the durable store for an exact one.

Deep dive

1) The hot-key problem, and why ordinary sharding does not solve it. Sharding by key (Ch.6) distributes different keys across different nodes, but a single viral counter is one key — hashing it always lands on the same shard no matter how many shards exist. The fix is to split that one logical counter into many physical sub-counters internally (hashing the incrementing request or session into one of, say, 128 sub-keys), so no single physical entry ever absorbs more than a slice of total traffic; a read sums across all sub-keys to reconstruct the logical value.

2) Edge batching cuts request volume before it ever reaches the shard layer. Combining many individual increments into one aggregated delta over a short window (on the order of 100ms) at the edge, before the sharded store even sees them, reduces request volume by orders of magnitude during the most extreme spikes, at the cost of a small added lag before an increment is even attempted — a worthwhile trade for a display counter, less so if increments need to be individually auditable.

3) Approximate speed versus durable exactness are two different read paths, on purpose. The in-memory sharded counters are fast but not durable between flushes, so a crash can lose the increments since the last checkpoint — a bounded, known risk that is acceptable for a display number and unacceptable for billing. Keeping two explicit read paths, an approximate one from the cache and a strong one from the durable store, lets each caller pick the trade-off it actually needs instead of forcing one compromise on everyone. Contrast this with the ad-click aggregation/counting system elsewhere in this chapter, which needs exact, fraud-checked, per-event counts for billing, not just a fast approximate display number — that is a fundamentally stricter durability bar than this problem's UI-facing counter.

Trade-offs

At 10x scale, a fixed 128-way split sized for the biggest spike ever seen can still be too coarse for a genuinely unprecedented moment — a counter suddenly taking 5 million increments/sec would still concentrate too much load per shard. The trade-off is over-provisioning shard count for a worst case that almost never happens (wasteful for the overwhelming majority of counters that never go viral) versus detecting a counter going hot in real time and dynamically re-splitting it, which adds real coordination complexity.

Say this

"I would keep the number the user sees on an approximate, eventually-consistent path, and route anything billing- or royalty-grade through a separate strongly consistent read against the durable store — forcing the display counter to pay for exact consistency is what would actually make this system fall over under a viral spike."

Final design

Batch increments at the edge, split one logical hot counter into many physical shards to spread load, sum shards for a fast approximate read, and periodically checkpoint to a durable store that backs a slower, exact read path when needed.

EM-level follow-up

Build-vs-buy: Redis Cluster with application-level sharding, or a managed atomic-counter primitive like DynamoDB's, versus building custom hot-key detection and dynamic resharding — most teams should buy the storage primitive and build only the hot-key detection logic on top. Rollout needs a way to detect a counter trending upward and bump its shard count without a redeploy, ideally automatically. Cross-team, this same sharded-counter primitive tends to get reused for ad-impression counting, rate-limiting counters, and leaderboard score updates (see the leaderboard problem in an earlier chapter for a case that adds ranking on top of counting) — a platform team owning it once is a better outcome than every product team rebuilding hot-key sharding from scratch.

Design a Distributed Configuration Propagation Service

Problem framing

An internal platform team needs a way to change behavior across thousands of running service instances — flip a feature flag, adjust a threshold, redirect traffic — without a code deploy, propagate that change quickly and safely, and instantly undo it if it turns out to be wrong. This is the system underneath feature-flag platforms like LaunchDarkly, and the internal config-distribution layer most large companies build or buy for exactly this reason.

Clarifying questions

  • Do service instances pull config on an interval, or does the system push changes to them? — decides propagation latency and the shape of the fan-out infrastructure.
  • Does every config key need strong, all-at-once consistency, or is staged, uneven propagation across instances fine? — most flags tolerate staggered rollout; a handful (an incompatible schema switch) genuinely need an atomic flip.
  • Should a bad config change trigger an automatic rollback, or always wait for a human? — decides whether the rollout controller watches health metrics itself.
  • Is config global, or does it vary by region? — affects whether the fan-out layer needs regional relay tiers.

Requirements

Functional requirements:

  • Publish a new value or bundle for a named config key, creating a new version.
  • Every running instance eventually receives the latest value and can read it locally.
  • Support instant rollback to a previous version.
  • Support staged rollout by percentage of instances or by region, not just all-at-once.
  • Keep an audit trail of who changed what, and when.

Non-functional requirements:

  • A config read inside application request-handling code must be effectively free — an in-process memory lookup, never a network call on the request path.
  • Propagation to all instances should complete in seconds.
  • If the config service itself is unreachable, every instance keeps serving its last known-good cached value rather than failing or blocking.
  • A bad push must be revertible without a code deploy.

Capacity estimate

Assume 20,000 service instances across 5 regions, each watching an average of 200 config keys — 4 million (instance, key) watch relationships. Config changes themselves are rare: assume 500 changes/day company-wide. Each change fans out to however many instances watch that key; assuming an average fan-out of 2,000 instances per change (most flags do not affect every service), that is 500 × 2,000 = 1 million propagation events/day, or about 11.6/sec average — a trivially low control-plane write volume.

The baseline read-side load, even with a pure push model, needs a fallback heartbeat so a missed push does not leave an instance stuck on a stale value forever; assuming each instance re-checks every 10 seconds as a safety net, that is 20,000 / 10 = 2,000 checks/sec sustained — easily handled, and it only spikes to the full fan-out size exactly when something actually changes.

Storage is small: assume 10,000 total keys company-wide, each keeping up to 50 historical versions for rollback, each version averaging 1KB — 10,000 × 50 × 1KB = 500MB total. A full fan-out burst to 20,000 instances at a few KB per message is roughly 100MB moved across the whole fleet at once — the engineering problem here is propagation speed and safety, not storage volume or steady-state bandwidth.

API design

PUT  /v1/configs/{key} {value, rollout:{strategy:"percentage", percent:10}} -> {version}
GET  /v1/configs/{key}?version=latest -> {value, version, updated_at}
POST /v1/configs/{key}/rollback {to_version}

// Client SDK, used inside application code — always a local read
configClient.getBool("new_checkout_flow")

High-level design

An admin publishes a change through a control plane, which validates it, assigns a version, and writes it to a strongly consistent config store. A rollout controller stages the change across a percentage or set of regions, watching a health-metrics feed and able to trigger an automatic rollback if error rates regress. A pub/sub fan-out layer pushes the change to a sidecar agent running next to every service instance, and that sidecar is the only thing application code ever talks to — always a local, in-memory read, never a network hop.

Deep dive

1) No network call on the request path, ever. The entire design exists to keep a config read out of the critical path of a real request. Each instance's sidecar refreshes its cache asynchronously, in the background; if the control plane and pub/sub layer are both fully down, the instance keeps serving the last value it successfully received, the same idea as a CDN serving stale content while it revalidates in the background, applied to config instead of bytes.

2) Staged rollout with automatic rollback prevents a known, common outage pattern. Flipping a company-wide flag to 100% instantly is a well-documented way config systems cause real outages. Staging by percentage or region, while watching an error-rate or latency signal from the observability pipeline (Ch.16), and auto-reverting to the last known-good version on regression turns a manual "who do we page to roll this back" incident into an automated guardrail, closer to a canary deploy than a big-bang flag flip.

3) Staggered propagation is a feature, except when it cannot be. During a staged rollout, different instances briefly hold different versions of a key on purpose — that staggering is the whole point. But a small subset of keys, like a breaking schema-version switch, need an atomic company-wide flip instead. Those are usually handled by deploying the new code path dark first, then flipping a single boolean at the very end, rather than trying to force the general propagation mechanism to be atomic for every key.

Trade-offs

At 10x scale (200,000 instances across many more regions), pushing directly from one control plane to every instance becomes a thundering-herd reconnect problem the moment the control plane restarts. The fix is a layered fan-out tree — regional relay nodes re-publishing to local instances — the same shape as the live fan-out trees covered in Ch.17, and the trade-off is the added operational complexity of relay nodes against a single hop that cannot survive a restart at this scale.

Say this

"The one design constraint I would not compromise on is that application code never makes a network call to read a config value — everything else, including how quickly a change propagates, is a tunable trade-off, but a config read on the request path turns this service into a new single point of failure for every request in the company."

Final design

A control plane versions and validates changes into a strongly consistent store; a rollout controller stages the change and can auto-rollback on a health regression; a pub/sub fan-out layer pushes updates to per-instance sidecars; and every application read is a local, in-memory lookup with a safe last-known-good fallback.

EM-level follow-up

Build-vs-buy: LaunchDarkly or Split.io as managed feature-flag platforms remove most of this system's operational burden, versus an internal etcd- or ZooKeeper-backed system that gives full control over rollout policy and cost at scale. Rolling this out org-wide means migrating services off hardcoded config and environment variables gradually, service by service, not in one cutover. Cross-team, a shared config namespace needs an explicit ownership model, or one team's flag name collides with another's, and a rollback for one team's bad flag silently reverts a value a different team depends on.

Design an API Gateway With Multi-Tenant Rate Limiting

Problem framing

A platform that exposes APIs to many external customers — each on a different pricing tier, each with their own usage quota — needs a single front door that authenticates every request, routes it to the right backend, and enforces per-customer limits, so no one tenant's traffic can degrade another's or overwhelm shared backend capacity. This is the edge layer behind a public API platform like Stripe's or Twilio's.

Clarifying questions

  • Are limits scoped per API key, per tenant across all their keys, or per endpoint too? — decides how many distinct counters the system tracks and how limit checks compose.
  • Should traffic over the limit be rejected outright, or throttled/queued? — queuing adds real complexity for a marginal fairness gain most API platforms decide is not worth it.
  • Do higher-paying tiers get burst allowances above their steady-state rate? — affects whether the underlying algorithm needs to be a token bucket (Ch.5) rather than a strict fixed window.
  • Is a small amount of over-limit traffic acceptable during a brief outage of the limiter's own backing store, or must it always reject? — this is a fail-open versus fail-closed decision that has to be made explicitly, not left as an accident of implementation.

Requirements

Functional requirements:

  • Authenticate every request and resolve it to a tenant and plan tier.
  • Route the request to the correct backend service.
  • Enforce a rate limit scoped to (tenant, endpoint), with different limits per plan tier.
  • Return standard 429 responses with remaining-quota and retry-after information.
  • Let operators override a specific tenant's limit without a deploy.
  • Emit accurate per-tenant usage events for billing.

Non-functional requirements:

  • The rate-limit check must add only a few milliseconds, since it runs on 100% of traffic.
  • The limit must be correct across many gateway instances — a tenant hitting different nodes must not effectively get N times their quota.
  • The gateway should fail toward a safe, explicitly chosen default (usually allow, with alerting) rather than taking down all traffic if the shared limit-counting store has a blip.
  • One tenant's traffic spike must not degrade another tenant's backend latency.

Capacity estimate

Assume 50,000 API tenants generating a combined 2 billion requests/day. Average QPS ≈ 2,000,000,000 / 86,400 ≈ 23,150/sec, peaking around 92,600/sec at 4x — every one of these needs a rate-limit check. Tenant traffic is heavily skewed: assuming the top 1% of tenants (500 of them) generate 60% of traffic, that is 1.2 billion requests/day across 500 tenants, averaging roughly 27.8/sec per top tenant and maybe a few hundred/sec even for the single largest one — nowhere near overwhelming, which is the useful contrast with the distributed counter service elsewhere in this chapter, where a single key really can spike to hundreds of thousands of increments/sec. Here the scale challenge is fanning a check out across many tenants, not absorbing one enormous hot key.

Rate-limit state: assume 50,000 tenants × up to 5 endpoint-scoped limits each = 250,000 counters, each needing a small window state (roughly 24 bytes) ≈ 6MB total — the state itself is tiny; the real load is the check rate against it, not its size.

Gateway fleet sizing: to sustain 92,600 req/sec peak with each gateway node comfortably handling roughly 5,000 req/sec of authentication, routing, and a rate-limit check, that is roughly 19 gateway nodes at peak — meaning any per-tenant limiter has to stay correct across at least that many concurrent nodes checking the same counters.

High-level design

A global load balancer terminates TLS and hands traffic to a stateless, horizontally-scaled gateway fleet that does authentication, routing, and a rate-limit check on every request. Correctness of that check across all fleet nodes depends on a shared atomic counter store; tenant plan and limit configuration is cached locally on each node with a short TTL. Traffic is routed into backend pools that are bulkheaded by tenant tier, so a free-tier spike cannot starve enterprise traffic of capacity, and every request emits a usage event for billing.

Deep dive

1) Correctness across many stateless nodes is the whole reason this is harder than a single-node rate limiter. Every gateway node must check against the same shared counter, typically via an atomic increment-and-compare (a single Lua script executed against Redis so check-and-increment happens as one indivisible step, as covered in Ch.5) so two nodes racing to check the same tenant at the same instant cannot both see "under limit" and together exceed it. This is a materially different problem from the standalone rate limiter covered elsewhere in this chapter, which is not also handling authentication, routing, and multi-tenant plan resolution on the same request.

2) A network round trip on every single request is too expensive to do naively. A shared-store check on 100% of traffic adds real latency and turns that store into a dependency for all traffic, not just over-limit traffic. The common mitigation is a local pre-check on each gateway node — an approximate local counter, or a small allotment of tokens periodically synced from the shared store — that can reject obviously-over-limit requests instantly with no network call, sending only the borderline cases to the authoritative shared check. This trades a small amount of precision right at the limit boundary for far lower average latency and far less load on the shared store.

3) Counting requests is not the same as isolating tenants. Rejecting a tenant's requests past their quota protects the front door, but if every tenant still shares the same backend connection pool or thread pool, a tenant approaching their limit can exhaust shared backend resources before the count-based rejection even kicks in. Bulkheading (Ch.15) backend capacity by tenant tier, not just gatekeeping request counts at the edge, is what actually isolates one tenant's spike from degrading another's latency.

Trade-offs

At 10x scale (500,000 tenants, roughly 1 million req/sec), the shared counter store itself becomes the bottleneck the entire limiter depends on. The trade-off is sharding that store by tenant ID (more operational complexity, and rebalancing work as tenants grow) against falling back to node-local-only approximate limiting (simpler, but a tenant spread evenly across many gateway nodes can burst past their true limit by roughly the node count before anything reacts).

Say this

"I would make the gateway fail open, with alerting, if the shared limiter store becomes unreachable, rather than fail closed — a brief window of unmetered traffic is a much cheaper outcome than rejecting every paying customer's request because of a dependency hiccup in the counter store, and I would say so explicitly rather than let it be an accident of whatever the client library happens to do on a timeout."

Final design

A stateless, horizontally-scaled gateway fleet does authentication, routing, and a fast local pre-check on every request, backed by a shared atomic counter store for correctness at the tenant level, tenant-tier bulkheaded backend pools, and a control plane for per-tenant overrides without a deploy.

EM-level follow-up

Build-vs-buy: most companies buy the gateway shell (Kong, Apigee, or a cloud provider's API gateway) and build only the tenant-plan resolution and billing integration on top, rather than writing routing and TLS termination from scratch. Rollout of strict enforcement against existing tenants who have never been limited needs a log-only, do-not-reject dry-run phase first, or the first real enforcement day breaks customers who were quietly over quota for months without anyone noticing. Cross-team, billing and finance need the usage-metering stream to be accurate to the request, a stronger consistency bar than the rate-limiting decision itself needs — in practice these end up as two separate pipelines fed by the same request, not one shared mechanism doing both jobs.
