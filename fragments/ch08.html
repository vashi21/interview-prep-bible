MongoDB and Redis look nothing alike, but interviewers probe both the same way: what shape does your data take, how do you query it fast, and what breaks first at scale. This chapter goes past "MongoDB stores JSON" and "Redis is a cache" into the parts that actually come up in an interview — schema design trade-offs, the aggregation pipeline, Redis as a real data-structure server, and how DynamoDB's partition keys and consistency choices work.

01BSON: What MongoDB Actually Stores

MongoDB documents look like JSON when you print them, but on disk and on the wire MongoDB stores and sends something called BSON — short for Binary JSON. BSON is a binary-encoded format: instead of human-readable text, every value is stored as a typed, length-prefixed sequence of bytes.

Two things separate BSON from plain JSON:

  • Richer types. JSON only really has a handful of types: string, a single generic "number," boolean, null, array, and object. That generic number type is a real limitation — JSON can't tell you whether 4 is meant to be an integer or a float. BSON fixes this by adding distinct types: Int32, Int64, Double, and Decimal128 (for exact decimal math, useful for money) are all separate types, plus a native Date type (stored as milliseconds since the Unix epoch), a Binary type for raw byte data like images, and MongoDB's own ObjectId type.
  • Faster to traverse. Every string and every embedded document in BSON is stored with its byte length written up front. That lets MongoDB's storage engine skip straight past a field it doesn't need instead of scanning character by character the way parsing text JSON requires. This is BSON's real reason for existing: it isn't reliably smaller than compact JSON — the extra type information can make it bigger — the trade is speed and richer typing, not raw size.

Every document has an _id field, and if you don't supply one, MongoDB generates an ObjectId: a 12-byte value made of a 4-byte timestamp (when it was created), a 5-byte random value unique to the process that created it, and a 3-byte counter that starts at a random number and increments with each new id. That's why ObjectIds sort roughly by creation time even though nothing forces them to — the leading timestamp bytes dominate the sort order.

One BSON fact worth keeping in your head through the next section: a single MongoDB document is capped at 16 MB. That number is the hard ceiling behind every "should I embed this or reference it?" decision that follows.

02Schema Design: Embed vs Reference

Relational schema design asks "what tables do I need, and how do I join them?" MongoDB schema design asks a different question: for any two related pieces of data, do I nest one inside the other in a single document (embedding), or do I store them as separate documents linked by an id (referencing, MongoDB's version of a foreign key)? There's no universal right answer — it depends on how the data is shaped and how it's read.

Embedding: a blog post with its comments

Embedding means nesting the related data directly inside the parent document, usually as a sub-document or an array of sub-documents.

{
  _id: ObjectId("64f1a2..."),
  title: "Why We Switched To MongoDB",
  author: "priya",
  body: "...",
  publishedAt: ISODate("2026-01-04T09:00:00Z"),
  comments: [
    { user: "arjun", text: "Great post!", postedAt: ISODate("2026-01-04T10:03:00Z") },
    { user: "meera", text: "Agreed on the schema part.", postedAt: ISODate("2026-01-04T11:15:00Z") }
  ]
}

One query — fetch the post by _id — returns the post and every comment needed to render the page. No join, no second round trip. This is a good fit for three concrete reasons:

  • Comments belong to exactly one post — this is a one-to-many relationship, not many-to-many.
  • Comments and their post are almost always read together — nobody loads a comment without the post it's attached to.
  • Growth is bounded. A post might collect a few thousand comments over its life, which stays comfortably under the 16 MB document limit from section 01.

If a post goes viral and its comment count starts threatening that limit, the common real-world fix is a hybrid: embed only the most recent N comments (say, 200) for fast rendering, and move older comments into their own collection referencing the post's id — embed the hot slice, reference the long tail.

Referencing: a social graph with followers

Referencing means storing an id that points at a document in another collection, instead of nesting the data.

// users collection
{ _id: ObjectId("u1"), username: "arjun", bio: "..." }
{ _id: ObjectId("u2"), username: "priya", bio: "..." }

// follows collection
{ _id: ObjectId("f1"), follower: ObjectId("u1"), following: ObjectId("u2"), createdAt: ISODate("2026-02-11T08:00:00Z") }

A "who follows whom" graph is the opposite shape from a blog post, on every count that mattered above:

  • It's many-to-many — arjun follows many people, and is followed by many people.
  • Growth is unbounded — a popular account can pick up tens of millions of followers. Embedding that as an array inside the user document would eventually blow past the 16 MB limit, and every new follow would mean writing into an already-huge array instead of a small, independent insert.
  • Both sides need independent queries that have nothing to do with a specific parent: "who does arjun follow," "who follows priya," "is arjun already following priya." Each of these is just a filtered, indexed query against the follows collection — you never need to load one giant array just to check membership.

The cost of referencing: getting the full picture back — a user and their recent followers, say — now takes a second query against another collection, or a $lookup aggregation stage (covered next section), MongoDB's version of a join. And a write to users and a write to follows aren't automatically one atomic operation — you'd need MongoDB's multi-document transactions (available since version 4.0) if you needed both to succeed or fail together, and those cost throughput compared to a plain single-document write.

The rule I use: embed when it's read together and bounded, reference when it's many-to-many, unbounded, or needs to be queried on its own."

03The Aggregation Pipeline

MongoDB's aggregation pipeline is its framework for turning raw documents into computed answers — filtering, grouping, reshaping, and joining — by pushing a collection through a sequence of stages, where each stage's output becomes the next stage's input. It's the same idea as piping commands together in a Unix shell, applied to documents instead of text, and it's MongoDB's answer to what a SQL query with WHERE, GROUP BY, and JOIN does in one relational statement.

A realistic example: given an orders collection, find the top 10 customers by total completed spend.

db.orders.aggregate([
  { $match: { status: "completed" } },
  { $group: {
      _id: "$customerId",
      totalSpent: { $sum: "$amount" },
      orderCount: { $sum: 1 }
  }},
  { $sort: { totalSpent: -1 } },
  { $limit: 10 }
])

Reading it stage by stage:

  • $match — a filter, like SQL's WHERE. Keep only orders with status: "completed", and drop everything else before doing any heavier work.
  • $group — bucket the remaining documents by customerId, like SQL's GROUP BY. For every bucket, $sum: "$amount" adds up that customer's order amounts into totalSpent, and $sum: 1 counts how many orders landed in the bucket.
  • $sort — order the one-document-per-customer result by totalSpent descending.
  • $limit — keep only the top 10.

Putting $match first isn't just tidy — it's a performance decision. It shrinks the set of documents before the more expensive grouping and sorting stages ever see them, and if status is indexed, an early $match can use that index exactly the way a WHERE clause would in a relational query. Pushing filters as early as possible in the pipeline is one of the few aggregation habits worth memorizing.

The other stage worth knowing by name is $lookup, which performs a left outer join against another collection — { $lookup: { from: "customers", localField: "customerId", foreignField: "_id", as: "customerInfo" } } would pull each customer's profile into the result above. This is exactly how a referenced design (section 02) reassembles data that a relational database would have joined at the database layer for free.

$lookup gives you a join, but it isn't a free one. A relational database has spent decades on join planning — picking join order, using indexes on both sides, choosing between hash and merge join strategies. MongoDB's $lookup is more of a per-document loop under the hood; it works, and it's fine at moderate scale with a good index on the foreign field, but it's rarely as fast as the equivalent join in a mature relational engine. A schema leaning on frequent, multi-collection $lookup stages is a signal you might actually want the relational model — see section 05.

04Indexing In MongoDB

MongoDB indexes work on the same underlying idea as a relational index — a sorted structure (a B-tree, the same data structure introduced for MySQL indexing in Ch.7) that lets the query planner jump straight to matching documents instead of scanning the whole collection. Every collection gets a unique index on _id automatically; everything past that is a design choice.

  • Single-field index — index one field, exactly like an index on one column in SQL.
  • Compound index — index several fields together. Field order matters, the same left-prefix rule from relational compound indexes applies: a query can use the index if it filters on a leading prefix of the indexed fields. MongoDB's own guidance for ordering a compound index is the ESR rule — put Equality fields first, then Sort fields, then Range fields.
  • Multikey index — automatically created when you index a field whose value is an array. MongoDB creates one index entry per array element, so a query can match a document by any one of its array's values.
  • Text index — supports basic text search across string fields (word-level matching, not a full search-engine relevance ranking — for that, reach for Elasticsearch, covered in Ch.11).
  • Geospatial index (2dsphere) — supports "find things near this point" and "find things inside this shape" queries on coordinate data.
  • TTL index — an index with an expireAfterSeconds setting that makes MongoDB automatically delete documents once they've aged past that limit. This is a common fit for session data or short-lived logs that should clean themselves up without a separate scheduled job.

A covered query is one where every field the query needs — both to filter and to return — is already inside the index, so MongoDB never has to fetch the actual document off disk. Run .explain("executionStats") on a slow query to check: a plan showing COLLSCAN means MongoDB scanned the whole collection with no index; IXSCAN means it used one. Chasing COLLSCAN out of your slow queries is the single highest-leverage MongoDB performance habit.

The shard key — the field MongoDB uses to decide which shard a document lives on — is a separate decision from any of the indexes above, covered in depth in Ch.6, including why a poorly chosen (monotonically increasing) shard key creates a write hot spot. Every collection needs an index on its shard key, but not every index needs to be a shard key.

05When Documents Beat Rows, And When They Genuinely Don't

Documents win when your data naturally nests as one aggregate that's read and written as a whole: a product with variants and attributes that differ per product, a blog post with its comments, a user profile with preferences that change shape over time without needing a schema migration that locks a table with a billion rows. MongoDB's flexible schema — sometimes called "schema-less," though it's really schema-flexible, since your application still has an implicit schema, MongoDB just doesn't enforce one at the database layer by default — means adding a new field to new documents doesn't require an ALTER TABLE-style operation across every existing row first.

Rows win when your data is highly relational, meaning many entities cross-reference each other, and the queries that join them change from request to request instead of following one fixed access pattern. A concrete example: an accounting or ERP-style system where orders, customers, products, warehouses, discounts, and tax rules all need to be joined in different combinations depending on the report someone's running this week. Forcing that into documents means either duplicating data across many documents (denormalizing everything, and now every duplicate needs updating when the source changes) or stacking up $lookup stages that are really just doing a join anyway, without a relational query planner's decades of join optimization behind them.

Rows also win when you need multi-row, multi-table ACID transactions as your default mode of operation — not an occasional case, but every write. A ledger where a debit on one account and a credit on another must commit together, every single time, is what relational transactions were built for from day one. MongoDB added multi-document transactions in version 4.0, and they work correctly, but they're a feature added on top of a document model, not the foundation the engine was designed around — and they cost meaningfully more throughput than a single-document write.

An EM-level answer doesn't reach for "NoSQL scales better" as the reason to move a relational system to MongoDB — plenty of relational systems scale fine with the sharding techniques from Ch.6. The real trigger is the shape of the data and its access pattern, not raw scale. Facebook's own history makes the point: their social graph — objects and the edges between them — didn't fit cleanly into either a pure relational model or a pure document model at their scale, which is why they built TAO, a graph-aware caching and storage layer running on top of sharded MySQL, instead of just picking one off-the-shelf database model. The lesson isn't "use TAO" — it's that the right answer to "rows or documents" is sometimes "neither, exactly — build the access pattern you actually need on top of one of them."

06Redis Beyond "It's Just A Cache": Lists, Sets, And Sorted Sets

Ch.4 introduced Redis as a cache and touched on its data structures in passing. It's worth stopping here and taking those structures seriously, because Redis is really a data-structure server that happens to also work great as a cache: every key holds a typed value, and each type comes with its own atomic operations, so many clients can safely push, pop, or increment shared state without racing each other.

Lists

A Redis list is an ordered sequence of values, with fast push and pop from either end: LPUSH/RPUSH add to the left or right end, LPOP/RPOP remove from either end, and BLPOP/BRPOP are blocking versions that wait for an item to appear instead of returning immediately. This makes lists a natural fit for a simple job queue (workers BRPOP from one end while producers LPUSH onto the other) or a capped "recent activity" feed (LPUSH the newest item, then LTRIM the list down to a fixed length so it never grows unbounded).

Sets

A Redis set is an unordered collection of unique values, with an O(1) membership check (SISMEMBER) and built-in set algebra: SUNION, SINTER, and SDIFF compute the union, intersection, and difference of two or more sets directly on the server. That makes sets a good fit for "tags on this post," "who follows both X and Y" (a set intersection), or deduplicating a stream of ids without pulling everything into the application to compare.

Sorted sets

A sorted set (Redis calls the type ZSET) is a set where every member also carries a floating-point score, and Redis keeps the entire set ordered by that score at all times. Internally it's backed by a skip list plus a hash table, which is what makes both "give me this member's rank" and "give me everyone between these two scores" run in roughly O(log N) time instead of requiring a fresh sort on every read. This is the structure behind leaderboards, priority queues, and any ranked list that changes constantly but needs to be read in order on every request.

07Redis Worked Example: A Leaderboard With A Sorted Set

A live leaderboard — "top players this week," updated after every match — is the textbook sorted-set use case.

ZADD leaderboard:global 4820 "player:1042"
ZADD leaderboard:global 3990 "player:2871"
ZADD leaderboard:global 5510 "player:9981"

ZREVRANK leaderboard:global "player:1042"     # this player's rank, 0-indexed, highest score first
ZSCORE  leaderboard:global "player:1042"      # this player's current score
ZREVRANGE leaderboard:global 0 9 WITHSCORES   # top 10 players and their scores
ZINCRBY leaderboard:global 150 "player:1042"  # add 150 points after a match

ZADD sets (or updates) a member's score. Because Redis keeps the whole set ordered by score at all times, reading "top 10" (ZREVRANGE 0 9) or "this player's current rank" (ZREVRANK) is a cheap lookup against an already-sorted structure — the sort cost is paid once, incrementally, on every write, instead of being paid all over again on every read the way a plain SELECT ... ORDER BY score DESC would if you weren't caching the result. ZINCRBY atomically adds to an existing score, so two concurrent matches finishing at the same instant and both trying to add points to the same player never race each other into a wrong final total — the increment is a single atomic server-side operation, not a read-modify-write your application code has to coordinate itself.

08Redis Worked Example: A Session Store

After a user logs in, something has to hold "who is this session, and are they still logged in" — and it has to be readable by whichever application server happens to handle their next request, since a load balancer usually won't pin a user to the exact server that authenticated them. Redis is a standard fit for this, storing session state in one place every application server can reach.

HSET session:a1b2c3 userId 4821 loginAt 1751000000 role "admin"
EXPIRE session:a1b2c3 1800
HGETALL session:a1b2c3

HSET stores the session as a hash — a small field-value map living inside one key, essentially a mini-document. EXPIRE sets a TTL (time to live) of 1800 seconds — 30 minutes — on the whole key; once that time passes with no refresh, Redis deletes the key on its own, so idle sessions clean themselves up without a background cleanup job. A common pattern re-issues EXPIRE on every request that touches the session, turning the fixed TTL into a sliding window: "log the user out after 30 minutes of inactivity," not 30 minutes after login. HGETALL reads the whole session back in one round trip.

A plain string key (SET session:a1b2c3 "{...serialized json...}" EX 1800) could store the same information, but a hash lets you update one field — bumping lastSeenAt, say — without re-serializing and rewriting the entire blob. And since Redis holds this in memory, production session stores usually run Redis replicated (Redis Cluster, or a managed offering like ElastiCache or MemoryDB) so that one node failing doesn't log out every active user at once — persistence and clustering trade-offs are covered in Ch.4.

09DynamoDB: Partition Keys And The Hot Partition Problem

DynamoDB is Amazon's managed, key-value and document store: every item has a primary key, and DynamoDB decides which internal partition an item lives on by hashing its partition key (also called the hash key) — conceptually the same idea as hash-based sharding from Ch.6, except fully managed. You never choose the number of partitions directly; DynamoDB creates, splits, and moves them for you as a table's size and throughput grow.

A table can use just a partition key, or a composite primary key: partition key plus sort key. Items sharing a partition key are stored together, sorted by the sort key — so partition key userId and sort key orderTimestamp gets you "all of this user's orders, in time order" as one cheap, local read, without touching any other partition.

Good partition-key design means picking a key with high cardinality (many distinct values) and roughly even access across those values — every distinct partition key should get a similar share of the table's total traffic. Here's how it fails: imagine an events table logging telemetry with partition key eventDate, a value like "2026-07-26". Every event created today writes to that exact same partition key value, so every write for the entire system, no matter how large the table is or how many partitions DynamoDB has allocated to it, funnels into a single partition. That one partition hits its throughput ceiling — AWS has documented per-partition limits on the order of 3,000 read capacity units and 1,000 write capacity units — and starts throttling writes, while every other partition in the table sits completely idle. This is DynamoDB's version of the monotonically-increasing shard key problem from Ch.6's MongoDB section: the fix is the same in spirit — pick a higher-cardinality key, or add a random or hashed suffix to spread one logical day's writes across many partition key values (say, eventDate#03 where 03 is a random number from 0–99), then fan reads out across all the suffixes and merge the results.

DynamoDB's adaptive capacity feature automatically shifts unused throughput from cold partitions toward a hot one, and it genuinely helps with mild, temporary imbalance. It cannot rescue a fundamentally bad key design, though — if every write in the system permanently targets one partition key value, there's no idle capacity anywhere else to borrow. Partition key choice is a design-time decision, not something you patch with a setting after launch.

10DynamoDB: Quorum-Style Reads And Writes

DynamoDB replicates every item across multiple availability zones within a region — AWS documents this as three copies — for durability and availability, using a quorum-style protocol under the hood: a write is durable once enough replicas have it, and a read is trustworthy once it has checked enough replicas that its answer is guaranteed to reflect the most recent completed write. That's the same core idea Ch.9 covers in full, tunable detail for Cassandra's R + W > N formula — DynamoDB doesn't expose the exact replica math as a dial the way Cassandra does, but the underlying trade-off is identical.

What DynamoDB does expose is a choice, on every read request, between two consistency levels:

  • Eventually consistent read — the default, and it costs half the read capacity of a strongly consistent read for the same item. It might return data from a replica that hasn't yet received the very latest write; read right after a write and you could see a slightly stale value, though AWS says that window is normally well under a second.
  • Strongly consistent read — guarantees the read reflects every write that completed successfully before it started. It costs more read capacity, adds a little latency, and — this is the real trade-off, a direct instance of the CAP theorem from Ch.12 — it can become unavailable under certain network-partition conditions where an eventually consistent read would still happily succeed.

"For the product catalog page, I'd use eventually consistent reads — a shopper seeing a price that's a fraction of a second stale is harmless, and it's half the read cost at our scale. For the 'confirm my payment went through' read right after the write, I'd pay for a strongly consistent read, because showing the user a false 'still pending' state, or worse, double-charging because a stale read said the payment hadn't landed yet, is the more expensive failure."

11DynamoDB: Global Secondary Indexes

DynamoDB can only efficiently query a table along its primary key — partition key alone, or partition key plus sort key. That's the price of a horizontally-partitioned store: there's no free "find all rows where this other column equals X" the way a relational index gives you almost for granted, because answering that against the base table's partitioning would mean checking every partition — an expensive full-table Scan, not a targeted Query.

A Global Secondary Index (GSI) solves this: it's a second, DynamoDB-managed index over the same table, with its own partition key (and optional sort key) chosen from other attributes on the same items — see the GSI on customerId in the diagram above, sitting alongside a base table partitioned by orderId. Query the GSI directly for "all orders for this customer," sorted however the GSI's sort key is defined, without ever touching how the base table itself is partitioned.

Two things worth knowing about GSIs specifically:

  • They're eventually consistent only. A GSI is really a separate, asynchronously-updated copy of the table's data, reorganized under a different partition key — propagation from a base-table write to its GSI entry takes a small amount of time. (A Local Secondary Index, by contrast, shares the base table's partition key and only varies the sort key, which is why it can offer strongly consistent reads — it's not really a separate physical copy in the same way.)
  • They have their own throughput, provisioned or on-demand separately from the base table. A GSI that gets hammered by one hot access pattern can throttle on its own, independent of how the base table itself is doing.

The design habit a GSI teaches is the same one that's run through this whole chapter: model the schema around the queries you actually need to run, whether that's MongoDB's shard key, Redis's choice of data structure, or a DynamoDB GSI added for exactly one extra access pattern — not one schema you hope covers every future question.

Every GSI is close to a second table: its own storage, its own throughput cost, its own capacity to throttle. Adding one isn't free just because DynamoDB manages it for you — at the design-review stage, each proposed GSI is worth asking "what specific query does this serve, and is it worth paying for a second copy of this data to serve it," the same build-vs-buy discipline that applies to standing up any other piece of infrastructure.
