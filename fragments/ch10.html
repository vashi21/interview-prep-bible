Every app has two very different appetites for data: the live system serving one user at a time, and the reports that need to look across everyone at once. This chapter covers why those two jobs cannot share one production database, and the stack most companies build instead — lakes, warehouses, lakehouses, and the file and table formats that hold them together.

01OLTP Vs OLAP: Two Very Different Workloads

OLTP stands for online transaction processing. It is the workload behind almost every feature you use in an app: placing an order, liking a post, updating an address, checking whether an item is in stock. Each of these operations touches a handful of rows, usually found through an index, and finishes in single-digit milliseconds. There are a lot of these operations happening at once — thousands per second on a busy service — but each one is cheap.

OLAP stands for online analytical processing. It is the workload behind reports and dashboards: "what was our revenue by region last quarter," "how many users churned this month," "which product category is growing fastest." Each of these queries scans a huge slice of historical data — millions or billions of rows — and computes an aggregate over it (a sum, a count, an average, a group-by). There are far fewer of these queries running at any moment, but each one is expensive, and can take seconds to minutes instead of milliseconds.

-- OLTP: one indexed row, a few milliseconds
UPDATE inventory SET qty = qty - 1
WHERE sku = 'ABC123' AND warehouse_id = 42;

-- OLAP: scans a year of history, seconds to minutes
SELECT region, SUM(revenue)
FROM orders
WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
GROUP BY region;

The two workloads also shape their tables differently. OLTP tables are normalized (see Ch.7) to avoid duplicating data on every write, and indexed for point lookups. OLAP tables are often deliberately denormalized (section 06 below) because scanning is cheaper when the engine does not have to join five tables together to answer one question.

Lock Contention

MySQL's InnoDB engine uses MVCC (multi-version concurrency control, see Ch.7) — readers see a consistent snapshot without blocking writers. But that snapshot has a cost: as long as a transaction holds it open, InnoDB cannot throw away old row versions that writers have since replaced, because that transaction might still need to read them. A long-running analytical query — say, five minutes to scan a year of orders — holds its read view open for those full five minutes. Every row any other transaction updates during that window creates one more old version InnoDB has to keep around. This shows up as a growing "history list length": the undo log (the storage InnoDB uses to keep those old versions) balloons, eating disk space and crowding the buffer pool cache that live checkout traffic depends on. A plain ad hoc SELECT like that report, on its own, does not take any locks at all under InnoDB's default isolation level, REPEATABLE READ, or under READ COMMITTED — it is a non-locking read that only reads a snapshot. Gap locks (locks on the empty space between index entries, so nothing new can be inserted into that gap) only come from locking reads (SELECT ... FOR UPDATE or LOCK IN SHARE MODE) or from a write with a range predicate, such as an UPDATE or DELETE that matches "all orders in March." The one isolation level (Ch.7) where an ordinary SELECT itself takes gap locks is SERIALIZABLE, which is exactly why production systems rarely run at that level — the locking cost is too high.

MongoDB's WiredTiger storage engine has its own version of this: it hands out a limited number of concurrency tickets to reads and writes, and a heavy aggregation pipeline holding tickets for a long stretch leaves fewer tickets available for the app's normal reads and writes, which start queueing behind it.

Scan Cost

OLTP databases store data row by row on disk (see section 03). To compute SUM(revenue) GROUP BY region over a year of orders, the engine has to read every row for that year off disk — including every column in that row, even the ones the query never asked for — because a row store cannot pull out just one column without reading the whole row it lives in. Say checkout writes roughly 2,000 orders per second at peak. Treating that peak rate as if it ran non-stop for a full year — real traffic is far lower most of the day, so this is a ceiling, not the real total — gives roughly 2,000 × 86,400 seconds × 365 days ≈ 63 billion order-events. Even the real, average-load figure is a small fraction of that ceiling, and it is still comfortably in the billions of rows for a year, so a single month's slice is still billions of rows to pull off disk for one report. That is a lot of disk I/O and CPU, all competing with the same disk and CPU the live system needs for its normal millisecond-scale reads and writes.

Blast Radius On Live Traffic

Put lock contention and scan cost together and the real risk becomes clear: the analytical query and the live app share the exact same machine — the same CPU, the same memory buffer pool, the same disk I/O bandwidth, and often the same fixed pool of database connections. A single heavy report can push CPU to its limit, evict the buffer pool pages the live app needs (forcing its queries back to slower disk reads), or hold connections for minutes at a time until the connection pool has none left for real users. If the query runs against the primary and grows the undo log enough, it can even slow down replication, because the primary now has more work to do just keeping its own storage engine healthy. None of this requires a bug — a single well-formed report query is enough to become an incident if it runs against the same box serving live traffic.

"I would never point a BI dashboard at the production MySQL primary. A GROUP BY over a year of orders holds a read view open, InnoDB cannot purge old row versions under that transaction, and the undo log grows until it crowds out the cache the checkout path needs. I would offload that query to a read replica at minimum, and to a warehouse for anything that runs on a schedule."

An EM-level answer adds the cost angle: a serverless query engine like Athena bills per byte scanned, and a small team's ad hoc analytics rarely justifies running and patching a dedicated Spark cluster in year one. The build-vs-buy call is usually: pay per query on managed infrastructure until the analytics workload is big and steady enough to justify owning the compute.

02Data Lake Vs Data Warehouse Vs Lakehouse: What Each One Is For

A data lake exists to store raw data of any shape — structured tables, semi-structured JSON, unstructured logs, images, video — cheaply and at huge scale, without deciding the schema upfront. This is called schema-on-read: you write the data first and figure out its structure when you query it, instead of designing tables before a single row lands. The point of a lake is to hold data you might not know how to use yet: raw event logs, ML training data, archived records for future reprocessing. It is normally built on commodity object storage (Amazon S3, Google Cloud Storage, Azure Blob Storage), which costs a small fraction of what database storage costs per gigabyte.

A data warehouse exists to store modeled, structured data optimized for fast answers to questions the business already knows it wants to ask. This is schema-on-write: the shape of the data — the tables, the columns, usually a star schema (section 06) — is decided before loading, so every BI dashboard and every analyst runs against clean, consistent, well-understood tables. Warehouses (Snowflake, BigQuery, Redshift, and older systems like Teradata) are built and priced for fast, repeated analytical queries, not for holding arbitrary raw files cheaply.

A lakehouse exists to close the gap between the two. The old pattern was to keep raw data in a lake and a separate, curated copy in a warehouse — which means transforming the data twice, paying for storage twice, and living with the risk that the two copies drift out of sync. A lakehouse puts warehouse-style guarantees (ACID transactions, schema enforcement, fast queries, the table formats in section 04) directly on top of lake-style cheap object storage, so raw processing, machine learning, and BI dashboards can all query the same underlying files instead of two separate systems.

A lake with no governance turns into what practitioners call a "data swamp" — files nobody trusts, because nothing enforced a schema or tracked which files even belong to a valid, consistent version of a dataset. Table formats (section 04) exist specifically to stop that from happening.

03File Formats: Parquet, ORC, And Avro

Underneath a lake or a warehouse, data has to sit in some file format. The biggest split is row-based versus columnar storage.

A row-based format stores every field of one record next to each other, then the next record, and so on — the same order you would write it by hand. A columnar format instead stores every record's value for column A together, then every record's value for column B together, and so on.

Why Columnar Wins For Analytics

Take the OLAP query from section 01: SELECT region, SUM(revenue) FROM orders GROUP BY region. It only needs two columns, region and revenue, out of a table that might have fifty. A columnar file lets the query engine read only the column chunks for those two columns off disk and skip every other column entirely. A row-based file cannot do that — reading any part of a row means reading the whole row, so the engine ends up pulling all fifty columns off disk just to use two of them.

Columnar layout also compresses much better. Values in one column tend to be similar — a region column has only a handful of distinct values, a status column is close to an enum. Storing those values contiguously lets the format use dictionary encoding (store each distinct value once, reference it by a small number), run-length encoding (store a repeated value once plus a count), and similar tricks far more effectively than a row-oriented layout ever could. Both Parquet and ORC also store per-column-chunk statistics — minimum and maximum values, null counts — so the query engine can skip whole chunks that cannot match a filter, without even decompressing them.

Parquet was created by engineers at Twitter and Cloudera, inspired by Google's Dremel paper, and is now an Apache project. It is the closest thing to a default columnar format across the modern lake ecosystem — Spark, Athena, Presto/Trino, and BigQuery's external tables all read it natively.

ORC (Optimized Row Columnar) grew out of the Apache Hive project, built by Hortonworks and Facebook engineers to replace an earlier format called RCFile. It is columnar in the same sense as Parquet, with its own built-in lightweight indexes, and remains the common default in Hive- and Hadoop-heavy shops.

Where Row-Based Avro Wins Instead

Avro is a row-based serialization format from the Apache Hadoop project. Its defining feature is that the schema travels with the data — either embedded in the file or, in streaming systems, referenced from a schema registry — and Avro has well-defined rules for evolving that schema (adding a field with a default value, for example) without breaking readers still using an older version. Because it writes one record at a time without needing to buffer a whole batch to build a column chunk, it is fast to serialize and matches how a stream actually produces data: one event at a time, as it happens. That is why Avro, not Parquet, is the standard choice for messages flowing through Kafka (see Ch.14) — a write-heavy, one-record-at-a-time workload is exactly what row-based storage is good at.

Columnar formats are not free at write time. Building a Parquet column chunk means buffering enough rows in memory first, which adds latency you cannot afford for a single Kafka message. That is exactly why streaming pipelines write Avro record by record and only convert to Parquet once the data has landed and been batched — see section 07 for that conversion happening in practice.

04Table Formats: Delta Lake, Iceberg, And Hudi

A file format decides how one file is laid out. A table format decides how a collection of files becomes something you can trust like a database table. Plain Parquet files sitting in an S3 folder have none of the guarantees a database gives you by default:

  • No atomicity — if a job writing thousands of files crashes halfway through, readers can see a half-finished, inconsistent mix of old and new files. There is no concept of "this write either fully happened or did not happen" for a folder of files.
  • No isolation — two jobs writing to the same table at the same time can step on each other with no locking or conflict detection.
  • No schema enforcement — nothing stops one bad job from writing files with a different schema and silently breaking every downstream reader.
  • No cheap row-level update or delete — updating one row has historically meant rewriting an entire file or partition, which makes something like a single-user data-deletion request expensive.
  • No time travel — no built-in way to ask "what did this table look like an hour ago," and no easy way to roll back a bad write.

Delta Lake, Apache Iceberg, and Apache Hudi all solve this the same general way: they add a transaction log or metadata layer next to the data files that tracks exactly which files make up which version of the table. A write commits by atomically adding one new entry to that log — either the whole entry lands or none of it does — which gives you ACID transactions, safe schema evolution (the log tracks schema versions too), and time travel (query, or roll back to, any earlier version by number or timestamp), all on top of storage that has none of that natively.

Delta Lake was built by Databricks and open-sourced; it uses a JSON transaction log (a folder called _delta_log) recording every file added or removed by each commit.

Iceberg was built inside Netflix specifically to fix problems with using plain Hive tables on top of S3 — slow file listing and unreliable partition tracking, among others — and was later donated to the Apache Software Foundation. It is now broadly adopted outside Netflix, with Snowflake, AWS Glue/Athena, Trino, and Spark all able to read and write Iceberg tables.

Hudi (Hadoop Upserts Deletes and Incrementals) was built at Uber to handle upsert-heavy ingestion — the kind of continuous, row-level updates you get from a CDC stream (section 07) — on top of Hadoop- and S3-style storage. Hudi offers two table types: copy-on-write, which rewrites the affected data file on every update, and merge-on-read, which appends changes to a small delta log and merges them in at read time.

Delta Lake vs Iceberg vs Hudi
ConceptDelta LakeIcebergHudi
OriginDatabricksNetflix, now ApacheUber, now Apache

Standout strengthDeep integration with Spark and Databricks toolingBroad, engine-neutral adoption (Snowflake, Trino, Athena, Spark)Fast upserts for CDC-style, continuously-updating ingestion

Hudi's two table types trade off in opposite directions. Copy-on-write rewrites the whole affected file on every update, so writes are slower but every read is simple and fast, with nothing to merge. Merge-on-read keeps writes cheap by appending to a delta log, but every read pays a merge cost until the next compaction cleans that log up. Choosing between them is choosing whether your pipeline is more write-heavy or more read-heavy.

05ETL Vs ELT

ETL stands for extract, transform, load: pull data out of the source system, clean and reshape it in a separate processing step, and only then load the already-transformed data into the destination. This was the standard pattern when warehouse compute was expensive and tightly coupled to its storage, so you wanted the warehouse doing as little work as possible and only ever holding clean, modeled data.

ELT stands for extract, load, transform: pull data out and load it into the destination — usually a lake or a cloud warehouse — close to its raw form first, then run the transformation using the destination's own compute (for example, dbt running SQL models inside Snowflake or BigQuery). This became the more common pattern once cloud warehouses decoupled storage from compute and made that compute cheap and elastic enough to absorb the transformation work itself. It also means you always keep an untouched copy of the raw data, so if a transformation has a bug or the requirements change, you can reprocess from the original instead of having already thrown it away.

That way, if a transformation ships a bug, I still have the original raw data to reprocess from — with ETL, the untransformed version is usually already gone by the time you notice."

06Star Schema Vs Snowflake Schema

Both schemas organize a warehouse around the same idea: one fact table holding the events you care about (an order, a click, a shipment) with numeric measures (revenue, quantity) and foreign keys, surrounded by dimension tables that describe those events (who the customer was, what the product was, what day it happened on).

A star schema keeps every dimension table denormalized (flat) — dim_product repeats its category name directly on every row instead of pointing to a separate categories table. Every dimension is exactly one join away from the fact table, which keeps queries simple for both a human writing SQL by hand and a query engine planning the joins.

A snowflake schema takes it one step further and normalizes the dimensions themselves — dim_product might point to a separate dim_category table, which might point to a dim_department table. This removes duplicate data (a category name is stored once, not on every product row) and keeps values consistent if something changes. The cost is extra joins: a single BI query can now have to walk fact → product → category → department instead of a single hop, which is more work for a columnar query engine and more complexity for whoever is writing the query.

Star vs snowflake schema
ConceptStar SchemaSnowflake Schema
Dimension shapeDenormalized, flatNormalized into sub-dimensions
Joins per queryOne join, fact to dimensionMultiple joins through normalized chains
Storage redundancySome repeated values across rowsLittle to none — each value stored once
Best fitFast, self-serve BI; the common default todayVery large, slowly-changing dimensions where redundancy really matters

Snowflaking a dimension saves storage and keeps values consistent, but every extra join is one more thing a columnar query engine has to match and shuffle across nodes. For most BI workloads today storage is the cheap resource and query latency is the expensive one — which is why star schemas, or even one wide denormalized table, are the more common default in cloud warehouses now.

07One Full Pipeline, End To End: From MySQL And MongoDB To A BI Dashboard

Everything above is easier to hold onto as one concrete flow. Here is a single e-commerce example that uses all of it: an app that writes orders to MySQL and product-view events to MongoDB (the same two databases from Ch.6, Ch.7, and Ch.8), ending in a dashboard a business team actually looks at.

Step 1: Writes Land In MySQL And MongoDB

Checkout inserts a row into a MySQL orders table — normalized, indexed on order_id and user_id, a few-millisecond write. Every product page view inserts a document into a MongoDB product_views collection — semi-structured, high write volume, no fixed schema across every event type. Both are textbook OLTP writes from section 01: small, fast, touching only what one request needs.

Step 2: Getting Data Out Without Touching Production

There are two ways to move this data out, and the choice depends on how fresh the analytics need to be.

  • CDC (change data capture) — a tool like Debezium tails MySQL's binlog directly, the same replication stream MySQL already uses to feed read replicas (see Ch.6). For MongoDB, Debezium instead watches MongoDB's change streams API, which is itself built on top of the oplog — the same underlying log MongoDB uses for its own replication, just not read as a raw file the way the binlog is. Either way, Debezium turns every insert, update, and delete into an event, continuously and near real time, without ever issuing a query against the live database. This is the low-risk option: it adds no scan cost and no extra locking to production, because it is just another consumer of a stream that already exists.
  • Batch export — for data where near-real-time is not needed, a scheduled job runs an export (a mysqldump-style extract, a mongoexport) on a fixed schedule, pointed at a read replica rather than the primary, and ideally during low-traffic hours. This bounds the blast radius from section 01 by keeping the heavy read entirely off the primary.

Step 3: Landing In The Lake As Parquet

A pipeline — commonly Kafka Connect running the Debezium connectors, feeding a Kafka topic (Ch.14), read by a Spark or Flink job, or a managed equivalent like AWS DMS — writes these change events into Amazon S3, converting them into Parquet files as they land, partitioned by date (for example, s3://lake/orders/dt=2025-07-26/). Landing in Parquet instead of raw JSON is the payoff from section 03: any later analytical query only pays for the column chunks and column statistics it actually needs, not for the whole record.

Step 4: Making The Lake Reliable With A Table Format

Those Parquet files get registered as an Iceberg table (Delta Lake works the same way) rather than being left as loose files in a folder. That means a schema change — say the app team adds a new discount_code field — does not silently break every downstream reader, and a bad ingestion run can be rolled back with time travel instead of someone manually deleting files. AWS Glue Data Catalog stores the table's schema and partition metadata so query engines know what exists without scanning the files first.

Step 5: Querying The Lake Directly

Athena (a serverless engine built on Presto/Trino) or a Spark job can now run ad hoc SQL directly against these Iceberg-backed files in S3, paying only for the bytes scanned, without ever touching MySQL or MongoDB again. This is the layer a data scientist or an analyst doing one-off exploration reaches for.

Step 6: Curating Into A Warehouse For BI

A scheduled job — dbt running SQL, an ELT pattern from section 05 — reads from the Iceberg tables and models the data into a star schema (section 06): a fact_orders table plus dim_customer, dim_product, and dim_date tables, loaded into Snowflake, BigQuery, or Redshift. This is the curated, fast layer that BI tools (Looker, Tableau, Metabase) actually query for dashboards — known questions, pre-modeled, sub-second responses.

Notice what never happens anywhere in this chain: at no point does a dashboard, a scheduled report, or an analyst's ad hoc query run against the MySQL or MongoDB instances serving live checkout and page-view traffic. Every one of the operational risks from section 01 — lock contention, scan cost, blast radius — is designed out by construction, because the analytical workload physically runs on a different system, built and priced for exactly that job.

"Checkout writes to MySQL and product-view events land in MongoDB. Debezium tails MySQL's binlog directly and watches MongoDB's change streams, which are built on top of the oplog — both hook into replication mechanisms the databases already run, so capturing changes costs production nothing extra. Those change events land in S3 as Parquet, registered as an Iceberg table for schema safety and time travel. Athena and Spark query that table directly for ad hoc analysis, and a nightly dbt job reshapes it into a star schema inside Snowflake, which is what the BI dashboards actually query. Production never sees a single analytical query."

An EM-level answer names the build-vs-buy choice at each hop: self-hosted Debezium plus Kafka Connect versus a managed CDC service like AWS DMS or Fivetran; a self-run Spark cluster versus serverless Athena; Iceberg or Delta tables in your own S3 buckets versus fully managed Snowflake or BigQuery storage. Every one of those is "pay with engineering time" versus "pay with a bigger cloud bill," and the right side of that trade shifts as data volume and team size grow.
