This chapter builds one system, ten times. Each version fixes the exact bottleneck that broke the version before it — the same walk interviewers expect you to narrate live, ending at an architecture that almost every "design X at scale" problem in this book borrows pieces from.

01Why we climb the ladder instead of jumping to the final design

A common mistake in an HLD (high-level design) interview is drawing the final, fully-scaled architecture in the first five minutes. That skips the part the interviewer actually wants to hear: which bottleneck showed up first, why the fix you chose solves that specific bottleneck, and what new problem the fix creates. This chapter walks through ten revisions, numbered 0 through 9, of the same product. Revision 0 is one server. Revision 9 is a multi-region, cached, queued, sharded system. Nothing here is exotic — every step is a direct answer to a concrete, nameable bottleneck.

Revision 0 is the honest starting point: a domain name, one server, and a database, all doing their jobs on a single machine. A user's browser resolves the domain to an IP address using DNS (Domain Name System — a third-party service that maps human-readable names to IP addresses; you almost never run your own), then sends an HTTP request straight to that IP. On the box itself, a web/app server process (something like Node, Rails, or a Java application server) and a database (say, MySQL) both run and both compete for the same CPU, memory, and disk.

Bottleneck: there is no "before" here — this is the starting point every real system passes through while traffic is small enough that one machine can handle everything. A single well-tuned server can often absorb a few hundred to a couple thousand simple requests per second before something gives, and for a brand-new product that is usually plenty.

What changed: nothing yet — this is the baseline the rest of the chapter reacts to.

One machine is a single point of failure (SPOF): if it crashes, gets a bad deploy, or needs a restart, every user is down at once. It also forces the web process and the database process to fight over the same CPU, RAM, and disk I/O, so a single slow query directly hurts request latency for everyone else.

"I'd name this as the baseline — one server running the app and the database. It is fine at low traffic. The interesting part of this problem is which bottleneck breaks it first, and that is almost always resource contention or a single point of failure, not raw request volume."

02Revisions 1 and 2 — split the tiers, then scale the web tier out

Revision 1 — split the web tier from the database tier

Bottleneck: the web app and the database are fighting for the same CPU and memory on one box. A heavy query can starve the web process of CPU, and a traffic spike can starve the database of memory — and because they are not independent, you cannot fix one without risking the other.

What changed: the database moves to its own machine. There are now two tiers — a web/application-server tier and a database tier — talking to each other over the network instead of over localhost.

You get independent scaling and independent failure: a database restart no longer has to take the web tier down with it. The cost is a new network hop between tiers (small, but real and non-zero) and now two machines' worth of OS patches, monitoring, and access control to manage instead of one.

"The first split is not about capacity yet, it is about decoupling failure domains — a database restart should not force an application restart, and a bad app deploy should not be able to touch the same disk the data lives on."

Revision 2 — add a load balancer and a second web server

Bottleneck: a single web server has a hard ceiling on concurrent connections and CPU-bound request handling. Past that ceiling, requests queue up — and that one web server is now a second single point of failure, on top of the database tier from Revision 1.

What changed: a load balancer (LB) sits in front of the web tier as the one address clients actually connect to. It spreads incoming requests across two or more identical web servers using a strategy such as round robin (rotate through servers in order) or least connections (send the next request to whichever server currently has the fewest open connections). Ch.5 covers load-balancing algorithms and health checks in full.

You gain horizontal scalability — add smaller servers instead of buying one bigger one — and you can lose one web server without full downtime. But the load balancer is now a new potential SPOF unless it is deployed redundantly, and if the app stores anything in a server's local memory (like "is this user logged in"), a second server will not have it. That specific problem does not get solved until Revision 6 — flag it now, fix it later.

"Adding a second web server behind a load balancer buys redundancy and horizontal scale, but only if the web tier is stateless. If I am storing session state in server memory right now, I would call that out as a problem I plan to fix by the time I talk about autoscaling, not something I am ignoring."

03Revisions 3 to 5 — protect the data, then stop hitting it so often

Revision 3 — database replication: one master, many slaves

Bottleneck: two web servers can now fire far more queries than before, so the single database becomes the new bottleneck — and it is still a SPOF: if that one machine dies, the whole product goes down no matter how many web servers are running.

What changed: database replication. One server is the master (or primary) and is the only one that accepts writes. One or more slave servers (replicas) continuously copy the master's changes — for example, via MySQL's binary replication log — and serve read queries. The application now writes to the master and reads from replicas.

You get read scalability (add more replicas for more read capacity) and a failover target if the master dies. But replication is asynchronous by default, so replicas lag behind the master by some amount — usually small, but it can spike under load. That is replication lag, and it means a user can write something and, on their very next read, not see it yet if that read lands on a lagging replica. This is a concrete case of eventual consistency (the guarantee that all replicas converge to the same value eventually, but not necessarily immediately).

"Master-slave replication buys availability and read scale, but I need to be explicit that reads from replicas are eventually consistent. If a feature needs read-your-own-write behavior — like showing a user their own comment right after they post it — I would route that specific read back to the master, or to whichever replica served the write."

Revision 4 — add a cache in front of the database

Bottleneck: even with replicas, the same popular rows — a trending post, a bestselling product page — get re-read from disk or re-computed for every single request, even though the answer has not changed since the last request.

What changed: an in-memory key-value cache, such as Redis or Memcached, sits between the web tier and the database. The most common pattern is cache-aside: the app checks the cache first; on a miss, it reads the database, then writes that result into the cache before returning it. The next request for the same key hits the cache and never touches the database. Ch.4 is a full deep dive on caching patterns.

Reads get dramatically faster — memory access is on the order of microseconds versus milliseconds for a disk-backed query — and database load drops a lot. The cost: you now have two copies of the truth that can disagree. You need an eviction policy for when the cache fills up (LRU is the common default) and an invalidation strategy for when the underlying data changes. And if the cache starts cold, or one very popular key expires for everyone at once, every request that would have hit the cache instead piles onto the database at the same instant — a thundering herd, also called a cache stampede.

"I would add cache-aside caching for the hottest reads, but I would flag two failure modes up front on purpose: cache invalidation — when a stale value actually gets refreshed — and thundering herd, where a cold cache or a mass key expiry sends every request straight to the database at once."

Stack Revisions 2 through 4 together and this is what the system looks like: a load balancer spreading requests across a redundant web tier, a cache absorbing the hottest reads, and a master database replicating to a slave for read scale and failover.

Revision 5 — push static assets to a CDN

Bottleneck: images, video, CSS, and JavaScript bundles never change per request, yet they are still served by your own web tier for every user — work that has nothing to do with your business logic, and slow for anyone far from your data center.

What changed: static assets move to a CDN (Content Delivery Network) — a globally distributed network of edge servers, run by a third party such as Cloudflare, Akamai, or a cloud provider's own CDN, that caches your files close to the user. On a pull CDN (the common default), the first request for a file still goes back to your origin server; every request after that, from any nearby user, is served from the edge — often in tens of milliseconds instead of hundreds. A push CDN, where you upload assets ahead of time instead of waiting for a cache miss, is the less common alternative, usually reserved for large files you know will be requested heavily right away.

Lower latency for distant users, and a large chunk of traffic taken off your own infrastructure entirely. The costs: a real, recurring bill that scales with bandwidth, a global cache-invalidation problem (shipping a new CSS file means a new URL or waiting out a TTL — time-to-live — everywhere), and a CDN outage, rare but real, can take your static assets down even if your servers are fine.

"Static assets — images, JS bundles, video — belong on a CDN, not on my own web servers. That is close to a free latency win for users far from my data center, and it is one entire category of request my own servers never have to handle."

04Revisions 6 and 7 — make the web tier disposable, then go multi-region

Revision 6 — stateless web tier plus autoscaling

Bottleneck: a debt from Revision 2 comes due. If any web server keeps state in its own memory — a logged-in session, an in-progress upload, a cart not yet saved to a database — the load balancer cannot freely send a user's next request to a different server. You either pin users to "their" server (sticky sessions) or you cannot add and remove servers without breaking people who are mid-session.

What changed: the web tier becomes stateless — no web server keeps anything in memory that would be lost, or that another server would not have, if the load balancer routed the next request elsewhere. Session data moves to a shared store, usually a fast shared cache like Redis. Once servers are truly interchangeable, they go into an auto-scaling group: a policy that adds servers automatically when a metric — CPU usage, queue depth, requests per second — crosses a threshold, and removes them when load drops.

Elastic capacity — you pay for roughly the servers you need instead of a fixed peak-sized fleet sitting idle most of the day — plus much better fault tolerance, since any server can replace any other. The cost: every request that needs session data now pays an extra network hop to the shared cache instead of a free local-memory read, and autoscaling has its own tuning problem — scale up too slowly and users see errors during a spike, scale too aggressively and you pay for capacity you did not need, and new servers take real time to boot and warm up, so autoscaling always reacts a little late, not instantly.

"Making the web tier stateless is the precondition for autoscaling and free failover, not a nice-to-have alongside them. I would move session state to a shared cache before I even talk about scaling policies."

Revision 7 — multiple data centers plus GeoDNS

Bottleneck: everything so far still lives in one physical location — one data center or one cloud region. One region-wide event — a power outage, a fiber cut, a cloud provider's regional outage — takes the whole product down at once. Every user, no matter where in the world they are, also pays the network latency of reaching that single location.

What changed: the whole stack — load balancer, web tier, data tier — runs in two or more geographically separate data centers. A GeoDNS (a DNS provider with geo-routing or latency-based routing) resolves the same domain name to a different data center's IP address depending on where the request originates, sending each user to the nearest or healthiest location.

Real disaster recovery — a whole region can fail and the product stays up from the other one — plus lower latency for spread-out users. The hard question this creates: how does data stay consistent across regions? Replicate the whole database cross-region (adds real, ongoing latency and its own lag), or shard by region so each data center mostly owns its own users' data (which then complicates any feature that needs to look across regions, like a single global leaderboard). This is also where data-residency law — for example, GDPR restricting transfers of EU users' personal data outside the EU/EEA unless an approved safeguard, such as an adequacy decision or standard contractual clauses, is in place — starts shaping the architecture, not just performance.

"Going multi-region is not only a latency win, it is an availability and compliance decision. I would ask the interviewer whether this product has a data-residency requirement, because that decides whether I replicate everything everywhere or shard user data by region."

An EM-level answer adds the cost angle out loud: running a second data center roughly doubles infrastructure spend, and if either region needs enough spare capacity to absorb 100% of traffic when the other one fails, you are provisioning for a disaster that — with luck — never happens. That is a real conversation with finance, not just an engineering decision.

05Revisions 8 and 9 — decouple with a queue, then shard the data

Revision 8 — message queue plus logging, metrics, and automation

Bottleneck: some work triggered by a request does not need to finish before you reply to the user — sending a confirmation email, generating a thumbnail, updating a recommendation model. If the web tier does that work synchronously, in the same request/response cycle, the user waits for it, and a slow downstream dependency (a flaky email provider, say) backs up the entire web tier. Separately, after seven revisions of growth, there is no longer one place to look to tell whether the whole system is healthy — a slow query buried in one of several services is invisible until users complain.

What changed: two additions, both about operability rather than raw throughput. A message queue (Kafka, RabbitMQ, or a managed queue like SQS) sits between the web tier, which publishes small messages such as "send welcome email to user 42," and background workers, which consume them whenever they can — decoupling request latency from that task's actual duration. Alongside it, centralized logging, metrics, and automation: every service ships logs and numeric metrics (request rate, error rate, latency percentiles) to one place, and automated systems — CI/CD pipelines, alerting rules, auto-remediation scripts — react to what those systems show instead of waiting for a human to notice.

The queue buys resilience against slow downstream dependencies and lets background work scale independently of the web tier. But "message accepted" is no longer the same thing as "task finished" — you need a way to tell a user their thumbnail is still processing, and you need to survive a worker crashing mid-task without losing or duplicating that message (Ch.14 covers at-least-once versus exactly-once delivery in depth). The observability stack, meanwhile, is pure added cost and complexity with no user-facing feature to show for it — which is exactly why teams tend to skip it until an outage makes the bill for skipping it very clear.

"Anything that does not need to block the response — sending an email, resizing an image, updating a model — I would move off the request path onto a queue. And I would say up front that centralized logging and metrics are not optional at this scale. Without them, you are debugging a multi-service system by guessing."

An EM-level answer treats the queue choice as build-vs-buy: a managed queue like SQS is usually cheaper to run than self-hosted Kafka for the first couple of years of a product's life, and only becomes the wrong call once you need Kafka-specific features — very high sustained throughput, long retention, replaying a stream from an offset.

Revision 9 — database sharding: the final architecture

Bottleneck: one database — even with read replicas and a cache in front of it — still has exactly one master accepting writes, and that master has a ceiling on write throughput and on how much data comfortably fits on one machine's disk and in its memory. Once write volume, or total data size, outgrows what a single very large master can hold, replication alone cannot save you. The data itself has to split across machines.

What changed: the database is sharded (partitioned): instead of one giant table on one server, rows split across N servers by a shard key — for example hash(user_id) % N, so a given user's data always lands on the same shard, or a range split (users A–H on shard 1, I–P on shard 2, and so on). Each shard is a full, independent database, usually still replicated internally for its own availability per Revision 3. The application, or a routing layer in front of it, computes the shard key and sends each query to the right shard. Ch.6 covers sharding strategies and consistent hashing mechanics in full — this section focuses on why sharding is the last domino to fall, not how the hashing works.

Near-linear write scalability — add more shards, get more write capacity — and each shard holds less data, so backups, indexes, and queries on it stay fast. The cost is real application complexity: a query that used to be "join two tables" can now mean joining across two different physical databases, which most databases will not do for you, so you either denormalize (duplicate data so one shard has what it needs) or join in application code. Resharding — changing N, or moving data once one shard outgrows the rest — is a genuinely hard, usually manual-heavy operation. And you can still get a hot shard, often called the celebrity problem: if the shard key is user_id and one account has millions of followers, that single user's shard takes disproportionate load no matter how evenly the rest of the key space is split. The fix is usually to spread one busy entity's data or load across multiple shards, or to give it dedicated extra capacity as a special case.

"I would only shard the database as a last resort, after caching and read replicas — it is the point where you trade a lot of application complexity for write throughput you cannot get any other way. And I would flag the celebrity problem specifically: whatever shard key I pick, I would check whether one unusually busy entity could overload a single shard on its own."

Eviction Cache eviction policies
  • LRU — evicts the least-recently-used entry. Most common default, since recently-used data tends to be requested again soon.
  • LFU — evicts the least-frequently-used entry. Better than LRU when access frequency matters more than recency.
  • FIFO — evicts the oldest entry regardless of how often or recently it was used. Simple, but ignores actual usage patterns.
  • TTL expiry — not really an eviction policy, but often combined with one: an entry is removed once a fixed time-to-live passes, regardless of how much cache space is free.
NoSQL When to reach for NoSQL instead of staying relational
  • Write volume or total data size is outgrowing what sharding a relational database comfortably handles.
  • The schema is naturally document-shaped (nested, variable fields — MongoDB) or graph-shaped (deep relationship traversal — Neo4j).
  • You need horizontal read/write scale-out without taking on a heavy manual sharding project — many NoSQL stores shard and rebalance automatically (Cassandra, DynamoDB).
  • Access patterns are simple key-value lookups at very high throughput, and you do not need multi-row ACID transactions across entities.
  • None of this is "NoSQL is faster" — it is a trade of strict consistency and rich joins for horizontal scale and schema flexibility. Ch.8 and Ch.9 cover the specific engines in depth.
Sharding The celebrity / hot-shard problem

Any shard key eventually meets an entity that is far busier than average — a celebrity account, a viral product. That entity's shard absorbs disproportionate load no matter how evenly the rest of the key space is split. Two common fixes: spread that one entity's data or traffic across multiple shards instead of one (for example, splitting a celebrity's followers across several shards), or give that entity dedicated extra capacity as a named special case.

Scaling Vertical vs horizontal scaling
  • Vertical scaling — buy a bigger single machine (more CPU/RAM/disk). Simple, but has a hard ceiling and zero redundancy: it is still one machine.
  • Horizontal scaling — add more machines of roughly the same size. Scales further and survives one machine dying, at the cost of needing a load balancer and, usually, a stateless design.
CDN Push vs pull CDN

Pull — the CDN fetches and caches a file from your origin server automatically on the first request (a cache miss), then serves every later request from the edge. This is the common default. Push — you upload assets to the CDN ahead of time, before any user requests them. Push is used less often, mainly when you know a large file will be hit hard immediately and cannot afford even one slow pull-through request.

08The closing checklist — this is the final answer

If an interviewer asks how you would scale a system to millions of users, everything in this chapter compresses into eight lines. Say them, then be ready to defend any single one of them with the reasoning above.

  1. Keep the web tier stateless.
  2. Build redundancy at every tier.
  3. Cache data as much as you can.
  4. Support multiple data centers.
  5. Host static assets in a CDN.
  6. Scale your data tier by sharding.
  7. Split tiers into individual services.
  8. Monitor your system and use automation tools.

Point 7 — splitting tiers into individual services — is where this chapter ends and the rest of the book begins: Ch.14 covers the messaging patterns that connect those services, and Ch.15 covers the resiliency patterns (circuit breakers, retries, service discovery) you need once "the system" means many independently-deployed services instead of one.
